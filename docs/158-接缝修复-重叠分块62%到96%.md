# docs/158 — 接缝问题的算法修复：重叠分块，速度不变，跨缝命中 62% → 96%

> `docs/157` 把「tile 接缝边界目标」列为 P1 风险：2×2 无重叠会把跨缝目标切断。
> 用户要求用算法解决（mAP 仍测不了）。这份给方案 + 实测。

---

## 0. 结论

| 方案 | 检出总数 | **跨缝目标命中** | 速度 |
|---|---|---|---|
| 2×2 无重叠（640/步640） | 472 | 81/130 = **62.3%** | 31.85 FPS |
| **2×2 重叠（768/步512）** | 483 | 125/130 = **96.2%** | **31.77 FPS** |
| 2×2 重度重叠（896/步384） | 428 | 116/130 = 89.2% | — |

**推理次数完全不变（仍是 4 次/帧），速度不受影响，跨缝命中率翻到 96.2%。**

---

## 1. 问题是什么

无重叠 2×2 分块时，一个横跨 x=640（或 y=640）的目标会被切成两半，
两个 tile 里各看到一半 —— **谁都不构成完整目标，YOLO 就漏检或给出半个框**。

用 native 1280 FP32 的结果当参考：27 张图共 376 个检出，其中 **130 个框跨过接缝**。
无重叠方案只命中了 **81 个（62.3%）**，也就是**每 3 个跨缝目标漏 1 个多**。

---

## 2. 方案：重叠分块（同推理次数）

```
无重叠：块 640px，步长 640px          → 4 块，覆盖 1280
重叠  ：块 768px，步长 512px          → 4 块，覆盖 1280（相邻块重叠 256px）
        每块缩放到 640 再喂模型
```

关键点：
- **块数不变**：2 块 × 768 − 256 重叠 = 1280，所以还是 2×2 = 4 次推理
- 每个跨缝目标在**至少一个 tile 里是完整的**
- 代价：768→640 的缩放让目标看起来小 0.83×（对极小目标略有影响）

为什么不用更大的 896/384：缩放比 0.71×，小目标掉得太厉害（89.2% < 96.2%）。

---

## 3. 验证方法（没有 mAP 时的替代判据）

拿 **native 1280 FP32** 做参考（`yolo11n_1280.onnx`），逐图对比：

1. 参考里挑出**框跨过 x=640 或 y=640** 的目标 → 共 130 个
2. 看分块方案能不能给出 IoU>0.5 的对应框

```
参考(native 1280 FP32): 27 图，检出 376，其中跨缝 130
方案                     检出总数    跨缝命中    命中率
非重叠 640/步640            472       81/130    62.3%
重叠 768/步512              483      125/130    96.2%
重叠 896/步384              428      116/130    89.2%
```

注意检出总数几乎没变（472 → 483），说明**不是靠多吐框刷命中率**，
是真的把被切断的目标拼回来了。

---

## 4. C 实现与速度

`bench_full.c` 增加了两个环境变量：

```bash
TILEPX=768 STRIDE=512 ./bench_full model anchor.npy stride.npy 54 6 tiles_ovl27.raw 27
```

坐标回映改成：

```c
float ks = tile_px / 640.0f;              // 模型空间 → 原图空间的尺度
float ox = (tid % 2) * stride;            // 块原点（步长，不是块边长）
outbox[k].x1 = x1 * ks + ox;  ...
```

实测：

| 配置 | 原始框/帧 | NMS 后/帧 | FPS |
|---|---|---|---|
| 非重叠 640/640 | 116.8 | 16.7 | **31.85** |
| **重叠 768/512** | 177.9 | **17.5** | **31.77** |

- **速度差 0.25%**（在测量噪声内）
- NMS 后 17.5 vs 16.7：多出来的正是被救回的跨缝目标
- 与 Python/ONNX 的对应值吻合（ONNX 重叠版 17.9/帧），说明 C 实现正确

---

## 5. 需要诚实标注的两点

### 5.1 建测数据里，768→640 的缩放是离线做的

测试用的 `tiles_ovl27.raw` 是**预先缩放好**的。真实部署里这一步要在线做：

- `cv2.resize(768→640)` 约 **0.3 ms/块** ⇒ 4 块 ≈ **1.2 ms/帧**
- 在 32 FPS（31 ms/帧）下相当于 **约 4%** 的开销
- 如果交给 **RGA 硬件**做，可以降到接近 0（`/dev/rga` 板上可用，未接）

⇒ **线上预期约 30.5~31 FPS**，而不是精确的 31.77。

### 5.2 判据是"与 FP32 一致"，不是绝对精度

跨缝命中率 96.2% 是相对 native 1280 FP32 的。如果 FP32 本身漏检，
这里也统计不到。**mAP 依然是缺的**。

---

## 6. 落地建议

| 项 | 取值 |
|---|---|
| 块边长 | **768 px** |
| 步长 | **512 px** |
| 每帧推理次数 | 4（与无重叠相同） |
| 预处理 | 768→640 缩放，建议走 RGA |
| 预期吞吐 | 31.8 FPS（离线缩放）/ 约 30.5 FPS（在线 cv2 缩放） |
| 跨缝恢复 | 62.3% → **96.2%** |
