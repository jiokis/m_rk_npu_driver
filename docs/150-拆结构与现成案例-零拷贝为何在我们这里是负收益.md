# docs/150 — 拆结构 + 查现成案例：哪些招真能用，哪些是负收益

> 用户的思路是对的：先看结构热点，再对照社区/官方已经验证过的做法。
> 这份把 **YOLO11 编译后的结构拆开**，并逐条实测社区方案在我们板子上的真实效果。

---

## 0. 结论

| 手段 | 来源 | 我们的实测 | 判定 |
|---|---|---|---|
| C 替代 Python 运行时 | 社区 | 31 ms → **28.41 ms**（+10%） | ✅ 小赢 |
| 单实例绑 1 核 vs 3 核 | 官方 API | **27.80 vs 28.49 ms**，1 核还略快 | ✅ 别再绑 3 核 |
| `rknn_set_io_mem` 零拷贝 | 社区 | **43.55 ms（慢 53%）** | ❌ **负收益** |
| `rknn_dup_context` 3 线程 | 社区 | 82.84 FPS ≈ Python 85.02 | ⚠️ 无额外收益 |
| 3 实例并发（各绑一核） | 上一轮 | **85 FPS = 2.67×** | ✅ 唯一大赢家 |
| 稀疏推理 | 理论最大 | 硬件不支持 | ❌ |

**核心洞察：社区里"零拷贝更快"是真的，但前提是数据来自 RGA/摄像头的 dma-buf。
如果像我们这样用 CPU 把数据写进 NPU 输入缓冲，零拷贝反而更慢** —— 因为那块内存是 uncached 的，
CPU 写 1.2 MB 比 memcpy 进缓存再让驱动搬要贵。

## 1. 编译后的结构拆解

从编译器 IR 表（`verbose=True`）按 `model.N` 归段：

| 区段 | 算子数 | NPU cycles | 占比 |
|---|---|---|---|
| **backbone (0–10)** | 68 | 3,213,600 | **58.2%** |
| **head (22–23)** | 59 | 1,613,600 | **29.2%** |
| neck (11–21) | 29 | 691,200 | 12.5% |

### 单点最贵的算子

| 占比 | 算子 | 说明 |
|---|---|---|
| **16.7%** | `Conv:/model.0/conv/Conv` | **stem**，3→16 通道、stride2，输出 320×320 |
| 4.2%×5 | `model.1/3/5/conv`、`model.2/m.0/cv1/cv2` | C3k2 的第一层卷积 |
| 4.2%×2 | `model.23/cv2.0/cv2.0.{0,1}` | 检测头 P3 分支 |

**stem 一个算子占 16.7%** —— 因为它要在 640×640 上做，且输入只有 3 通道（算术强度极低）。

### 159 个算子里有 71 个是"零 cycle"的内存算子

```
ConvExSwish 77 · Conv 9 · ConvAdd 2        ← 88 个真正算的
Concat 21 · Add 14 · Split 11 · Reshape 10
MaxPool 3 · Resize 2 · Sub 2 · Mul 2
Softmax 1 · Transpose 1 · Sigmoid 1        ← 71 个纯搬运
```

编译器给这 71 个算子的 `Cycles` 记 **0/0/0**，但运行时它们照样要占提交
（`docs/149` 测到 `model.23/dfl/Softmax` 一个就占 350 条 task）。

## 3. 逐条实测（C 语言版，写实）

### 3.1 环境确认

板上全部齐备：

```
rknn_api.h  ✓ (在 ~/rk-llama/ggml/src/ggml-rknpu2/libs/include)
/usr/lib/librknnrt.so ✓
/dev/rga + librga.so.2 + /usr/include/rga/im2d*.h  ✓
gcc 11.4 ✓, /usr/include/linux/dma-heap.h ✓
```

零拷贝/上下文复用所需的 API 全部导出：

```
rknn_set_io_mem ✓  rknn_create_mem ✓  rknn_dup_context ✓  rknn_mem_sync ✓
```

### 3.2 C 单实例：拷贝路径 vs 零拷贝

```
copy: 中位 28.41 ms  p90 29.93  FPS 35.20      ← rknn_inputs_set + outputs_get(want_float=0)
zero: 中位 43.55 ms  p90 44.33  FPS 22.96      ← rknn_create_mem + rknn_set_io_mem
```

**零拷贝慢了 53%。** 原因推断：`rknn_create_mem` 给的是 **uncached / DMA 一致内存**，
CPU 每次写 1.2 MB 输入都绕开 cache；而拷贝路径是 memcpy 进缓存再由驱动搬，反而更快。

### 3.3 C 多线程：dup_context

```
multi_copy (3 线程, dup_context, 拷贝路径): 300 帧 / 3.62 s = 82.84 FPS
   实例0 32.29 ms · 实例1 33.01 ms · 实例2 33.10 ms

multi      (3 线程, dup_context, 零拷贝):   300 帧 / 4.83 s = 62.15 FPS
   实例0 41.87 ms · 实例1 42.32 ms · 实例2 41.79 ms
```

对比 Python 版（`docs/149`）：**3 实例 85.02 FPS**。
⇒ C + `dup_context` 的 82.84 FPS **并没有超过** Python 多实例，二者基本持平。
`dup_context` 省的是**模型内存**（3 个实例共享一份权重），不是时间。

### 3.4 单实例绑核：C 侧复核

```
core_mask=7 (三核): 中位 28.49 ms
core_mask=1 (单核): 中位 27.80 ms   ← 反而更快
```

Python 和 C 两边结论一致：**单实例绑 3 核没有收益**，因为推理内部的提交有 56% 本来就只能用 1 核
（`docs/144`），多绑核只增加调度开销。

## 4. 为什么社区的"零拷贝"和我们的不是一回事

社区案例的零拷贝链路是：

```
摄像头 / 视频解码 → dma-buf → RGA(硬件缩放) → NPU 输入缓冲（全程 CPU 不碰）
```

而我们的测试是：

```
CPU 生成图像 → 写进 uncached 的 NPU 输入缓冲 → 跑
```

**后者只是把 memcpy 换成了更慢的 uncached 写。** 真正的零拷贝必须让**上游硬件**
（RGA / VPU / 摄像头）直接产出 NPU 能读的 dma-buf。

⇒ 所以下一步不是继续调 API，而是**搭 RGA → NPU 的直通链路**。

## 5. 当前最优组合（基于全部实测）

| 场景 | 组合 | 实测 |
|---|---|---|

| 1280 高分辨率 | 2×2 分块（零拷贝宿主侧）+ 3 实例 | 137 ms→再叠加并发 |

## 6. 下一步（按性价比）

1. **RGA 预处理直通**：把 letterbox 交给 RGA，输出直接进 NPU 输入 dma-buf。这才是社区零拷贝的真实形态。
   - 预期：省掉 CPU 的 0.22 ms(640) / 4.5 ms(1280) + 输入 memcpy
2. **CPU/NPU 锁频**：我们测到 p90 是中位数的 1.5~2 倍（`docs/147` 1280 场景 p90 243 ms vs 中位 147 ms），
   锁频是最直接的降抖动手段。
3. stem 优化（16.7%）：输入只有 3 通道，算力/带宽比极低；用 RGA 直接输出 **RGB 且已缩放到 320×320**
   可以把 stem 的输入读取量减半（需改模型输入分辨率，需重新量化验证）。
