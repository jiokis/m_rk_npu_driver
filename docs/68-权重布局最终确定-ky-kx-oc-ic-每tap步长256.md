# 68 · ★ 权重布局**最终确定**：`[ky][kx][oc][ic]`，每 tap 步长 256

> 接 [docs/63](63-权重布局解码成功-oc-ky-kx-ic对齐16.md)（假设 `[oc][ky][kx][ic]`）
> 与 [docs/65](65-权重布局的重新判定-顺序是对的但6%行异常.md)。
> 本轮用 [docs/67 拿到的 `.model`（编译器自己的量化权重块）] 做对照，
> **一次就把真正的布局读出来了** —— 而且它与 docs/63 的假设**不同**。

---

## 0. 最终布局

```
offset(ky, kx, oc, ic) = (ky*kw + kx) * 256  +  oc * 16  +  ic

  · 256 = 每个 kernel tap 的步长 = 16 oc × 16（对齐宽度）
  · 16  = 同一 tap 内、相邻 oc 的步长 = align(in_ch, 16)
  · ic  = 0 .. in_ch-1 为真实权重；其余槽填 `128`
  · 真实零权重 → 字节 `0`（与「不存在通道」的填充 `128` 不同）
```

**⇒ kernel tap 在**最外层**，`oc` 第二，`ic` 最内。**
docs/63 把 `oc` 放在最外层，所以斜坡探针永远对不上（docs/64/65 的「6% 异常行」就是这个错位）。

---

## 1. 证据（`probe4`：只有 oc0 非零，斜坡 1..27）

按**每 tap 256 字节**切开，9 个 tap 各自的前 16 字节：

```
tap0 (ky=0,kx=0) @   0: 前3=[137, 222, 51]   其余是否全 128 = True
tap1 (ky=0,kx=1) @ 256: 前3=[147, 232, 61]   True
tap2 (ky=0,kx=2) @ 512: 前3=[156, 241, 70]   True
tap3 (ky=1,kx=0) @ 768: 前3=[166, 251, 80]   True
tap4 (ky=1,kx=1) @1024: 前3=[175,   4, 89]   True
tap5 (ky=1,kx=2) @1280: 前3=[185,  14, 99]   True
tap6 (ky=2,kx=0) @1536: 前3=[194,  23,108]   True
tap7 (ky=2,kx=1) @1792: 前3=[204,  33,118]   True
tap8 (ky=2,kx=2) @2048: 前3=[213,  42,127]   True
```

**四条独立证据**：

1. **9 个 tap 的步长恰好是 256**（0, 256, 512, …, 2048）—— 不是 16。
2. **每个 tap 的前 3 槽是真实值，第 4~15 槽全为 `128`** ⇒ 确认「`ic` 内层、对齐 16、
   不存在的通道填 128」。
3. **每个 tap 的第 16~255 字节全为 `0`** ⇒ oc1..15 是真实零权重，编码成 `0`
   （**与填充的 `128` 明确区分** —— 这解决了 docs/66 的矛盾：
   `128` = 不存在通道的填充码，`0` = 浮点 0.0 的编码）。
4. **三条槽序列各自单调**：

```
ic=0: [137, 147, 156, 166, 175, 185, 194, 204, 213]   严格递增 ✅
ic=1: [222, 232, 241, 251,   4,  14,  23,  33,  42]   8 位回绕后仍递增 ✅
ic=2: [ 51,  61,  70,  80,  89,  99, 108, 118, 127]   严格递增 ✅
```

**ic=1 那条 `251 → 4` 正是 8 位回绕**（251 + 9.5 = 260.5 → 260 − 256 = 4）——
步长 ~9.5 与「27 个值铺满 256 级」完全吻合（256/27 ≈ 9.5）。
**这一条是布局正确性最强的证据**：回绕位置可预测。

## 2. 与 `.model` 的一致性

```
probe4.model 偏移 3616 起的 2304 字节  vs  板上 DRAM 前 2304 字节
  ⇒ 逐字节相同 2160 / 2304 = 93.75%
  不同的位置全部落在各 tap 的前 16 字节内（即真实权重/填充槽）
```

**⇒ 编译器自己的权重块与 NPU 实际读的那块是同一套布局**，
差异只在填充槽（`.model` 里可能存了另一种填充值）。**布局本身已无歧义。**

---

## 3. 还差的一点：三个 ic 槽的偏移不同

三条序列的**步长相同（~9.5）但起点不同**（137 / 222 / 51）。
斜坡里 ic=0/1/2 的值域分别是 [1,9] / [10,18] / [19,27]，
**同样的步长 ⇒ 同一 scale；起点不同 ⇒ 每个 ic 的 zero_point 不同**
（或 RKNN 对权重按**输入通道**做了分组量化）。

**⇒ 这不影响布局，但影响反量化。** 需要下一轮确认：
`.cfg` 里给的是**激活**的 scale/zero_point（`c/r/gap/g/output…`），
权重的 per-ic 参数不在 `.cfg` 里 —— 可能要回到 DRAM 里的那张 40 字节表（docs/67 的块）
或从 `.model` 的字节直接反解。

## 5. 教训（本轮新增）

1. **★★ 拿到「标准答案」之后，布局是一行代码就读出来的。**
   我用 6 轮探针（docs/62~67）没解出布局；拿到 `.model` 后，**按 256 切一刀就看见了**。
   **前 6 轮的失败不是因为问题难，而是因为我在没有参照物的情况下猜。**
2. **★ 「步长」比「内容」更能暴露布局。** 我一直盯着字节**值**的单调性，
   而真正的线索是**位置**的规律：非零字节以 **256** 为步长出现。
   **先看「东西出现在哪」，再看「它们是什么」。**
3. **★ 8 位回绕是可预测的，因此是强证据。** ic=1 的 `251 → 4` 不是噪声 ——
   它恰好是 +9.5 溢出 256。**能预测的异常比「看起来对」的规律更有说服力。**
4. **★ 之前的「6% 异常行」有了归宿。** docs/65 发现 9 行异常且「自身有规律」，
   当时判断是「某个未建模的偏移」——**现在知道那是 `oc` 与 `ky,kx` 的层级搞反了**。
   **当时那个「有结构的异常」正是正确的路标。**
