# 55 · 9 个真实模型的命令流横向对比：**两种完全不同的瓶颈**

> 接 [docs/54](54-真实预训练模型上板9导出9转换9跑通.md)。本轮把 9 个真实预训练模型的
> **命令流全部抓下来**（`RKNPU_DUMP_SLACK=64`，段尾完整），做横向预算对比。
> 这是「针对特定模型的优化」的主体数据。
>
> 语料：`~/align2/tvcap/<模型>/`（9 个目录 + 各自的 timer 日志）

**提交数跨度 3 → 183（61 倍）；地板占比跨度 18% → 109%。**

---

## 1. ★ 结论一：存在**两种完全不同的瓶颈**，按提交数分开

「残差隐含带宽」= 残差 ÷ 总流量。若残差由流量决定，这个值应当收敛；实测**跨度 11 倍**（1.89~21.0 GB/s），
**不收敛** ⇒ 残差不是单纯带宽。但把它和提交数并排看，规律非常清楚：

| 组 | 模型 | 提交 | 隐含带宽 | 判读 |
|---|---|---|---|---|
| **A：提交少** | `mobilenet_v2` | 3 | **21.00 GB/s** | 接近实测 DDR 上限（23.84）⇒ **带宽受限** |
| | `mnasnet0_5` | 3 | **16.38** | 同上 |
| | `resnet18` | 5 | **12.79** | 同上 |
| **B：提交多** | `densenet121` | 183 | 3.10 | 地板占 84% ⇒ **提交地板受限** |
| | `regnet_x_400mf` | 113 | 3.14 | 地板占 99% |
| | `efficientnet_b0` | 88 | 2.71 | 地板占 64% |
| | `shufflenet_v2_x0_5` | 63 | **1.89** | 地板占 **109%** |

**A 组**：硬件在满速搬数据（12.8~21.0 GB/s），**算术量小到可以忽略**（0.02~0.32 ms）。
优化方向 = **减流量**（已经是 w8a8，再往下的空间在数据复用/算子融合）。

**B 组**：隐含带宽只有 2~3 GB/s（**DDR 只用了 8~13%**），时间几乎全是提交地板。
优化方向 = **减提交数**。以 `densenet121` 为例：84% × 14.6 ms = **12.3 ms 是地板**。

⚠️ **注意 109% / 99% 这两个值**：地板按 67.4 µs × 提交数算出来**超过了实测时间**。
⇒ **67.4 µs 不是普适常数**，这些模型的实际每次提交代价只有 40~62 µs。
（与 docs/45/46/49 的结论一致：地板随配置变化。）

---

## 2. ★ 结论二：一个被**否掉**的假设 —— 提交数不由「布局算子」决定

我的假设是：`Concat`/`Reshape`/`Transpose` 这类**改变内存布局**的算子会强制提交边界，
所以它们越多、提交越碎。逐个 ONNX 数了一下：

```
模型                 提交   Conv  布局类算子（明细）
mnasnet0_5             3     52    0
mobilenet_v2           3     52    0
resnet18               5     20    0
regnet_x_400mf       113     71    0     ← ★ 一个布局算子都没有，却发了 113 次
efficientnet_b0       88     81    0     ← ★ 同上，88 次
densenet121          183    120   62    Concat×62
shufflenet_v2_x0_5    63     56  103    Reshape×32, Slice×26, Concat×16, Transpose×16, Gather×13
squeezenet1_0         22     26    8    Concat×8
googlenet             35     57   16    Concat×10, Gather×3, Unsqueeze×3
```

**回归：提交数 ~ 布局类/Conv ⇒ R² = 0.040（n=9）—— 假设被否掉。**
`regnet_x_400mf` 与 `efficientnet_b0` **零布局算子却发了 88~113 次提交**，直接推翻它。

**换个角度看「每个提交里有多少 Conv」**：

```
mnasnet0_5        17.3 conv/提交
mobilenet_v2      17.3
resnet18           4.0
googlenet          1.6
regnet_x_400mf     0.63
squeezenet1_0      1.2
densenet121        0.66
shufflenet_v2_x0_5 0.89
efficientnet_b0    0.92
```

**跨度 26 倍（0.63 ~ 17.3）**，而且**和布局算子数没有单调关系**。
⇒ **驱动提交切分的因素我还没找到。** 这是本轮最大的未结项。

（线索：`mnasnet0_5`/`mobilenet_v2` 都是**深度可分离**为主、17 conv/提交；
`regnet_x_400mf` 是**分组卷积**、0.63 conv/提交。怀疑与「分组/深度可分离的通道对齐」
或「编译器对某些 op 类型的融合规则」有关，但没有证据。）

## 3. 逐模型的可操作建议

| 模型 | 瓶颈 | 建议 | 预期空间 |
|---|---|---|---|
| `densenet121` | 提交地板 84% | **减少提交数**（183 → 数十次量级） | 最大 ~12 ms |
| `regnet_x_400mf` | 提交地板 99% | 同上（113 次） | ~7.5 ms |
| `efficientnet_b0` | 提交地板 64% | 同上（88 次） | ~6 ms |
| `shufflenet_v2_x0_5` | 提交地板 109% | 同上（63 次） | ~2.5 ms |
| `squeezenet1_0` | 地板 47.5% | 同上（22 次） | ~1.5 ms |
| `googlenet` | 地板 39.5% | 同上（35 次） | ~2.4 ms |
| `mobilenet_v2` | **带宽** 21 GB/s | 减流量（已接近 DDR 上限） | 小 |
| `mnasnet0_5` | 带宽 16.4 GB/s | 同上 | 小 |
| `resnet18` | 带宽 12.8 GB/s | 同上 | 小 |

**总结成一句**：**同一块 NPU 上，有的模型在撞带宽墙（DDR 用掉 90%），
有的模型 DDR 只用 8% 却在等提交。而模型落在哪一边，由编译器的提交切分决定。**

## 5. 教训（本轮新增）

1. **★ 假设要被明确地否掉，而不是悄悄丢掉。** 「布局算子 → 提交边界」这个假设很自然，
   我把它写出来、量化、回归，**R²=0.040 被否掉**。这比「我没找到原因」有用得多 ——
   它**排除了一整类解释**，而且 `regnet_x_400mf` 零布局算子发 113 次提交这个反例
   是可以直接拿去问人的。
2. **★ 横向对比能看出单模型看不出的东西。** 只测 `densenet121` 只能说「它很慢」；
   9 个模型并排才看出**两种瓶颈**，而且**分界线是提交数**。
   **模型集本身就是实验设计。**
3. **★ 用「隐含量」把不一致变成发现。** 残差隐含带宽跨度 11 倍 ——
   如果我只看「残差」会觉得模型很乱；算成隐含带宽之后，A 组 12.8~21.0（接近 DDR 上限）
   与 B 组 1.9~3.1（DDR 闲置）**立刻分成了两组**。
   **把一个量除以另一个量，往往能看出结构。**
4. **109% 这种「不可能的值」要留下而不是修掉。** 地板占比 109% 说明全局常数 67.4 µs
   对这些模型不适用 —— 这是一个**关于常数适用范围的发现**，不是一个需要抹掉的误差。
