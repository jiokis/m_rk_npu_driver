# 第一部分：真实困惑度（量化方向的成果）

> 代码：[quant_ppl.py](../src/quant/quant_ppl.py) ·
> 前向传播：[qwen2_numpy.py](../src/quant/qwen2_numpy.py)（纯 numpy 实现 Qwen2）
> 原始输出：[ppl_results.txt](../src/quant/ppl_results.txt)

## 为什么必须做这个

docs/08 的最大缺口是「只测张量误差，没测下游指标」。
而实验已证明**全局 Frobenius 误差是不可靠的代理**。

现在补上了：在**真实的 Qwen2.5-0.5B-Instruct 权重**上，
用纯 numpy 前向传播算**真实困惑度**（24 层 / hidden 896 / GQA 14Q-2KV / 独立 lm_head）。

## 结果

文本 141 token · 上下文 256 · 各方案**共用同一套分词与同一份前向实现**，
唯一变量是权重量化方式。

| 方案 | 困惑度 | 相对基线 | 判定 |
|---|---|---|---|
| **fp32 基线** | **25.518** | — | 参考 |
| int8 per-tensor | 62.294 | **2.44×** | 明显退化 |
| **int8 per-输出通道** | **25.591** | **1.00×** | ✅ **几乎无损** |
| int8 per-group g128 | 25.700 | 1.01× | ✅ 几乎无损 |
| **int4 per-tensor** | **1.03 × 10¹⁰** | **4 亿倍** | ❌ **完全崩坏** |
| int4 per-输出通道 | 57.276 | 2.24× | 退化严重 |
| int4 per-group g128 | 40.261 | 1.58× | 有损但可用 |
| **int4 per-group g64** | **34.298** | **1.34×** | int4 里最好 |

## ★ 关键验证：零值占比才是正确的预测量

这是本次实验最重要的结论 —— **两条指标给出的判断完全相反**：

| | int4 per-tensor 的读数 | 判断 |
|---|---|---|
| 全局 Frobenius 输出误差 | 21.48% | 「好像还行」 |
| **张量零值占比** | **77–99%** | 「全毁了」 |
| **真实困惑度** | **4 亿倍** | **确认全毁** |

**零值占比预测对了，全局误差指标把灾难掩盖了。**
这从下游任务的角度坐实了 docs/08 的论断：
**做量化实验必须看张量级指标（尤其零值占比），不能只看输出误差。**

## 可落地的结论

| 结论 | 依据 |
|---|---|
| **int8 用 per-输出通道或 per-group，几乎零损失** | 1.00× / 1.01× 困惑度 |
| **int8 千万别用 per-tensor** | 2.44× 退化 |
| **int4 必须至少 per-group，且组越小越好** | g128 1.58× → g64 1.34× |
| **int4 per-tensor 绝对不可用** | 困惑度爆到 1e10 |
| int4 目前仍有 1.34× 的损失 | 需要配合激活侧旋转/更细的分组继续压 |

> 对 RK3588 的直接意义：官方只给到 w8a8，而 **w8a8 若用 per-channel 就是无损的**。
> 想上 int4 则必须支持分组量化（g64 或更细），否则不要用。

## 过程中修掉的两个自身 bug（方法论价值）

纯 numpy 实现前向传播时踩了两个坑，都是**自检**（"France 的首都是？"）抓出来的：

| Bug | 现象 | 原因 |
|---|---|---|
| **分词缺 byte-level 映射** | `'The capital of France is'` → `[785, 0, 65063, 0, ...]`，每个空格都退化成 id 0 | GPT-2/llama-bpe 词表里空格存的是 `Ġ`(U+0120)，必须先做字节→unicode 映射 |
| **RoPE 配对约定错了** | 输出完全退化，top-1 是个孤立空格 | 用了 GPT-NeoX 的 interleaved 配对 `(0,1),(2,3)…`；llama/Qwen2 用的是 **half-split** `(i, i+D/2)`。修好后 top-1 立刻变成 `'ĠParis'`，领先第二名 1.4 |

**教训：实现复杂算子时一定要有一个"答案已知"的自检。** 两个 bug 都不是靠读代码发现的，
是靠"模型该答对 Paris"这个外部判据发现的。

# 第二部分：硬件手搓提交的终止决定

## 两次事故

| 次数 | 提交内容 | 故障形态 | 诊断 |
|---|---|---|---|
| 第 1 次 | `OP_40` + `OP_NONE` + **`OP_ENABLE`** | ARP INCOMPLETE，**彻底失联** | 无描述符就使能 → 硬件拿垃圾地址 DMA → **写坏内存** |
| 第 2 次 | **仅 4 × `OP_NONE`** | ping 通、**所有 TCP 端口超时** | 网络栈（软中断）还活着但内核卡死 → **疑似中断风暴** |

第 2 次的形态很说明问题：**没有内存损坏**（网络栈正常），但内核不可用。
高度指向 task 参数里的 `int_mask`：

```
我填的：   int_mask = 0x1ffff   ← 17 个中断源全开
真实运行时：int_mask = 0x300     ← 只开 DPU 两位（外部调研提供）
```

17 个中断源全开、又没有配套的处理逻辑 → 中断持续触发 → 系统卡死。
**即使命令流本身全是空操作，任务级的参数错误也足以搞死系统。**

## 决定：停止手搓硬件提交

理由是**证据+前人结论一致**，不是畏难：

1. **已经损坏板子两次**，每次都需用户物理断电。这是真实的代价。
2. **外部调研早就把这条路列为死路**：
   > 「无保护的硬件寄存器 fuzzing（会 wedge，且**寄存器会自清零，readback 不能用来验证写入**）」
3. **regcmd 逆向已被上游完成**（Linux v6.18 的 `drivers/accel/rocket` + Mesa 25.3），
   手搓提交是在重造一个已经有官方实现的东西。
4. **纯软件方向已经在产出真实成果**（本文件第一部分），零风险、可量化。

**投入产出比和风险都不支持继续手搓。**

## 如果将来还要碰硬件，正确的做法

不要从零手搓，而是：

1. **换到主线 `accel/rocket` + Mesa** —— UAPI 定稿、内核托管调度与 IOMMU、
   Mesa 有官方 `intercept.c` + `decode.py` 工具链，且用户态驱动已处理掉所有细节
2. 若必须在 vendor 驱动上做，**先满足这些前提**：
   - `int_mask` 用实测值 `0x300`，**绝不全开**
   - 命令流必须带上完整 trailer（外部资料给出：`OP_NONE` / `OP_REG_PC` / `OP_40` / `OP_ENABLE`）
   - 用真实样本的**完整 47 条指令模板**改几个变量槽位，而不是从零构造
   - 逐条增加、每步验证，而不是一次性提交
   - 板子要有**可远程恢复的手段**（当前没有，这是硬约束）

## 对项目目标的影响

用户的原始目标是「提高模型部署自由度与优化空间」。终止硬件线**不影响这个目标**：

| 目标 | 现在靠什么达成 |
|---|---|
| 部署自由度 | 量化方案（int8 per-channel 无损）+ 图重写层（待做） |
| 优化空间 | 量化自由度（已有真实困惑度数据支撑） |
| 摆脱闭源 | 走主线 rocket + Mesa（文档已给出路径），而不是自己写驱动 |

**教训总结成一句话：把风险高的实验做在能承受失败的地方，把力气花在能验证收益的地方。**
