## 0. 实现

```
src/sim/rknpu/weights.py

  dequant(q, scale, zero_point)          反量化（含 byte 0 特判）
```

**`expected_size(3,16,3,3) = 2304`，与实测寄存器 `WEIGHT_SIZE0 = 2304` 完全一致** ——
这是布局公式的又一次独立确认。

## 1. ★ 验证：从 DRAM 重建权重 vs ONNX 浮点权重

```
最大绝对误差 0.059294      （量化容差 scale/2 = 0.052907）
落在 ±scale/2 内: 430/432 = 99.5%
```

* **oc0**（真实权重 1..27）：重建 `[0.9523, 9.9465, 18.9407]` vs 原始 `[1, 10, 19]`
  ⇒ 误差 0.048 / 0.054 / 0.059，**就是量化步长量级** ✅
* **oc1**（真实权重全 0）：重建 `[0, 0, 0]` vs 原始 `[0, 0, 0]` ✅

**⇒ 权重加载路径正确。** 2 个点略微超出容差（超 12%）是值域端点的舍入，不是结构错误。

## 2. ★ 本轮发现的新事实：**byte `0` 是「精确零」标记**

第一次验证时最大误差是 **13.544** —— 正好等于 `(0 − (−128)) × 0.105814 = 13.54`。

**原因**：`oc1..15` 的真实权重全是 0，DRAM 里对应字节也全是 **`0`**。
若直接套 `(q − zp) × scale`，`q = 0` 会算出 `128 × scale = 13.54`，而真值是 0。

**⇒ `byte 0` 不是「量化值 0」，而是「精确零」的标记。**

这与 docs/66/68 的观察连成一条线：

| 字节 | 含义 |
|---|---|
| **`0`** | **精确零**（真实权重就是 0.0） |
| **`128`** | **不存在的输入通道**（对齐出去的槽） |
| 其它 | 正常量化值，`w = (q_signed + 128) × scale` |

**三种语义各不相同，必须分开处理。** 这也回头解释了 docs/66 里那个「同一个浮点 0.0
在两个探针里编码不同」的矛盾：**探针4 的 0.0 是真实零权重 → `0`；
探针3 的 0.0 是「不存在的通道」→ `128`。** 它们本来就是两回事。

## 5. 教训（本轮新增）

1. **★ 验证时「最大误差」要先去解释，不要先去调参。** 看到 13.544 我没有改 scale，
   而是算了一下 `128 × scale = 13.54` —— **一眼就看出它是「把 0 当成量化值」造成的**，
   而不是拟合错了。**异常值往往能直接指向缺失的分支。**
2. **★ 三种语义（0 / 128 / 其它）分开之后，前面的矛盾自动消解。**
   docs/66 那个「同一个 0.0 编码不同」的矛盾，在本轮变成「两种不同的 0」——
   **当时我以为是同一个东西，其实不是。**
3. **★ `expected_size` 与寄存器对齐是免费的交叉验证。** 布局公式算出 2304，
   寄存器报 2304 —— 一行代码就多了一个独立确认。**能算出来的量就顺手算一遍。**
