## 为什么做这个

RK3588 的 NPU（3 核 / 6 TOPS）官方栈是这样的：

```
你的模型 ──► rknn-toolkit2 (闭源编译器) ──► .rknn 模型
                                              │
                                    librknnrt.so (闭源运行时)
                                              │  ioctl
                                    drivers/rknpu  ← GPL，开源 ✅
                                              │
                                           NPU 硬件
```

**上面两层闭源**，带来三个硬约束：

| 约束 | 具体表现 |
|---|---|
| **算子集固定** | 编译器不支持的算子只能回退 CPU，或整个图编译失败 |
| **调度不透明** | 无法控制算子如何映射到三核、何时 DMA、能否乒乓重叠 |
| **量化受限** | 实测 w4a16 在 RK3588 上被工具链直接拒绝（只能 w8a8），无法自定义量化粒度 |

而**内核驱动是 GPL 开源的** —— 这是整个逆向工作的立足点。

## 核心洞察

读驱动源码得到的结论（详见 [docs/02-内核驱动UAPI.md](docs/02-内核驱动UAPI.md)）：

> **内核驱动完全不解析命令流。** `struct rknpu_task` 只带一个 `regcmd_addr`，
> 驱动把 task 结构 DMA 过去、写几个控制寄存器、等中断就完事了。

这带来一个干净的分工：

- **控制面已被开源**：怎么分配内存、怎么提交任务、怎么同步 —— 6 个 ioctl 全部公开
- **数据面仍需逆向**：`regcmd` 那段字节码的格式只存在于闭源 `librknnrt.so` 和硬件里

所以路线是：**用开源驱动当发射器，把闭源运行时的真实命令流抓下来当样本，反推格式，然后自己造弹药。**

这意味着 **不需要改内核**，也不需要替换驱动 —— 在用户态就能做完全部工作。

### 已破解的指令格式

```
每 8 字节一条指令（小端）：
  [u16 寄存器地址][u32 值][u16 操作码≈0x0201]
```

寄存器地址与 GPL 头文件里的偏移表**完全对上**（`0x1010`=PC_DATA_ADDR、
`0x1014`=PC_DATA_AMOUNT、`0x1020`=INT_MASK …），这是格式正确性的铁证。

**关键架构发现**：`PC_DATA_ADDR`/`PC_DATA_AMOUNT` 本身就是命令流里的指令
→ NPU 执行模型是**自延续的**：命令可以指定下一段取指地址，链式执行。

### 硬件模块拓扑（从 615 条真实样本反推）

| block_id | 次数 | 推断 |
|---|---|---|
| `0x0201` | 9431 | 主计算单元 |
| `0x1001/0x2001/0x4001/0x8001` | 3628 | **四个同构单元**，寄存器基址 0x4004/0x5004/0x6004/0x7004（步长 0x1000） |
| `0x0101` | 110 | **PC 链控制**（下一段命令流地址 + 长度） |
| `0x0041/0x0081` | 110 | op_en 前置与总使能 |

## 两个必须知道的事实

1. **RK3588 上 SRAM 是 0 字节。** 实测 `ACTION: GET_TOTAL_SRAM_SIZE` 返回 0，
   驱动源码确认 `sram_mm` 为空；config 表里只有非 RK3588 的 SoC 有 `nbuf_size`。
   外部资料说明：片上有 956KB SRAM，但**默认分给了 rkvdec（视频解码）**，
   要让给 NPU 就得牺牲硬件视频解码。**所以"用 SRAM 绕开 DRAM 带宽墙"这条路在 RK3588 上走不通。**

2. **regcmd 编码已被上游完成。** 详见 [docs/07](docs/07-战略转向.md)。

## 踩过的坑（省得重走）

| 坑 | 现象 | 正解 |
|---|---|---|
| 只挂 `mmap` 拦不到 | 抓到 7 次 MEM_MAP 但 0 次 mmap | librknnrt 走的是 **`mmap64`** 的 PLT 入口，两个都要挂 |
| 按精确地址查缓冲区 | 明知有 regcmd 却 dump 不出来 | regcmd 地址**落在别的缓冲区内部**（权重缓冲尾部），必须**区间查找** |
| 把 `regcfg_amount` 当精确长度 | 命令流末尾被截断，看不清边界 | 驱动实际读 `regcfg_amount + 4`，且槽位预留远大于用量，dump 时要加 slack |
| 板上 apt 装不上包 | `connect to 192.168.31.74:3128 timed out` | 板子 apt 配了指向 WSL 的代理但代理没跑；其实**不需要 strace**，LD_PRELOAD 更准 |
| **无保护地写 `OP_ENABLE`** | **板子彻底失联，需物理断电** | 使能位会让模块开始工作，而描述符还是未初始化的垃圾 → 硬件拿垃圾地址 DMA → 写坏内存。**第一次提交只能用 `OP_NONE`，目标是"让 ioctl 返回"而不是"让硬件干活"** |
| `gcc ... \| head` 吞掉退出码 | 编译**失败**却打印"✅ 语法通过"，坏代码被提交推送 | **永远用 `if cmd; then` 或 `$?` 判断，不要把编译/命令接进管道再判断**。这与前面"只 curl 一次就判定启动失败"是同一类错误：**判据本身不可靠** |
