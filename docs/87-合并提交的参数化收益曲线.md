# 87 · 合并提交的**参数化收益曲线**：每减少一次提交 = 省该模型的一次地板

> 接 [docs/84](84-离线实验-合并提交的上界31.6ms是去冗余拷贝的14倍.md)（上界 31.60 ms）
> 与 [docs/85](85-依赖不限制合并-可达值取决于编译器的融合策略.md)（可达值算不出来）。
> **本轮换一个能算的角度**：不追「编译器能融到多少」，而是给**曲线**。

---

## 0. 为什么给曲线而不是一个数

docs/85 的结论是：可达值取决于**编译器的融合策略**，而我**没有把它建模出来**
（docs/58 试过：R²=0.82 但系数不迁移）。

**⇒ 与其给一个算不出来的数，不如给「每减少一次提交能省多少」——
使用者代入自己判断的可达融合度即可。**

## 1. 曲线

```
模型                 提交   地板µs   实测ms  -25%提交  -50%   -75%   每提交占比
mnasnet0_5             3   265.2   0.817    0.20   0.40   0.60   24.4%
mobilenet_v2           3   356.4   1.118    0.27   0.53   0.80   23.9%
shufflenet_v2_x0_5    63    49.0   3.894    0.77   1.54   2.32   19.8%
resnet18               5   308.4   1.866    0.39   0.77   1.16   20.7%
squeezenet1_0         22   132.0   3.123    0.73   1.45   2.18   23.3%
googlenet             35    70.9   5.977    0.62   1.24   1.86   10.4%
regnet_x_400mf       113    58.3   7.692    1.65   3.29   4.94   21.4%
efficientnet_b0       88    61.5   9.294    1.35   2.71   4.06   14.6%
densenet121          183    67.7  14.614    3.10   6.19   9.29   21.2%
──────────────────────────────────────────────────────────────────────
合计                        减 25% → 9.07 ms / 减 50% → 18.13 ms / 减 75% → 27.20 ms
```

**⇒ 「每减少一次提交」的价值 = 该模型的一次地板**，占实测时间的 **10.4% ~ 24.4%**。

---

## 2. 怎么用这条曲线

| 使用者能判断的事 | 直接代入 |
|---|---|
| 「我大概能把提交数减半」 | 省 **18.13 ms**（9 模型合计） |
| 「我能把 densenet 的 183 次降到 20 次」 | 省 **(183−20) × 67.7 µs = 11.03 ms** |
| 「编译器侧改不动，但能改一个模型」 | 按该模型的「每提交占比」估算 |

**⇒ 曲线比单个数有用：它把「可达融合度」这个我算不出来的变量交给了使用者。**

---

## 3. 与 docs/84 上界的关系

```
docs/84 上界（融到 159 tile/提交）  : 31.60 ms
本曲线 减 75% 提交                   : 27.20 ms
本曲线 减 50% 提交                   : 18.13 ms
去冗余拷贝（已实测，docs/86）        :  2.22 ms
```

**⇒ 上界 31.60 ms 对应「几乎全部融合」（>90% 减少），而 75% 减少已经是 27.20 ms。**
**⇒ 曲线的两端是自洽的**（上界 ≈ 曲线的极限），这反过来验证了曲线的算法没有算错。

---

## 4. 诚实的边界

* **地板用逐模型实测值**（docs/59），不是全局 67.4 —— 用全局会让 `shufflenet` 算出 102%（docs/84 的教训）
* 曲线**假设「减少提交不影响其他分量」** —— 即算术时间与带宽时间不变。
  对地板主导的模型成立（docs/80：误差 ≤13.4%）；对带宽主导的模型（`mnasnet`/`mobilenet`）**不成立**
  ⚠️ 所以 `mnasnet`/`mobilenet` 那两行（24.4%/23.9%）**只是参考**，它们的瓶颈是带宽不是地板
* 1 趟抓取，含首次运行效应

## 5. 教训（本轮新增）

1. **★★ 算不出来的量，改成「曲线」就能交付。**
   我在 docs/84/85 卡了两轮（上界 → 可达值算不出）。本轮换角度：
   **不去算「能融到多少」，而是算「每融掉一次省多少」** —— 立刻可交付，
   而且**把算不出来的变量交给使用者**。
   **卡住时问：能不能把「我不知道的量」变成「使用者代入的参数」？**
2. **★ 曲线两端自洽是免费的验证。** 上界 31.60 ms ≈ 曲线在「几乎全融合」处的极限（27.20 ms @75%）
   ⇒ 两轮独立算出的数互相印证。**新结果要和旧结果在重叠处比一下。**
3. **★ 曲线的每一行都要标注适用性。** `mnasnet`/`mobilenet` 那两行是按地板算的，
   但它们**实际是带宽受限** ⇒ 数值只是参考。**不标的话，使用者会照单全收。**
