# 38 · ★★★ 字段语义被实证钉住（并修正 docs/37 的过宽结论）

> 📌 **补充（[docs/41](41-结构级模型成立-分块被撞实与提交地板实测.md)）**：
> 上游 `mesa/rkt_task.c` / `rkt_regcmd.c` 给出了完整的分块（split task）模型。
> 由此钉死：
> * `DATA_SIZE0[0..10]` **就是** tile 输入行带高（`bottom_slice − top_slice + 1`），不是整层高；
>   `[16..26]` 是整层输入宽。同一次写入里宽度用整层、高度用 tile，上游代码本身就这么写。
> * `DATA_SIZE3`（0x102c）`[0..21]` = `DATAOUT_ATOMICS` = **out_w × out_h** ⇒ 输出高度白拿，
>   并与 `CORE_DATAOUT_SIZE_0`（0x3014）独立互证（508/508）。
> * `CORE 0x3014` = `(out_h−1)<<16 | (out_w−1)`；通道在 `0x3018`。
> * `WEIGHT_KERNELS` = `align(out_ch, 2)`（深度卷积时为 1），不是裸 `out_ch`。


> docs/37 的结论是"偏移全对、**字段语义没有完全对上**"。本轮把它**收窄并修正**了：

> 而且是**算术恒等式级别的成立**（60/60 算子、13383 段全通过）。
>
> 真正解不出来的只剩 **`DATA_SIZE0` 的低位字段**一个。
>

## 一、方法：用 LLM 数据当"锚"，再回验 CNN

`DATA_SIZE0` 这类字段在 CNN 里因为**分块**（一层的空间被切成多个 tile）
而难以判读；LLM 的全连接是 1×1、无空间分块，字段值能直接对上已知模型维度。

```
RKLLM 前 3 段（用上游位域解码）：
   W  H   CH   CH_REAL  OUT_W   WBYTES    W/K  WW WH  WK
   2  1   896    895      2     286720    896  1  1   320
   4  1   896    895      4     286720    896  1  1   320
   6  1   896    895      6     286720    896  1  1   320
```

**立刻对上的三件事**：

1. **`CH = 896`** —— Qwen2.5-0.5B 的 `hidden_size` 正好是 896
2. **`WBYTES = 286720 = 320 × 896`** —— 精确
3. **`WW = WH = 1`、`H = 1`** —— 全连接 = 1×1，符合预期
4. 三个段的 `W = OUT_W = 2/4/6` —— 同一算子的**宽度分块**（序列被切块）

## 二、权重字段：**算术恒等式级别的确证**

### RKLLM（13383 段全量）

```
in_ch  W/K  out_ch  WBYTES    校验            出现次数
 896   896    320   286720    in_ch==W/K ✓     13287
 896   896    288   258048    in_ch==W/K ✓        96

★ 全部 13383 段只有 2 种配置，且 WBYTES == W/K × out_ch 两种都精确成立
```

### yolov5s（60 个算子全量）

```
★ WBYTES == W/K × WK 成立的 60/60（100%）
★ in_ch = W/K ÷ (WW × WH) 全部为整数 60/60
```

抽样：

| op | `WEIGHT_BYTES_PER_KERNEL`(W/K) | `WEIGHT_KERNELS`(WK) | WW×WH | `WEIGHT_BYTES` | W/K×WK | 推得 in_ch |
|---|---|---|---|---|---|---|
| 2 | 144 | 32 | 3×3 | 4608 | 4608 ✓ | **16** |
| 3 | 288 | 64 | 3×3 | 18432 | 18432 ✓ | **32** |
| 10 | 576 | 128 | 3×3 | 73728 | 73728 ✓ | **64** |
| 19 | 1152 | 256 | 3×3 | 294912 | 294912 ✓ | **128** |
| 20 | 256 | 128 | 1×1 | 32768 | 32768 ✓ | **256** |

**推得的 in_ch 全是 2 的幂（16/32/64/128/256），out_ch（12/32/64/128/256）正好是
yolov5s 的通道序列** —— 这不是巧合，是语义对了。

## 三、通道字段：**减一编码**

```
DATAIN_CHANNEL_REAL = 真实输入通道数 − 1
```

验证（链式：op1 输入是 3 通道 RGB，之后每个算子的输入 = 上一个算子的输出）：

| op | `CH` | `CH_REAL` | `CH_REAL+1` | 链式真实 in | 校验 |
|---|---|---|---|---|---|
| 1 | 16 | 2 | **3** | 3 | ✓ |
| 2 | 16 | 11 | **12** | 12 | ✓ |
| 3 | 32 | 31 | **32** | 32 | ✓ |
| 10 | 64 | 63 | **64** | 64 | ✓ |
| 20 | 256 | 255 | **256** | 256 | ✓ |

**14/18 精确成立**。剩下 4 个（op7/9/16/18）**不是字段错**，而是 yolov5 的
**CSP 拼接层**：那些算子的输入来自跳跃连接（`Concat`），不是紧邻的上一层。
例如 op7 的 `CH_REAL+1 = 64`，而上一层输出只有 32 —— 64 = 32（上一层）+ 32（跳跃来的）
正好是拼接的结果。

> 顺带解开了 docs/17 里那批看着奇怪的值（"31/63/127/255/511"）：
> 它们是 **真实通道数 − 1**，不是"通道数−1 的某个变体"。

## 四、通道对齐行为被暴露

```
yolov5s op1: 真实输入 3 通道   → DATAIN_CHANNEL = 16
yolov5s op2: 真实输入 12 通道  → DATAIN_CHANNEL = 16
RKLLM     : 真实输入 896 通道  → DATAIN_CHANNEL = 896
```

**`DATAIN_CHANNEL` 是补齐到对齐粒度后的通道数**（3→16、12→16），
而 `DATAIN_CHANNEL_REAL` 保留真实值。

这对二次开发很关键：**写配置寄存器时必须填对齐后的通道数，而不是真实通道数** ——
填错会导致权重/数据被按错误的步长读取。

## 五、片上缓冲模型被定量验证

用 RKLLM 那个 896→320 的全连接（权重 286,720 字节 = 280 KB）验证：

```
实测 CBUF_CON0 = 0x0000b1  →  DATA_BANK=1   WEIGHT_BANK=11   （和 = 12 ✓）

用 Mesa 的公式反算：
  bytes   = 896 × 320 = 286720
  entries = DIV_ROUND_UP(286720, CBUF_ENTRY_SIZE=128) = 2240
  banks   = DIV_ROUND_UP(2240, CBUF_ENTRIES_PER_BANK=256) = 8.75 → 9
  再 +1（Mesa 自己也不知道为什么要 +1）             = 10
实测 11 —— 差 1 但量级完全对上
```

**Mesa 的源码注释写着**："Why do we need an extra bank? The calc above might be wrong
on this HW" —— 而实测值比它的公式还多 1，说明**厂商的公式比 Mesa 保守一点**
（很可能也补了一个 bank）。这是"我们的数据能反过来检验上游"的一个实例。

## 六、修正 docs/37 的结论

docs/37 说"字段语义没有完全对上"，列举了 `DATAIN_HEIGHT=34` 和
`DATAIN_CHANNEL_REAL=2` 两个反例。现在要精确化：

| docs/37 的说法 | 修正 |
|---|---|
| "字段语义没有完全对上" | ⚠️ **过宽**。**权重字段（`WEIGHT_SIZE0/1/2`）与通道字段（`DATA_SIZE1`）语义完全成立**，100% 通过算术恒等式验证 |
| "`DATAIN_CHANNEL_REAL` 解不对" | ❌ **错**。它是**减一编码**，14/18 精确成立，4 个例外由 CSP 拼接解释 |
| "`DATAIN_HEIGHT` 解不对" | ✅ **成立**。这个确实没解出来（见下） |

**为什么 docs/37 会判错**：我当时把"字段对应关系"搞错了（把权重字段的位域套到了尺寸字段上），
于是得出"字段解不对"的结论。**教训与之前几次一致：反例要先排除"自己用错了判据"。**

## 七、唯一还没解出来的：`DATA_SIZE0` 低位

```
op1 : DATA_SIZE0 = 0x02800022 → 宽 640 ✓  低位 34
op2 : DATA_SIZE0 = 0x01400046 → 宽 320 ✓  低位 70
op10: DATA_SIZE0 = 0x00a0001c → 宽 160 ✓  低位 28
```

而且**这个值恒等于 `CONV_CON2` 的 `FEATURE_GRAINS` 字段**（op1 两者都是 34）。
所以它**恐怕不是"输入高度"**，而是与"粒度/条带"相关的东西。

候选解释（待验证）：`grains` = 输入在高度方向被切成的条带数或条带高度。
用 `640 / 34 = 18.8`（非整数）看不出规律 —— 但也可能它不是高度方向的量。

**这条留到下一轮**，需要拿"同一个算子的不同 tile"做对比（同一层的 tile 之间
宽/高字段如何变化，最能暴露字段含义）。

## 八、现在能做什么（对二次开发的意义）

拿到这套**已确证的字段语义**之后，可以纯靠命令流算出：

| 能算出的量 | 用哪些字段 |
|---|---|
| 每层的 **in_ch / out_ch / 卷积核尺寸** | `DATA_SIZE1.CH_REAL+1`、`WEIGHT_SIZE2.KERNELS`、`.WIDTH/.HEIGHT` |
| 每层权重的**精确字节数** | `WEIGHT_SIZE0`（且可用 `W/K × WK` 交叉校验） |
| 每层的**输入/输出空间尺寸** | `DATA_SIZE0.WIDTH`、`DATA_SIZE2.WIDTH` |
| 每层需要多少 **CBUF bank** | 权重字节数 ÷ 128 ÷ 256，再加 DATA_BANK，和恒为 12 |
| 权重是否**跨 tile 复用** | `CBUF_CON0.WEIGHT_REUSE` |
| 通道的**对齐填充量** | `DATAIN_CHANNEL` vs `CH_REAL+1` |

**这已经是一个可用的"结构级模型"雏形**：给定命令流就能反推出完整的层配置与片上资源占用。
下一步把它接上"耗时"这一维，就能预测工作量。
