# 117 · 布局的观测通道被**彻底关闭**：不是「hook 太早」，而是**之后没有任何回调**

> 接 [docs/113](113-两个方向都到边际-建议收口.md)（那里说「hook 位置太早」）。
> 本轮做了决定性的检查：**第 20 步（`RKNNLayoutMatchPass`）之后还有没有规则触发？**

---

## 1. ★ 决定性结果：**0 条**

```python
# 同时捕获 C 层的 pass 标记（fd 级重定向）与 Python 层的规则触发（monkeypatch）
LayoutMatchPass 之后的 RULE 数: 0
```

**⇒ `RKNNLayoutMatchPass`（第 20 步，就是添加 `layout` 属性的那一步）之后，
**没有任何 Python 规则被触发**。**

---

## 2. ★ 这修正了 docs/113 的说法

| 说法 | 状态 |
|---|---|
| docs/113：「**hook 位置太早**」（暗示换个更晚的 hook 点就行） | ❌ **不准确** |
| **本轮：「layout pass 之后没有任何 Python 回调」** | ✅ **准确** |

**⇒ 不是「选错了 hook 点」，而是「**不存在**更晚的 hook 点」。**
**⇒ 用「monkeypatch Python 规则」这条路径**永远**读不到 `layout`。**
**⇒ 要读 layout 只能走 gdb / 反汇编（`librknnc.so`，完整符号表已 strip）。**

---

## 3. 顺带确认的一条：规则的触发**全部集中在早期**

（本轮的 pass 标记是 build 结束后统一打印的，所以顺序对照需要在流式日志里看；
但「LayoutMatch 之后为 0」这个结论是可靠的 —— 因为规则计数是按触发时机累计的。）

**⇒ 这与 docs/109 的观察一致**：规则触发发生在 `OpFusing` 阶段（早期），
而 layout / tiling / 权重转置等都在更后面（C++ 侧）。

---

## 4. 更新后的边界（写进 docs/114 那张表）

| 未答 | 之前的原因 | **修正后的原因** |
|---|---|---|
| 任意 `out_ch` 的通用权重布局 | 「hook 位置太早」 | **「layout pass 之后没有任何 Python 回调」⇒ 非 gdb 路径不可能** |

**⇒ 这是一个更强的结论**：它把「还没找对方法」变成了「**这条方法不存在**」。

## 6. 教训（本轮新增）

1. **★★★ 「hook 太早」和「没有回调」是两种不同的诊断，指向不同的行动。**
   前者意味着「换个位置再试」（低成本），后者意味着「这条路不存在」（该放弃）。
   **我上一轮给的是前者，本轮证明是后者 —— 差一个数量级的行动成本。**
   **诊断卡点时要问「是位置不对，还是这条路上根本没有我要的东西」。**
2. **★ 「0」这个结果比「非 0」更有决定性。** 「LayoutMatch 之后 0 条规则」
   一举关闭了一整条路径。**当你想确认「某条路通不通」时，去找那个「0」。**
3. **★ 修正边界时要把「原因」一起改强。** docs/113 的「hook 太早」是**弱**原因
   （暗示可解）；本轮的「没有回调」是**强**原因（判定不可解）。
   **边界说明的强度直接影响后来者的行动决策。**
