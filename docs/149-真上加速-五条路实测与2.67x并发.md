# docs/149 — 真上加速：试了五条路，只有一条拿到 2.67×

> 用户要求"数据传输、算子融合都上"。这份把能想到的加速手段逐条实测，
> 包括**两条被硬件/工具链直接否掉的**，最后只有一条有量级上的收益。

---

## 0. 结论

| # | 手段 | 结果 | 判定 |
|---|---|---|---|
| 1 | `remove_reshape=True` | 159→158 个算子，cycles 完全不变 | ❌ 无效 |
| 2 | `sparse_infer=True`（4:2 稀疏） | **`rk3588 does not support sparse inference`** | ❌ 硬件不支持 |
| 3 | DFL softmax 切到 CPU | NPU 省 16%，尾部补回 3.5 ms ⇒ 净 **+5%** | ⚠️ 微弱 |
| 4 | 宿主侧零拷贝 | 分块流水 277 → 137 ms | ✅ 已在 `docs/148` |
| 5 | **多实例并发（每实例绑一核）** | **31.85 → 85.02 FPS = 2.67×** | ✅ **量级收益** |

---

## 1. 被直接否掉的两条

### 1.1 稀疏推理：硬件不支持

把 80 个 Conv 权重按 4:2 结构化稀疏剪枝（每组 4 个输入通道保留幅值最大的 2 个），
再开 `sparse_infer=True`：

```
ValueError: rk3588 does not support sparse inference, ignore this parameter!
```

⇒ **RK3588 的 NPU v2 不支持权重稀疏**。这条理论收益最大（卷积占 93.8% 的 NPU cycle，
理论上可 2×），但硬件层面就没开。

### 1.2 remove_reshape：只少了一个算子

```
base       算子 159   NPU cycles 5,518,400
remove_reshape 算子 158   NPU cycles 5,518,400   （一模一样）
```

Reshape 10 → 9。cycles 一点没变，属于编译器的 no-op。

## 2. DFL softmax：抓到了真凶，但收益被 CPU 吃掉

### 2.1 定位

用抓取库拿 task 描述符，按 `op_idx` 统计（1093 条 task / 99 次提交）：

| op_idx | 类型 | task 条目 | 占比 |
|---|---|---|---|
| **141** | **`exSoftmax13:/model.23/dfl/Softmax`** | **350** | **32.0%** |
| 61 | `exSDPAttention`（model.10 注意力） | 57 | 5.2% |
| 1 | stem conv | 20 | 1.8% |

**一个 softmax 算子占了 32% 的 task 条目** —— 因为 DFL 是 `(1,64,8400)` 上按通道做 softmax，
NPU 必须转成"归约维连续"的布局，被切成 350 个 tile。

### 2.2 手术

把 ONNX 从 `/model.23/dfl/Softmax` 处切开：

```
原图: ... → Concat(1,64,8400) → Reshape(1,4,16,8400) → Transpose → Softmax(axis=3)
        → Transpose_1 → Conv(arange16) → Reshape(1,4,8400) → Slice/Add/Sub/Div/Mul(×stride)
        → Concat(box, sigmoid(cls)) → output0
新图: 输出 [Concat(1,64,8400), Sigmoid(1,80,8400)]，尾部用 numpy 复刻
```

numpy 尾部与 ORT 参考对齐：**最大相对误差 2.9e-7**。

### 2.3 结果：只有 +5%

```
完整模型            32.57 ms
head + 全量 DFL     50.43 ms   (-35%)   ← numpy 全量 softmax 太慢
head + 候选 DFL     31.02 ms   (+5%)    ← 只对 score>0.25 的锚点算
  其中 head 推理    27.53 ms
  其中 CPU 尾部      3.49 ms
```

NPU 侧确实省了（32.6 → 27.5 ms，16%），但**尾部 3.5 ms 把大头吃回去了**。

> 关键优化：**DFL 只对候选锚点算**（先看类别分数筛，通常 <300 个），
> 而不是对全部 8400 个锚点算 —— 这一条把尾部从 26.75 ms 压到 3.49 ms。

## 3. ★ 多实例并发：2.67×

### 3.1 起因：逆向数据里的暗示

`docs/144/148` 反复测到同一个现象：**单次推理里 56% 的提交只用 1 个核**。
也就是单个推理根本吃不掉 3 个核。

于是直接验证：同一个模型，开 3 个 runtime 实例，各自绑一个核，三线程并发。

### 3.2 结果（三轮交替测量，消除热漂移）

| 配置 | 第1轮 | 第2轮 | 第3轮 | 中位 FPS | 相对 |
|---|---|---|---|---|---|
| 1 核单实例 | 32.20 | 32.63 | 32.40 | 32.40 | 1.02× |
| 3 核单实例 | 31.85 | 31.84 | 32.02 | **31.85** | 1.00× |
| 2 实例并发（0/1） | 59.38 | 56.59 | 57.91 | 57.91 | 1.82× |
| **3 实例并发（0/1/2）** | 83.19 | 85.02 | 87.01 | **85.02** | **2.67×** |

三轮偏差 <2%，这个结论是稳的。

**两个反直觉点：**

1. **单实例开 3 核完全没有收益**（31.85 vs 32.40，反而略慢）。
   和 `docs/148` 的结论一致：任务组凑不满 3 的倍数时另外两核空转，
   多核只增加同步开销。
2. **并发几乎线性**：2 实例 1.82×、3 实例 2.67×（理想 3.0×）。

### 3.3 实现

```python
from rknnlite.api import RKNNLite
MASKS = [RKNNLite.NPU_CORE_0, RKNNLite.NPU_CORE_1, RKNNLite.NPU_CORE_2]

# 每个 worker 线程持有自己的一份 runtime
def worker(mask, q_in, q_out):
    r = RKNNLite(verbose=False)
    r.load_rknn("yolo11n_640.rknn")
    r.init_runtime(core_mask=mask)          # ★ 绑死一个核
    while True:
        img = q_in.get()
        if img is None: break
        q_out.put((img, r.inference(inputs=[prep(img)])))
    r.release()
```

要点：
- **`init_runtime(core_mask=...)` 必须每个实例单独设**，不能共用
- 模型文件可以共用同一个 `.rknn`，但每实例各加载一份（4.6 MB ×3，可接受）
- 输入数组**每线程独立**（避免竞争），预处理放线程内

## 4. 该用哪种，取决于你要延迟还是吞吐

| 场景 | 推荐 | 理由 |
|---|---|---|
| **单帧延迟**（点一下出一张） | 单实例、1 核 | 3 核没收益，1 核反而略快、更省电 |
| **视频流 / 多路**（要 FPS） | **3 实例并发** | 2.67× 吞吐，但单帧延迟不变（~31 ms） |
| **1280 高分辨率** | 分块 + 3 实例 | `docs/148` 分块省 14%，再叠加并发 |

⚠️ 并发提升的是**吞吐**，不是单帧延迟：每个实例仍是 ~31 ms。
如果你的业务是"来一帧处理一帧、要求尽快返回"，并发没用；
如果是"连续视频流、多路摄像头"，并发直接 2.67×。

## 5. 还没试的（诚实列出）

| 想法 | 为什么没试 |
|---|---|
| `op_target` 把内存算子放 CPU | key 格式没文档，试了 ID / 节点名 / 类型名都被拒（`Invalid key of ...`） |
| 头模型 + 并发叠加 | 需要把尾部也塞进并发线程，工作量大，且尾部只省 5% |
| 3 实例共享同一份模型权重 | rknnlite 没有共享上下文 API |
| 温度墙 | 并发跑满 3 核后的持续热表现未测（本轮都是短时 80 帧） |
