# docs/156 — NMS 对齐：算法没错，是我把解码格式搞错了

> `docs/155` 发现 C 的 NMS 与 OpenCV 结果差很多。这轮定位到底：
> **NMS 算法三者完全一致，真正的 bug 在解码格式** —— 模型输出是 `(cx, cy, w, h)`，
> 而我在 Python 侧一直当成 `(x1, y1, x2, y2)` 用。

---

## 0. 结论

| 检查项 | 结果 |
|---|---|
| **NMS 算法是否一致** | ✅ **完全一致**（torchvision / OpenCV / 我们的贪心，35/35 且集合相同） |
| **差异来源** | ❌ **解码格式**：YOLO11 导出模型的输出是 **`(cx, cy, w, h)`**，Python 侧按 xyxy 解释 |
| **谁是对的** | ✅ **C 版是对的**（它从 DFL 直接算 x1,y1,x2,y2） |
| 修正后的对齐度 | C 16.7 检出/帧 vs Python 14.9/帧（同一 27 帧，差 12%） |

---

## 1. 先证明 NMS 算法本身没问题

造 120 个框（30 个目标 × 每个 4 个近似框），分别喂三个实现：

```
输入 120 个框
torchvision : 保留 35
OpenCV      : 保留 35
我们的贪心  : 保留 35
tv ∩ greedy = 35 / cv ∩ tv = 35
```

**三个实现保留数和集合完全相同。** ⇒ NMS 算法不是差异来源。

> 补充：OpenCV 的 `NMSBoxes` 在 **C++ dnn 模块**里，C API（老接口）没有这个函数。
> 所以「用 OpenCV 的 C 版」这条路不存在；但既然算法一致，自己写贪心就够了。

---

## 2. 真正的 bug：`(cx,cy,w,h)` vs `(x1,y1,x2,y2)`

从 ONNX 图里能直接读出来：

```
Sub   = anchor - lt      → x1y1
Add_1 = anchor + rb      → x2y2
Add_2 = x1y1 + x2y2
Div_1 = Add_2 / 2        → center     ★
Sub_1 = x2y2 - x1y1      → wh         ★
Concat_2 = [center, wh]
```

⇒ **模型输出的前 4 行是 `(cx, cy, w, h)`**（Ultralytics `dist2bbox(..., xywh=True)` 的约定）。

而我在 `pipeline1280.py` 里写的是：

```python
box = np.concatenate([(x1 + x2) * 0.5, x2 - x1], 1) * st   # → (cx, cy, w, h)
...
# 然后 NMS 里当成 xyxy 用：
xywh = np.concatenate([b[:, :2], b[:, 2:4] - b[:, :2]], 1)   # ✗ 把 cx,cy 当左上角
```

**NMS 拿到的是"以中心点为左上角"的框** → IoU 算错 → 抑制行为乱掉。
这解释了为什么差异**双向都有**（有时多留、有时少留）。

### C 版为什么对

C 里根本没走 `(cx,cy,w,h)` 这一步，它直接算：

```c
float x1 = (anc0 - d[0]) * st, y1 = (anc1 - d[1]) * st;
float x2 = (anc0 + d[2]) * st, y2 = (anc1 + d[3]) * st;   // 直接就是 xyxy
```

---

## 3. 修正与验证

### 3.1 改法

```python
# 之前：(cx + cy 的均值, 差) = (cx, cy, w, h)
box = np.concatenate([(x1 + x2) * 0.5, x2 - x1], 1) * st
# 之后：直接输出 xyxy
box = np.concatenate([x1, x2], 1) * st
```

### 3.2 逐帧对比（ONNX FP32，正确解码后）

| frame | raw | ONNX keep | C keep |
|---|---|---|---|
| 0 | 63 | 6 | 7 |
| 1 | 31 | 3 | **3** |
| 2 | 15 | 4 | 3 |
| 3 | 40 | 4 | **4** |
| 4 | 57 | 7 | 9 |
| 5 | 11 | 2 | **2** |
| 6 | 52 | 9 | 8 |
| 7 | 13 | 2 | **2** |
| **合计** | 282 | **37** | **38** |

**合计 37 vs 38，逐帧差 ±1~2** —— 这就是 INT8 与 FP32 的量化误差，属于正常范围。

### 3.3 同 27 帧的整体对齐

| 实现 | 检出/帧 |
|---|---|
| C（INT8，贪心 NMS） | **16.7** |
| Python（INT8，OpenCV NMS，修正后） | **14.9** |

差 12%，来源是两套 NMS 在边界情况上的细节差异（单元测试证明算法等价，但浮点顺序、排序稳定性会带来少量分歧）。

## 4. 影响面

`docs/153` 里"检出 1419 vs ONNX 1490 = 95.2% 一致"这个结论**需要打个折**：
当时两边都用了错误的 xyxy 解释，属于"同错同对"，所以一致性数字虚高。

**修正后的真实情况**：
- 解码格式错 → 检出数虚高（52.6/帧，实际 16.7/帧）
- 修正后 C 与 FP32 的逐帧对齐是 ±1~2 个框

⇒ 结论从"95.2% 一致"改成 **"逐帧框数差 ±1~2，合计 38 vs 37"**，这个更可信也更有意义。

---

## 5. 教训

1. **单元测试先行**：NMS 这种独立算法，先隔离测（合成数据喂三种实现），
   能立刻排除"算法不对"这个方向，不至于在集成层瞎猜。
2. **输出格式必须从图里读出来，不能猜**。ONNX 的 `Div`/`Sub` 节点已经写明是 center+wh，
   我却是按"YOLO 输出 xyxy"的**印象**写的。
3. **一致性高不代表对**：两边用同样的错误假设时，对比结果会非常"漂亮"（95.2%）。
