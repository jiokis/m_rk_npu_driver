## 一、为什么用"跨运行时"而不是"跨模型"

原计划步骤 3 是换 `mobilenet_ssd.rknn` 验证。但那个模型**在本板上是坏的**：

```
E RKNN: Verify ModelBuffer failed!
E RKNN: Invalid RKNN format          ← 与 librknnrt 2.3.0 不兼容
```

板上没有别的可用模型，也没有 onnx / rknn-toolkit2 可转换。

**于是换了更强的一条路**：让 NPU 跑 **LLM**。LLM 走的是 `librkllmrt`
（另一个闭源运行时，与 `librknnrt` 完全独立实现），
**跨运行时的验证比跨模型更有说服力** —— 它证明的是"硬件约定"而不是"模型特性"。

## 二、验证结果（13383 / 13383 全中）

| 断言 | RKLLM（Qwen2.5-0.5B） | yolov5s（librknnrt） | 结论 |
|---|---|---|---|
| **段布局**：使能在 `amount+3`、`OP40` 在 `amount+2` | ✅ **13383/13383** | ✅ 611/615 | ✅ **硬件约定** |
| **`block_id = target \| 1`**，target 是 2 的幂 | ✅ 0x41→0x40 · 0x81→0x80 · 0x101→0x100 · 0x201→0x200 · 0x801→0x800 · 0x1001→0x1000 | ✅ | ✅ **硬件约定** |
| **张量地址寄存器**取值落在真实缓冲区 | ✅ **100%**（CNA `0x1070`/`0x1110`、DPU `0x4020` 各 1500/1500） | ✅ | ✅ **硬件约定** |
| 指令编码（8 字节三字段） | ✅ | ✅ | ✅ |
| ⚠️ **ENABLE 位图取值** | **只有 `0x0D = CNA\|CORE\|DPU`** | `{0x18, 0x1D, 0x60}` | ❌ **我之前的"只有 3 种取值"是错的** |

### ★ 被纠正的结论

我在 [docs/18](18-NPU结构-流水构建-指令集.md) 里写过：

> "615 个段里**只有 3 种取值**"

**这是错的** —— 它只是 yolov5s 的情况。RKLLM 用的是 **`0x0D`（无 DPU_RDMA）**。
位图取值取决于**运行时/工作负载**，不是固定的 3 种。

**位图语义仍然成立**（bit0=CNA / bit2=CORE / bit3=DPU / bit4=DPU_RDMA / bit5=PPU / bit6=PPU_RDMA），
只是"有几种组合"是开放的。

## 三、★ 一个有意义的差异：链槽是**可选**的

两个运行时的段布局逐字节对比：

| 位置 | librknnrt（yolov5s） | **librkllmrt（Qwen2.5）** |
|---|---|---|
| `[amount]` | `PC 0x0010 = 下一段地址` | **`NONE`（空操作）** |
| `[amount+1]` | `PC 0x0014 = 下一段的 DATA_AMOUNT` | `PC 0x0014 = 0` |
| `[amount+2]` | `OP40` | `OP40` |
| `[amount+3]` | `ENABLE` | `ENABLE` |

**⇒ 硬件有两种推进方式**：

| 方式 | 谁在用 | 硬件怎么走 |
|---|---|---|
| **链式** | librknnrt（整个 yolov5s 一条 588 段的链） | 顺着 `0x0010` 指针走 |
| **数组式** | librkllmrt（13383 个 task 独立提交） | 按 `task_number` 遍历任务数组 |

这解释了 yolov5s 那 615 个段里"4 个链槽是 `NONE`"的情况 —— 那正是**链结束**，
与 RKLLM 的做法**同构**。

**这也修正了 [docs/18](18-NPU结构-流水构建-指令集.md) 的表述**：
链不是段结构的必需部分，而是**一种可选的推进机制**。

## 四、★ LLM 的 NPU 使用模式（对利用率极重要）

RKLLM 跑 8 个 token 的抓取统计：

```
SUBMIT 次数 : 4152          ← 8 个 token 就 4152 次提交
task 总数   : 13383
平均每提交 : 3.2 个 task
task_number : 3(×3963) · 6(×165) · 21(×24)
core_mask   : 0x4(×1352) · 0x1(×1400) · 0x2(×1400)   ← 轮转！
flags       : 全部 0x5
```

### 4.1 两种运行时用了**完全不同的多核策略**

| | yolov5s（librknnrt） | Qwen2.5（librkllmrt） |
|---|---|---|
| 提交次数 | 4 ~ 77 | **4152** |
| 每提交 task 数 | 分批 = 核数（3/6/9…） | **几乎全是 3** |
| core_mask | **单次提交内固定** | **0x1/0x2/0x4 轮转**（一次一核） |
| 并行方式 | **批次内 3 核并行** | **提交间轮转单核** |

**⇒ librkllmrt 没有做"一次提交用三核"，而是把活切成极小的批次、在三个核之间轮转。**

### 4.2 每 token 约 519 次提交

```
4152 次提交 / 8 token ≈ 519 次/token
```

按 [docs/22](22-多核实验结论.md) 粗估的 **~0.14 ms/次提交**，光提交开销就是
**约 73 ms/token**，而实测 decode 是 **14~20 t/s（50~70 ms/token）**。

**⇒ 提交开销很可能是 LLM 解码的主要瓶颈之一，而不是算力。**
（这是量级估算，需要性能计数器确认 —— 但方向很明确。）

这条正好与 [docs/22](22-多核实验结论.md) 的结论呼应：**提交开销是当前最大的可优化项。**

## 五、抓取工具的两个 bug（都踩到了）

### 5.1 `LD_PRELOAD` 必须在 shell 里设

```python
os.environ["LD_PRELOAD"] = so     # ❌ 无效！只对新 exec 的进程生效
```
第一次抓 mobilenet 与 LLM 都是 0 样本，就是这个原因。

### 5.2 ★ 设备地址的符号扩展不一致（两阶段才修对）

| 运行时 | `regcmd_addr` 给的值 |
|---|---|
| librknnrt | `0x0000000080c48580` |
| **librkllmrt** | **`0xfffffffffed1e000`** |

而 `MEM_CREATE` 报的 `dma_addr` 是 `0x00000000fed1e000`。

**第一次修（错的）**：掩到 40 位（驱动 `dma_mask = BIT_MASK(40)`）
→ `0xfffffffffed1e000 & 0xFFFFFFFFFF = 0xfffed1e000`，**还是对不上**。
因为它是**从 32 位符号扩展**来的，bit32-39 也是 1。

**正解**：按高 32 位判断
```c
static uint64_t norm_dma(uint64_t v) {
    if ((v >> 32) == 0xFFFFFFFFULL) return v & 0xFFFFFFFFULL;  /* 32 位符号扩展 */
    return v & 0xFFFFFFFFFFULL;                                 /* 40 位 IOVA */
}
```

修好后 **13383 个样本全部 dump 成功，0 警告**。

> 教训：**"掩到 N 位"这种操作要先想清楚对方是哪种扩展**。
> 我第一版掩对了位数、掩错了语义，于是又空跑一轮。

## 六、对结论体系的影响

| 结论 | 状态 |
|---|---|
| 指令编码（8 字节三字段） | ✅ **跨运行时确认** |
| 段布局（使能@amount+3、OP40@amount+2） | ✅ **跨运行时确认（13383/13383）** |
| `block_id = target \| 1`，target 是 2 的幂 | ✅ **跨运行时确认** |
| 张量地址寄存器（各级一个） | ✅ **跨运行时确认（100% 命中）** |
| `0x0014` 低 16 位公式 | ✅ 仅链式推进时使用；数组式写 0 |
| **链是段结构的必需部分** | ❌ **推翻** → 链是**可选**推进机制 |
| **ENABLE 位图"只有 3 种取值"** | ❌ **推翻** → 取决于运行时/负载（RKLLM 用 `0x0D`） |
| 分块结构（同层空间分块） | 🟡 仅 yolov5s 验证过，RKLLM 侧未做（task 结构不同） |
