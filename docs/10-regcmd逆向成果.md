> 工具：[src/analysis/regcmd_disasm.py](../src/analysis/regcmd_disasm.py)（纯静态分析，零硬件风险）
> 原始产出：[data/analysis/](../data/analysis/)（寄存器表 / 算子总览 / 地址交叉比对 / 反汇编样例）
> 素材：从闭源 `librknnrt.so` 抓取的 **615 条真实命令流**（见 [04](04-regcmd格式.md)）

## 一、指令编码（已确证）

每 **8 字节**一条指令，小端：

```
word0 = [u16 reg_offset][u16 value_lo]
word1 = [u16 value_hi ][u16 block_id ]
        ↓
block_id = word1 >> 16
value    = (value_hi << 16) | value_lo
```

**为什么确信是 8 字节**：解出的 `reg_offset` 全部落在规整的寄存器 bank 里
（`0x10xx` CNA、`0x40xx` DPU、`0x50xx` DPU_RDMA…），并且与 GPL 头文件的
`RKNPU_OFFSET_*` 偏移表精确吻合。试过 6 字节步长，解出来的是 `0x0201` 这种
block_id 值 —— 明显错位。

## 二、block 映射（615 条样本逐条核对）

| block_id | 名称 | 出现次数 | 寄存器窗口 |
|---|---|---|---|
| `0x0000` | OP_NONE（空操作） | 277 | — |
| `0x0041` | OP_40（使能前置） | 110 | — |
| `0x0081` | **OP_ENABLE**（总使能位图） | 110 | — |
| `0x0101` | **OP_REG_PC** | 220 | `0x0xxx` |
| `0x0201` | **OP_REG_CNA**（卷积） | 19519 | `0x1xxx` |
| `0x0801` | **OP_REG_CORE** | 20 | `0x3xxx` |
| `0x1001` | **OP_REG_DPU** | 5486 | `0x4xxx` |
| `0x2001` | **OP_REG_DPU_RDMA** | 1071 | `0x5xxx` |
| `0x4001` | **OP_REG_PPU** | 1066 | `0x6xxx` |
| `0x8001` | **OP_REG_PPU_RDMA** | 475 | `0x7xxx` |

### 2.1 `OP_ENABLE` 的位图语义被独立复现

`OP_ENABLE` 的 `reg 0x0008` 在 110 个样本里**只有 3 种取值**：

```
24 = 0x18   → DPU + DPU_RDMA
29 = 0x1D   → PC + CNA + DPU + DPU_RDMA     ← 卷积类算子的常用组合
96 = 0x60   → PPU + PPU_RDMA                ← 池化类算子的组合
```

外部资料给出的位定义是「bit0=PC / bit2=CNA / bit3=CORE / bit4=DPU / bit5=DPU_RDMA /
bit6=PPU / bit7=PPU_RDMA」。代入验证：

| 值 | 位分解 | 与外部定义是否一致 |
|---|---|---|
| `0x1D` = `0b00011101` | bit0,2,3,4 | ✅ PC+CNA+CORE+DPU |
| `0x60` = `0b01100000` | bit5,6 | ✅ DPU_RDMA+PPU |
| `0x18` = `0b00011000` | bit3,4 | ✅ CORE+DPU |

**这是我们自己数据独立复现的**，不是照抄资料。

## 三、★ 寄存器语义表（核心交付物）

完整表在 [data/analysis/register_map.txt](../data/analysis/register_map.txt)，
共 **146 个不同寄存器**。判读规则：

- 取值唯一 → **固定常量**（规格的一部分）
- 取值 ≤4 种 → **模式/档位字段**
- 取值多、且 >80% 落在已知设备缓冲区内 → **张量地址字段**
- 其余大取值 → 形状/步长/长度等数值字段

### 3.1 每个流水级都有自己的张量地址寄存器

这是本次逆向最有价值的发现 —— **架构上完全自洽**（流水每一级都要读写自己的张量）：

| block（流水级） | 张量地址寄存器 | 命中率（值落在真实缓冲区） |
|---|---|---|
| **PC** | `0x0010` | **109 / 109** |
| **CNA** | `0x1070` | **132 / 132** |
| **CNA** | `0x1110` | **104 / 104** |
| **DPU** | `0x4020` | **75 / 75** |
| **DPU_RDMA** | `0x5018` | 4 / 5 |
| **DPU_RDMA** | `0x5020` | 18 / 19 |
| **PPU** | `0x6070` | **5 / 5** |
| **PPU_RDMA** | `0x701c` | **5 / 5** |

**判据为什么强**：这些值不是"看着像地址"，而是**精确落在我们从 ioctl 侧独立观测到的
`MEM_CREATE.dma_addr` 缓冲区内**（见 [addr_xref.txt](../data/analysis/addr_xref.txt)）。
两条完全独立的观测路径（内核 ioctl 侧 / 命令流内容侧）对上了同一批地址。

> 这是"能自己生成算子配置"的关键前提：**知道往哪个寄存器填张量地址**。

### 3.2 常量的规模说明很多东西

CNA 与 DPU 里有**大量取值唯一的寄存器**：CNA 的 `0x105c/0x1060/0x1064/0x1074/0x1078/
0x1100/0x1104/0x1140…0x1168`，DPU 的 `0x4034…0x40c4`（一长串）、`0x4108…0x411c`。

**含义**：每个算子配置里有**一大块固定规格**（硬编码的流水时序/使能/算术配置），
只有少数几个槽位是变量（地址、形状、步长）。这对生成自定义配置是好消息 ——
**模板的绝大部分可以照抄，只需改那几个变量槽位**。

### 3.3 若干可读出的模式字段

| 寄存器 | 取值 | 推断 |
|---|---|---|
| CNA `0x1014` | `[9, 18, 2313]` | 精度/数据类型档位（9 vs 18 像是 int8 vs int16 的某个倍数） |
| CNA `0x1028` | `0x14..0x140` | 数值字段（步长或通道数） |
| CNA `0x102c` | `0x50..0x5640` | 数值字段（尺寸类） |
| CNA `0x1044` | `[80, 160, 320, 20480]` | 档位 |
| CNA `0x1068` | `[0, 16, 17, 34]` | 档位（16/17/34 像是通道分块相关） |
| DPU `0x4004` | `[14, 48]` | 模式（`0xe` / `0x30`） |
| DPU_RDMA `0x7014` | `[31, 255]` | 掩码类 |
| PC `0x0014` | `0x6..0x226` | PC 链的段长度 |

> 这些是**推断**，不是结论。要确认得做"只改这一个寄存器值"的对照实验（有硬件风险，见下）。

## 四、算子分类（从 block 组成看）

| 类型 | block 组成 | 例子 |
|---|---|---|
| **卷积类**（绝大多数） | `CNA×45 + DPU×1 + DPU_RDMA×1` | op 1/2/3/… |
| **另一类** | `DPU×39 + DPU_RDMA×1` | **op 8 / 17 / 28 / 35 / 44 / 48 / 53 / 57 / 62 / 65 / 70 / 73 / 78** |
| **DPU 密集** | `DPU×…`（137 条指令） | op 80 / 82 / 84 |

op 8/17 这类**完全不用 CNA**，只用 DPU —— 说明不是卷积，可能是池化/逐元素/布局变换。
这是一个天然的算子分类维度，对做算子覆盖很有用。

## 五、未决问题（诚实标注）

### 5.1 `regcfg_amount` 的单位没搞清 ★

这是目前最大的疑点，有明确的矛盾证据：

| 观测 | 数值 |
|---|---|
| op 1 声明的 `regcfg_amount` | 126 |
| 126 ÷ 8（字节/指令） | **15.75 —— 不是整数** |
| 而确凿的张量地址寄存器 `0x1070`（132/132 命中真实缓冲区）出现在**指令 [26]** | 即第 208 字节处，**远超 126 字节** |
| 整个 dump 区域的 block 序列跨样本一致到第 39 条 | 说明是连贯的同一条流，不是下一个 task 的数据 |

**已排除的解释**：
- 不是 6 字节/条（那样解出的是 block_id 值，明显错位）
- 不是 16 位或 32 位字数（126×2=252、126×4=504 都不对齐 8 字节，且与 PC_DATA_AMOUNT 公式对不上）

**下一步实验设计**（需要硬件，风险可控）：
一次 capture，把 slack 设成**大于一个槽位**（槽距实测 0x440 = 1088 字节），
dump 完整槽位，然后：
1. 找 `regcmd_(seq)_task(N+1).bin` 的内容在 task N 的 dump 里首次出现的偏移
2. 那个位置就是 task N 槽位的真实结束边界
3. 与 `regcfg_amount` 一比，单位自然就出来了

**这个实验是纯读取（只是放大 dump 窗口），不提交任何东西，零风险。**

### 5.2 其他未决项

| 问题 | 怎么解决 |
|---|---|
| 各寄存器的精确含义（形状/步长/量化参数） | 需要"单寄存器改写 + 观察行为"的对照实验（**有硬件风险，暂缓**） |
| PC 链的完整语义 | 已知 `0x0010`=下一段地址、`0x0014`=长度；还需确认终止条件 |
| CNA 的 `0x100c/0x1010/0x1020/0x1024/0x1030/0x1038` 为何"疑似地址但不落在已知缓冲区" | 可能指向 SRAM/NBUF 或经过变换的内部地址，需确认 |
