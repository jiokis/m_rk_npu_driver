# docs/143 — 通用逆向工具流：分层调研与本机落地

> 问题：「有没有什么通用的逆向工具流？」
> 答案：**有，而且是分层的**。但比"装什么工具"更重要的是——
> 这轮一查发现两件改变后续路线的事（见 §0.2、§0.3）。

---

## 0. 结论先行

### 0.1 有标准流水线，我们只用了两层的边角

业界的事实标准是 **L0–L7 八层**，不是一个工具：

| 层 | 干什么 | 本项目的现状 |
|---|---|---|
| L0 | 元信息、字符串、段统计 | 手搓（readelf/strings） |
| **L1** | 反汇编 + **反编译** | **只有 objdump/capstone，没有反编译器** ← 最大缺口 |
| **L2** | 类型/类/符号恢复 | 手搓了 RTTI 解析（161 类），**没有权威实现对照** |
| L3 | 动态插桩/追踪 | 裸 gdb（attach 后手打命令） |
| L4 | 仿真/指令级 | 无 |
| L5 | 符号执行/约束求解 | 无 |
| L6 | 差分/模糊测试 | **有，且是全项目最有效的**（`backtest_cost_model.py`） |
| L7 | 硬件寄存器级 | `debugfs` 只读过，没做寄存器流 |

**缺口集中在 L1/L2/L4**：能看汇编，但看不到「C 语言层面的意图」；能抠出类名，但没有第二个人来核对。

### 0.2 ★ 板子的内核驱动根本不是黑盒

之前一直在逆向**用户态** `librknnrt.so`，默认把内核里那一层当黑箱。实测：

```
$ grep -c ' rknpu' /proc/kallsyms
85
```

**85 个 `rknpu_*` 符号全部可见**，包括：

```
rknpu_submit_ioctl          rknpu_job_schedule        rknpu_job_subcore_commit
rknpu_core0_irq_handler     rknpu_core1_irq_handler   rknpu_core2_irq_handler
rknpu_get_task_number       rknpu_job_next.part.0     rknpu_power_on / _off
rknpu_iommu_dma_map_sg      rknpu_iommu_switch_domain rknpu_gem_mmap_obj
rknpu_debugfs_open          rknpu_get_bw_priority     rknpu_clear_rw_amount
```

且内核配置：

```
CONFIG_FUNCTION_TRACER=y   CONFIG_DYNAMIC_FTRACE=y   CONFIG_UPROBES=y
CONFIG_KPROBES         未设置   ← 唯一缺的那块
CONFIG_DEBUG_INFO_BTF  未设置   ← 没有免费的内核类型信息
```

⇒ **`ftrace` 的 function_graph 模式完全可用**，可以对 85 个驱动函数抓「调用树 + 每段耗时」。
`kprobes` 没开不影响这件事 —— function tracer 走的是编译期插桩，不需要 kprobes。

**这条路径本项目一次都没走过。** 它对「运行侧段边界规则」「`f08/f0c/f18` 字段语义」「submit→irq 的真实路径」这几个未解项是直接打击。

### 0.3 ★ runtime 里躺着 8 套「寄存器任务」实现

用新写的独立工具（§4.3）扫 `librknnrt.so`，37 个类，其中这一组是首次看到：

```
RKNNRegisterTask        RKNNRegisterTask_lite   RKNNRegisterTask_v2
RKNNRegisterTask_t3     RKNNRegisterTask_t4     RKNNRegisterTask_f2
RKNNRegisterTask_w1     RKNNRegisterTask_w2
RKNPUEmitter{V2, Lite, T4, F2}
```

⇒ **运行库不是针对一块 NPU 写的，而是按 NPU IP 版本分派**（8 个 task 变体 × 4 个 emitter）。
这直接解释了为什么 `librknnrt` 里同一段逻辑有多份相似代码，也解释了 `DPU(4097).16416`
这种"看不懂的寄存器编号"——它们大概率是**按 IP 版本分支的**。

对「私有化驱动构建」这条主线，**这张分派表是最该先读的东西**：它等于官方给出的
"这块芯片该走哪套寄存器写入流程"的索引。

## 1. 八层工具流：每层到底解决什么

### L0 元信息
`file` / `readelf` / `strings` / `checksec` / `ent`
→ 只回答"这是什么"。价值低，但没有它会误判（比如把 aarch64 当 x86 反汇编）。

### L1 静态反汇编与反编译
| 工具 | 状态 | 说明 |
|---|---|---|
| **Ghidra** | 免费，**必选** | 唯一同时满足：免费 + AARCH64 完备 + headless 可脚本化 + 自带 RTTI 类恢复脚本 |
| IDA Pro | 付费 | 反编译质量最好，成本不可接受 |
| Binary Ninja | 付费 | API 最好用，同上 |
| rizin / radare2 | 免费 | 轻量，xref/函数边界快；反编译靠 rz-ghidra 插件 |
| RetDec / Snowman | 免费 | 学术向，做**第二意见**（两个反编译器同时错同一处的概率低） |

> **本项目的具体收益**：67 个 pass 目前只有"地址 + 虚函数表"层面的认识，
> 反编译后能直接看到 `run()` 里的判定顺序，也就是 tiling 规则的**代码本身**。

### L2 类型与符号恢复
- **RTTI 脚本**：Ghidra 自带 `RecoverClassesFromRTTIScript.java`（GCC Itanium ABI），
  输出类名、父类、虚函数表、交叉引用。
- **BSim / FLIRT / FunctionID**：按函数指纹识别库函数（能认出 `memcpy` 的内联展开）。
- **DWARF / BTF / pahole**：有调试信息时的免费午餐。**本机两个都没有**。
  - `librknnrt.so` 的 **build-id** = `9b92e50f0c883beaeb178d27d14c6c2c4500fb09`。
    注意：**没有 `.gnu_debuglink` 段**（Ghidra 报的 "DWARF external debug information
    found" 指的就是 build-id，不是 debuglink，别被它误导）。
    build-id 是符号文件的**匹配键** —— 若 SDK 里能找到对应 `.debug` 文件，
    `eu-unstrip` / `debuginfod` 能直接对上；找不到就说明 Rockchip 没发布。
- **`c++filt`**：所有 mangled 名的权威解码器，别自己写（我写过，模板就翻车）。

### L3 动态插桩与追踪
| 手段 | 板端可用性 | 用途 |
|---|---|---|
| **ftrace function_graph** | ✅ | 内核函数调用树 + 耗时。**本项目最大遗漏** |
| **uprobes** | ✅ | 用户态函数级追踪，不需要重编译 |
| gdb + gdbserver | ✗ 未装 | 需要现场时用 |
| Frida | 装不上 | aarch64 支持好，能 hook 任意地址，比 gdb 轻 |
| rr（录制-重放） | ✗ | 一次推理录下来，之后可倒退。aarch64 支持有限 |
| eBPF/bpftrace | 价值有限 | 没有 kprobes，只剩 uprobes 一种用法 |

### L4 仿真与指令级
- **Unicorn**（已装）：CPU 指令仿真库。
  → 若能把 NPU 指令流逆到「编码 + 语义」，就能用 Unicorn 之外的方式写解释器并**回归验证**。
- **Qiling**：Unicorn + QEMU 的全系统仿真，能跑 aarch64 用户态而不碰板子。
- **QEMU TCG plugin**：不改 guest 就能对每条指令插桩（做 ISA 逆向时非常有用）。
- gem5：cycle 级，对本项目过重。

### L5 符号执行
angr / Triton / Miasm / z3。**本机一个都没装**，而且不建议优先装：

- 真实目标是 5 MB 的 C++ 二进制 + 模板 + 间接调用，符号执行的路径爆炸不可控。
- 唯一可能有效的用法很窄：**反推某个分支的判定常量**（"要让 `can_fuse` 返回 true，
  `group` 必须是什么"）。这用 Triton 的单路径 concolic 就够，不需要 angr 全家桶。

### L6 差分与模糊测试
**这是本项目唯一的成功经验**：`docs/140` 的同构链差分（N=1..8 拟合边际成本 + 固定开销）
就是标准的差分测试。AFL++/honggfuzz 在本项目用途有限（输入是模型文件，不是攻击面）。

### L7 硬件寄存器级
`devmem` / `/dev/mem` / `regmap` debugfs / ftrace on `regmap_*`。
板端 `debugfs` 要 root，`regmap` 目录也没暴露。**这条路要么补 root，要么放弃。**

## 4. 已经落地的东西

### 4.1 Ghidra 11.4.2 headless（无 root、GitHub 直连不通）

```bash
# 1) GitHub release 被墙 → 用 gh-proxy 镜像（实测 ~500 KB/s）
curl -L -o ghidra.zip \
  https://gh-proxy.com/https://github.com/NationalSecurityAgency/ghidra/releases/download/\
Ghidra_11.4.2_build/ghidra_11.4.2_PUBLIC_20250826.zip

# 2) 解压（本机没有 unzip，用 python zipfile 更省事）
python3 -c "import zipfile; zipfile.ZipFile('ghidra.zip').extractall('.')"

# 3) ★ 坑一：zipfile 解压丢可执行位，原生组件会 Permission denied
find . -path "*/os/linux_x86_64/*" -type f -exec chmod +x {} \;
chmod +x support/analyzeHeadless support/*.sh

# 4) ★ 坑二：Ghidra 要 JDK 不是 JRE。本机只有 JRE →
#    用 apt-get download 拉 jdk-headless 并覆盖合并（见 4.2）
export JAVA_HOME=~/rknn-work/tools/jdk21

# 5) 跑（aarch64 ELF 直接 import，自带 RTTI 恢复脚本）
./support/analyzeHeadless <projdir> <proj> -import librknnrt.so \
  -scriptPath Ghidra/Features/Decompiler/ghidra_scripts \
  -postScript RecoverClassesFromRTTIScript.java
```

### 4.2 无 root 装包（本项目第二次用这招）

```bash
apt-get download binutils-aarch64-linux-gnu gdb-multiarch libbabeltrace1 ...
for d in *.deb; do dpkg-deb -x "$d" root/; done
```

- `gdb-multiarch` 可用（缺 libbabeltrace/libipt/libsource-highlight/libdebuginfod，
  补齐后 `ldd` 零缺失）。

### 4.3 `src/tools/re_stack.py`

```bash
python3 src/tools/re_stack.py capability --board   # 能力矩阵（本机+板端）
python3 src/tools/re_stack.py route 成本           # 问题→工具链路由
python3 src/tools/re_stack.py elf <bin>            # LIEF 重述 ELF 事实
python3 src/tools/re_stack.py vtables <bin>        # RTTI→vtable→虚函数（独立算法）
python3 src/tools/re_stack.py ghidra               # Ghidra 安装状态
```

`vtables` 的算法和项目里的 `rtti_find.py` **刻意不同**：

- `rtti_find.py`：靠**硬编码的段偏移**（按架构写死），快但脆（踩过）
- `vtables`：**两跳指针搜索** —— 名字串 → typeinfo 对象 → vtable 槽，
  不假设任何段布局；用 LIEF 而非 pyelftools 解析。

结果（`librknnrt.so`，0.4 秒）：

```
候选 mangled 名 116 个 → 解析出 vtable 的类 37 个
   256+  RKNNRegisterTask / _lite / _v2 / _t3 / _t4 / _f2 / _w1 / _w2
     4   RKNPUEmitterV2 / Lite / T4 / F2
     3   RKNNTensor, RKNNJob, RKNNJobV2
     2   RKNNTarget, RKNNTargetLite
   ...  (nlohmann/jsonxx 的适配器与异常类若干)
```

## 5. 踩到的坑（可复用）

1. **`zipfile.extractall` 不保留权限位** → 所有原生组件 `Permission denied (13)`。
   Ghidra 报的错是 `Unable to create decompiler` / `GNU Demangler executable may not be
   compatible with your system`，**看起来像架构不兼容，其实是没加 x**。
2. **Ghidra 需要 JDK**（要 `javac` 存在）。只装 JRE 时它说
   `unsupported java version`，非常误导。
3. **`.rela.dyn` 的 addend 和指针长得一模一样**。第一版扫描把每条重定位都当成
   vtable 槽（45 个"槽"→ 0 个类）。必须把索引限制在 `.data.rel.ro/.data/.got`。
4. **"连续代码指针"不能当作 vtable 长度**。`0x6c86b8` 那个 typeinfo 槽后面跟着
   **2905 个连续代码指针**才遇到非代码值 —— 那不是 2905 个虚函数，那是紧邻的
   一张大分派表。**工具的前提假设必须单独验证**，这正是教训 5 的又一次复现。
5. **SSH 到板子约三成概率卡在 kex**（`expecting SSH2_MSG_KEX_ECDH_REPLY`）。
   重试 + `-o IPQoS=none` 可解；脚本里必须写重试，否则会误判"板端不可达"。

## 6. 不建议做的

| 方向 | 理由 |
|---|---|
| angr 全量符号执行 | 5 MB C++ + 模板 + 间接调用，路径爆炸；只有"反推单个分支常量"值一点，用 Triton 就够 |
| IDA Pro / Binary Ninja | 成本换来的增量（相对 Ghidra）不足以覆盖本项目需求 |
| rr 录制重放 | aarch64 支持有限，且板端 perf 权限不够 |
| syzkaller | 驱动是 Rockchip 闭源二进制 + 我们有 UAPI 头文件，不需要盲 fuzz |
| 自己写 mangled name 解码器 | `c++filt` 就在那儿；我写过，模板一进来就翻车 |

1. **`ftrace function_graph` 抓驱动**（半天，投入最低、信息量最高）
   - 覆盖 `rknpu_submit_ioctl` → `rknpu_job_schedule` → `rknpu_job_subcore_commit` → `*_irq_handler`
