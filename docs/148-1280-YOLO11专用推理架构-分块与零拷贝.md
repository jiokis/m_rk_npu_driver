# docs/148 — 1280 YOLO11 的专用推理架构：2×2 分块 + 零拷贝宿主侧

> 用户要求「针对 1280 YOLO11 开发一个专门的加速推理架构」。
> 这份不是拍脑袋的方案，每一条都对着实测数据。

---

## 0. 结论

| 架构 | 中位延迟 | FPS | p90 | 寄存器溢出 |
|---|---|---|---|---|
| 原生 1280 模型 | 159.69 ms | 6.3 | 164.36 ms | **30 次** |
| **2×2 分块（640 模型）** | **137.15 ms** | **7.3** | **152.43 ms** | **0 次** |

**分块快 14%，尾延迟更稳，而且完全避开 13 位字段溢出。**
只需要**一个 640 模型**，不需要单独的 1280 模型（省一半内存）。

⚠️ 但真正的收益不在"分块"本身，而在**宿主侧必须零拷贝**：
朴素写法分块要 **277 ms**（比原生还慢），优化后 **137 ms**。差的那 140 ms
全在 Python/CV 的临时拷贝上。

## 1. 证据链

### 1.1 同进程 A/B：分块在推理层面就更快

```
640  ×1  :  30.29 ms
1280 ×1  : 152.56 ms      (比值 5.04×)
4×640    : 121.16 ms      = 1280 的 0.79×   ⇒ 省 20.6%
```

同一进程、同一 core_mask(7)、同样预热 —— 排除跨进程差异。

### 1.2 ftrace：提交次数和核利用率与分辨率无关

| | 640 | 1280 |
|---|---|---|
| 每次推理提交数 | ~99 | ~94 |
| 单核提交占比 | 56.6% | 56.4% |
| 三核提交占比 | 43.4% | 43.6% |
| **每提交耗时** | 0.28 ms | **1.56 ms** |

⇒ 超线性**不是**「切得更碎」或「核没吃满」造成的，是每次提交干的活变贵了。

### 1.3 IR 表：算力和带宽都不是瓶颈

| | NPU cycles | DDR cycles | DDR/NPU |
|---|---|---|---|
| 640 | 5,518,400 | 1,882,591 | 0.341 |
| 1280 | 22,073,600 | 7,190,316 | 0.326 |

- cycle 数比值 **正好 4.00×**，DDR/NPU 比**几乎不变**
- 但实测墙钟是 **5.04×** ⇒ 多出的 1.04× **编译器模型解释不了**
- 1280 的 93.8% 是 `ConvExSwish`；热点是 head `model.23`(26.6%)、stem `model.0`(16.7%)、`model.2`(13.9%)

### 1.4 ★ 寄存器 13 位字段溢出：640 干净，960/1280 都撞

| 分辨率 | `REGTASK ... exceeds the limit` 次数 |
|---|---|
| **640** | **0** |
| 960 | 18 |
| 1280 | 30 |

报错内容：`offset 0x4038 / 0x5048, limit 0x1fff(8191), value 0x7fc0(32704)`
按 `docs/146` 的 `reg>>12 == stage+1`，这两个是 **stage3(DPU)** 和 **stage4(DPU_RDMA)** 的窗口。

⇒ **全 640 的分块方案天然不碰这条暗雷**，这是选它而不选「原生 1280 + 调优」的硬理由。

## 2. 宿主侧的三处浪费（这是本架构的关键）

在板上逐项量出来的：

| 操作 | 朴素写法 | 优化写法 | 单次成本 |
|---|---|---|---|
| tile 切分 | `img[y0:y1, x0:x1]` 直接喂给 resize（隐式拷贝） | 预先 `np.ascontiguousarray` 一次 | 0.98 → **0.12 ms** |
| letterbox | 640→640 仍走 resize + 新建画布 | tile 本就是 640 ⇒ **直接零拷贝喂 `tile[None]`** | 0.22 → **0 ms** |
| decode | `squeeze().T` 再 `p[:,4:].max(1)`（转置后跨步访问） | 直接在 `(84,N)` 上 `a[4:].max(0)` | 1.56 → **1.20 ms** |

单帧 4 tile 的宿主侧总开销：**~133 ms → ~5 ms**。

整机效果：

```
朴素流水线   tile 277.39 ms  /  native 183.38 ms
优化后       tile 137.15 ms  /  native 159.69 ms
```

> 注：`native` 也受益（183 → 160 ms），说明这套宿优化跟分块无关，是普遍该做的。

## 3. 实现

`deploy/bench/tiled_fast.py`，三个要点：

```python
# ① 切块一次，之后零成本复用（视频流里每帧一次，约 0.5 ms）
tiles, origins = split_tiles(img, 2)      # 每块 640×640，ascontiguousarray

# ② 640→640 不做任何 resize，直接喂
a = r640.inference(inputs=[tile[None]])[0][0]

# ③ decode 不转置：a 是 (84, N) 连续布局
sc = a[4:].max(0)                 # 类别分数
idx = np.flatnonzero(sc > 0.25)
b = a[:4, idx].T                  # xywh
```

坐标回映：tile 内的框加 `(x0, y0)` 偏移，再跨 tile 做一次 NMS。

## 4. 边界与未验证（必须说清楚）

| 项 | 状态 |
|---|---|
| **检出质量** | **完全没验证**。手里的 rknn 是用**随机噪声**标定的（`docs/147`），检出恒为 0。本架构只证明了**速度**。 |
| 边界目标 | 2×2 无重叠会在 tile 接缝处切断目标。要保质量得加 10~15% 重叠 → 变 4 个大 tile，每块要缩放，反而更慢。**没测**。 |
| 精度对齐 | 分块的 NMS 是跨 tile 后做的，理论上等价于全图 NMS；但小目标在 tile 里分辨率更高，检出分布会**和原生 1280 不同**。未对比 mAP。 |
| 更大分辨率 (1920/4K) | 按同样思路可以 3×3=9 块，但宿主侧开销线性增长，需重新测。未做。 |
