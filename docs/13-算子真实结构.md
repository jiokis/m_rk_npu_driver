## 一、此前的理解是错的

一直以来的模型是：

```
一个 task  ↔  一个算子        ← 错
```

于是我以为 op1 只有几十条指令。**实际完全不是这样。**

## 二、真实结构：算子 = 一条 task 链

`regcfg_amount` 是**本 task 槽位内的指令条数**（已证），而槽位内**最后一条**是 PC 链指令
（`block 0x0101 / reg 0x0010`）：

| 链的值 | 含义 |
|---|---|
| `0x0` | **链结束** —— 这个算子到此为止 |
| 下一个地址 | 该 task 与下一个 task **属于同一个算子** |

验证（在全部样本上）：

```
✅ 链目标 == 下一个 task 的起始地址 : 231 条
   链目标 == 0（链结束）            : 380 条
```

所以硬件的执行方式是：**从第一个 task 的地址出发，顺着 PC 链一直走到链值为 0**。
`PC_TASK_CONTROL` 里的 task_number 告诉它最多走多少步。

### 槽位大小随算子变化

前 40 个 task 的地址步长有四种：`0xc0`(24条) / `0x100`(32条) / `0x240`(72条) / `0x440`(136条)，
而对应的 `regcfg_amount` 是 18/20/23/24/61/64/126 —— **都 ≤ 槽位容量**，
再次印证它是指令条数、槽位按需分配。

## 四、一个完整算子的样子（op1，前 57 条）

```
  [  0] CNA     0x1040 0x0000001b
  [  1] CNA     0x1104 0x00000000
  [  2] CNA     0x1100 0x00000000
  [  3] CNA     0x100c 0x6000a000
  [  4] DPU     0x4004 0x0000000e
  [  5] DPU_RD  0x5004 0x0000000e
  [  6] CNA     0x100c 0x6000a000
  [  7] CNA     0x1010 0x00000220
  [  8] CNA     0x1014 0x00000012
  [  9] CNA     0x1020 0x02800022
  ...
  [ 26] CNA     0x1070 0xfef77000     ← 张量地址（输入/特征）
  [ 35] CNA     0x1110 0xff811280     ← 张量地址（权重）
  ...
  [ 52] CNA     0x1180 0x00000fff
  [ 53] CNA     0x1184 0xffffff80
  [ 54] CORE    0x3010 0x00000001
  [ 55] CORE    0x3014 0x0010013f
  [ 56] CORE    0x3018 0x0000001f
```

可以看出的东西：
- **前半段是 CNA 的配置**（寄存器 `0x100c`–`0x1184`），地址寄存器 `0x1070`/`0x1110` 在其中
- **中间切到 CORE 块**（`0x3010`–`0x3018`）—— 一个算子的配置**跨多个 block**
- 值 `0x00000fff` / `0x0010013f` 这种带明显位域的形态，是形状/尺寸字段
- `0xffffff80` 是**符号扩展的小负数**（-128），不是地址

## 五、这对"自己造算子配置"意味着什么

| 影响 | 说明 |
|---|---|
| **规模预期要修正** | 一个算子的配置是**上千条指令**，不是几十条。手写不现实，必须**用模板 + 变量替换** |
| **模板复用更可行** | 24 个 task 里绝大部分是重复的规格（不同空间位置/通道切片），**模板化收益极大** |
| **多段拼接是硬需求** | 生成配置时必须会**构造 PC 链**，否则硬件走不完 |
| **分组本身就是算子信息** | 链的长度/组成 = 算子的类型特征，是分类的好特征 |
