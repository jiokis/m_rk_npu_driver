# docs/147 — YOLO11n 适配 1280 输入：权重来源、转换、实测速度

> 承接 `docs/146` 之后的一个实际问题：**图片更大时 NPU 有多快**。
> 之前的结论是「YOLOv5s 是静态 640，大图只影响 CPU 解码」，
> 这次真的把模型做到 1280 输入来测。

---

## 0. 结论

| 模型 | 输入 | 中位延迟 | FPS | 相对 |
|---|---|---|---|---|
| YOLOv5s | 640 | **21.76 ms** | 46.0 | — |
| YOLO11n | 640 | **27.28 ms** | 36.7 | — |
| **YOLO11n** | **1280** | **146.7 ~ 150.4 ms** | **6.6 ~ 6.8** | **5.4×** |

- 1280 的像素是 640 的 **4×**，耗时是 **5.4×** ⇒ **超线性**，不是简单按面积翻倍。
- 我事前按 MAC 量线性外推的估算是 85~90 ms，**实测 147 ms，比估算差 1.7×**。
  ⇒ 又一次印证：**别用线性外推预测 NPU 延迟**（`docs/142` 教训 6）。

## 3. 导出 ONNX（1280）

```python
from ultralytics import YOLO
YOLO("yolo11n.pt").export(format="onnx", imgsz=1280, opset=12,
                          simplify=False, dynamic=False)
```

- **opset 必须 12 左右**，默认的新版本 RKNN 吃不消
- `dynamic=False`：RKNN 要静态形状
- 导出结果：`input [1,3,1280,1280]`、`output [1,84,33600]`
  （33600 = 160² + 80² + 40²，三尺度 stride 8/16/32 ✓）

## 4. ★ 转换时的告警：寄存器字段位宽溢出

`rknn.build()` 报了这些：

```
E REGTASK: The bit width of field value exceeds the limit, target: v2,
           offset: 0x4038, shift = 0,  limit: 0x1fff, value: 0x7fc0
E REGTASK: ...            offset: 0x5048, shift = 19, limit: 0x1fff, value: 0x7fc0
E Unkown op target: 0
```

- `0x1fff = 8191` 是**13 位字段上限**，`0x7fc0 = 32704` 越界
- 出现位置：`0x4038`（DPU 窗口）、`0x5048`（DPU_RDMA 窗口）
- 对照 `docs/146`：`reg>>12 == stage+1`，所以 `0x4038` 属 stage 3（DPU）、`0x5048` 属 stage 4（DPU_RDMA）

**但模型仍然转成功、板上也能跑、输出形状正确。**
⇒ 这说明该字段是「某个按 tile 计算的量」，1280 下超出了编码范围。
**后果未知**：可能被截断导致结果错，也可能该字段只是上界提示。

⚠️ **这条必须记着**：1280 输入在编译器层面已经碰到了寄存器编码边界，
不是「换个尺寸重导一下」这么轻松。

## 5. 板上实测

```bash
# 1280
python3 bench_y11.py yolo11n_1280.rknn 1280
#   首次推理输出: [(1, 84, 33600)]
#   中位 146.70 ms  min 127.02  p90 243.10  FPS 6.8

# 640（同架构对照）
python3 bench_y11.py yolo11n_640.rknn 640
#   首次推理输出: [(1, 84, 8400)]
#   中位 27.28 ms  min 25.46  p90 32.26  FPS 36.7
```

测试条件：3 核、NPU 1.0 GHz、温度 35 ℃、空闲负载。
1280 两次独立测量 150.4 / 146.7 ms，一致。

### p90 偏高的现象

1280 的中位数 147 ms，但 p90 到 **243 ms**（min 127）。抖动接近 2 倍。
640 的抖动小得多（27 → p90 32）。推测是 1280 下 tile 数多、访存压力大，
更容易被后台任务/热降频影响。**做实时应用时 1280 的尾延迟要按 250 ms 规划。**

## 6. ★ 这次产出的模型只能测速，不能直接用

标定集用的是**随机噪声图**（本机没有 COCO/真实数据集，GitHub 也不通）。
对量化来说这是分布错误的输入 ⇒ **INT8 精度不可信**。

要得到可用的 1280 模型，必须：

1. 准备 50~100 张**真实场景图**（最好和实际业务分布一致）
2. 用它们做 `dataset.txt` 重新 `build(do_quantization=True, ...)`
3. 用 `yolo val` 对 ONNX 版先确认 FP32 精度，再对比 RKNN 版的 mAP

现成的 22 张本地图（`dsvideo/models/*.jpg`）偏人物姿态，最多算「聊胜于无」。

## 8. 对「大图」场景的建议

按 `docs/147` 与上一轮的解码实测（4K 源图解码要 **286 ms**）：

- **不要**为了「看得清」把检测输入拉到 1280：延迟 5.4×，而 4K 图的解码本身才是 286 ms 的大头
- 正确做法是**降采样解码**（`cv2.IMREAD_REDUCED_COLOR_4`）+ 640 输入 —— 解码从 286 ms 降到几十毫秒
- 只有「小目标必须靠高分辨率」时才上 1280，且要接受 6.8 FPS
