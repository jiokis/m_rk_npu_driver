## 二、性能总表

### 2.1 最终配置

```
1280 输入 → 2×2 切 4 块 640 → 6 worker（每人独立 rknn 上下文，按 i%3 绑核）
          → 640 双输出 INT8 → 候选 DFL（CPU）→ 坐标回映 → 跨 tile NMS
```

| 指标 | 值 | 置信度 |
|---|---|---|
| **吞吐** | **32.06 FPS**（19 分钟均值） | 高（58 个采样点，波动 <2%） |
| 单帧平均耗时 | 31.2 ms | 高 |
| 单帧原始框 | 116.7 个 | 高 |
| 单帧 NMS 后 | 16.7 个 | 中（与 FP32 差 ±1~2/帧） |
| NMS 耗时 | 0.03 ms/帧 | 高 |
| 进程 RSS | **252 MB** | 高 |
| 线程数 | 7（6 worker + 主） | 高 |
| CPU 占用 | **170%**（约 1.7 核） | 高 |
| 峰值温度 | **49.9°C** | 高 |
| NPU 频率 | 恒 1.000 GHz | 高 |

### 2.2 优化路径（每一步都是实测）

| 阶段 | ms/帧 | FPS | 相对上一阶段 |
|---|---|---|---|
| ① 1280 native 模型，单实例绑 3 核 | 153.8 | 6.50 | — |
| ② 改 2×2 分块（4×640），串行 | 123.7 | 8.08 | +24% |
| ③ 3 实例各绑一核并发 | 50.7 | 19.72 | +144% |
| ④ worker 超订到 6（纯推理，C） | 37.4 | 26.6 | +35% |
| ⑤ 完整链路（含 DFL+NMS），Python | 69.1 | 14.27 | −46% |
| **⑥ 完整链路，C 实现** | **31.2** | **32.06** | **+125%** |

**累计：6.50 → 32.06 = 4.93×**

> ⑤ 是插入点：Python 版把 ④ 的收益吃掉近一半，所以必须 ⑥。

### 2.3 其它参照点

| 配置 | 吞吐 |
|---|---|
| 640 单帧（C，1 核） | 35.9 FPS（27.8 ms） |
| 640 视频流（3 实例并发） | 85 FPS |
| 1280 native（单实例 3 核） | 6.50 FPS |

## 四、正确性评估（只到一致性，不含 mAP）

### 4.1 前提：修复了 INT8 把分类分数打成零的 bug

Ultralytics 导出的 ONNX 最后 `Concat` 把框(0~640)与分数(0~1)合并成**同一个输出张量**，
INT8 只给一个 scale ⇒ 分数全部量化成 0。修复方式：在 `Concat` 前切开，输出两个张量。
详见 `docs/152`。

| 模型 | 分数 max | 非零数 |
|---|---|---|
| FP16 | 0.9268 | 10331 |
| INT8 单输出（坏） | **0.0000** | **0** |
| INT8 双输出（修复） | 0.8920 | 1060 |

### 4.2 与 FP32 的一致性

| 指标 | 值 |
|---|---|
| box 通道 cosine | **0.9991** |
| cls 通道 cosine | 0.9880（min 0.568，有 1 张异常） |
| 原始框数 | 与 FP32 吻合（例：63 vs 66、31 vs 32） |
| **NMS 后逐帧**（8 帧） | C **38** vs ONNX-FP32 **37**，逐帧差 ±1~2 |

### 4.3 NMS 实现验证

120 个合成框，三种实现结果**完全一致**（保留 35 个，集合相同）：
torchvision / OpenCV `dnn.NMSBoxes` / 我们的贪心。

> 过程中发现一个坑并已修正：模型输出是 `(cx,cy,w,h)`，Python 侧曾误当 `(x1,y1,x2,y2)`。
> 详见 `docs/156`。

### 4.4 ⚠️ 未做 mAP

**这是本报告最大的缺口。** 目前所有"一致"都是相对 FP32 的一致性，
**不是绝对精度**。要给出可用性结论必须补 mAP（COCO val 或业务自有数据）。

## 五、瓶颈分析

### 5.1 NPU 侧：并行度受限于提交粒度

ftrace 实测（`docs/144`）：

- 单次推理 **99 次 `submit_ioctl`**
- **56% 的提交只用 1 个核**（任务数凑不满 3 的倍数就整组降级）
- 单实例绑 3 核与绑 1 核耗时几乎相同（28.49 vs 27.80 ms）

⇒ **单个推理吃不掉三个核**，这是所有优化必须绕开的根本约束。

### 5.2 CPU 侧：提交路径会饱和

3 个 worker 时只有 19.7 FPS，加到 **6 个** 才 26.6+ FPS。

原因：3 路并发时每秒约 1 万次 ioctl，**内核提交路径先饱和，NPU 在等**。
反证：把输入写入方式从 memcpy 换成 `rknn_inputs_set` 无差别（19.94 vs 20.41），
说明瓶颈不在数据拷贝。

### 5.3 Python 封装：每次调用约 +10 ms

| 实现 | 每 tile 推理 |
|---|---|
| C | ~28.5 ms |
| Python（单 worker） | **38.18 ms** |
| Python（6 worker） | **59.08 ms**（GIL + 锁争用） |

⇒ 最终实现必须是 C。

## 六、结论与建议

### 6.1 可以确认的

1. **1280 输入在 RK3588 上能跑到 32 FPS**，且 19 分钟压测无降频，温度余量 30°C
2. **相比直接用 1280 模型（6.50 FPS）提升 4.93×**
3. 资源占用温和：252 MB 内存、1.7 核 CPU、6 个 worker 线程
4. NMS 与 DFL 的解码正确性已与权威实现对齐

### 6.2 上生产前必须补的

| 优先级 | 项 | 理由 |
|---|---|---|
| **P0** | **mAP（COCO 或业务数据）** | 没有绝对精度就无法判断是否可用 |
| **P1** | tile 接缝处的边界目标评估 | 2×2 无重叠会切断跨接缝目标 |
| **P2** | 更长时间（≥1 小时）+ 高温环境 | 当前只测了 19 分钟、室温环境 |
| **P3** | 端到端含视频解码的吞吐 | 当前输入是预先解好的帧；4K 解码本身要 286 ms（`docs/147`） |

### 6.3 如果还要更快

已经到"多核天花板"：单 tile 约 23 ms × 4 tile ÷ 3 核 ≈ 31 ms/帧。
再快只有两条路：

1. **降低单 tile 耗时**（改模型/量化/算子调优），不能靠加并发
2. **减少每帧 tile 数**（如只检测上半部分），属于业务取舍
