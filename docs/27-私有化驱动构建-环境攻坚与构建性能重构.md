# 27 · 私有化驱动构建：环境攻坚 + 构建性能重构

> 承接 docs/26（私有化驱动构建方案）。本篇记录**实际动手构建时**踩到的环境问题、
> 对构建机的性能剖析结论，以及据此重构出的构建/部署链路。
>
> 状态：内核构建中（`6.1.99-rockchip-rk3588-priv1`），产物尚未上板。

---

## 1. 构建机是什么——先认清机器，再谈优化

之前一直假设这是一台普通笔记本。实测发现它是一台**虚拟机**：

| 项目 | 实测值 | 影响 |
|---|---|---|
| CPU | AMD Ryzen 9 8945H，8 物理核 / 16 vCPU（SMT） | 并发上限 16 |
| cpufreq | **`/sys/devices/system/cpu/cpu*/cpufreq/` 完全不存在** | 虚拟机不暴露调频；无法钉频，也无法靠 governor 加速 |
| 内存 | 7582 MB + 2048 MB swap | |
| 磁盘 | `/dev/sdd`，`lsblk -o ROTA` = **1**（机械盘虚拟盘） | 随机小文件写入慢 |
| 温度 | `sensors` 无输出 | 虚拟机不透传 |

这条直接推翻了「靠调 governor / 钉频来提速」的思路——**没有可调的东西**。

## 2. 免 root 补齐主机工具链（flex / bison / m4 / mkimage / dtc）

内核构建需要一堆主机工具，而这台机器上 **`flex`、`bison`、`m4`、`mkimage`、`dtc` 全都没有**，
`sudo` 又要密码（本会话审批关闭，`apt install` 不可用）。

解法：`apt-get download` 普通用户就能用，`dpkg-deb -x` 可以把 deb 解到任意目录。

```bash
mkdir -p ~/.local/kbtools/debs && cd ~/.local/kbtools/debs
apt-get download flex bison m4 libsigsegv2 u-boot-tools device-tree-compiler
mkdir -p ~/.local/kbtools/root
for d in ~/.local/kbtools/debs/*.deb; do dpkg-deb -x "$d" ~/.local/kbtools/root/; done
```

**两个必须知道的坑**（否则解出来也用不了）：

1. **bison 找不到 m4**：Debian 把 m4 路径编译成写死的 `/usr/bin/m4`，而我们解到了 `~/.local`。
   症状是 `bison: m4 subprocess failed: No such file or directory`。
   用环境变量覆盖：`export M4=~/.local/kbtools/root/usr/bin/m4`
2. **bison 找不到 skeleton**：skeleton 在 `/usr/share/bison`。
   覆盖：`export BISON_PKGDATADIR=~/.local/kbtools/root/usr/share/bison`

flex 反而不需要覆盖（skeleton 编译进二进制了）。这些都固化在
`scripts/build/host-tools-env.sh` 里，任何构建脚本 `source` 它即可。

验证：`flex 2.6.4` + `bison 3.8.2` + `m4 1.4.19` + `mkimage 2025.10` + `dtc 1.7.0`，
`make olddefconfig` 一次通过——**bison 3.8.2 与 6.1 内核的 kconfig 没有不兼容问题**。

> 附带收获：`mkimage` 本来只是为了让 dtb overlay 的 `fixup.scr` 能编出来，
> 而它正好也是后面做**双启动 `boot.scr`** 和**打包 `uInitrd`** 的必需工具。
> 我们还额外下了一份 **arm64** 的 `u-boot-tools` deb，作为板子离线时的兜底。

### 构建依赖预检结论（省掉了很多白等）

读板子原厂 `.config` 逐项确认，以下**都不需要**：

| 潜在依赖 | 结论 | 原因 |
|---|---|---|
| `pahole` | 不需要 | `CONFIG_DEBUG_INFO_BTF` 根本没开 |
| `libssl` / `openssl` 开发头 | 不需要 | `CONFIG_MODULE_SIG` 未开，不签名模块 |
| `objtool` / `libelf` | 不需要 | `CONFIG_OBJTOOL`、`CONFIG_STACK_VALIDATION` 均未开（那是 x86 的机制） |
| `cpio` | 不需要 | `CONFIG_INITRAMFS_SOURCE=""`，走内核自带的 `gen_init_cpio` |
| `lz4` / `lzo` | 不需要 | arm64 产出未压缩的 `Image`；且 `CONFIG_MODULE_COMPRESS_NONE=y` |

## 3. 性能剖析：真正的瓶颈不是内存，是「没人让路」

第一次用 `make -j14 Image dtbs modules` 直接把整机冻住，用户反馈「卡死了」。
按经验第一反应是内存打爆——**实测证明这个判断是错的**：

```
并发 gcc（-j8）：7 个 cc1，合计 RSS 369 MB，**均值只有 53 MB**
swap：138 MB，全程不增长
iowait：0.1%          ← 磁盘并没有在拖住 CPU
idle：49.1%
进程 %CPU 合计：约 1000%（可用 1600%）
```

- **内存从来不是瓶颈**：内核 .o 很小，8 个并发 gcc 才 400 MB 出头。
  真实内存消耗的是**链接 vmlinux 那一步**，而不是编译。
- **磁盘也不是 CPU 侧的瓶颈**：iowait 0.1%。
- 冻死的真正原因：**16 个线程被占满，且编译进程优先级与前台完全平等**，
  前台（桌面/我的 SSH/工具链调用）抢不到 CPU 时间片，表现就是「整机卡死」。

### 三重护栏

```bash
nice -n 15 ionice -c 3 make -j"$JOBS" LOCALVERSION="$LV" Image dtbs
```

1. `nice -n 15` —— 编译让出 CPU，前台永远是第一优先级
2. `ionice -c 3` —— 编译走 idle I/O 类，机械盘的带宽优先给前台
3. `-j8` —— 不发满 16 线程（实测 `-j8` 已能拿到 2.46 个 .o/秒）

效果（编译进行中实测）：**`bash -c true` 的启动延迟 0.02 s，机器完全可用。**

## 4. 最大的优化：砍掉 99.5% 的模块编译

翻板子原厂配置时发现一个决定性的事实——**所有启动关键驱动本来就全是 `=y`**：

```
MMC_DW_ROCKCHIP=y      MMC_SDHCI_OF_DWCMSHC=y   MMC_BLOCK=y    BLK_DEV_NVME=y
EXT4_FS=y              PCIE_ROCKCHIP_HOST=y     PCIE_DW_ROCKCHIP=y
PHY_ROCKCHIP_SNPS_PCIE3=y   PHY_ROCKCHIP_NANENG_COMBO_PHY=y
CFG80211=y             MAC80211=y               RFKILL=y       ← 连无线协议栈都是内置
```

整份配置里有 **792 个 `=m`**，而跟这块板子启动 + 联网真正相关的**只有 4 个**：

```
rtw89_core  rtw89_pci  rtw89_8852b  rtw89_8852be
```

依赖链是**平的**——`cfg80211/mac80211/rfkill` 全是 `=y`，这 4 个模块不依赖任何其他模块。

所以构建目标从

```bash
make -j14 Image dtbs modules      # 编 792 个用不上的模块
```

改成

```bash
make -j8 Image dtbs                                     # 全部内置代码
make -j8 M=drivers/net/wireless/realtek/rtw89 modules   # 只编那一个目录
```

**收益是双份的**：① 少编近一半工作量；② 顺带省掉
`modules_install` → `depmod` → 打 200 MB 模块包 → 传给板子 → 装 `/lib/modules` → 重建 initramfs
一整条链路，改为只搬 8 个 `.ko`。

> 注意：这是**构建范围**的优化，**没有改配置**。`.config` 相对原厂仍然只差 8 行
> （`DEBUG_INFO` 关闭 + pahole 版本号这类装饰项），`RTW89_8852BE` 依然是 `=m`。
> 保持配置忠实，插桩改动才是唯一的显式 diff。

### DEBUG_INFO 为什么关掉

本机 7.6 GB 内存，arm64 vmlinux 带 DWARF 链接要吃 4–8 GB，而我们要反复迭代插桩构建。
关闭后：**运行行为零差异**，`CONFIG_KALLSYMS=y` 保留，oops/panic 回溯照样有符号名。
原始配置完整保留在 `build/.config.vendor`（**从未被改动**），想还原只需删掉
`prepare-kernel.sh` 里的两行 `set_kv`。

## 5. LOCALVERSION：模块目录绝不重叠

厂商侧是 `LOCALVERSION=-${LINUXFAMILY}`，即 `-rockchip-rk3588`。
我们用 **`-rockchip-rk3588-priv1`**（保留家族名 + 私有后缀）：

- 新内核模块落在 `/lib/modules/6.1.99-rockchip-rk3588-priv1/`，**与现有目录物理隔离**
- 即使新内核完全起不来，旧内核 + 旧模块目录毫发无损，双启动回退随时可用
- 版本号来源已查清：源码树里没有 `localversion*` 文件，`EXTRAVERSION` 为空，
  `CONFIG_LOCALVERSION=""` —— 所以 `-rockchip-rk3588` 是 orangepi-build 在
  make 命令行上传的，不是配置里的

## 6. 部署设计：安装与切换分离

`/boot/boot.scr`（由 `boot.cmd` 编译）里**写死了三个固定名字**：`Image`、`dtb/${fdtfile}`、`uInitrd`。

因此双启动用**符号链接切换**实现，而不是改 U-Boot：

| 做法 | 是否采用 | 理由 |
|---|---|---|
| 改 `boot.cmd` 做启动菜单 | ✗ | 要碰 U-Boot，有刷砖风险，还得改 `boot.scr` |
| U-Boot `bootcount`/`altbootcmd` 自动回退 | 待评估 | 最稳，但依赖 U-Boot 编译选项，需上板查环境 |
| **改 `/boot/{Image,dtb,uInitrd}` 符号链接** | ✓ | U-Boot 环境一点不动；旧内核文件原封不动；SSH 一条命令切换 |

配套脚本：

- `scripts/board/install-kernel.sh` —— **只新增带版本号的文件**，
  绝不碰 `Image`/`dtb`/`uInitrd` 三个符号链接。装完做完整性自检并明确说「尚未切换」。
  → 「装到一半失败」永远不会让板子起不来。
- `scripts/board/kernel-select` —— 切换/回退。首次运行会记录原厂指向到
  `/boot/.kernel-orig.targets`，`kernel-select orig` 一键回退。
- `scripts/build/deploy-to-board.sh` —— 笔记本侧：传输 + 触发板子侧安装，
  `--switch` 可以顺带切换重启并等板子回来做自动验收。

回退路径（按可行性排序）：
1. 还能进系统 → `kernel-select orig && reboot`
2. 完全起不来 → 串口进 U-Boot，或重刷 boot 分区 / SD 卡（D 盘有完整镜像 + RKDevTool）

## 7. 板子第 5 次假死，与两味「料」

构建期间板子**第 5 次失联**，症状：

```
ping 192.168.31.128     → 100% packet loss
ip neigh                → MAC 在表里（cc:21:9d:b0:5d:a2），状态 DELAY
并发 ping 扫 192.168.31.0/24 → 只有 .1/.8/.74/.104/.223/.237，板子没换 IP
```

「链路层有影子、网络层全丢」= 典型的 **WiFi 关联着但流量不通**，而不是内核挂死
（内核挂死的话 ARP 也不会应答，而且之前有过自愈记录）。这次需要断电重启。

针对这个毛病准备了两味料，都写好了脚本，等板子回来就能装：

| 脚本 | 治什么 | 原理 |
|---|---|---|
| `scripts/board/setup-watchdog.sh` | **内核真挂住** | 不自己写喂狗程序，直接用 systemd 的 `RuntimeWatchdogSec=60`。由 PID 1 负责喂狗，没有「喂狗进程自己被饿死导致误重启」的风险。60 s 足够宽松不会误杀，又能在卡死后一分钟自愈 |
| `scripts/board/setup-net-watchdog.sh` | **内核活着但 WiFi 假死** | 网关连续 3 次探测失败 → 分级自愈：重启 NetworkManager → 重装 rtw89 模块（重置固件状态机）→ 网卡 down/up → 连续 15 分钟不可达则重启板子。有冷却时间，全程写 journald |
| `scripts/board/setup-network.sh` | 从源头减少假死 | 关掉 WiFi 省电（`wifi.powersave=2`）。RTL8852BE 的 PS-Poll 状态机是假死的头号嫌疑；同时把连接设为无限重试 + 高优先级自动连接、启用 SSH 开机自启、清掉 apt 里那个已经死掉的 Docker 代理 |

> 硬件看门狗只治「内核挂住」；假死那种「内核还活着」的情况它无能为力 —— 两个都要有。
> 另外硬件看门狗有个前提：`CONFIG_DW_WATCHDOG=y` 已在，但**现在没有任何人喂它**，
> 所以内核真挂住时板子只能等人工断电。这就是之前多次失联本可自愈却没自愈的原因。

## 8. 本轮到目前的状态

```
release         6.1.99-rockchip-rk3588-priv1
构建目标        Image dtbs + rtw89 模块（4 个 .ko）
构建并行        -j8  nice=15  ionice=idle
实测速率        2.46 个 .o/秒；编译期间 bash 启动延迟 0.02 s、swap 不增长
配置差异        相对原厂 8 行（DEBUG_INFO 关闭 + pahole 版本号）
驱动源码        与板子在跑的 v0.9.8 **逐字节一致**（diff 为空）→ 首版运行行为 = 现状，零回归
```

`diff -rq` 的结论值得单独强调：**内核树里的 `drivers/rknpu/` 与板子上正在运行的驱动源码完全一致**。
也就是说这份新内核的 NPU 行为与现状**完全相同**，「私有化驱动构建」这一步先把
「能自己编译出等价内核并成功上板」这件事做扎实，插桩再作为显式 diff 叠上去。
