## 一、为什么想读硬件计数器，以及为什么这条路走不通

要"最大化 NPU 利用率"，最想要的数据是**每个算子实际搬了多少字节** —— 有了它就能把带宽墙
量化到字节，直接算出融合优化的收益。驱动里明明有一套现成接口：

```
RKNPU_ACT_CLR_TOTAL_RW_AMOUNT = 13     RKNPU_GET_DT_WR_AMOUNT = 14
RKNPU_GET_DT_RD_AMOUNT        = 15     RKNPU_GET_WT_RD_AMOUNT = 16
RKNPU_GET_TOTAL_RW_AMOUNT     = 17
```

但读驱动源码发现，**RK3588 上这套接口是空转的**：

```c
static const struct rknpu_config rk3588_rknpu_config = {
        ...
        .amount_top  = NULL,      // ★ RK3588 没接线
        .amount_core = NULL,      // ★
};
```

`rknpu_get_rw_amount()` 开头就是：

```c
if (config->amount_top == NULL) {
        LOG_WARN("Get rw_amount is not supported on this device!\n");
        return 0;                  // 直接返回，args->value 原封不动
}
```

对比一下：**rk3576** 用的是 `rknpu_top_amount = {clr 0x2210, dt_wr 0x2234, dt_rd 0x2238, wt_rd 0x223c}`
和 `rknpu_core_amount = {clr 0x2410, dt_wr 0x2434, ...}` —— 都落在 **0x2000 块**，
而 0x2000 块在 RK3588 已知的寄存器布局里是**空白**（CNA 0x1000 / CORE 0x3000 / DPU 0x4000 /
DPU_RDMA 0x5000 / PPU 0x6000 / PPU_RDMA 0x7000）。

厂商还留了另一组：`rknpu_old_top_amount = {clr 0x8010, dt_wr 0x8034, ...}`（0x8000 块），
RK3588 也没用。

**于是合理怀疑：寄存器存在，只是厂商没给 RK3588 接上。** 如果验证成立，
补上 `.amount_top` 就能白拿一套硬件带宽计数器 —— 这正是"私有化驱动"的价值所在。

## 二、事故：盲扫寄存器把内核打挂了（看门狗 86 秒救回）

### 做法

写了个 `src/probes/npu_regscan.py`，通过 `/dev/mem` mmap NPU 寄存器窗口，
在推理前后各取一次快照，diff 出变化（变化且单调递增的就是计数器）。

先确认了合法边界（设备树 `npu@fdab0000` 的 `reg`，原始字节）：

```
core0: 0xfdab0000  大小 0x10000 (64KB)
core1: 0xfdac0000  大小 0x10000
core2: 0xfdad0000  大小 0x10000        ← 每核一个 64KB 窗口
```

（顺带纠正：我第一次用 `od -t x4` 读 DT 时被字节序骗了，把 64KB 看成了 256 字节。）

扫描范围限制在窗口内、只读不写，看起来安全。实际扫了这 9 段：
`0x0000-0x0100, 0x1000-0x1200, 0x2000-0x2600, 0x3000-0x3200, 0x4000-0x4200,`
`0x5000-0x5200, 0x6000-0x6200, 0x7000-0x7200, 0x8000-0x8100`。

### 结果

**板子直接失联，然后自己重启了。** 时间线：

| 时刻 | 事件 |
|---|---|
| 11:40:45 | 扫描命令开始执行 |
| ~11:40:45 | 内核卡住（此后不再喂看门狗） |
| 11:42:11 | 板子重启 |
| **差 86 秒** | **= systemd 硬件看门狗周期 1min29s** |

两条独立的证据确认这不是 panic：

1. `/sys/fs/pstore/`（ramoops 持久存储）是**空的** —— 真 panic 会被完整记下来。
2. 重启时刻与看门狗周期吻合，而与任何 panic 瞬间都不吻合。

**结论：读那 64KB 窗口里的某些偏移会让内核/互联挂死**（最可能是 0x2000 那一块 ——
RK3588 上未实现，读它触发 external abort 或让 AXI 事务永不返回）。
CPU 卡在不可中断状态 → systemd 停止喂狗 → 86 秒后硬件看门狗复位。

> **教训（重要）**：之前逆向一直走 regcmd dump（`docs/10`、`docs/14`）、
> **从不直接碰硬件寄存器**，这个克制是有道理的。设备树声明了 64KB 窗口，
> 不代表这 64KB 里每个偏移都可读。**盲扫设备寄存器不是"低风险试探"，是"直接把内核送走"。**
> 这条路封了：要拿寄存器数据，只能通过驱动里**明确的、有出处的**偏移。

### 意外收获：看门狗第一次实战就证明了价值

docs/27 里装 systemd `RuntimeWatchdogSec=60` 时只是"预防性"的。这次它是唯一
把板子救回来的机制 —— **从卡死到自动重启 86 秒，完全不需要人工断电**。
如果没有它，这块板子会一直卡到有人手动拔电。

（另一个副产物：`/tmp` 是 tmpfs，重启会清空，所以所有依赖 `/tmp/.a.sh` 的 sudo 免密
脚本在重启后都会失效。已改用持久位置。）

## 三、换路：从命令流直接量 DRAM 流量

既然计数器读不到、寄存器不能扫，就换一条**只依赖已确证证据**的路：

**每个流水级都有自己的张量地址寄存器（10 个，docs/15 确证）。同一个算子里相邻 tile 的
地址差值 = 那个 tile 的真实字节数。** 不需要知道张量形状、不需要猜数据格式、不需要读计数器。

工具：`src/analysis/dram_model.py`（`summary` / `ops` / `tensor`）。

### ★ 第一版栽的跟头：必须按缓冲区聚类

第一版直接对同一寄存器的所有地址取 `max−min` 当跨度，结果**单个算子算出 36 MB 输出**
—— 而整个设备只有 7 个缓冲区、最大 8.28 MB。荒谬值的来源：
**只有 2 个 tile 时，那两个地址可能一个在 A 缓冲区、一个在 B 缓冲区**，差值跨了半个
地址空间，被当成了 tile 步长。

修法：先用 `MEM_CREATE` 记录把每个地址归属到具体缓冲区，**只在同一缓冲区内算跨度**；
同缓冲区内步长不等距时也保守取最小步长并**标记为不可靠**（不静默吞掉）。

### 结果（yolov5s 640×640，单次推理）

```
缓冲区            7 个，合计 18.6 MB
算子数            229
总段数            615
读（输入+权重）     99,736,320 B =  95.12 MB
写（输出）          51,109,760 B =  48.74 MB
合计（下限）       150,846,080 B = 143.86 MB
不可靠的测量项      33 项（步长不等距 / 地址在缓冲区外，已按保守值计入）
```

这是**下限**：地址跨度覆盖不到"权重被每个 tile 重复读"和"层间经 DRAM 往返"的部分，
所以真实流量只会更大。

## 四、两个有分量的发现

### 发现 A：95% 的 DRAM 流量挤在同一个 7.78 MB 缓冲区上

```
      流水级      寄存器   缓冲     大小MB       读MB       写MB     段数    算子
 DPU_RDMA 0x5018    4      7.42     63.53      0.00      95     44
 DPU      0x4020    4      7.42      0.00     48.07     458    141
 CNA      0x1070    4      7.42     24.69      0.00     353    109
 CNA      0x1070    3      1.17      4.70      0.00      49      5
 DPU_RDMA 0x5038    4      7.42      2.20      0.00      19      9
 ...
                                    ─────────────────────────────
                          前三个合计 ≈ 136.3 MB / 143.86 MB = 95%
```

（缓冲区编号 #4 = `dma 0xff0a3000, size 7782400`，就是 docs/18 里那 7 块固定缓冲中最大的两块之一。）

整个网络的中间结果在**同一个 7.78 MB 缓冲区**里反复写回、再读回：
- DPU 往它写了 48.07 MB
- DPU_RDMA 从它读了 63.53 MB
- CNA 从它读了 24.69 MB

它的容量是 7.42 MiB，而单次推理经过它的流量是 136 MB —— **约 18 倍于容量**。
这说明它是纯粹的"乒乓缓冲"，没有任何片上保留。

**这就是融合优化的靶心**：如果能把相邻算子之间的中间结果留在片上（CNA→CORE→DPU 本来
就是流水线），省掉"写回再读回"这一趟，理论上能砍掉这 136 MB 里的一大半。

#### 把"写出去再读回来"单独算出来

同一缓冲区 #4 上，两个流水级的数据量高度对称：

```
DPU      往 buf#4 写   48.07 MB
DPU_RDMA 从 buf#4 读   63.53 MB
                ─────────────────
                 一趟往返 ≈ 96 MB
```

**96 MB / 143.86 MB ≈ 67%。**

也就是说：**单次推理里约三分之二的 DRAM 流量，就是"DPU 写出去、DPU_RDMA 再读回来"
这一趟**。这不是不同算子之间的数据流，而是**同一级流水内部把中间结果经 DRAM 绕了一圈**。

> 判定强度：两个数字落在同一缓冲区、量级对称，**强烈指向**是这样一趟往返；
> 但本工具还没有逐字节比对两侧的地址区间，所以严格说这是"强推断"而非"证实"。
> 要做成证实，需要把 DPU 写过的区间与 DPU_RDMA 读过的区间做区间匹配 —— 这是下一步。

**这直接给出了融合优化的收益上限：如果能消掉这一趟，DRAM 流量最多可降到原来的约 1/3。**
即使只消掉一半，按发现 B 的带宽约束也能带来可观收益。

### 发现 B：带宽不随 DMC 频率线性缩放 ⇒ NPU **不是纯**带宽受限

用同一份流量数（143.86 MB）反推有效带宽：

| DMC 频率 | 实测耗时 | 反推有效带宽 |
|---|---|---|
| 534 MHz | 46.00 ms | 3.28 GB/s |
| 2400 MHz | 28.91 ms | 5.22 GB/s |

**频率差 4.5×，有效带宽只提升 1.59×。**

如果 NPU 是纯带宽受限，时间应该按 1/4.5 缩到 10 ms 量级。实测是 28.91 ms。
所以**只有一部分时间在等 DRAM**，另一部分是流水线串行/控制开销。

这和 docs/19 的结论对上了 —— **核内天花板仅 16%**（CNA 串行瓶颈、流水级之间未能重叠）。
两个瓶颈叠加：DRAM 墙（1.59×）+ 流水串行（~16% 利用率）。

> 这个判断对优化方向很关键：**光靠 DDR 钉频最多拿到 1.59×，剩下的必须从
> 流水重叠（pipeline overlap）和 CNA 串行入手。** 这也解释了为什么三核只有 1.28× ——
> 加核对 DRAM 墙和串行瓶颈都无能为力。

### 关于 5.22 GB/s 这个数字的旁证

RK3588 的 DMC 在 2400 MHz 时，若按 32-bit LPDDR4x/5 估，理论峰值约 9.6 GB/s
（`2400 MT/s × 4 B`）。5.22 GB/s 意味着**实测效率约 54%** —— 对访存密集型负载来说，
这个效率区间（50~70%）非常典型，反过来支持"流量确实是从 DRAM 走的"这个前提。

## 五、本轮的判定与下一步

| 问题 | 结论 | 证据强度 |
|---|---|---|
| RK3588 有硬件带宽计数器可用吗？ | **驱动没接线**（`amount_top = NULL`）；寄存器能不能读**未知**，且盲探会挂内核 | 驱动源码确证 |
| 能盲扫寄存器找计数器吗？ | **不能**。实测把内核打挂，靠看门狗 86 秒救回 | 事故 + pstore + 时间线三重证据 |
| 单次推理 DRAM 流量 | **≥143.86 MB**（读 95.12 / 写 48.74） | 命令流地址实测，下限 |
| 流量在哪 | **95% 挤在同一个 7.78 MB 缓冲区**（爆容量 18 倍） | 缓冲区聚类后统计 |
| NPU 是纯带宽受限吗？ | **不是**。DMC 频率 4.5× 只换来带宽 1.59× | 两个频率点的实测反推 |

下一步（按收益排序）：

1. **量化"融合能省多少"**：把发现 A 的 136 MB 按算子对拆开，算出"相邻算子的输出正好是
   下一个的输入"的那部分流量 —— 那就是可省的部分。工具已在，加一个 `fusion` 子命令即可。
2. **补硬件计数器要谨慎**：如果确认 0x2210/0x2234 在 RK3588 上真的存在，就在驱动里
   按明确偏移接线（读**单个已知偏移**是可控的，和盲扫一个 64KB 区间完全不同）。
   验证方法：写一个只读这 4 个偏移的驱动补丁，跑推理看数值是否随流量单调增长。
3. **流水重叠**：发现 B 指出还有一半时间不在等 DRAM。回到 docs/19 的 CNA 串行问题，
   用插桩（per-core busy/idle，安全、纯软件计数）去确认到底卡在哪一级。
