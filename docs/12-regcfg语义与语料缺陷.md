## 二、用模拟器破案

### 思路

写一个 **regcmd 软件模拟器**（用户建议的"搭配仿真"方向）：
把 NPU 寄存器空间建成 `{(block, reg): [写入历史]}`，
逐条执行命令流，记录**控制流的形状**（不建模计算）。

它能回答"假设自不自洽"，而且**零硬件风险**——比等板子做实验快得多，
这在板子被我搞挂两次之后尤其重要。

### 关键功能：找结构标记

模拟器在流里标记两类结构事件：
1. **首条指令的重复位置** —— 流重新开始 = 新一段的强信号
2. **PC 链指令**（`block 0x0101 / reg 0x0010`）—— 它指向下一段命令流地址

### 破案瞬间

probe 输出里出现了这样三行：

| task | op | 声明 `regcfg_amount` | PC 链指令位置 |
|---|---|---|---|
| 21 | 2 | **24** | **[24]** |
| 22 | 2 | **18** | **[18]** |
| 23 | 2 | **23** | **[23]** |

**三个样本，`regcfg_amount` 精确等于 PC 链指令的索引。**

→ **`regcfg_amount` 是「指令条数」，不是字节数。**

### 系统性验证：109/109，零例外

在全部 615 条样本上跑这个检验：

```
有 PC 链指令的样本: 109 条
  ✅ 索引 == regcfg_amount : 109 条
  ❌ 不等                  : 0 条
```

**这是完全干净的验证结果**，假设成立。

### 更完整的语义

结合"PC 链跳转"的存在，`regcfg_amount` 的准确含义是：

> **本段命令流的指令条数。段的最后一条是 PC 链指令，它指向下一段。**
> 长命令流因此是**多段链式拼接**的，而不是一整块。

这解释了 op 80 为什么声明 611 条：**它的流被拆成了多段，611 是本段的条数**
（或者该段跨了多个缓冲区）。无论如何，"按字节理解"是错的。

## 三、⚠️ 这暴露了我方语料的严重缺陷

既然 `regcfg_amount` 是**条数**，那我抓取时的这一行就是错的：

```c
/* 我写的（错） */
uint32_t amt = t->regcfg_amount + g_slack;      /* 当成字节 */

/* 应该 */
uint32_t amt = t->regcfg_amount * 8 + g_slack;  /* 条数 × 8 字节 */
```

**后果量化：**

| 项 | 数值 |
|---|---|
| 完整样本 | **109 条（17.7%）** |
| **被截断样本** | **506 条（82.3%）** |
| 截断样本的平均覆盖率 | **41.4%**（最低 15.4%，最高 63.9%） |

按算子看最惨的几个：

| op | 声明条数 | 实际看到 | 覆盖率 |
|---|---|---|---|
| **80** | **611** | 108 | **26.4%** |
| 82 | 449 | 87 | 30.0% |
| 84 | 411 | 82 | 30.9% |
| 12 / 21 / 22 / 23 | 123 | 47 | 38.1% |
| 1 | 101 | 44 | 47.3% |

### 这对已发布结论的影响（必须说清楚）

| 结论 | 是否受影响 |
|---|---|
| 指令编码（8 字节三字段） | ✅ **不受影响** —— 截断只是少了尾部，编码格式照样成立 |
| block 映射与寄存器窗口 | ✅ 不受影响（前段已足够覆盖全部 10 个 block） |
| `OP_ENABLE` 位图 [0x18/0x1D/0x60] | ✅ 不受影响 |
| **每个流水级的张量地址寄存器** | ✅ **不受影响**（PC 0x0010 / CNA 0x1070 / CNA 0x1110 / DPU 0x4020 / PPU 0x6070 / PPU_RDMA 0x701c 都在前段） |
| **寄存器语义表（哪些是常量、哪些是变量）** | ⚠️ **受影响** —— 只覆盖每条流的**前段**，靠后的寄存器可能根本没被观测到 |
| "绝大部分寄存器是常量"这个观察 | ⚠️ 仍是前段的观察，需重抓后复核 |

**所以：[10](10-regcmd逆向成果.md) 里的寄存器表已加醒目警告，标为"仅覆盖前段"。**

## 五、这次的方法论收获

| 教训 | 说明 |
|---|---|
| **换手段能破僵局** | 抓取（动态）和反汇编（静态）都没解决 `regcfg_amount`；**模拟器**（第三种手段）一眼看穿 |
| **模拟器的成本极低、收益极高** | 几十行代码、零硬件风险，却解决了一个卡住两轮的问题 |
| **验证要追求"零例外"** | 3 个样本的吻合只是线索；**109/109 零例外**才是结论 |
| **发现自己的错误要立刻量化影响面** | 不是"哦我错了"，而是"82.3% 的样本受影响、这几条结论作废、那几条仍成立" |
| **一个语义搞错会污染整条链路** | 把"条数"当"字节"这一个错误，让我 82% 的语料不完整，而我一直没察觉 |

> 这也再次印证了 [07](07-战略转向.md) 的判断：**在能验证的地方花力气**。
> 模拟器这条路不需要硬件、不会搞挂板子、跑得还快 —— 应该更早用上。

## 七、这次的完整闭环（值得记录的工作方式）

```
① 模拟器发现语义（regcfg_amount 是指令条数）
        ↓
② 立刻意识到自己的抓取逻辑错了
        ↓
③ 量化影响面（82.3% 样本受影响，逐条判断哪些结论作废）
        ↓
④ 修工具 + 给已发布文档加醒目警告（不是偷偷改）
        ↓
⑤ 等硬件可用后重抓
        ↓
⑥ 新旧对比，给出精确的"哪些结论变了、哪些没变"
```

**第 ③④ 步是关键**：发现问题时不是笼统说"可能有问题"，
而是给出"多少受影响、哪几条作废、哪几条仍成立"，
并在原文档上留警告而不是悄悄改掉。
