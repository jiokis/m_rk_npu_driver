## 一、先纠三个常见误解（有源码证据）

| 流传的说法 | 实际情况 | 证据 |
|---|---|---|
| UAPI 头在 `include/uapi/drm/rknpu_drm.h` | **不存在**。真身在驱动私有目录 `drivers/rknpu/include/rknpu_ioctl.h` | 4.19/5.10/6.1/6.6 四分支全 404 |
| 存在 `RKNPU_CMD_*` 操作码枚举 | **不存在**。`drivers/rknpu` 全量 grep 零命中 | 也没有 `rknpu_pc.h` / `rknpu_reg_cmd.h` |
| regcmd 是"操作码流" | 是 **64 位寄存器写对**：`reg_offset` + `block_id` + `value` | 见 [04](04-regcmd格式.md) |

第二条特别重要：**我们不可能从 GPL 源码里拿到命令集，因为它压根不在里面。**
这从反面证明了第一手抓取是唯一路径 —— 也就是我们做的事。

## 二、已有成果（必须承认的前人工作）

| 项目 | 是什么 | 对本项目的意义 |
|---|---|---|
| **[oRKLLM/ork-driver](https://github.com/oRKLLM/ork-driver)** | 第三方逆向工程，含 `rknpu_ioctl.h` UAPI 副本、**能跑的最小提交实现 `src/npu.c`**、`regcmd-ISA-Reference` wiki | ⭐ **最重要的前人工作**。它的解码公式与我们的实测三字段吻合；它的最小提交是我们的起点而非重复劳动 |
| **[mainline `accel/rocket`](https://github.com/torvalds/linux/blob/master/drivers/accel/rocket/rocket_job.c)** | 官方 mainline 驱动（同硬件、清洁室实现、`drm_accel` + `drm_sched`） | ⭐ 寄存器语义一致（`PC_DATA_AMOUNT=(regcmd_count+1)/2-1`、`INTERRUPT_MASK=DPU0\|DPU1`），是**交叉验证的金标准**，也是迁移到纯 mainline 的出路 |
| Rockchip TRM（二手渲染） | 描述了 64 位指令的位域与模块位表 | 提供位域解读，但**模块命名与实测有系统性错位**，需以实测为准 |
| 各路博客/wiki | 零散记录 | 部分字段表**与源码不符**（如 `enable_mask` 被驱动读取的说法），需逐个验证 |

**结论：这件事有先行者，但没有做透。** 特别地：
- 命令格式**已有人解出**（我们的独立实测再次确认）
- 但 **block_id ↔ 硬件模块的确定映射**、**未文档化寄存器的语义**、
  **SRAM/NBUF 的容量与收益**，都还没有可靠答案

## 三、我们做出了什么（本次工作的独有贡献）

| 贡献 | 说明 |
|---|---|
| **`LD_PRELOAD` 抓取方法** | 不依赖 strace/gdb，直接在用户态拦截 ioctl 并 dump 设备内存。**在只读、无调试器的板上也能用** |
| **615 条真实命令流样本** | 覆盖 84 种算子，含 task 数组与完整 ioctl 时序，**已全部入库** |
| **独立复现并验证指令格式** | 与第三方公式**逐字段吻合**，说明该格式可靠 |
| **block_id 频次与偏移分布表** | 从真实数据反推硬件模块拓扑（含四个同构单元 0x1001/0x2001/0x4001/0x8001） |
| **自延续执行模型的直接证据** | 在 `0x0101` block 里抓到"下一段命令流地址 + 长度"，把推断变成实测 |
| **三个踩坑的正解** | `mmap64` 拦截、区间查找、`regcfg_amount` 长度语义（见 README） |

## 四、当前知识状态

```
已知 ────────────────────────────────────────────────
  ✅ 六个 ioctl 的编号、结构体、语义
  ✅ 任务提交的 7 个寄存器写序列
  ✅ regcmd 指令编码（8 字节/条，三字段）
  ✅ 硬件有 17 个中断源，每核一个 IRQ
  ✅ 内存模型：GEM→shmem/IOMMU，DMA-heap 可选
  ✅ shmem-rss 暴涨的根因（GEM 由 tmpfs 页承载）
  ✅ 命令流自延续，可链式跳转

未知 ────────────────────────────────────────────────
  ❌ block_id ↔ 硬件模块的**确定**映射（命名有争议）
  ❌ 0x1040 / 0x1044 / 0x104c / 0x1070 / 0x1080 等未文档化寄存器
  ❌ 张量描述符格式（形状 / stride / 数据类型 / 量化参数）
  ❌ SRAM 与 NBUF 的**容量**与实际带宽收益  ← 优化主战场
  ❌ 17 个中断位各自代表什么
```

## 五、下一步路线（按价值排序）

### 优先级 1：SRAM / NBUF 量化实验

**为什么最优先**：我们已知 NPU 推理的瓶颈是 **DRAM 带宽**（实测有效带宽天花板
25.9 GB/s）。SRAM/NBUF 是片上存储，**带宽与延迟都远优于 DRAM**，
这是绕开带宽墙的**唯一硬件级手段**。而 `RKNPU_MEM_TRY_ALLOC_SRAM` / `TRY_ALLOC_NBUF`
两个 flag 就在 UAPI 里摆着。

要做的事：
```
1. ACTION: GET_TOTAL_SRAM_SIZE / GET_FREE_SRAM_SIZE   → SRAM 到底多大
2. 用 TRY_ALLOC_SRAM 分配不同大小的缓冲区 → 找出可分配上限
3. 对比同一算子在 SRAM vs DRAM 上的耗时 → 量化收益
4. 找 NBUF：字符串里有 _Cache_Slice_0/1_Load_to_Nbuf 与 SramHit，
   说明运行时已在用；搞清楚它的容量与替换策略
```

### 优先级 2：最小自制命令流

用第三方 `npu.c` 为起点，逐步验证：
```
a. 提交空命令流 → 观察报什么错（反推校验逻辑）
b. 提交单条 `op_en` → 看是否能正常完成并产生中断
c. 复用真实样本的模板，只改变量槽位 → 验证"模板+槽位"假设
d. 做一次真实的 memcpy/scale 类 DMA 操作 → 端到端跑通
```
兜底：`ACTION: ACT_RESET`（软复位）· `POWER_ON/OFF`（免重载反复试）。

### 优先级 3：中断位语义枚举

故意构造各类错误命令（非法地址、非法 block_id、非法寄存器偏移），
观察 `INT_RAW_STATUS` 的哪一位被置起 → 建立**17 位 → 错误类型**的映射表。
这张表是后续所有调试的基础设施。

### 优先级 4：未文档化寄存器测绘

对 `0x1040`–`0x1088` 这段逐个做"只改这一个值"的对照实验，
观察行为差异（耗时、输出、中断）。这是工作量最大但信息量最高的一步。

## 六、风险与兜底

| 风险 | 兜底 |
|---|---|
| 写坏命令流导致 NPU 挂死 | `ACTION: ACT_RESET` 软复位；最坏重启板子 |
| 板子重启后网关不自启 | 见 `../PROJECT.md`，需要时手动 `~/rkllm-gateway/start.sh start` |
| 命令流把内存写坏 | 所有实验都在**独立分配的缓冲区**上做，不碰正在服务的网关 |
| 长时间实验烧板子 | 已有 `fan.sh` 可直接满速散热；温度超过 75°C 应停 |

## 七、对长期目标的意义

用户的原始目标是**提升模型部署自由度与优化空间**。本阶段工作的价值在于：

1. **自由度**：regcmd 是硬件唯一能听懂的语言。现在我们知道它的语法、
   有 615 条真实语料、有模板变量槽位表 —— 意味着**理论上可以自己生成任意算子配置**，
   不再受 rknn-toolkit2 的算子集约束。
2. **优化空间**：找到了 DRAM 带宽墙的**硬件级绕行方案**（SRAM/NBUF），
   以及命令流链式跳转带来的**分段加载**可能。
3. **可维护性**：整套方法论（LD_PRELOAD 抓取 + 区间映射 + 模板 diff）
   可以复用到任何闭源加速器上。
