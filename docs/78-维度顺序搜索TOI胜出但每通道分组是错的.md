**`TOI`（tap → oc → ic，ky 先）胜出：均值误差 0.0923，比其他候选小 2.5 倍。**
⇒ **维度顺序的方向是对的**（与 docs/68 一致）。

**但最大误差 0.558 在幅值 ~1.0 的权重上仍是 50% ⇒ 仍然不对。**

---

## 2. ★ 进一步查 per-channel scale —— 结果**自相矛盾**

我猜测剩下的误差来自「每通道独立 scale」，于是逐通道拟合：

```
全局统一 scale :  max 误差 0.5580
逐通道独立 scale: max 误差 0.6054   ← ★ 更差！
```

**而同时，每个「通道」的 q 取值范围都是完整的 `[-128, 127]`：**

```
oc 0: q ∈ [-128, 127]   W ∈ [-0.576, +1.000]
oc 1: q ∈ [-128, 127]   W ∈ [-1.000, +0.416]
…
oc15: q ∈ [-128, 127]   W ∈ [-0.499, +0.649]
```

### 矛盾在哪

* 若「每通道归一化到满量程」⇒ **每通道独立 scale 应当拟合得更好**（事实是更差）
* 若「全局统一 scale」⇒ 各通道的 q 范围**不该都恰好是满量程**（事实是都是）

**两个事实互相矛盾 ⇒ 唯一的解释是：我按 `oc` 分的这 16 组，并不是真正的 16 个输出通道。**
（每组恰好满量程，说明每组内部是「自己归一化」的 —— 但它们不是按输出通道归的。）

## 3. 结论

| 项 | 状态 |
|---|---|
| tap 步长 = `out_ch × align(in_ch,16)` | ✅ 由 `WEIGHT_SIZE0` 三算例确认 |
| 每 tap 内前 `in_ch` 槽为真实值 | ✅ 位置直接读到 |
| 维度顺序「tap 最外」 | 🟡 **系统搜索支持（TOI 胜出），但误差仍不合格** |
| **`oc` 的具体分组方式** | ❌ **不是简单的「连续 16 个槽一组」** |
| 完整布局 | ❌ **未确定** |

**⇒ 简单维度顺序（6 种排列 × 2 种 ky/kx）已被排除。剩下的可能性是
「`oc` 被分块/交错」（例如按 32 宽度分块、或 oc 与 ic 交织），
需要专门的探针或从编译器产物里直接读。**

## 5. 教训（本轮新增）

1. **★ 两个事实互相矛盾时，说明我的「分组」假设错了，而不是「参数没调好」。**
   「每通道满量程」与「逐通道拟合更差」不可能同时成立 ——
   我一开始想的是「再试试别的 scale 形式」，但矛盾本身直接指向**分组错误**。
   **矛盾不是噪声，是假设错误的信号。**
2. **★ 系统搜索的价值在于「排除」而不是「找到」。**
   本轮没找到正确布局，但**排除了 12 种维度顺序**（TOI 虽最好但误差不合格）。
   **搜索空间被确定地缩小了。**
3. **★ 连续第二次卡在同一处（docs/76/77/78 都在 `oc` 分组上）。**
   这说明**从 DRAM 字节反推布局**这条路可能本身就不经济 ——
   应该优先找「编译器直接给出结构」的接口（#1），而不是继续设计探针。
