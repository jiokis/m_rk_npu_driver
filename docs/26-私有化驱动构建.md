# 私有化驱动构建：方案、进展与风险

> 目标：把 RKNPU 驱动**拿下来自己构建**，以便改调度、加桩、加 UAPI。
> 没有这一步，前面所有关于"能不能优化调度/利用率"的讨论都落不了地。

---

## 一、为什么不能简单地 insmod

板上驱动的实际形态：

```
$ modinfo rknpu
filename: (builtin)           ← 编译进内核，不是模块
$ zcat /proc/config.gz | grep RKNPU
CONFIG_ROCKCHIP_RKNPU=y
CONFIG_ROCKCHIP_RKNPU_DRIVER... 
```

**built-in 驱动无法被同名模块覆盖**（设备已被平台驱动绑定）。
所以真正"用上私有驱动"必须**重新构建内核**。

> 但**构建出模块**本身就是里程碑：它证明我们能拿到源码、能改、能编出产物。

### 2.1 工具链版本为什么重要

```
板子 /proc/version: aarch64-none-linux-gnu-gcc (GNU Toolchain for the Arm
                    Architecture 11.2-2022.02 (arm-11.14)) 11.2.1 20220111
我们下载的:          aarch64-none-linux-gnu-gcc (GNU Toolchain for the Arm
                    Architecture 11.2-2022.02 (arm-11.14)) 11.2.1 20220111
```

**逐字一致** —— 避免了编译器版本差异带来的 ABI/内联问题。

### 2.2 两个幸运的配置

```
# CONFIG_MODVERSIONS is not set     ← 不需要 Module.symvers 的符号 CRC
# CONFIG_MODULE_SIG is not set      ← 不需要签名，可加载自建模块
```

**这两条让"构建外部模块"从"很麻烦"变成"很直接"。**

## 三、构建步骤

```bash
# ① 准备构建树（解压 + 应用板子配置 + modules_prepare）
scripts/build/prepare-kernel.sh

# ② 构建 rknpu 模块
scripts/build/build-rknpu-module.sh
```

`prepare-kernel.sh` 会做一个关键改动：

```diff
- CONFIG_ROCKCHIP_RKNPU=y      # 板子上是 built-in
+ CONFIG_ROCKCHIP_RKNPU=m      # 改成模块，才能独立构建/加载
```

`modules_prepare` **不编译内核本体**，只生成 `include/generated/*`，几分钟即可。

## 四、⚠️ 风险分析：真机安装这一步

**要真正用上私有驱动，必须重建内核并替换 `/boot/Image`。这有变砖风险。**

| 环节 | 风险 | 缓解 |
|---|---|---|
| 构建内核 | 编译错误 | 可在笔记本上反复重试，零风险 |
| 替换 `/boot/Image` | **新内核不启动 → 板子起不来** | ① 先备份原 Image 与 dtb ② 确认有 USB 烧录回退路径 |
| 全新 eMMC 刷写 | 需物理接触 + RKDevTool | D 盘有完整镜像与工具（见 `docs/刷机指南`） |

### 回退方案

```
① /boot/Image 与 /boot/dtb 先备份成 .bak
② 新 Image 启动失败 → 需物理接入，用 u-boot 从 SD 卡或 USB 启动
③ 最坏情况 → RKDevTool + D 盘镜像重刷（已验证可行）
```

**⇒ 我建议：先把"构建 + 验证产物"做完（零风险），
安装这一步等你确认后再做。**

## 五、有了私有驱动之后想做什么

按价值排序：

| # | 改动 | 目的 | 依据 |
|---|---|---|---|
| 1 | **加每次提交的耗时/计数器日志** | 定论调度开销（当前只能靠 `hw_elapse_time` 间接测） | [docs/25](25-DDR带宽瓶颈与测量方法危机.md) |
| 2 | **暴露每核忙/闲时间** | 查清"双核为何完全无用"（1.05×） | [docs/25](25-DDR带宽瓶颈与测量方法危机.md) §3 |
| 3 | **加带宽计数器接口**（`GET_DT_WR_AMOUNT` 等已有，但没有按提交的细分） | 量化"带宽上限"到底是多少 | [docs/25](25-DDR带宽瓶颈与测量方法危机.md) §1.3 |
| 4 | **支持 NONBLOCK / FENCE 提交** | 消除同步屏障（若它真有代价） | [docs/24](24-调度逻辑解剖.md) §6 |
| 5 | **修 `subcore_task[core_index+2]` 的索引怪癖** | 让 2 核的语义更清晰 | [docs/24](24-调度逻辑解剖.md) §1.1 |
| 6 | **在驱动里做 DDR 频率联动** | 有 NPU 负载时提 DDR 频率 | [docs/25](25-DDR带宽瓶颈与测量方法危机.md) §1.4 |

> **注意 #6**：DDR 钉频已能带来约 2× 提升，而且**一条 echo 就能做**，
> 不需要改驱动。但"按 NPU 负载自动提频"需要驱动配合（当前 `dmc_ondemand` 不看 NPU）。
