# 48 · 那条冗余拷贝的计数规则：**每个算子、每核一份**（= 每核 prologue，幂等）

> 接 [docs/47](47-命令流里可证的冗余-同一个32字节拷贝执行81遍.md)。
> 上轮知道「同一条 1×1×32 拷贝每次推理发 81 遍」，但不知道为什么是 81。
> 本轮把计数规则查清了 —— 而且规则本身**指向了机制**。
>
> 工具：`src/analysis/copy_redundancy.py`（产物 `data/analysis/copy_redundancy.txt`）

---

## 0. 规则

| 配置 | 不同 `op_idx` | 拷贝总数 | 每个 op 的次数分布 |
|---|---|---|---|
| cm=7（3 核） | **27** | **81** | `{3: 27}` —— 每个 op 恰好 3 次 |
| cm=3（2 核） | **27** | **54** | `{2: 27}` —— 每个 op 恰好 2 次 |
| cm=1（1 核） | **27** | **46** | `{1: 8, 2: 19}` |

⇒ **多核下就是「每个算子、每核一份」**：`27 op × 核数`。
⇒ **27 个 `op_idx` 的集合在三份语料里完全相同**（7, 8, 16, 17, 27, 28, 34, 35, 37, 44, 46, 48, …）——
   也就是说「哪些算子需要这条拷贝」是编译期决定的，与核数无关。
⇒ 单核是 **46**（19 个 op ×2 + 8 个 op ×1），**不是 27** —— 单核那条路另有一套规则。

---

## 1. 规则指向的机制（**是推测，标明是推测**）

`27 op × 核数`，而且每一次的 **源地址和目标地址都完全相同**
（`src=0xfff0a180 → dst=0xfff09d80`，docs/47 已证）——
这形状非常像**每个核在开工前刷一遍自己的暂存位**（per-core prologue）：
编译器把同一段 prologue 编进了**每个核的 task 列表**，于是有几个核就刷几遍。

**推论**：既然源和目标都一样，**只有第一遍有意义**，后面 N−1 遍是幂等的空转。
运行时（闭源 librknnrt）**没有对这条 prologue 做去重**。

⚠️ **这一整段是推测。** 有证据的只有：计数 = `27 × 核数`、源/目标/几何全同、源从未被写。
「per-core prologue」是**对这三条的最简解释**，不是观测到的。

---

## 2. 单核为什么是 46 而不是 27（**没解释**）

`19 × 2 + 8 × 1 = 46`。若按「每核一份」应当是 27。多出来的 19 次可能来自：
* 单核路径下某些算子的 prologue 被编了两遍（例如为两条分支各备一份）；
* 或者单核路径用了不同的 buffer 划分，需要两次初始化。

**只有三个数据点，不硬下结论。** 如实记为「单核 46，规则不明」。

## 3. 这条规则对「抬高二次开发上限」的两个含义

### 3.1 命令流层：每个拷贝只发一遍 ⇒ 拿回 ≥8~11%（docs/47 已量化）

### 3.2 ★ 驱动层：一个**具体、可实施**的优化点

这是本轮新想清楚的一件事。docs/47 说「自建命令流时每个拷贝只发一遍」——
但那是**要替换闭源运行时**才做得到的事。

**而这条冗余其实可以在 GPL 的驱动层去掉**，因为它的判据**只需要看命令流内容**：

```
同一个提交里，若两个 task 的「写地址寄存器 + 读地址寄存器 + 尺寸寄存器」
完全一致，则第二个是幂等的 ⇒ 可以跳过
```

* 这在**厂商驱动里做不到**（`drivers/rknpu` 只搬 `regcmd` 块，不解析内容）；
* 但**我们已经有私有化驱动**（docs/26/28，`6.1.99-rockchip-rk3588-priv1` 已上板），
  驱动里加一个「重复 task 消除」是**可以做的**，而且判据是纯文本比对，不需要碰硬件。

⚠️ **但必须说清楚风险**：跳过 task 会改变硬件看到的命令流，
而 docs/07/09 的教训是「自造命令流会把板子搞挂」。
所以这条路**要先在模拟器里验证**（`src/sim/rknpu/` 已经有机器模型），
再考虑上板 —— **不能直接改驱动试**。

这是本轮给出的**最有实施价值的一条建议**，同时带着明确的前置条件。

## 4. 目标 ② 的「指令流水构建机制」收口

| 问题 | 状态 | 依据 |
|---|---|---|
| 命令流怎么组织 | ✅ 段 + PC 链；提交 = 若干「轮」，一轮 = 每核一个 tile | docs/45 |
| 一次开火使能哪些级 | ✅ `0x1d` 卷积 / `0x0d` LLM GEMM / `0x18` 逐元素 / `0x60` 搬运 | docs/41/43/46 |
| **运行时往命令流里塞了什么** | ✅ 卷积侧分块按算子类型分叉；搬运侧只有 7 种操作，其中一条**每核每算子各发一遍**（幂等） | docs/43/46/47/48 |
| 各级缓冲怎么分 | ✅ CBUF 384 KB / 12 bank / entry=128 B = 1 像素×128 通道；CNN(11+1) 与 LLM(1+11) 相反 | docs/36/42/44 |
| 流水重叠机制 | ✅ 定性 + 一个负结果：权重驻留 CBUF（强对照 63/63）；权重流量对时间**无解释力**（R²=0.0004）⇒ 搬运藏在计算后面 | docs/42 |
| stage 级重叠**比例** | ⛔ 需硬件计数器；本机不可得（驱动没接线 + 寄存器不能盲扫，docs/29 事故） | — |

**「指令流水构建机制」这一栏现在是四轮里最实的一块** ——
从「有哪些位图」走到了「运行时具体塞了哪些操作、各几份、哪些是幂等的」。

## 5. 教训（本轮新增）

1. **★ 把「计数」查清楚，机制往往自己就浮出来了。** 上轮只知道「81 遍」，
   什么解释都说得通；本轮查出「27 × 核数」，**per-core prologue** 这个解释几乎是被逼出来的。
   **先问「几份」，再问「为什么」。**
2. **★ 幂等的冗余有两条实施路径，价值完全不同。** 上轮我只想到「自建命令流」；
   本轮意识到**驱动层也能做**（判据只是比对寄存器值），而我们**已经有私有化驱动**。
   **同一个发现的实施路径值得再想一遍** —— 从「需要替换闭源件」变成「在自己已有的东西上加十行」。
3. **★ 给出建议时要连前置条件一起给。** §3.2 我明确写了「必须先过模拟器、不能直接改驱动试」，
   并引了 docs/07/09 两次挂板的事故。**能实施的建议必须带上不能怎么做的边界。**
4. **推测要标出来，而且要标两次**（正文一次、小标题一次）。§1 我写了两遍「是推测」。
   上一轮（docs/47 §8）就是因为一个没标的推测差点变成错误结论。
