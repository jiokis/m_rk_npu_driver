## 1. `regcfg_amount` = 指令条数（每条 8 字节）

### 1.1 旧的矛盾

`docs/10` §5.1 记录了一个死结：

- op1 声明 `regcfg_amount = 126`
- 126 ÷ 8 = **15.75，不是整数**
- 但确凿的张量地址寄存器 `0x1070` 出现在**指令 [26]**（第 208 字节处）—— 远超 126 字节

当时试过 6/16/32 位各种单位，都不对齐，于是悬着。

### 1.2 真相：单位是「条」，不是「字节」

打开抓取库源码 `src/probes/rknpu_capture.c`，里面早就有一句自我修正：

```
/* ★★ 重大修正：regcfg_amount 是**指令条数**，不是字节数！★★
 * 用软件模拟器在 615 条真实样本上验证：
 *   regcfg_amount 精确等于「PC 链指令」在流中的索引，109/109 全中。
 *
 * 之前的错误：当成字节用 → dump 长度 = amt + slack，
 * 导致 82% 的样本被截断（平均只看到 41.4%，
 * op80 声明 611 条却只看到 108 条）。
 * 正确做法：amt * 8 字节。
 */
```

⇒ 126 条 × 8 = 1008 字节，`0x1070` 在指令 [26] 完全合理。

**`docs/10` 那 615 条样本是修正前抓的**：dump 长度 = `amount + 256`，
而正确长度是 `amount × 8`。所以 op80 声明 611 条，手上只有 108 条。

### 1.3 重抓之后的四重验证

用板上的修正版 `.so` 重抓（resnet18 / mobilenet_v2 / shufflenet / mnasnet，共 4 个模型、**1057 条命令流**）：

| 检验 | 结果 |
|---|---|
| 所有流的字节数 ÷ 8 有余数吗 | **0 条**有余数（74/74 在 cm7 组） |
| 声明的条数与文件长度对得上吗 | 126 条 ↔ **1008 字节**，精确 |
| 末尾记录是完整的吗 | 是；最后一条的 block **恒为 `0x2001`（DPU_RDMA）或 `0x1001`（DPU）** |
| 8 字节解码在整条流上还自洽吗 | 是；block 序列 `1001 2001 0201…0201` 贯通到底 |

作为对照，旧数据（截断版）的实际覆盖率：

```
amount=126 → 旧 dump 382 字节（覆盖 37.9%）
amount=122 → 旧 dump 378 字节
```

### 1.4 和驱动源码对得上

驱动里写硬件寄存器的那一行：

```c
REG_WRITE((first_task->regcfg_amount + RKNPU_PC_DATA_EXTRA_AMOUNT +
           pc_data_amount_scale - 1) / pc_data_amount_scale - 1,
          RKNPU_OFFSET_PC_DATA_AMOUNT);
```

- `RKNPU_PC_DATA_EXTRA_AMOUNT = 4`（`rknpu_ioctl.h`）
- `pc_data_amount_scale = 2`（RK3588 的 `rknpu_drv.c` 配置）

⇒ `PC_DATA_AMOUNT = ceil((条数 + 4) / 2) - 1`，即**硬件按「2 条一组」计数**，
并额外补 4 条（PC 收尾用）。126 条 → 62，硬件实际消费 (62+1)×2 = 126 条。
**数值自洽。**

## 2. ★ 段边界规则：连续扫描 + 三的倍数 + 余数降级

### 2.1 观测：提交串是任务数组的严格连续扫描

shufflenet_v2_x0_5，**63 次提交**，`task_start` 与上一次的 `start+number` **无一例外严丝合缝**（0 空隙、0 重叠）：

```
 #  core_mask  start  num  mod3
 0     0x7     486    6    0
 1     0x1     492    1    1     ← 余数
 2     0x7     493   18    0
 3     0x7     511   12    0
 4     0x7     523    6    0
 5     0x1     529    3    0     ← 3 条也走了单核
 6     0x7     532   12    0
 …
61     0x1     978    1    1
62     0x7     979    6    0
```

### 2.2 规律：三核提交恒为 3 的倍数（55/55）

四个模型合计：

| 模型 | 提交数 | 三核提交 | 其中 `num % 3 == 0` | 单核提交 |
|---|---|---|---|---|
| resnet18 (cm1) | 1 | 0 | — | 1（num=75） |
| resnet18 (cm7) | 5 | 3 | **3/3** | 2 |
| mnasnet0_5 | 3 | 2 | **2/2** | 1 |
| mobilenet_v2 | 3 | 2 | **2/2** | 1 |
| shufflenet_v2_x0_5 | 63 | 48 | **48/48** | 15 |
| **合计** | 75 | **55** | **55/55** | 20 |

三核提交的 `task_number` 取值：`{6, 9, 12, 18, 21, 60, 159, 162}` —— **全是 3 的倍数**。
单核提交的取值：`{1, 1, 1, 2, 2, 3, 75}` —— **余数与「整体单核」两种**。

### 2.3 机制

```
一个算子组的任务数 N：
  N % 3 == 0  →  core_mask = 0x7，三等分给三个核
  N % 3 != 0  →  core_mask = 0x1，整组塞给 core0（不拆）
```

shufflenet 里最清晰的是这个**重复单元**（一个 ShuffleNet block）：

```
[cm7 12][cm7 9][cm7 6][cm1 2]   ← 12+9+6+2 = 29 条任务
```

三个能三等分的卷积走三核，末尾那个 2 条的残差加法**只能走单核**。

### 2.4 代价：这是白白浪费，不是性能选择

`core_mask = 0x1` 意味着另外两个核**空转**。在 SD 的场景里这个代价很大
（`docs/144` 实测：806 次提交里 **44% 是三核、55% 是单核**）——
说明 SD 的算子组普遍偏小、凑不满三的倍数。

**这就是「3 核模式只用了一半提交」的根因**：不是驱动不想并行，是
**用户态按算子组切分的粒度太细**。

## 3. core_mask 实验：直接改变提交次数

同一个 resnet18：

| 传入 core_mask | 提交次数 | 单次任务数 |
|---|---|---|
| `0x1` | **1** | 75 |
| `0x7` | **5** | 6 / 1 / 60 / 1 / 6 |

⇒ core_mask 不只是「用几个核」，它**直接改变了任务如何被切段提交**。
这也解释了 `docs/144` 里为什么同一个模型在 IR 层的算子数远小于运行侧的提交数。

## 4. 一个还悬着的细节（诚实标注）

`subcore_task[]` 字段的语义没完全对上。抓取日志打的是 `subcore[0..2]`，
但驱动源码里三核路径用的是 **`subcore_task[core_index + 2]`**（即 [2][3][4]）：

```c
case 3:
    task_start  = args->subcore_task[core_index + 2].task_start;
    task_number = args->subcore_task[core_index + 2].task_number;
```

而日志里 3 核提交的 `subcore[0..2]` 打印出 `(79,2) (105,2) (79,2)` ——
第 2 项和第 0 项重复，像是读错了偏移。

⇒ **`subcore_task[]` 的布局与三块任务区（start 79 / 105 / 129）的对应关系还没坐实**，
需要在抓取库里按正确偏移重打一遍。这条不影响上面两条结论。
