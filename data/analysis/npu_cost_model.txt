## 四、★★★ 结论：有效吞吐只有标称峰值的 5~9%

单算子 3×3 Conv 640ch/64×64 = 15.1 G-MAC：
* 标称（3 核 × 1.024 T-MAC/s）= 3.07 T-MAC/s ⇒ 理论 **4.9 ms**
* 实测 FP16 **94.2 ms** / INT8 **55.7 ms** ⇒ **只有峰值的 5%~9%**
* 而按带宽算：读入 5.2 MB + 权重 7.4 MB + 输出 5.2 MB ≈ 18 MB @23.84 GB/s = **0.75 ms**
  ⇒ 实测比带宽极限还慢 **75~125 倍**

**⇒ 既不是算力受限、也不是带宽受限 ⇒ 存在一个**结构性开销**（最可能是 tiling/内部 SRAM 反复搬运）。**

## 五、对仿真器的意义

现有模型 `t ≈ max(n_submit × 67.4 µs, traffic / 23.84 GB/s)` **无法解释**上面这些数：

* `unet_up3` 实测 2474.7 ms；访存算出 1459.8 MB ⇒ 按带宽只有 **61.2 ms**（差 40×）
* 提交地板按 67.4 µs 算，要 2474.7 ms 就得 36,700 次提交 —— 远超实际

**⇒ 需要补的第三个分量**（建议方向）：
1. **算子级的固定成本**（与空间尺寸相关，而非与 MAC 相关）
2. **高分辨率算子的惩罚**：`p1`(11.9×) 与 `up3`(19.1×) 都在 **64×64**，而 `vae_v1`(1.6×) 只有 113 个算子却最准
3. **datatype 因子**：INT8 ≈ FP16 / 1.7

**⇒ 可直接标定的形式**：
```
t_part ≈ Σ_ops ( a + b × 像素数 × 通道数^α )   +   datatype_factor
```
用本文件的单算子表 + 逐段实测表即可拟合。

# 八、Phase A1：单算子成本曲线（**按元素线性，无 SRAM 拐点**）

## 方法

自己造单算子 ONNX（`Conv2d` / 纯 `x*1.5`）→ 转 RKNN（FP16）→ 板上 `core_mask=0_1_2` 实测（中位数 15 次）。

## 结果（640 通道）

| 空间 H | `conv3` 3×3 Conv | ns/元素 | `mul` 纯逐元素 | ns/元素 |
|---|---|---|---|---|
| 16 | **5.048 ms** | — | **2.905 ms** | 17.7 |
| 32 | **20.907 ms** | 31.9 | **10.641 ms** | 16.2 |
| 64 | **77.942 ms** | 29.7 | **40.917 ms** | 15.6 |
| 128 | **357.212 ms** | — | **204.416 ms** | 19.5 |
| 256 | **1373.787 ms** | 32.8 | **823.001 ms** | 19.6 |

## ★★★★★ 两个硬结论

### ① 成本**按元素数线性**，16→256 全程无拐点

`ns/元素` 基本恒定（conv3 30~33、mul 16~20）⇒ **没有 SRAM 边界导致的阶跃**。
⇒ 「高分辨率张量超过 SRAM 所以变慢」这个假设**不成立**（至少在这条曲线上不成立）。

### ② **MAC 数几乎不进入成本**

3×3 Conv 的 MAC 是纯逐元素 `Mul` 的 `9×C = 5760` 倍，但耗时只贵 **1.4~1.7 倍**。

**⇒ 成本几乎完全由「碰了多少个元素」决定，与算力无关。**

**⇒ 这条曲线直接解释了为什么编译器按 MAC 算的周期模型会乐观 4.7×：
  它数的是「算力周期」，而真实成本是「元素搬运」。**

## 由此推出的「等效元素带宽」

纯 `Mul` = 读 1 元素 + 写 1 元素（float32 各 4 B）⇒ 8 B/元素。
* H=256：41.9 M 元素 ⇒ 336 MB / 823 ms = **408 MB/s**
* H=16：164 K 元素 ⇒ 1.3 MB / 2.9 ms = **450 MB/s**

**⇒ 等效只有 ~**400 MB/s**，而板子 DDR 的 memcpy 实测是 **23.84 GB/s**（docs/55）
⇒ 相差 **60 倍** ⇒ **瓶颈不是 DDR 带宽，而是别的东西**（host↔NPU 搬运 / NPU 侧访存效率）。

**线性拟合无固定项**：`F + 164K·p = 2.9 ms` 与 `F + 41.9M·p = 823 ms` ⇒ `p ≈ 19.7 ns/元素`、`F ≈ 0`
⇒ **每个元素约 20 ns，与尺寸无关**。

## ★ 对优化的直接指向

既然成本 ∝ **碰过的元素数**，而 `unet_up3` 的访存里
**`Mul` 314.6 MB + `Reshape` 273.5 MB = 40%** 都是**非计算算子**：

**⇒ 优化方向应是「减少元素搬运」而不是「减少 MAC」**：
1. **消除/融合 `Mul`、`Reshape`、`Add`、`exNorm` 这类逐元素算子**（它们各自都要读一遍写一遍）
2. **避免张量在 host↔NPU 之间往返**（每个模型的输入/输出都要过一遍 4 B/元素）
3. 量化到 INT8 能**减半 I/O 字节**（FP16→INT8 是 2 B/元素）—— 这比「算力变快」更可能是 INT8 的真实收益来源

## ⚠️ 未解（留待 A2/A3）

`unet_up3` 的 730 M 元素（Σ in+out）× 20 ns = 14.6 s，但实测只有 **2.47 s**
⇒ **模型内部的逐元素成本（约 3.4 ns/元素）远低于单算子测到的 20 ns/元素。**
⇒ 说明**单算子测量里混进了 host↔NPU 往返的开销**，两者不能直接换算。
**A2 要做的正是把这两部分分离**（用 IR 表的 tile/中间张量信息 + 只测「模型内」的增量）。

# 九、Phase A2：**分离出「每次调用固定开销」与「模型内每算子成本」**

## A2.2 核心实验（relu 阻断折叠的 N 链）

**⚠️ 第一个坑：纯线性链会被折叠。**
`x*1.5*0.8*1.5…` 的 `chain64` 实测 **NPU 算子数 = 1**（编译器把它折成一个 `Mul`），
`do_constant_folding=False` 也拦不住 ⇒ **必须插入非线性算子**。

改用 `x = relu(x*1.5)` 重复 N 次 ⇒ 编译器融合成 `MulRelu`，**算子数精确等于 N**：

| 模型 | NPU 算子数 | 校验 |
|---|---|---|
| rc1 / rc2 / rc4 / rc8 / rc16 / rc32 / rc64 | 1 / 2 / 4 / 8 / 16 / 32 / **64** | ✅ 全部等于 N |

（顺带一个 RE 细节：**`Mul+Relu` 会被融成一个 `MulRelu` 算子**。）

## ★★★★★ 实测与拟合（640ch × 64×64，2.62 M 元素/张量）

| N | 耗时 |
|---|---|
| 1 | 48.903 ms |
| 2 | 50.465 ms |
| 4 | 53.216 ms |
| 8 | 59.026 ms |
| 16 | 75.370 ms |
| 32 | 81.727 ms |
| 64 | 119.134 ms |

```
t(ms) = 49.98 + 1.0865 × N        R² = 0.978
```

### ① **每次调用固定开销 `a = 50 ms`**（本次实验最重要的发现）

`rc1`（1 个算子）就要 **48.9 ms** ⇒ **这 50 ms 与模型大小基本无关**。

**⇒ 单算子实验里那些「20 ns/元素」几乎全是它** —— 例如 640/64 的 `mul` 实测 40.9 ms，
   而边际成本只有 1.09 ms ⇒ **96% 是固定开销**。

### ② **模型内每算子边际成本 `b = 1.0865 ms`** = **0.414 ns/元素**

比单算子表观值（20 ns/元素）低 **50 倍** ⇒ **两者不能直接换算，必须分离。**

## 用两档尺寸反推「每算子 = 常数 + 线性」

| 场景 | 张量元素数 | 每算子成本 |
|---|---|---|
| N 链（640ch×64×64） | 2.62 M | **1.09 ms** |
| `unet_up0`（1280ch×8×8，69 算子） | 0.082 M | **0.39 ms** |

⇒ 解出：**每算子 ≈ 0.37 ms（常数）+ 0.28 ns/元素**

**⇒ 小张量时「每算子常数」占主导；大张量时线性项占主导。**

## ⚠️ 仍未解释：`unet_up3`

用上面的模型预测 `up3`（172 算子、平均 4.2 M 元素/算子）：
`172 × (0.37 + 0.28×4.2) + 50 ≈ 313 ms`，**实测 2475 ms ⇒ 仍差 8 倍。**

**⇒ `up3` 有额外的成本来源，`up0`/`up1`/`up2`/`p1`/`p2` 用这个模型都对不上。**
（`up3` 与 `p1` 恰好是「实测/编译周期」最差的两段：19.1× / 11.9×）

**⇒ 这就是 A3 的入口：按算子类/尺寸分解，找出 `up3` 独有的成本项。**

## ★ 立即可用的两条结论

1. **50 ms/次 的固定开销**：对**小段**影响极大 —— `unet_up0` 实测 76.6 ms，
   其中固定开销占 **65%**。⇒ **合并小段**（如 `up2+up3`、或把 CLIP 三段并成一段）能直接省下这部分。
2. **INT8 的真实收益应来自 I/O 字节减半**，而不是算力 —— 但受 50 ms 固定开销掩盖，
   **单算子上的 INT8 测试（1.7×）很可能低估了整段上的收益**，需要在**整段**上重测。

# 十、★★★ Phase A3：找到「第三分量」—— **compute 算子比逐元素贵 20~37 倍**

## ⚠️ 先纠正 A1 的一个错误结论

A1 曾写「**MAC 数几乎不进入成本**，3×3 Conv 只比纯 Mul 贵 1.4~1.7 倍」。

**⇒ 那是假象。** A1 的所有单算子测量**都被 50 ms 固定开销掩盖**：
`mul` 实测 40.9 ms、`conv3` 实测 74.4 ms，看着只差 1.8 倍 ——
但扣掉 50 ms 后是 `-9 ms` vs `24 ms`，**真实差距是「几乎免费」vs「很贵」**。

## 正确的测法：compute 算子链（不同权重，折叠不掉）

用 N 个**独立权重**的 3×3 Conv / GroupNorm 造链（编译器无法折叠），
测 N=1 与 N=16，`边际 = (t16 − t1)/15`：

| 算子类 | t(N=1) | t(N=16) | **边际成本/算子** | **ns/元素** | 相对逐元素 |
|---|---|---|---|---|---|
| **Conv 3×3**（640ch×64×64） | 93.03 ms | 586.37 ms | **32.890 ms** | **12.55** | **37×** |
| **GroupNorm** | 87.93 ms | 347.35 ms | **17.294 ms** | **6.60** | **19×** |
| `MulRelu`（逐元素） | 48.66 ms | 61.85 ms | **0.879 ms** | **0.34** | 1× |

（算子数校验：`conv_16` = 16 个 `Conv`、`norm_16` = 16 个 `exNorm` + 2 个 `Reshape` ✅）

## ★★★★★ 完整成本模型

```
t_part ≈ 50 ms（每次调用固定开销）
       + Σ_算子  marginal(算子类, 张量元素数)
```

其中 `marginal` 在 2.62 M 元素时：
* 逐元素类（`Mul`/`Add`/`exSwish`）：**0.88 ms**
* `exNorm`：**17.3 ms**
* `Conv`/`ConvAdd`：**32.9 ms**

## ★ 回测 `unet_up3`（172 个算子）

按 IR 表的算子构成：

| 算子类 | 个数 | × 边际 | 小计 |
|---|---|---|---|
| `Conv` + `ConvAdd` | 37 + 21 = 58 | 32.9 ms | **1908 ms** |
| `exNorm` | 18 | 17.3 ms | **311 ms** |
| 其余（Mul/Add/Reshape/Split/BN/SDPA/Concat/Transpose） | 96 | ≈0.9 ms | ~86 ms |
| 固定开销 | — | — | **50 ms** |
| **预测** | | | **≈2355 ms** |
| **实测** | | | **2475 ms** |
| **误差** | | | **−4.8%** ✅ |

**⇒ 这就是「第三分量」：编译器按 MAC 周期建模，而真实成本是
「compute 算子的边际成本」，两者对逐元素算子的估价差了 20~37 倍。**

## ★ 由此得出的优化优先级（与之前完全不同）

**之前（基于错误的 A1 结论）**：以为要「减少元素搬运、融合逐元素算子」。

**现在（正确）**：
1. **`Conv`/`ConvAdd` 是大头** —— `up3` 里 58 个就占 **1908 ms（77%）**
   ⇒ 优化应针对**卷积**：INT8 量化（算力路径）、减通道、或让卷积跑满阵列
2. **`exNorm`（GroupNorm）第二** —— 18 个占 311 ms（13%）
   ⇒ **若能融进 Conv（BN 折叠那样）就直接省掉**
3. **逐元素算子几乎不要钱**（96 个才 ~86 ms）⇒ 之前「融合 Mul/Reshape」的方向**收益很小**

## 方法论教训（记下来）

**用「单算子模型」测成本是错的** —— 每次调用有 50 ms 固定开销，
任何比它小的算子差异都会被淹没。
**必须用「同构链的差分」**（`(t16−t1)/15`）才能测出真实边际成本。

这与本项目反复吃过的那类亏同源：**测量手段本身引入的偏差，会伪装成结论。**

# 十一、★★ Phase B：INT8 量化的实测结论 —— **在真实模型上不成立**

## B1. 纯 Conv 链：INT8 确实快 3.19×

用独立权重的 3×3 Conv 链（`conv_1` / `conv_16`，640ch×64×64），边际成本差分：

| | t(N=1) | t(N=16) | **边际/Conv** |
|---|---|---|---|
| FP16 | 89.88 ms | 585.34 ms | **33.031 ms** |
| **INT8** | 45.60 ms | 200.94 ms | **10.356 ms** |
| | | | **3.19× 加速** |

（这次修正了之前被 50 ms 固定开销掩盖的「1.7×」假读数。）

## B2. 但真实模型 `unet_up3` 上只快 1.12×，且精度掉出阈值

| | 耗时 | 输出 std |
|---|---|---|
| FP16 | **2379.5 ms** | 0.5448 |
| **INT8** | **2133.3 ms（1.12×）** | 0.5172 |

**精度：与 FP16 输出的余弦 = 0.967582，相对误差 25.35%**
（我的门控阈值是 **0.99** ⇒ **不达标**）

**⇒ 1.12× 的速度换 3% 的精度损失，不划算。**

### 为什么纯 Conv 链的 3.19× 没兑现

`up3` 的 172 个算子构成：`Conv` 37 + `ConvAdd` 21 + `exNorm` 18 +
`Reshape` 50 + `Mul` 12 + `Split` 10 + `BN` 9 + `Add` 9 + `exSwish` 7 +
`exSDPAttention` 6 + `Concat` 3 + `Transpose` 1。

**⇒ 即使 58 个 Conv 类全部 3.19× 加速（1908 ms → 598 ms），整段也应降到 ~1165 ms，
   但实测只到 2133 ms** ⇒ **量化后那些 Conv 并没有真的快 3.19×**
（可能被混合精度/量化 scale 不佳/算子间格式转换吃掉）。

## B3. `vae512_v2`（占 49%）的 INT8 转换**直接失败**

```
E RKNN: Unkown op target: 0
```
⇒ 256×256 的 VAE 解码器里有算子（最可能是 `Resize` 上采样）在 INT8 下没有可用的实现
⇒ **最大的一块根本没法量化。**

## ★ 结论：INT8 不是这个负载的出路

| 目标 | 结果 |
|---|---|
| 纯 Conv 链 | ✅ 3.19× |
| 真实 `unet_up3` | ❌ 1.12× + 精度 0.9676 |
| 真实 `vae512_v2` | ❌ 转换失败 |

**⇒ 优化方向应转向「结构性」而非「数值精度」**：
1. **减少每次调用的固定开销**（50 ms × 29 次 ≈ 1.45 s，约占 4%）—— 收益有限
2. **减少段数 / 合并模型** —— 但仍受 IOVA ~3.6 GB 限制
3. **接受当前性能**：512 档 4 步 35.5 s、1 步 23 s

1. **笔记本的 `/tmp` 重启会被清空**（和板子一样）⇒ 标定集/脚本要放持久目录

# 十二、★★★ C1a：`exSDPAttention` 是真正的瓶颈（比 Conv 贵 15 倍）

## 测法

造注意力链（**每层独立权重**，含 softmax ⇒ 不会被折叠），640ch × 64×64（4096 tokens，8 heads，d=80）。
IR 算子数校验：`attn_1` = **1 SDPA + 4 Conv + 6 Reshape**、`attn_16` = **16 SDPA + 64 Conv + 66 Reshape** ✅
（一层 SD 注意力 = 1 个 SDPA + 4 个 q/k/v/o 投影 Conv + 若干 Reshape。）

| | 耗时 |
|---|---|
| `attn_1` | 685.438 ms |
| `attn_16` | 10030.553 ms |
| **每层边际** | **623.008 ms**（含 4 个 Conv 投影） |
| 扣掉 4×Conv（132.1 ms） | **`exSDPAttention` ≈ 490.884 ms** |
| 折算 | **187.26 ns/元素** |

## ★★★★★ 与其它算子类对比

| 算子类 | 边际成本 | ns/元素 | 相对逐元素 |
|---|---|---|---|
| **`exSDPAttention`** | **490.9 ms** | **187.26** | **550×** |
| `Conv` / `ConvAdd` | 32.9 ms | 12.55 | 37× |
| `exNorm` | 17.3 ms | 6.60 | 19× |
| 逐元素（`Mul`/`Add`/`Reshape`…） | 0.88 ms | 0.34 | 1× |

## 为什么「编译器周期模型乐观 4.7×」终于解释清楚了

编译器按 MAC 周期建模，而**注意力的实际开销是 MAC 的 70 倍**
（按峰值算这层应 7 ms，实测 491 ms）。注意力在 SD 的 UNet 里每层都有，
层数一多，MAC 模型的偏差就被放大 —— 这正是 `p1`(11.9×)、`up3`(19.1×) 这些
「实测/编译周期」最差的段的成因。

## ★ 优化含义（与之前完全不同）

**之前的判断（基于 A1/A3）**：Conv 是大头 ⇒ 优化卷积。
**现在的判断**：
1. **注意力是第一优先级** —— 它比 Conv 贵一个量级，且 SD 每层都有
2. 可能的着手点：
   * **head 维度**：SD 的 `attention_head_dim=[5,10,20,20]`，head 越小越碎
     ⇒ 试统一成 32/64 这类「阵列友好」的 head dim（会改变模型，需重新导出）
   * **token 数**：64×64=4096 tokens 时注意力矩阵是 4096²×8
     ⇒ 这正是「高分辨率注意力」的固有代价；SD 本身也在这里最贵
   * **`exSDPAttention` 是否真的跑在 NPU 上**（IR 表标 NPU，但 70× 离峰说明实现低效）
3. **INT8 已证否**（真实 `up3` 仅 1.12×、精度 0.9676；`vae512_v2` 转换失败）

## 回测校核（注意：与 up3 实测有出入）

按 6 层 SDPA × 490.9 = **2945 ms**，已**超过** `up3` 的实测总时长 **2475 ms**
⇒ 说明 `up3` 里的注意力**比我这套测试便宜**（head dim 可能不同：SD 配置是 `[5,10,20,20]`，
我这套用了 8 heads / d=80）。
**⇒ 记录为待定项：SD 真实 head dim 下的注意力成本需单独测。**

### 最可能的原因（未验证）

```

```

2. 按实测曲线做**分档查表**，而不是硬套线性

# 十五、C3 修正：**排除权重/bias 后，0/8 → 2/8**（中位 151.6% → 62.2%）

## 修正了一个**计数错误**

IR 表的 `InputShape` 里**包含权重与 bias**：

```
Conv  (1,640,64,64),(640,640,3,3),(640) → (1,640,64,64)
        ↑激活        ↑权重 3.7 M   ↑bias
```

一个 3×3 Conv 的权重是 **3.7 M 元素，比激活（2.62 M）还大**
⇒ 全算进去会把元素数高估约 **1.7 倍**，整段预测系统性偏高。

**修正**：只统计**第 1 个输入（激活）+ 输出**，排除权重/bias。

## 修正后的回测

| | 修正前 | **修正后** |
|---|---|---|
| ≤30% 的段 | 0/8 | **2/8** |
| 中位绝对误差 | 151.6% | **62.2%** |
| `vae512_v2` | +63.1% | **+62.6%** |

**⇒ 有明显改善，但离目标还远。**

## ★★★ 剩下的系统性偏差：**per-element 成本随张量尺寸下降**

`vae512_v2` 仍 **+62.6%**。主因很清楚：
它的张量是 `(1,512,256,256)` = **33.5 M 元素**，
而我标定各类成本时用的是 **2.62 M** 元素的张量 —— **大了 13 倍**。

**⇒ 张量越大，每元素成本越低（摊薄）。**
**⇒ 所以「固定 ns/元素」这个假设本身就不成立，不是常数项能救的。**

## 下一步（明确）

**对同一算子类，测 2~3 个张量尺寸，得到 `cost(元素数)` 曲线**：

| 候选形式 | 含义 |
|---|---|
| 线性 `c·N` | 已证否（会系统性高估大张量） |
| `c·N^α`（α<1） | 「摊薄」形态，最可能 |
| 分档查表 + 插值 | 不依赖解析式，工程上最稳 |

**建议直接用「分档查表 + 插值」** —— 不再追求解析式。
理由：本项目已经在这个方向上试过 3 次解析式（MAC 周期、常数+线性、单 ns/元素），
每次的偏差都来自「同一个假设在另一档尺寸下不成立」。
