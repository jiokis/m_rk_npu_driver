## 2. ⚠️ 卡点：`can_fuse` 需要 **IR 节点对象**，而 `m.nodes` 只给索引

```
can_fuse(<原始 ONNX 节点>) ⇒ False（对 Conv→Relu 也返回 False，明显不对）
can_fuse(<int>)           ⇒ AttributeError: 'int' object has no attribute 'op_type'
m.nodes                   ⇒ {'conv': 0, ...} —— 值是索引，不是节点对象
```

**⇒ 需要找到「按索引取节点对象」的访问器**（候选：`m.get_node(i)` / `m.node_list` /
`m.get_array(...)` / 从 `m.graph.node` 与 IR 索引的对应关系）。

**⇒ 这是纯粹的接口发现，不是机制问题** —— 再花一点时间就能找到。

## 5. 教训（本轮新增）

1. **★★ 「接口发现」和「机制理解」是两类工作，前者的成本低得多。**
   我花了 20 轮做「机制理解」（设计探针 → 否证 → 再探针），
   而本轮做的「接口发现」（读签名、试调用）**两三轮就拿到了关键入口**。
   **遇到黑盒时，先花少量时间枚举它的公开接口，再决定要不要从外部观测。**
2. **★ 卡点要说清是「接口没找到」还是「机制不懂」。**
   本轮卡在「不知道按索引取节点对象的方法」—— 这是**接口问题**，不是原理问题，
   所以它值得继续（再试几个名字就行），而不该被当成「此路不通」。
   **区分这两类卡点，才能正确决定要不要继续。**
3. **★ 能离线跑的东西优先。** `IRGraph` 在本机构建成功 ⇒
   可以在**不上板、不转换**的情况下反复试 —— 这让接口发现的成本进一步降低。
