# 71 · ★ 输入布局确定：**原始 uint8、NHWC、缓冲区偏移 0**（逐字节 100% 吻合）

> 接 [docs/70](70-执行器权重加载路径实现并验证.md)（权重加载路径已验证）。
> 上一轮结尾指出「输入侧一直喂全 0，无法验证」。本轮喂了一个**已知图案**的输入，
> **一次就 100% 对上了。**

---

## 0. 结论

```
输入缓冲区（dma 0xfffef000，4096 B）：
  · 偏移 0 起 = 原始 uint8、NHWC（H, W, C）
  · 长度 = 1×32×32×3 = 3072 字节，之后全 0
  · 逐字节与 numpy 输入比对：3072/3072 = 100.00%

⇒ **uint8 → int8 的换算不在 CPU 侧预先做**，由 NPU 内部（CVT 单元）完成。
```

### 实测

```
输入图案: x[h][w][c] = (h*32 + w) % 256，三通道相同
缓冲区前 12 字节: [0, 0, 0, 1, 1, 1, 2, 2, 2, 3, 3, 3]
输入前 4 像素:   [0, 1, 2, 3]        ← 三通道展开正是上面那 12 字节
第 2 行开头:     输入 32 → 缓冲偏移 96(=32*3) = 32   ✅
偏移 3072 之后:  非零 0 字节                        ✅
```

---

## 1. 这个结论对执行器的意义

`.cfg` 里有 `input`（float32）与 `input_int8`（int8, scale=0.00392156862745098=1/255, zp=-128）。
我原本以为运行时会在 CPU 侧先量化成 int8 再交给 NPU。

**实测否定了这一点**：缓冲区里是**原始 uint8**。

⇒ 执行器要模拟的是：**NPU 自己**按 `CVT` 的配置把 uint8 转成内部定点。
这与 docs/17 记的 `CVT_CON*`（scale/offset/truncate）是同一件事 ——
**输入侧的换算也在 CVT 里，不在 CPU。**

## 4. 教训（本轮新增）

1. **★ 「喂一个已知图案」比「分析空数据」强一个数量级。**
   输入侧我拖了两轮没做（因为「要先想清楚怎么验证」），
   而实际做法极简单：**喂 `(h*32+w)` 这种位置序号，布局直接肉眼可读**。
   **先用最省事的已知输入把结构读出来，再考虑复杂验证。**
2. **★ 100% 吻合这种结果要敢于确认。** 3072/3072 逐字节相同 ⇒ 不需要再解释，
   直接下结论。**不要因为「太简单」而怀疑一个完全吻合的结果。**
3. **★ 一个否定（「不在 CPU 侧量化」）同样是有价值的结论。**
   它把执行器的职责边界划清了：**换算在 NPU 内部，仿真器必须实现 CVT。**
