## 一、指令编码：**逐位确证**

Mesa 的编码器（`rkt_regcmd.c`）：

```c
static void emit_raw(struct util_dynarray *regs, uint32_t target, uint32_t reg, uint32_t value)
{
   uint64_t packed_value = 0;
   packed_value  = ((uint64_t)target) << 48;
   packed_value |= ((uint64_t)value)  << 16;
   packed_value |= ((uint64_t)reg);
   util_dynarray_append(regs, packed_value);
}
static void emit(struct util_dynarray *regs, uint32_t reg, uint32_t value)
{
   uint32_t target = rkt_get_target(reg) + 0x1;    /* ★ target = block | 1 */
   emit_raw(regs, target, reg, value);
}
```

对照我们**纯靠 615 条样本逆向**出来的格式（docs/04）：

| 字节 | Mesa | 我们的逆向 |
|---|---|---|
| b0-b1 | `reg` (bits 15:0) | word0 低 16 = 寄存器偏移 ✅ |
| b2-b3 | value bits 15:0 | word0 高 16 = value_lo ✅ |
| b4-b5 | value bits 31:16 | word1 低 16 = value_hi ✅ |
| b6-b7 | `target = block + 1` | word1 高 16 = block_id（**bit0 = 写位**）✅ |

**编码格式与「block_id = target \| 1」这条核心结论，被上游实现逐位证实。**

## 三、那两个上游没有的 target：**段终止序列**

它们每段各出现一次。Mesa 的源码把整条终止序列用 **TRM 原文**注释出来了：

```c
if (num_tasks == 1)
   append(0x0);                                  /* 单 task：8 字节全 0 */
else
   EMIT(REG_PC_BASE_ADDRESS, 0);                 /* 多 task：(0x101, 0x0010) = 0 */

EMIT(REG_PC_REGISTER_AMOUNTS, 0);                 /* (0x101, 0x0014) = 0 */

/* TRM: before op_en, 64'h0041_xxxx_xxxx_xxxx must be set. */
append(0x0041000000000000);                       /* ← 我们观测到的「OP40」 */

/* TRM: 64'h0081_0000_007f_0008 will set each block's op_en(CNA, CORE, ..., PPU_RDMA). */
emit_raw(regs, 0x81, REG_PC_OPERATION_ENABLE,
         PC_OPERATION_ENABLE_RESERVED_0(14) | PC_OPERATION_ENABLE_OP_EN(1));   /* = 0x1D */
```

三条关键结论：

1. **`0x0041_xxxx_xxxx_xxxx` 是 TRM 要求的"开火前必须设置"的指令** —— 对应我们观测到的
   `target 0x40, reg 0x0000`。我们当时只能描述它是"段尾固定出现"，现在知道它是**流程屏障**。
2. **开火指令 = `0x0081_0000_007f_0008`**，TRM 原文说它"**set each block's op_en
   (CNA, CORE, ..., PPU_RDMA)**" —— **这直接确认了我们把该字段解成「流水级组成位图」是对的**。
   而且注意：**上游的 autogen header 把这个字段标为 `RESERVED_0`**，Mesa 却往里写 14
   —— 说明上游自己也没完全搞清这些位，而我们解出来了。
3. 注释里的例子值 `0x007f` = 7 位 = 七个块全开，与我们"每位对应一个块"的解释一致。

### 位映射：**两个独立来源确认**

我们用 615 段做相关性（"置了该位的段里，哪些块真的被配置了"）：

```
0x1d  468 段  → CNA+CORE+DPU+DPU_RDMA (402/468)
0x18   89 段  → DPU+DPU_RDMA        (89/89 = 100%)
0x60   58 段  → PPU+PPU_RDMA        (58/58 = 100%)
```

而 **Mesa 的 conv 路径实际 emit 的块**是：`CNA×58 + CORE×4 + DPU/DPU_RDMA×82`，
它写的使能值正是 **0x1D（4 个位）** —— 四个块、四个位。

**结论（两条独立证据）**：

```
bit0=CNA   bit2=CORE   bit3=DPU   bit4=DPU_RDMA   bit5=PPU   bit6=PPU_RDMA
bit1 从未被置位（含义未知）
```

## 四、DPU 的数据通路被"命名"揭开了

拿到权威命名后，DPU 那 51 个我们只当成"未知偏移"的寄存器，立刻显出结构：

| 寄存器组 | 含义 |
|---|---|
| `BS_CFG` `BS_ALU_CFG` `BS_MUL_CFG` `BS_OW_CFG` `BS_OW_OP` | **Bias / Scale** 级（含 ALU 与乘法器配置） |
| `BN_CFG` `BN_ALU_CFG` `BN_MUL_CFG` | **BatchNorm** 级 |
| `EW_CFG` | **ElementWise** 级 |
| `LUT_ACCESS_CFG` `LUT_ACCESS_DATA` | **查找表 / 激活函数** |
| `DATA_CUBE_WIDTH` `DATA_CUBE_HEIGHT` `DATA_CUBE_NOTCH_ADDR` | 数据立方体（三维分块）布局 |
| `DST_BASE_ADDR` `DST_SURF_STRIDE` `DATA_FORMAT` | 输出地址 / 跨距 / 格式 |
| `WDMA_SIZE_0` | 写 DMA 尺寸 |

**所以 DPU 是一条后处理流水：Bias/Scale → BatchNorm → ElementWise → LUT(激活)。**
我们之前只知道 `0x4020` 是输出地址、`0x4030` 是"尺寸−1"，现在知道了整条链的语义。

顺带纠正我们的一处逆向：`0x4030` 我们记为"尺寸−1"，上游名是 **`DATA_CUBE_WIDTH`**、
`0x4034` 是 **`DATA_CUBE_HEIGHT`** —— 也就是**分别的宽与高**，而不是笼统的"尺寸"。

> 另外注意 `LUT_ACCESS_DATA` 被写了 **12,801 次**，是全场最多的寄存器 ——
> **激活函数的查找表是逐算子装载的**。这是个此前完全没注意到的成本项。

## 五、★★★ 微架构核心：片上 CBUF 是 12 个 bank

### 5.1 上游给出的硬件参数

```c
/* Mesa rkt_ml.h */
#define CBUF_BANK_SIZE        32768      /* 32 KB */
#define CBUF_BANKS            12
#define CBUF_ENTRIES_PER_BANK 256
#define CBUF_ENTRY_SIZE       (CBUF_BANK_SIZE / CBUF_ENTRIES_PER_BANK)   /* = 128 */
#define ATOMIC_K_SIZE         16
```

**→ CNA 的片上系数缓冲 CBUF 总共 = 12 × 32 KB = 384 KB。**

### 5.2 `CBUF_CON0 @ 0x1040` 的位域（权威）

```
bits 0..3   DATA_BANK       输入数据占几个 bank
bits 4..7   WEIGHT_BANK     权重占几个 bank
bits 8..10  FC_DATA_BANK    全连接的数据 bank
bit  12     DATA_REUSE      复用已加载的输入
bit  13     WEIGHT_REUSE    复用已加载的权重
```

### 5.3 厂商实际怎么用它（我们解码 655 个真实样本）

```
DATA_BANK  WEIGHT_BANK   出现次数
   11          1         200 / 176 (带 WEIGHT_REUSE)
    7          5          97
   10          2          66 / 28
    3          9          22 / 18
    9          3          16 / 12
    4          8          14
    7          5           6
```

**★ 两个独立确证：**

1. **`DATA_BANK + WEIGHT_BANK ≡ 12`，无一例外** —— 与 `CBUF_BANKS = 12` 完全吻合。
   也就是说厂商把 12 个 bank **全部分配**给「输入数据 + 权重」，
   分配比例随每层的权重/输入规模变化（1:11 到 9:3）。
2. **`WEIGHT_REUSE` 只在 40%（264/655）的情况下置位；`DATA_REUSE` 从未置位（0/655）。**

### 5.4 这解释了此前的几个观察

- **为什么要分块（588 个 tile）**：权重张量 + 输入切片必须塞进 12 个 bank（384 KB）。
  塞不下就切分。Mesa 的 `calc_weights_banks()` 算的就是整层权重的字节数 → 需要多少 bank。
- **为什么权重被重读 2.3×（docs/31）**：`WEIGHT_REUSE` 只有 40% 置位，
  剩下 60% 的情况每个 tile 都把权重重新从 DRAM 拉一遍。
- **`DATA_REUSE` 完全没用**：输入侧没有做任何跨 tile 复用。

> ⚠️ **修正我在 docs/31/34 里说过的一句话**：我当时据 `GET_TOTAL_SRAM_SIZE = 0` 断言
> "RK3588 的 NPU 没有可用片上 SRAM、融合物理上无处可留"。
> **这句话不准确**：硬件**有** 384 KB 的片上 CBUF（12 bank），只是**不以 SRAM 的形式
> 通过 ioctl 暴露**，而是由命令流里的 `CBUF_CON0` 直接配置。
> 更准确的说法是：**片上缓冲存在，但容量只有 384 KB，且需要与权重共享** ——
> 这仍然是"中间特征图放不下"（yolov5s 的中间张量动辄 3.28 MB），所以"跨算子融合无空间"
> 的结论不变，但**"硬件没有片上缓冲"这个理由是错的**。

## 七、仍然没搞清的（诚实列出）

1. **`0x0014` 的 bit16**：上游把 bits 31:16 标为 `RESERVED_0`，而厂商会置 bit16。
   我们此前测到它与"段 amount == 122"精确相关 —— 一个**厂商在用、上游标为保留的位**。
   含义仍未解（可能是个隐藏的段属性位）。
2. **op_en 的 bit1**：615 段里从未置位。七个块只用到六个 bit（0,2,3,4,5,6），
   bit1 对应哪个块、还是别的含义，不明。
3. **DDMA(0x10000) / SDMA(0x20000)**：上游定义了这两个块的寄存器（各 10 个），
   但**我们的 615 段里一次都没观测到**。是这个模型用不到，还是厂商的运行时走别的路径？
4. **`FC_DATA_BANK`**：位域存在（bits 8..10），但我们观测到的所有样本里都是 0 ——
   全连接层（RKLLM 那边可能用到）。
5. **CBUF 分配策略是否最优**：厂商的 1:11 ~ 9:3 分配是编译器定的，
   是否存在更优分配（比如更倾向于给权重留 bank 以减少重读），没有验证过。

## 八、这些对"抬高二次开发上限"意味着什么

1. **寄存器层已经没有盲区了**：111/154 有我们的观测样本，且大部分拿到了权威命名
   → 想直接写命令流驱动 NPU，现在有完整的寄存器字典（`data/analysis/register_crossref.txt`）。
2. **流水构建有开源参照**：Mesa 的 `rkt_ml.c` / `rkt_task.c` / `rkt_regcmd.c`
   是把一个算子编译成 regcmd 序列的完整示例 —— **这是二次开发最直接的模板**。
3. **片上资源模型清楚了**：384 KB CBUF / 12 bank / 必须与权重分享
   → 任何自己写的调度都必须按这个约束分块。
4. **看到了两个明确的浪费点**：`WEIGHT_REUSE` 只用 40%、`DATA_REUSE` 完全没用。
   如果能自己生成命令流，这两处就是现成的优化目标。

## ⚠️ 修正（由 [docs/41](41-结构级模型成立-分块被撞实与提交地板实测.md) 给出）

本篇有两处需要修正：

1. **「我们观测到 39 个上游未定义的寄存器」是错的 —— 实际只有 2 个。**
   错误来源：本篇的「来源 A」用的是 Mesa 的 `registers.xml`（**154 条，是子集**），
   而不是上游**内核头文件** `drivers/accel/rocket/rocket_registers.h`（**199 条**）。
   用正确的头文件重算：

   ```
   上游头文件 199 条；我们观测到 148 条；交集 146；上游有我们未见 53；我们见上游无 2
   ```

   仅剩的 2 个（`0x003030`、`0x0040c4`）上游也**在写**，只是没给名字：
   `emit_raw(regs, CORE | 0x1, 0x3030, 0)` 和 `emit_raw(regs, DPU | 0x1, 0x40c4, 0)`
   （后者是 `DPU_SURFACE_ADD(0x40c0)` 的高 32 位，低字 mask 为 `0xfffffff0`）。
   ⇒ **上游覆盖了我们观测到的 100% 的寄存器。**

   本篇只记录了「偏移对上了」。docs/41 用上游 `rkt_task.c` 的代码把语义钉死：
   `DATA_SIZE0 = DATAIN_WIDTH(整层宽) | DATAIN_HEIGHT(**tile 输入行带高**)`。
   所以 docs/17 记的「`DATA_SIZE0[0..10]` = 34/70/28，不是高度」要反过来读：
