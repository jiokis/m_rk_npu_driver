# 第一部分 · 指令集本身

## 1.1 命令流不是"计算指令"，是**寄存器写命令**

每条 8 字节：

```
word0 = [u16 reg_offset][u16 value_lo]
word1 = [u16 value_hi ][u16 block_id]
```

而 `block_id` 的结构是：

```
block_id = target | op        op = 1 → 写寄存器
          ↑ 2 的幂，每个硬件块占一位
```

| block_id | target | 块 |
|---|---|---|
| `0x0041` | `0x40` (bit6) | （未定名） |
| `0x0081` | `0x80` (bit7) | **GLOBAL**（总使能位图） |
| `0x0101` | `0x100` (bit8) | **PC** |
| `0x0201` | `0x200` (bit9) | **CNA**（卷积主算） |
| `0x0801` | `0x400` (bit10) | **CORE** |
| `0x1001` | `0x800` (bit11) | **DPU** |
| `0x2001` | `0x1000` (bit12) | **DPU_RDMA** |
| `0x4001` | `0x2000` (bit13) | **PPU** |
| `0x8001` | `0x4000` (bit14) | **PPU_RDMA** |

**⇒ 指令集极简：`{ 写寄存器(块, 偏移, 值) }` + `{ 空操作 }`。**
没有算术指令、没有分支指令 —— **硬件是"配置驱动"的，不是"程序驱动"的**。

这与 NVDLA 一致（CSB 寄存器编程），**但 Rockchip 在外面套了一层命令流**（见第二部分）。

## 1.2 所以"指令集"的实质 = 各块的寄存器接口

每个块的寄存器集合就是它能接受的"指令"。已自证的部分见 [17](17-字段语义与模板生成.md)：
地址类（每级一个）、尺寸/通道类（每级一对）、跨距类、模式类、大量固定常量。

> **推论**：想让 NPU 做新事情，不是"写新指令"，而是**给已知块写新的寄存器组合**。
> 这也是为什么"理解寄存器语义"是提升利用率的唯一途径。

# 第二部分 · 指令流水的构建 ★

## 2.1 段的完整布局（611/615 验证）

**这是本次最重要的结构发现。** 一个 task 槽位的布局是：

```
偏移(条)          内容                        作用
─────────────────────────────────────────────────────────────
[0 .. amount-1]   体（向各级写寄存器）          配置：把这一层要用的块设好
[amount]          PC 0x0010 = 下一段地址       链接：顺着走
[amount+1]        PC 0x0014 = 下一段 DATA_AMOUNT
[amount+2]        OP40 (0x0041, 0x0000)       ┐ 开火前置
[amount+3]        ENABLE (0x0081, 0x0008)     ┘ **本段的总使能位图**
[amount+4 ..]     NONE 填充
```

### 关键点：使能在**链之后**

一开始我以为使能应该在配置的末尾、链之前。实测是**反的**：

```
[ 126] PC       0x0010 = 0xfff0a9c0  ← 链:地址
[ 127] PC       0x0014 = 0x00000040  ← 链:长度
[ 128] OP40     0x0000 = 0x00000000  ← 链之后
[ 129] ENABLE   0x0008 = 0x0000001d  ← 链之后 ← **开火**
```

**⇒ 链是「说明书」（告诉硬件下一段在哪），使能才是「扳机」。**
硬件把本段整段执行完（含末尾的使能），本段的工作才真正开始。

### 验证

| 断言 | 结果 |
|---|---|
| 链指令在 `index == amount` | **611 / 615**（4 个例外是链结束段，地址槽为 `OP_NONE`，已知） |
| 使能指令在 `index == amount + 3` | 同上 |
| **使能出现次数 == task 数** | **615 / 615 —— 每段恰好一次** |

## 2.2 内核常数 `RKNPU_PC_DATA_EXTRA_AMOUNT = 4` 的含义被解出

内核里那个一直无从解释的 `+4`：

```c
PC_DATA_AMOUNT((regcfg_amount + RKNPU_PC_DATA_EXTRA_AMOUNT + scale - 1) / scale - 1);
```

**`+4` 就是「链 2 条 + 使能 2 条」。** 硬件实际读取长度：

```
读取条数 = round_up(regcfg_amount + 4, 2)
```

| task | amount | PC_DATA_AMOUNT | 读取条数 | 体+链+使能 |
|---|---|---|---|---|
| 0 | 126 | 64 | **130** | 126+2+2 = **130** ✅ |
| 2 | 61 | 32 | **66** | 61+2+2 = 65 → 取偶 **66** ✅ |

（`PC_DATA_AMOUNT` 以「2 条指令」为单位，故向上取偶。）

## 2.3 所以"流水"是这样搭起来的

```
硬件从首 task 地址出发
   ↓
读 round_up(amount+4, 2) 条 = 体 + 链 + 使能
   ↓
执行体（配置各级寄存器）→ 执行链（记下下一段）→ 执行使能（**开火**）
   ↓
跳到链给出的地址，重复 —— 直到执行完 task_number 个 task
```

**这就是"指令流水"**：一批**「配置 → 开火」**的小段，用链串成一条流水线。
每段的使能位图决定了这一段会动用到哪几级硬件。

# 第三部分 · NPU 结构

## 3.1 硬件的"级"与每级的张量地址（已确证）

每个流水级都有自己的张量地址寄存器 —— **共 10 个，全部值为真实设备地址**：

| 级 | 地址寄存器 | NVDLA 对应 |
|---|---|---|
| PC | `0x0010` | 无（Rockchip 新增） |
| CNA | `0x1070`（特征）/ `0x1110`（权重） | CDMA `D_DAIN_ADDR_LOW` |
| DPU | `0x4020` | SDP `D_DST_BASE_ADDR_LOW` |
| DPU_RDMA | `0x5018` / `0x5020` / `0x5038` | SDP_RDMA `0xa018`/`0xa02c`/`0xa05c` |
| PPU | `0x6070` | PDP `0xd070`（**偏移完全相同**） |
| PPU_RDMA | `0x701c` | PDP_RDMA `0xc01c`（**偏移完全相同**） |

### 重要细节：DPU_RDMA 的三个地址寄存器**大部分时候是 0**

| 寄存器 | 530 次中为 0 的次数 |
|---|---|
| `0x5018` | **416** |
| `0x5038` | **499** |
| `0x5020` | 83 |

**⇒ 这三个不是"全都用"，而是"按需启用"** —— 只在需要第二条数据通路的算子（残差/逐元素）里才填值。
**这是流水可配置性的直接证据。**

## 3.2 内存布局：7 块固定缓冲区，18.6 MB

| dma_addr | 大小 | 谁在用 |
|---|---|---|
| `0xff80f000` | **8.28 MB** | `CNA 0x1110` **447/447 全指向它** → **权重区** |
| `0xff0a3000` | 7.78 MB | CNA 特征读 408、DPU 512 → **主特征图区** |
| `0xfede7000` | 1.64 MB | 少量 |
| `0xfef77000` | 1.23 MB | CNA 特征 39 次 |
| `0xfed83000` | 409 KB | 少量 |
| `0xfed6a000` | 102 KB | 少量 |
| `0xffff5000` | 45 KB | flags=`0x40b`（与其他 `0x403` 不同）→ **控制/参数区** |

**权重区与特征区分离**，且**特征区被 CNA 读、DPU 写** —— 说明**中间结果在同两块大缓冲区之间来回**。
这一条直接指向利用率的瓶颈（见第四部分）。

## 3.3 ★ 使能位图 = 每层用了哪几级（硬件的"算子分类"）

`ENABLE` 位图的位定义（Mesa/内核 + 我们数据双路确认）：

```
bit0 CNA_OP_EN   bit2 CORE   bit3 DPU   bit4 DPU_RDMA   bit5 PPU   bit6 PPU_RDMA
```

**615 个段里只有 3 种取值**，而且分布与我们预期完全一致：

| 位图 | 位分解 | 段数 | 流水组成 | 含义 |
|---|---|---|---|---|
| `0x1D` (29) | CNA\|CORE\|DPU\|DPU_RDMA | **468** | 四级全开 | **卷积/矩阵乘**（主力计算） |
| `0x18` (24) | DPU\|DPU_RDMA | **89** | 只用 DPU | **纯逐元素/激活**（无卷积） |
| `0x60` (96) | PPU\|PPU_RDMA | **58** | 只用 PPU | **池化/后处理** |

**⇒ 这一位图直接就是「算子用了哪几级流水」的标签**，而且**保留位 bit1 从未置位**。

# 第四部分 · 对"最大程度利用 NPU"的推论

## 4.1 已量出的不利事实

| 观察 | 数值 | 影响 |
|---|---|---|
| **特征区只有 2 块大缓冲** | 8.28M（权重）+ 7.78M（特征） | 中间结果必须在**片外**来回；这就是带宽墙 |
| **DPU_RDMA 的三个地址寄存器大多为 0** | 416/530、499/530 | 第二条数据通路**基本没用上** |
| **我这次抓取只用了 1 个核** | `core_mask=0x1`（3 核只开 1） | **2/3 算力闲置** |
| **整模型是一条 588 段的串行链** | 单次 submit | 没有跨核并行 |

## 4.2 可挖的方向（按确定性排序）

1. **多核**：`core_mask` 支持 `0x1/0x2/0x4/0x3/0x7`。
   我抓取时显式指定了 core 0（`NPU_CORE_0`），**这 2/3 闲置是我自己造成的**。
   想知道真实上限，应重抓一次 `core_mask=0x7` 对比。

2. **逐元素层（`0x18`，89 段）不占 CNA**
   ⇒ 这类层与卷积层**理论上可以并行**（一个用 CNA，一个用 DPU）。
   它们目前串在一条链上 —— **是否存在跨段重叠是利用率的下一个关键问题**。

3. **池化层（`0x60`，58 段）只用 PPU**
   ⇒ 同理，与 CNA/CORE 无资源冲突。

4. **DPU_RDMA 的第二通路**（`0x5018`/`0x5038`）在 89 段逐元素层里可能被用上 ——
   值得单独统计"哪些算子用了它"，那就是残差连接的实现方式。

## 4.3 下一步该做的实验（都不碰危险操作）

- [ ] **重抓一次 `core_mask=0x7`**：对比命令流结构是否变化，量化多核的影响
- [ ] **统计哪些算子用了 DPU_RDMA 的第二通路**（`0x5018`/`0x5038` 非 0）
      → 找出残差/逐元素的实现方式
- [ ] **测量层间串行度**：相邻两段的使能位图若资源不冲突，理论上可重叠 ——
      这是判断"硬件是否已自动流水"的关键
- [ ] 用 `mobilenet_ssd.rknn`（300×300）抓一遍，验证结构结论**不依赖 yolov5s**
