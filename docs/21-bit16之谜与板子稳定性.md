## 一、bit16 到底是什么（结论：未定，但刻画精确）

### 1.1 曾经的两个猜测都被推翻

| 猜测 | 被推翻的证据 |
|---|---|
| "流水相位标志"（按时间交替） | **不是交替**。bit16=1 覆盖 task 205..585 **一整片连续区间** |
| "算子边界标记" | **不是**。281 个 task 里，105 个在算子的第 0 块、68 个在第 1 块…分布与位置无关 |

### 1.2 精确刻画：它**完全由「本段 `amount == 122`」决定**

```
amount  bit16=0  bit16=1
     9        2        0
    18       27        0
    23       14        0
    26       58        0
    61       16        0
    69       75        0
   122        0      281   ← 全部为 1
   126      121        0
  1097       12        0
```

**每个 amount 的 bit16 取值都唯一 ⇒ 它是一个「由段规模决定」的量，不是调度标记。**

而那些 `amount=122` 的段有什么特征：

| 特征 | 值 |
|---|---|
| 数量 | 281 个 |
| task 区间 | 205..585（模型后半段） |
| **使能位图** | **全部 `0x1D`（卷积级全开）** |
| 覆盖 op 类型 | 58 种 |
| 在算子内的位置 | 0~9 都有，分布均匀 |

### 1.3 而低 16 位的公式依然稳固

```
0x0014 低16位 == (目标段 regcfg_amount + 4 + 2 − 1) / 2 − 1
验证: 610 / 610 ✅
```

**⇒ 结论：低 16 位是「下一段的 PC_DATA_AMOUNT」（已确证）；高 16 位是一个尚未定性的量，
与段规模（`amount==122`）强相关，但不是调度相位。**

不确定就写不确定 —— 这条不影响链机制的使用（我们重建链时是**按原字节带过**这个位域的，
见 [16](16-算子重建验证.md)：587/588 段逐字节重建成功）。

## 二、⚠️ 板子稳定性记录（值得警惕的变化）

### 2.1 四次失联事件

| # | 触发 | 现象 | 归因 |
|---|---|---|---|
| 1 | 我提交含 `OP_ENABLE` 的命令流 | ARP INCOMPLETE，彻底失联 | **我方实验**（无描述符使能 → 内存损坏） |
| 2 | 我提交仅 `OP_NONE` 的命令流 | ICMP 通、所有 TCP 超时 | **我方实验**（疑似中断风暴） |
| 3 | **无任何实验**，板子静置 | 同上 | **不明** |
| 4 | **无任何实验**（刚部署完脚本文件） | 同上 | **不明** |

**关键变化：第 3、4 次失联与我方实验无关。**

### 2.2 现象签名（两次不同）

| 签名 | 出现 | 含义 |
|---|---|---|
| **ARP INCOMPLETE**（连 ping 都不通） | 事件 1 | 网络栈也不响应 → 硬挂 |
| **ICMP 通、全部 TCP 超时** | 事件 2/3/4 | ICMP(内核软中断) 正常，TCP 协议栈不处理 → 内核部分卡死 |

事件 4 的过程：SSH 确认健康（三核 0%、39.8°C、1000MHz）→ 编译抓取器成功 →
scp 实验脚本时 `Connection closed` → 此后一直 TCP 超时。

### 2.3 对实验计划的影响

**步骤 1（多核）与步骤 3（跨模型）都需要板子稳定在线。** 当前状态不适合跑长实验。

**建议的应对**（按性价比）：
1. **一次断电后先跑一个"最短路径"实验**：只做一次推理计时，确认板子能稳定跑完
2. **把实验脚本改成"断点续跑"**：每个配置独立落盘，掉了也能从中断处继续
3. 若仍频繁失联，**优先排查硬件**（供电、散热、内存），而不是继续在上面做实验
