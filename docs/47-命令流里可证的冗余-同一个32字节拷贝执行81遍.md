# 47 · 命令流里**可证的冗余**：同一个 32 字节拷贝，每次推理执行 81 遍

> 本轮（第 9 轮）追的是「指令流水构建机制」里最实在的一块：
> **运行时到底往命令流里塞了什么。**
> 结果是一个硬结论 —— 整个模型里只有 **7 种**搬运操作，其中一种
> **每次推理被执行 81 遍**，而且它**不可能产生新结果**。
>
> 工具：`src/analysis/copy_redundancy.py`（产物 `data/analysis/copy_redundancy.txt`）

---

## 0. 结论

```
整个 yolov5s 模型里，OP_ENABLE=0x60（搬运通路）一共只有 7 种操作：
  6 种是真做了核的（2×2×256，各 1~2 次）
  1 种是退化的 1×1×32 拷贝：src=0xfff0a180 → dst=0xfff09d80
      每次推理执行 **81 遍（3 核）/ 54 遍（2 核）/ 46 遍（1 核）**
```

**判据是硬的（三条同时成立）**：
1. 81 个 tile 的 **源地址、目标地址、几何、kernel_cfg 全部相同**；
2. **源地址从未被写过**（整趟 0 次写）；
3. 目标地址的**每一次写都来自这同一次拷贝**（46 次写，全部同源同目标）。

⇒ 把同一份数据从同一处搬到同一处，第 2~81 遍**不可能产生新结果**。这是**纯冗余**。

**时间上值多少**：只算「纯搬运提交」（一个 MAC 都不做的提交，hw 可直接量到）——

| 配置 | 纯搬运提交 | tile | Σhw | 整趟 | 占比 |
|---|---|---|---|---|---|
| cm=7（3 核） | 8 | 25 | 0.922 ms | 11.056 ms | **8.3%** |
| cm=3（2 核） | 9 | 26 | 1.525 ms | 13.571 ms | **11.2%** |
| cm=1（1 核） | 0（全混在大提交里） | 0 | — | 15.401 ms | — |

其余冗余 tile 混在含卷积的提交里，边际代价量不到 ⇒ **8~11% 是下界，不是全量。**

## 1. 我是怎么先看错的（这条比结论本身更值钱）

第一版工具把搬运 tile 的身份定义为
`(op_idx, 源地址, 目标地址, 几何, kernel_cfg)` —— **多带了一个 `op_idx`**。
结果：

```
cm=7：87 个 tile → 去重后 33 种，重复次数分布 {1: 6, 3: 27}
⇒ 读起来像「27 个不同的拷贝各做了 3 遍」
```

**真相是「同一个拷贝被 33 个不同算子各做一遍」** —— 把 `op_idx` 去掉：

```
cm=7：87 个 tile → 去重后 **7 种**，重复次数分布 {1: 6, 81: 1}
⇒ 同一种 1×1×32 拷贝，执行了 81 次
```

**教训：身份判据里多带一个无关维度，会把一个巨大的重复拆成很多「看起来正常」的小组。**
`op_idx` 是「哪个算子在调用它」，不是「这次搬运是什么」——
**判定两个操作是否相同，只能用它真正作用的对象（源、目标、几何），不能带上调用者。**

（这与 docs/46 的教训是同一族：**名字/标签不是语义**。这里是**调用者不是身份**。）

## 2. 为什么运行时这么干（推测，标明是推测）

这个拷贝的形状是 `1×1×32`：**一个像素的 32 个通道**，源地址在 `0xfff0xxxx` 段
（和 docs/43 里那些 1×1×16 的 PPU tile 同段），那一带看起来是**每算子的参数/量表区**。

所以我的**推测**是：这是每个算子命令流里的「把默认参数块刷进固定暂存位」的样板动作，
运行时按算子逐个发出，**没有做去重**（因为目标地址固定，去重本该是显然的）。

⚠️ **这是推测，没有证据。** 有证据的只有：形状、地址、次数、以及「不可能产生新结果」。

## 3. 对「抬高二次开发上限」的意义（本轮最实在的一条）

| 杠杆 | 量级 | 依据 |
|---|---|---|
| 4–6 路并发 | 2.44–2.57× | docs/34 |
| **去掉冗余搬运** | **≥ 8~11%**（且**不需要改硬件、不需要加带宽**） | 本轮 |
| 减少「轮」数 | 3 核下 145 轮 × 22.3 µs = 3.23 ms，占 38% | docs/45（措辞见 docs/46） |
| DDR 定频 / 加带宽 / 改驱动 | 1.59× / ≈1.0× / ≈1.0× | docs/28/32/33 |

**「自己构建命令流」以前是一个方向，现在有了第一个具体靶子**：
把这条拷贝从 81 次降到 1 次，就能拿回 8~11% 的 NPU 时间。
而且这是**幂等的**（同源同目标），所以**不需要理解它在干什么**就能安全去掉 —— 这是最理想的一类优化。

## 4. 顺带修正 docs/46 的一个说法

docs/46 写的是「同一个琐碎算子**每核发一遍**」。本轮的精确数字是：

```
3 核 → 81 次 = 27 × 3
2 核 → 54 次 = 27 × 2
1 核 → 46 次（≠ 27 × 1）
```

⇒ 多核下确实是「27 个槽位 × 核数」，但**单核下是 46 次，不是 27 次**。
所以规则不是干净的「一核一份」，更像「27×核数」加一个与核数无关的余量。
**只有三个数据点，不硬下结论** —— 如实记为「27×核数（多核）／46（单核）」。

## 7. 教训（本轮新增）

1. **★ 判定「两个操作是否相同」，只能用它的作用对象，不能带调用者。**
   我把 `op_idx` 放进身份，于是「同一个拷贝做 81 次」被拆成「27 个拷贝各做 3 次」，
   读起来完全正常。**去掉无关维度，重复才现形。**
2. **★ 冗余要证明「幂等」才算冗余。** 我没有停在「看起来一样」，而是去查了
   「源地址有没有被写过」「目标地址的写是不是都来自这一次」——
   三条同时成立才能说「不可能产生新结果」。**「看起来重复」和「证明冗余」差一个量级。**
3. **推测要标出来。** §2 里我给了一个机制解释（每算子刷默认参数块），
   但明确写了「这是推测，没有证据」。有证据的只有形状、地址、次数、幂等性。
4. **最理想的优化是「不需要理解它就能安全去掉」的优化。** 这条拷贝正是如此 ——
   幂等 ⇒ 去掉不影响正确性。**在逆向工作中，优先找这种靶子。**

## 8. ⚠️ 一次没写进结论的过度解读（以及为什么被我自己拦下来）

追这条冗余时我顺手查了「这个目标地址有没有被读过」：

```
全扫所有寄存器（不做任何分类）：
  0xfff09d80（那条拷贝的目标）只出现在 1 个寄存器：0x6070（PPU 目标）—— 出现 81 次
  ⇒ 读侧寄存器（0x1070/0x1110/0x5018/0x701c…）里一次都没有
```

**这看起来是「死代码」——写了 81 次、从没人读，比「冗余」还严重。**
差一点就写进结论了。**但我加了一个对照，把它否掉了：**

```
对照：op82 的输出 0xfed83000（一个**确实被后续算子消费**的真实张量）
      也只出现在 1 个寄存器：0x4020（DPU 目标）
```

⇒ **「某个地址只出现在写地址寄存器里」是正常的**，因为消费者读它时用的地址表达式
（基址 + 偏移）**通常不等于写入时的那个值**。
**所以「读侧没出现这个值」根本不能推出「没人读它」。**

**结论：本篇只保留「幂等冗余」这个说法，撤回「死代码」这个解读。**

### 两条判据为什么一条成立、一条不成立

| 判据 | 成立? | 为什么 |
|---|---|---|
| 「源地址从未被写」 | ✅ | **写目标必须出现在写地址寄存器里**（`0x4020`/`0x6070`），而这两个寄存器里从来没有 `0xfff0a180`。这是**必要条件**，可以否定 |
| 「目标地址从未被读」 | ❌ | 读地址是**表达式**（基址+偏移），不要求等于写时的字面值。**不是必要条件**，不能否定 |

**教训：只有「必要条件」才能用来否定。** 「某值没出现在某类寄存器里」
在写侧是必要条件（能用来证明「没写过」），在读侧**不是**（不能用来证明「没读过」）。
**同一个句式，两个方向，一个有效一个无效。**
