# 42 · 流水重叠与片上缓冲复用：`WEIGHT_REUSE` 语义确证 + LLM 路径「零复用」的结构性后果

> 目标 ②「搞清 CORE 数据通路、流水级结构与各级缓冲、**流水重叠机制**」本轮推进一块。
>
> 做法：`CBUF_CON0@0x1040` 里两位从来没人解释过 —— `bit12 DATA_REUSE`、`bit13 WEIGHT_REUSE`。
> docs/36 只记录了「WEIGHT_REUSE 只在 40% 样本里置位、DATA_REUSE 从未置位」，
> 没回答**语义是什么**、**省了多少流量**、**省下来的流量换没换成时间**。
>
> 工具：`src/analysis/cbuf_reuse.py`（产物 `data/analysis/cbuf_reuse.txt`）

## 1. `WEIGHT_REUSE` 到底是什么：用「算子首个 tile」当强对照

这两位如果语义是「上一块的数据/权重还留在片上、这次不用重搬」，
那就有个**必须成立**的推论：

> **一个算子的第一个 tile 上，这两位必须为 0** —— 片上还什么都没有，无从复用。

实测（`python3 src/analysis/cbuf_reuse.py`）：

```
align1（cm=7，508 个可读 tile）
  算子『首个 tile』  (DATA_REUSE, WEIGHT_REUSE) = {(0,0): 63}
  算子『后续 tile』  (DATA_REUSE, WEIGHT_REUSE) = {(0,0): 313, (0,1): 132}
  ⇒ 首 tile 两位全 0：63/63   ★ 100%

dumps2（cm=1，468 个可读 tile）
  算子『首个 tile』  = {(0,0): 63}
  算子『后续 tile』  = {(0,0): 252, (0,1): 153}
  ⇒ 首 tile 两位全 0：63/63   ★ 100%
```

**两份独立抓取、各 63 个算子、0 个反例。** 这个对照是决定性的：不是「置位比例像什么」，
而是「有个位置物理上必须为 0，实测恰好全为 0」。

### 顺带结案两个字段

* **`DATA_REUSE` 厂商从未使用**（三份语料 0/508、0/468、0/13383）。
  ⇒ 特征图**从不**在 tile 之间留在片上。这与 docs/31 的结论一致
  （「读的确实就是写过的」—— 层间走 DRAM 往返，没有片上保留）。
* **`FC_DATA_BANK`（bit8-10）厂商从未使用**（连 `data/rkllm` 的 **13383 个 LLM tile** 都是 0）。
  docs/36 曾猜它是「FC/LLM 专用分区」。实测：**定义了、但运行时不用它**。
  一个字段就此结案 —— 不是我们没解出来，是**没人用**。

## 2. CBUF 是完全分区的，没有余量

```
DATA_BANK + WEIGHT_BANK 分布：
  align1 : {12: 508}       ← 100%
  dumps2 : {12: 468}       ← 100%
  rkllm  : {12: 13383}     ← 100%
```

CBUF 是 12 个 32 KB bank = **384 KB**（docs/36）。三份语料、14359 个 tile，
**每一次都是恰好 12** —— 运行时把整块 CBUF 分干用尽，一个 bank 都不留。
这条约束现在有了第三重独立确认（前两重：docs/36 的 655 样本、docs/38 的字段级验证）。

---

## 3. ★ bank 划分在 CNN 和 LLM 之间正好相反

| 负载 | 最集中的 `(DATA_BANK, WEIGHT_BANK)` | 解读 |
|---|---|---|
| CNN（`dumps2`） | **(11, 1)** 占 267/468 = 57% | 特征图驻留片上，**权重靠流** |
| LLM GEMM（`rkllm`） | **(1, 11)** 占 13239/13383 = 98.9% | 权重驻留片上，**特征只有 1 个 bank** |

这是一个很干净的结构证据：**`CBUF_CON0` 的 bank 划分不是固定架构，而是运行时按算子类型选的策略**。
CNN 的算术强度高（大特征图反复用同一批权重），所以把 bank 给特征；
LLM decode 的 GEMV 权重远大于激活（896×320 vs 1~6 个像素），所以把 bank 给权重。

---

## 4. ★★ LLM GEMM 路径的 `WEIGHT_REUSE` **恒为 0**

这是本轮最意外的一处：

```
rkllm（13383 个 tile，全部 op_idx=0）
  WEIGHT_REUSE 置位比例 = 0.000        ← 一个都没有
  『首个 tile』  = {(0,0): 1}
  『后续 tile』  = {(0,0): 13382}      ← 13382 个后续 tile，全部不复用
```

**同一个算子内连续 13382 个 tile，权重一次都没有留在片上复用。**
而 `data/rkllm` 里每个 tile 的权重是完整的 896×320 矩阵 = **286,720 字节**。

⇒ 每次提交（3 个 tile，形状无歧义）实际从 DRAM 搬的权重：

```
每个 tile 权重      = 896 × 320 = 286,720 B
每次提交 3 个 tile  = 860,160 B        ← 三个 tile 用的是**同一个**权重矩阵
每次提交 MAC        = 12 px × 896 × 320 = 3.44 M-MAC
⇒ 算术强度 = 3.44e6 / 860160 = 4.00 MAC/字节
```

**4 MAC/字节意味着什么：**

```
要在 1.024 T-MAC/s（单核标称峰值）上跑，需要 1.024e12 / 4.00 = 256 GB/s 的权重带宽。
实测本机 DDR2400 可达            = 23.84 GB/s（docs/32）
⇒ 结构天花板 = 23.84e9 × 4.00 = 95.3 G-MAC/s = **峰值算力的 9.3%**
实测                                 = 1.99e10 / 0.45124 s = 44.1 G-MAC/s
```

⇒ **LLM decode 路径在结构上不可能变成算力受限** —— 它的算术强度比「跑满算力所需」
低一个数量级以上。它的瓶颈在**权重搬运**（按当前零复用的构造），以及提交地板。

如果把 `WEIGHT_REUSE` 打开（每次提交只搬一次权重），权重带宽需求从
**8.60 GB/s 降到 2.87 GB/s**（按 100 µs/提交算），也就是 **3× 的流量削减**；
再考虑到相邻 token 的同一个 GEMM 用同一批权重，实际冗余度更高。

> ⚠️ **这一段是推理，不是实测。** 我们**不能**从外部改这个位（它由闭源 librknnrt 决定），
> 所以「打开 reuse 能快多少」没有实测数字。**这是本项目"自建命令流"的一个明确靶子**：
> 一个已经被寄存器证实的、3× 的流量冗余，就摆在 `CBUF_CON0` 的 bit13 上。

## 5. 权重流量对时间没有解释力 —— 一个可证伪的负结果

CNN 侧（`align1`，154 次提交）把「本次提交实际需要从 DRAM 搬的权重字节」
（按 `WEIGHT_REUSE` 逐 tile 折算）对实测 hw 时间回归：

```
hw ~ 需搬权重字节（含 reuse 效果）   R² = 0.0004   截距 145.9µs   斜率 −0.0099 ns/B
hw ~ 权重字节（忽略 reuse）          R² = 0.0007   截距 146.3µs   斜率 −0.0095 ns/B
hw ~ Σ MAC                       R² = 0.0035   截距 135.2µs   斜率  8.12e-5
hw ~ tile 数                      R² = 0.0155   截距 121.7µs   斜率  3992 ns/tile
```

**斜率近 0、甚至为负 ⇒ 权重 DRAM 流量对每次提交的耗时没有解释力。**

这个负结果有两个正面含义：

1. **权重搬运已经被藏在计算后面** —— 权重是靠 DMA 预取进 CBUF 的，DMA 与
   CNA/CORE/DPU 的乘法并行推进。**这就是「流水重叠」的直接证据**：
   如果搬运是串行的，流量降 20% 时间就该降。
2. 与 docs/32「不是带宽墙」相互印证：DDR 只用 26%，再往这条路上加带宽没有收益。

反过来它也给出一个**排除性结论**：

> **对 CNN 负载，「把 `WEIGHT_REUSE` 全打开」不是时间杠杆。**
> 它能省 20.5% 的权重流量（align1；dumps2 是 7.6%），但省下来的流量本来就不占时间。
>
> 但**对 LLM 负载相反** —— 那里不是「省一点流量」，而是「算术强度 4 MAC/B vs 需要 256 GB/s」
> 的结构性矛盾。同一个位，在两个负载上的价值完全不同。

## 6. 这对目标 ② 意味着什么

「流水重叠机制」现在有了**三个正向证据 + 一个负向证据**：

| 证据 | 内容 |
|---|---|
| ✅ `OP_ENABLE` 位图（docs/41 §5.3） | `0x1d`/`0x0d` 一次开火同时使能 CNA+CORE+DPU —— 四级**并行**处理不同数据 |
| ✅ `WEIGHT_REUSE` 语义（本篇 §1） | 权重在 tile 之间驻留 CBUF，跳过重搬 —— **跨 tile 的流水重叠**（双缓冲） |
| ✅ 段间 PC 链（docs/15/18） | 命令流按链指针串起来，下一段的配置可以边跑边下 |
| ✅ 权重流量与时间无关（本篇 §5） | 搬运被藏在计算后面 —— 重叠**实际发生了**，不是纸面能力 |
| ⛔ `DATA_REUSE` 从未使用 | 特征图**不**做跨 tile 保留，层间走 DRAM 往返 |

还缺的一块是 **stage 级的重叠度**（CNA 取数 / CORE 乘累加 / DPU 后处理各自的时间占比）。
那需要硬件计数器，而 RK3588 的驱动没有接线带宽计数器、寄存器又不能盲扫
（docs/29 的事故）。**这一块是本目标里唯一还没找到可行测量手段的部分**，
只能靠 §4 那种「按算术强度反推天花板」的间接办法。

## 7. 教训（本轮新增）

1. **强对照 > 比例。** 「WEIGHT_REUSE 在 26% 的样本里置位」几乎没有信息量；
   「**算子的第一个 tile 上必须为 0**，实测 63/63 成立」才是语义证明。
   **找那种「如果语义猜错了就不可能出现」的观测点。**
2. **一个字段「解不出来」和「没人用」是两件事。** `DATA_REUSE` 和 `FC_DATA_BANK`
   我们花了力气想解语义，实测是**厂商根本不用**。先把「用没用」查清楚，
   再决定值不值得解语义。
3. **同一个开关在不同负载上价值完全不同。** `WEIGHT_REUSE` 对 CNN 是「省 20%
   却不省时间」，对 LLM 是「3× 流量冗余 + 算术强度差一个数量级」。
   **结论必须绑定负载，不能绑定寄存器。**
4. **负结果要写下来。** §5 那个 R²=0.0004 的斜率，比再加一张相关图有用得多 ——
   它一次性排除了「加带宽」「开 reuse」两条优化路（对 CNN 而言），
   并且**反过来成了「流水重叠存在」的证据**。
