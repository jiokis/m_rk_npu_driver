## 一、★★★ 最重要的发现：DDR 被压在最低频率

### 1.1 现象

```
$ cat /sys/class/devfreq/dmc/governor      → dmc_ondemand
$ cat /sys/class/devfreq/dmc/cur_freq      → 534000000     ← 534 MHz
$ cat /sys/class/devfreq/dmc/max_freq      → 2400000000    ← 2400 MHz
```

**DDR 默认跑在 534 MHz，而它的最高档是 2400 MHz —— 4.5 倍差距。**

### 1.2 同进程内交替 A/B（消除其他变量）

```
dmc_ondemand  DMC= 534MHz  →  51.80 ms
performance   DMC=2400MHz  →  28.25 ms     ← 快 1.83×
dmc_ondemand  DMC=2400MHz  →  20.41 ms     ← governor 名改了但频率没降
performance   DMC=2400MHz  →  20.13 ms
```

**⇒ 决定性能的是「DDR 实际频率」，不是 governor 的名字。**
534MHz → 2400MHz 带来约 **2~2.5×** 的提升。

### 1.3 为什么

NPU 是**重度带宽受限**的：
- 特征图在 7.78 MB 与 8.28 MB 两块缓冲区之间来回（见 [docs/18](18-NPU结构-流水构建-指令集.md)）
- 每层都要读出特征、读权重、写回特征
- 算力（3×2 TOPS）远不是瓶颈，**内存搬运才是**

### 1.4 可行动结论

| 做法 | 效果 |
|---|---|
| `echo performance > /sys/class/devfreq/dmc/governor` | **实测约 2× 提升**（零成本） |
| 或在应用里用 `devfreq` 的提升接口 | 同上 |
| （根治）让模型**尽量留在片上** | 需要算子融合/分块策略，见 [docs/20](20-分块结构与并行粒度.md) |

**这是整个项目里性价比最高的一条优化 —— 一条 echo 命令换 2 倍。**

## 二、⚠️ 我的测量方法危机（必须记录）

### 2.1 同一个实验，四次结果差 2 倍

| core_mask | 第1轮 | 第2轮 | 第3轮 | 第4轮 |
|---|---|---|---|---|
| 1 | 44.8 | 56.5 | 52.2 | 37.6 |
| 3 | 42.8 | 72.9 | 61.3 | 73.0 |
| 7 | **25.5** | 33.8 | 42.6 | **55.0** |

**cm=7 从 25.5ms 到 55.0ms —— 我一度据此得出"三核 1.76×"，但那个数字不可靠。**

### 2.2 三个方法错误（逐条）

| 错误 | 后果 | 修正 |
|---|---|---|
| **没有钉死 NPU/DMC 频率** | DDR 在 534↔2400MHz 之间飘 → 结果差 2 倍 | 先 `performance` 钉死再测 |
| **顺序分组测量**（先跑完 cm=1 全部，再跑 cm=3…） | 时间漂移全部计入组间差异 | **交错测量**：每轮把各配置都跑一次 |
| **只测一两次就下结论** | 噪声被当成信号 | 20 轮交错 + 报中位数与四分位 |

### 2.3 用 `hw_elapse_time` 分离硬件时间与开销

驱动其实早就把每次提交的硬件耗时写回用户态（`rknpu_job.c:267`）：
```c
args->hw_elapse_time = job->hw_elapse_time;
job->hw_elapse_time  = ktime_sub(now, job->hw_commit_time);
```

于是写了 [src/probes/rknpu_submit_timer.c](../src/probes/rknpu_submit_timer.c)：
拦 `ioctl`、返回后读该字段 → **把「硬件真正干活」与「提交/调度开销」分开**。

**实测（钉频后）**：

| core_mask | 提交数/次推理 | 提交墙钟 | 提交硬件 | **提交开销占比** |
|---|---|---|---|---|
| 1 | 4 | 312 ms | 306 ms | **2.1%** |
| 3 | 77 | 322 ms | 285 ms | **11.4%** |
| 7 | 77 | 175 ms | 163 ms | **7.3%** |

**⇒ 提交开销只有 2~11%，远小于我在 [docs/24](24-调度逻辑解剖.md) 里估算的 42~62%。**
那条估算是**两点拟合出来的，是错的**。

> **教训**：两点拟合出来的参数不要当结论用。有现成的测量手段（`hw_elapse_time`）
> 就该先用它，而不是去拟合。

## 三、修正后的多核结论

**方法**：NPU 与 DMC 均钉在 performance，三配置**交错** 20 轮，报中位数。

| core_mask | 中位数 | 平均 | 最小 | Q1 | 加速 |
|---|---|---|---|---|---|
| 1（单核） | 26.46 | 30.22 | 22.67 | 26.29 | 1.00× |
| 3（双核） | 25.14 | 28.58 | 23.13 | 23.56 | **1.05×** |
| 7（三核） | 20.74 | 25.32 | 19.83 | 20.21 | **1.28×** |

### 与旧结论的对照

| | 旧（未钉频，顺序测） | **新（钉频，交错测）** |
|---|---|---|
| 双核加速 | 1.05× | **1.05×**（一致） |
| 三核加速 | 1.76× | **1.28×** |
| 提交开销 | 42~62%（估算） | **2~11%（实测）** |

**⇒ 三核的真实加速约 1.28×，不是 1.76×。**

### 为什么只有 1.28×（而不是 3×）

**带宽**。§1 已证明 NPU 重度带宽受限；三核并行不增加带宽，所以加速被带宽上限卡住。
这也解释了为什么 **双核完全无用**（1.05×）—— 一个核可能就接近带宽上限的一部分，
再加核无法线性扩展。

> 仍待解释：为什么双核比三核差这么多（1.05× vs 1.28×）。
> 候选：驱动在 `use_core_num==2` 与 `==3` 下的分片策略不同（见 [docs/24](24-调度逻辑解剖.md) §1.1 的 `+2` 索引怪癖）。
> 这需要一个专门的实验，我没有做。

## 四、这一轮真正学到的东西

| 学到的 | 具体 |
|---|---|
| **先钉频再测** | 否则 DDR 在 534↔2400 之间飘，结果差 2 倍 |
| **交错测量** | 消除时间漂移，比"多测几次"有效得多 |
| **优先找现成的测量手段** | `hw_elapse_time` 一直在那，用它就不用拟合 |
| **不要用两点拟合下结论** | 我在 docs/24 就是这么错的 |
| **别忽视系统级因素** | DDR governor 一条 echo = 2 倍性能，比调度优化大得多 |
