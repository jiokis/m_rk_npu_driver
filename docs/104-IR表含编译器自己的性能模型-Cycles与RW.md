## 1. ★ IR 表的完整列（之前只看了前几列）

```
ID  OpType  DataType  Target  InputShape  OutputShape  Cycles(DDR/NPU/Total)  RW(KB)  FullName
```

实例：

```
0  InputOperator  INT8  CPU  \                          (1,3,224,224)  0/0/0                0    InputOperator:input
1  ConvClip       INT8  NPU  (1,3,224,224),(32,3,3,3),(32)  (1,32,112,112)  23540/112896/112896  151  Conv:/features/.../Conv
2  MaxPool        INT8  NPU  (1,64,112,112)             (1,64,56,56)   0/0/0              784   MaxPool:/maxpool/MaxPool
3  ConvAddRelu    INT8  NPU  (1,64,56,56),(64,64,3,3),... (1,64,56,56) 27036/112896/112896  428  Conv:/layer1/.../Conv_ConvAddRelu
```

### 四个之前没注意的列

| 列 | 含义 | 价值 |
|---|---|---|
| **`Target`** | **CPU / NPU** | 哪些算子跑在 CPU 上（我抓命令流时看不到这些！） |
| **`Cycles(DDR/NPU/Total)`** | **编译器自己的周期估算** | ★ **一个现成的性能模型** |
| **`RW(KB)`** | 每算子读写量 | 流量可直接求和 |
| **`FullName`** | **原始 ONNX 节点名** | ★ 把 IR 算子映射回原图 |

**注意 `MaxPool` 的 `Cycles = 0/0/0` 但 `RW = 784 KB`** ——
**池化没有计算周期，却有可观的访存** ⇒ 与 docs/63「池化被实现成 7×7 depthwise」一致。

## 2. ★ 编译器自己的估算 vs 实测

（`ΣTotal` 周期 ÷ 1 GHz 换算成 ms）

```
模型             编译ms   实测ms    误差
resnet18         2.662   1.866   +42.7%
squeezenet1_0    2.769   3.123   -11.3%
googlenet        1.050   5.977   -82.4%   ← 严重低估
regnet_x_400mf   1.861   7.692   -75.8%   ← 严重低估
efficientnet_b0  4.045   9.294   -56.5%
```

**⇒ 编译器的估算与实测**同量级**，但同样**严重低估碎片化模型**（googlenet/regnet）。**

**⇒ 这与 docs/80 我的时序模型**失败的方式一模一样** ⇒
说明「缺失的分量」**不在逐算子周期模型里**。**

## 3. 加上提交地板：两种形式都试了

### 形式一：`编译周期 + 提交数 × 地板`（求和）

```
模型             编译ms   +地板   实测    原误差    加地板
resnet18         2.662   4.204  1.866  +42.7%  +125.3%  ❌
squeezenet1_0    2.769   5.673  3.123  -11.3%   +81.7%  ❌
googlenet        1.050   3.532  5.977  -82.4%   -40.9%  ✅改善
regnet_x_400mf   1.861   8.449  7.692  -75.8%    +9.8%  ✅大改善
efficientnet_b0  4.045   9.457  9.294  -56.5%    +1.8%  ✅大改善
```

**⇒ 对碎片化模型（efficientnet/regnet）**大改善**，但对已经准的（resnet18/squeezenet）**变差**
⇒ 说明**编译器的周期估算里已经含了部分地板成分**。**

### 形式二：`max(编译周期, 提交数 × 地板)`

```
模型             编译ms   地板ms   max     实测    原误差   max误差
resnet18         2.662   1.542   2.662   1.866  +42.7%  +42.7%
squeezenet1_0    2.769   2.904   2.904   3.123  -11.3%   -7.0%  ✅
googlenet        1.050   2.482   2.482   5.977  -82.4%  -58.5%  ✅改善
regnet_x_400mf   1.861   6.588   6.588   7.692  -75.8%  -14.4%  ✅大改善
efficientnet_b0  4.045   5.412   5.412   9.294  -56.5%  -41.8%  ✅改善
```

**⇒ `max` 形式 4/5 改善，且 `regnet` 从 −75.8% 收到 **−14.4%**（目前对该模型最好的预测）。
但 `resnet18` 仍 +42.7%、`googlenet` 仍 −58.5%。**

**⇒ 两种形式都不是最终答案，但 `max` 形式明显更好，且它给了 `regnet` 一个可用的预测。**

## 4. ⚠️ 一个卡点：IR 表**只在流水线末尾打印一次**

```
IR 表出现 7 次（= 7 个成功构建的模型各一次）
每次都在 `end: rknn::RKNNModelExportPass` 之后
pass 的 start/end 紧挨着，中间**不打印 IR 表**
```

**⇒ 从日志**看不到 `RKNNTilingPass` 前后的差异** ⇒ 要观察切分过程**必须 hook**。**

## 5. 教训（本轮新增）

1. **★★★ 表格的**列**比行更有价值。** 我看了这个 IR 表好几次（docs/100/101/102），
   但只用了前几列（OpType/Shape）。**这轮才发现还有 `Target` / `Cycles` / `RW` / `FullName` 四列**
   —— 其中 `Cycles` 是**编译器自己的性能模型**。
   **读一张表时，先把表头读完。**
2. **★★ 编译器自己的估算也低估碎片化模型 —— 而且低估的方式和我一样。**
   这说明**缺失的分量不在「逐算子周期」里**，而在**算子之间**（提交/同步开销）。
   **两个独立的模型犯同样的错，是对「错误位置」的强指示。**
3. **★ 「已经准的部分变差」是模型形式错误的信号。** 求和形式让 resnet18 从 +43% 变成 +125%
   —— **一个修正让原本准的变差，说明形式错了**（这与 docs/81 的教训同族）。
