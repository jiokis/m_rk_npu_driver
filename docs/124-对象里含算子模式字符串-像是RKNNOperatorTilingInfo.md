# 124 · ★★★ 断点处对象里含**算子模式字符串** —— 像是 `rknn::RKNNOperatorTilingInfo`

> 接 [docs/123](123-在断点处dump到pass对象的内部结构.md)（dump 到内部结构）。
> 本轮做「入口 vs 返回」对比 —— **对象没变**，但**看清了它装的是什么**。

---

## 1. 方法：`finish` 到返回，对比同一对象

```
入口 this=0x64eec80
  … 20 个 quadword …
finish（跑到返回）
返回后 同一对象
  … 20 个 quadword，**与入口完全相同** …
```

**⇒ 这个函数**不修改**该对象。**
**⇒ 说明它是「查询/判定」类方法（或对象是只读描述符），而**被修改的东西在参数里**（Module/IR）。**

---

## 2. ★★★ 但 dump 看清了对象装的是什么

```
0x64eec90:  0x0                  0x6d5f747500000000
                                  ↑ 字节 75 74 5f 6d = "ut_m"（某个长名字的一部分，SSO 短字符串）
0x64eecd0:  0x0                  0x0000000000000081   ← 129
0x64eecf0:  0x0000000000000020   0x0000000000000030   ← 32, 48
0x64eed10:  0x00000000ffffffff   0x00000000766e6f43
                                  ↑ 字节 43 6f 6e 76 = **"Conv"** ★★★
```

**⇒ 对象里存着**字符串**：`"Conv"`（和 `"ut_m"` 片段）—— 这是**算子模式名**。**

### 与 docs/105 的命名对上

docs/105 从 RTTI 里提取到 **`rknn::RKNNOperatorTilingInfo`** ——
一个「承载 tiling 结果的数据结构」。

**⇒ 本轮的观测（对象里含算子模式字符串 + 若干数值参数）与这个名字**一致**：
它很可能是「某个算子的 tiling 描述」（模式名 + 尺寸/对齐参数）。**

⚠️ **仍是「像是」，不是「确认」** —— 要确认需读 `RKNNOperatorTilingInfo` 的 RTTI 并比对其 vtable。

---

## 3. 数值参数的线索

```
0x81 = 129
0x20 = 32     ← 可能是对齐宽度（C2=16 的倍数？或 32）
0x30 = 48
0xffffffff = -1   ← 「未设置」的哨兵值
```

**⇒ `0x20 = 32` 值得注意**：docs/44 记过「out_ch 对齐到 32」，而 docs/100 的 `NC1HWC2` 给出 `C2=16`。
**两个数（16 与 32）都出现过 ⇒ 需要分别对应到「输入通道对齐」与「输出通道对齐」。**

## 4. 下一步（更具体了）

**#1 最便宜且最有价值**：`python3 src/compiler/rtti_find.py RKNNOperatorTilingInfo` ——

⚠️ 但要注意：**`0x1e090d0` 是 `RKNNTilingPass` 的 vtable**（docs/120/122 已双重验证）。
**所以本轮 dump 的对象如果是 `RKNNOperatorTilingInfo`，它的 vtable 应该是**另一个**地址** ——
**这本身就是一个可检验的预测。**

## 5. 教训（本轮新增）

1. **★★★ 「对象没变」也是结论。** 我本来期待「入口 vs 返回有差异」；
   **结果完全相同 ⇒ 立刻推断出「被修改的是参数，不是 this」** ——
   这**直接指向下一步该看哪里**（`rsi` 而不是 `rdi`）。
   **否定的观测同样能定位方向。**
2. **★★ dump 里的**字符串**比数字好认得多。** 一堆十六进制里，`0x766e6f43` 一眼就是 `"Conv"`；
   **在 dump 里先找可打印 ASCII，能快速建立「这是什么对象」的直觉。**
3. **★ 我做了一个**可检验的预测**（若对象是 `RKNNOperatorTilingInfo`，其 vtable ≠ `0x1e090d0`）。**
   这比「像是」强 —— **预测被证伪也是有价值的结论。**
