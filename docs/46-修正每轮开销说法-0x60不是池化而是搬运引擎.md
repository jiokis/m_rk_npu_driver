## 1. ★ 推翻了「0x60 = 池化」这个标签

`OP_ENABLE` 位图（`0x0081/0x0008`）我们一直这样读：

```
0x1d = CNA|CORE|DPU|DPU_RDMA   → 卷积
0x0d = CNA|CORE|DPU            → LLM GEMM（docs/41 新观测）
0x18 = DPU|DPU_RDMA            → 逐元素/激活
0x60 = PPU|PPU_RDMA            → 「池化」        ← 这个标签是错的
```

`python3 src/analysis/ppu_path.py`：

```
cm=7（3 核）：`0x60` tile 87 个，涉及 33 个算子
    (in_h, in_ch, out_w, out_ch, kernel_cfg) 分布：
      (1, 32, 1, 32, 0)      × 81   ← 退化的 1×1×32 拷贝
      (20, 256, 20, 256, 514) ×  6   ← 真做了核（2×2 核，stride 从 cfg 解出）
```

**93% 的 `0x60` tile 是「把一个像素的 32 个通道搬一遍」**（`in_height=1, out_width=1,
`in_channel = out_channel = 32`，`POOLING_KERNEL_CFG = 0`）。
这是**通道切片 / concat 前的拷贝**，不是池化。

### 这条为什么值得单独写

这个标签是从**位图的名字**推出来的（`PPU` 在 NVDLA 术语里是 pooling unit），
**语义从来没有被验证过**，然后它一路被用进了 docs/41/43/45 的表格里
（「19 个纯 PPU 算子占了 258 个 tile」）。

**教训**：位图告诉你「哪几级被使能了」，**不告诉你「这一级在干什么」**。
从名字外推到功能，和从偏移外推到字段语义，是同一种错误 —— 后者我上一轮刚栽过一次
（docs/36 的「39 个未定义寄存器」）。

## 2. ★ 这些提交是最纯的地板

一个 1×1×32 拷贝 = **32 B 读 + 32 B 写 = 64 字节**。实测：

| 配置 | 零算术量提交 | 中位 hw | 每次搬运 |
|---|---|---|---|
| cm=7（3 核） | 126 | **65.0 µs** | 64 B |
| cm=3（2 核） | 162 | **174.7 µs** | 64 B |

⇒ **搬 64 字节要 65 µs。地板完全不是数据量撑起来的。**
这是比 docs/43 那次更好的地板证据：那次是「零 MAC 但仍有特征图读写」，
这次是**连数据量都小到可以忽略**（64 B），所以 hw 就是纯粹的提交/轮开销。

## 3. ★ 拷贝 tile 数随核数放大 —— 多核在这条路上是「重复」

| 配置 | 27 个拷贝算子 → tile 数 | 6 个真核算子 → tile 数 |
|---|---|---|
| cm=7（3 核） | **3 个/算子 = 81** | 1 个/算子 = 6 |
| cm=3（2 核） | **2 个/算子 = 54** | 1 个/算子 = 6 |
| cm=1（1 核） | 46 个（25 个算子 2 个 + 8 个算子 1 个） | 12 个 |

**同一个琐碎算子，有几个核就发几遍**（3 核 3 遍、2 核 2 遍）。
而每个 tile 的几何**完全相同**（都是 1×1×32）——
所以这不是「把工作切开并行」，是**同一个拷贝被重复执行**。

这与 docs/43 那个「单核 ΣMAC 是 3 核 1.80×」的异常**形状相同、方向相反**：
* 拷贝算子：核越多，重复越多（3 核 3 份）
* 卷积算子：核越少，tile 越多（cm=1 编程了 1.5× 更多的不同 tile 配置）

⇒ **运行时的分块既不「与核数无关」，也不「总是按核数并行」。** 两类算子走两条不同的策略。

## 4. ⚠️ 修正 docs/45：「每轮同步开销」是恒等式，不是测量

docs/45 给出 SYNC = 1.5 / 22.3 / 36.7 µs/轮，并把它解释成「多核每轮的同步代价」。
本轮用两种办法检验这个说法：

### 4.1 支持的部分：残差**确实**随轮数增长

用**零算术量提交**（工作量 = 0，hw 就是纯开销）按轮数分组：

| 配置 | 1 轮 | 2 轮 | 增量 |
|---|---|---|---|
| cm=7 | 52.8 µs（n=108） | 155.0 µs（n=18） | **+102.2 µs/轮** |
| cm=3 | 137.4 µs（n=90） | 188.4 µs（n=72） | **+51.0 µs/轮** |

⇒ **「有每轮分量」这件事成立**，docs/45 的方向是对的。
而且 `rounds` 是**最好的单特征预测子**（per-submit hw 回归）：
cm=7 R² = 0.147、cm=3 R² = **0.412**，斜率 21.6 / 32.1 µs/轮
（对比：`macs` R² 0.100/0.220，`wsize0` R² 0.002/0.074 —— 权重字节**没有解释力**）。

### 4.2 不支持的部分：它**不是固定常数**

**同一进程内交错 A/B**（排除跨进程与热漂移），零算术量提交：

```
3 核：28 个样本，中位 89.0 µs
2 核：144 个样本，中位 138.0 µs      ← 核更少，反而更慢
```

而两者的 tile 几何**完全相同**（都是 1×1×32），2 核的 tile 数还更少（2 vs 3）。

⇒ **docs/45 里那些 SYNC 数字是「总残差 ÷ 轮数」算出来的恒等式**，
不是对「每轮开销」的独立测量。**这个区别很重要**：
恒等式不能用来预测另一个配置，测量可以。

### 4.3 修正后的说法

> **提交耗时里有一个「随轮数增长」的分量，但它的大小随核数变化**
> （1 轮零算术量提交：3 核 89.0 µs / 2 核 138.0 µs），
> **不是一个可以跨配置搬运的硬件常数。**
> `rounds` 仍是目前最好的单变量预测子，但只限于**同一配置内**。

## 5. 还没解释的（如实记录）

⛔ **为什么 2 核的零算术量提交比 3 核慢**（138.0 vs 89.0 µs，同进程交错，
几何相同、tile 数还更少）。三个候选，都没有证据：
1. 提交的 `core_mask` 本身影响驱动侧派发代价（`0x3` vs `0x7`）；
2. 2 核时每个核拿到的 tile 序列不同，同步点更多；
3. 我的「零算术量提交」签名按 `(位置, task_start, n)` 匹配，2 核下可能匹配到了
   结构相似但不同的提交。

## 6. 教训（本轮新增）

1. **★ 位图的名字 ≠ 位图的功能。** `PPU` 在 NVDLA 术语里是 pooling unit，
   于是我们把它读成「池化」并用了四轮文档。实测：93% 是通道拷贝。
   **凡是「从名字推出来的语义」，都要有一个独立的验证** ——
   这和上一轮「从偏移推字段」是同一类错误。
2. **★ 区分「恒等式」和「测量」。** `SYNC = 残差 / 轮数` 是定义，不是发现。
   我当时把它写成了「每轮同步开销」，读起来像测出来的 —— **这是措辞上的过度声称**。
   判据：**这个量能不能用来预测另一个没参与计算的配置？** 不能就是恒等式。
3. **★ 一个异常换个角度就是另一条线索。** docs/43 的「单核 tile 更多」和本轮的
   「多核拷贝重复」是同一件事的两面：**运行时的分块策略按算子类型分叉**。
   上一轮我把它当成「未解释的异常」，这一轮它变成了一个结构性结论。
4. **零工作量的样本要挑「连数据量都可忽略」的。** docs/43 的零 MAC 提交仍在搬特征图；
   本轮找到的 1×1×32 拷贝只搬 64 字节 —— **这才是最纯的地板**。

## ⚠️ 补充与修正（由 [docs/47](47-命令流里可证的冗余-同一个32字节拷贝执行81遍.md) 给出）

**§3「拷贝 tile 数随核数放大」的精确数字要改。** 本篇按 `op_idx` 分组，得到
「27 个拷贝算子 → 3 核 81 tile / 2 核 54 tile」；**去掉 `op_idx` 之后真相更强**：

```
整个模型里只有 7 种搬运操作。其中一种是退化的 1×1×32 拷贝
  src=0xfff0a180 → dst=0xfff09d80
它每次推理被执行 81 遍（3 核）/ 54 遍（2 核）/ 46 遍（1 核）。
```

判据是硬的：81 个 tile 的源/目标/几何全同、**源地址整趟 0 次写**、
目标地址的每一次写都来自这同一次拷贝 ⇒ **不可能产生新结果，是纯冗余**。

⇒ 所以「每核发一遍」的说法要改成：**同一个拷贝被发了 81 次**（多核下 ≈ 27×核数，
单核 46 次）。**这不是「多核重复」，是运行时根本没有对这条样板拷贝做去重。**

时间上：纯搬运提交占 **8.3%（3 核）/ 11.2%（2 核）**，是**下界**。
