## 1. ★ 卡点解开：`can_fuse` 的**正确用法**

```python
can_fuse(node, node2, relu=False, quant_tab={})
```

**关键是 `relu` 参数** —— 融合 Conv 与其后的 Relu 时**必须显式传 `relu=True`**：

```
can_fuse(conv, relu)                = False      ← 不传 relu
can_fuse(conv, relu, relu=True)     = True       ← ★ 正确用法
can_fuse(relu, flat)                = False
can_fuse(flat, fc)                  = False
can_fuse(conv, flat)                = False
```

**⇒ 判定**准确**：只对「Conv + Relu」这一对返回 True。**

节点对象从 `m.node` 取（`{n.name: n for n in m.node}`），不需要额外的访问器。

## 2. 真实模型上的结果

```
模型                  节点   可融合对   融合比   实测提交
mnasnet0_5             99      35     35.7%      3
resnet18               49      17     35.4%      5
densenet121           372     121     32.6%    183
regnet_x_400mf        163      67     41.4%    113
efficientnet_b0       239       0      0.0%     88   ← ★
```

### ★ `efficientnet_b0` 的可融合对是 **0**

**239 个节点里没有一对能融合** ⇒ 与它「88 次提交、`tile/提交` 只有 3.6（最低）」
高度一致 —— **它的碎片化有了直接解释：图里根本没有可融合的结构。**

### ⚠️ 但「融合比」与提交数**不是线性关系**

`mnasnet0_5`（35.7% → 3 次提交）与 `regnet_x_400mf`（41.4% → 113 次提交）
—— **融合比相近，提交数差 38 倍。**

**⇒ `can_fuse` 是**判定工具**，不是**预测公式**。
它给出「哪一对能融合」，但「融合了之后怎么打包成提交」是**另一层**（编译器的 tiling/packing）。**

**⇒ 这正好对上了 docs/95 找到的 `hardware_rules`（12 条 tiling 规则）——
`can_fuse` 管「融合」，`hardware_rules` 管「切分」，两层合起来才决定提交数。**

## 5. 教训（本轮新增）

1. **★★★ 卡在「接口找不到」时，去读**函数签名里的参数**，而不是换接口。**
   我试了 `can_fuse(a,b)`、`can_fuse(int)`、换节点对象来源 —— 全都失败。
   **真正的答案是签名里那个 `relu=False` 参数**：它要求调用者**声明**「我在融合一个 Relu」。
   **签名里的每个参数都是一条使用说明。**
2. **★ 拿到判定工具 ≠ 拿到预测公式。** `can_fuse` 立刻可用，但融合比与提交数不成线性
   （35.7%→3 vs 41.4%→113）。**不要因为工具能跑就假设它直接回答了大问题** ——
   它回答的是「哪一对能融合」，不是「提交数是多少」。
3. **★ 两层机制要分开找。** `can_fuse`（融合）与 `hardware_rules`（切分）是两层；
   我之前 20 轮把它们当成一个问题在找。**拆成两层后，每层都有对应的工具。**
