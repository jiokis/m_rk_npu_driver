# 138 · **负结果**：tensor 地址链**不能**揭示段边界（并修正 docs/134 的一处外推）

> 接 [docs/137](137-运行侧算子数等于IR表NPU算子数-段结构反映块结构.md) §5 #1 的判据。
> 结论是**否定的** —— 而且顺带修正了 docs/134 里一条我外推过的说法。

---

## 1. 判据与做法

**待检假设**：「段边界 = 缓冲复用边界」⇒ 段边界两侧的 tensor 地址应出现**不连续跳变**。

做法（9 个模型全做，regcmd 全量拷回）：
1. 按 `(submit, task)` 排序所有 task
2. 每个 task 取两个地址寄存器：`CNA(513).4368`（输入）与 `DPU_RDMA(8193).20512`（输出）
3. 算相邻 task 的 `下一输入 − 上一输出`
4. **按「是否跨 submit 边界」分成两组**，比较两组的差值分布

---

## 2. ★★★ 结果：**不成立**

| 模型 | 段内差值（众数） | 跨界差值（众数） | 段内首位占比 |
|---|---|---|---|
| resnet18 | `1024×13, 512×11` | `512×2, 1623296×1` | 25% |
| squeezenet1_0 | `512×13, 256×11` | `256×1, −1375488×1` | 25% |
| mnasnet0_5 | `512×35, 256×27` | `37120×1, 1536×1` | 23% |
| mobilenet_v2 | `1536×21, 3072×17` | `103680×1, 2560×1` | 14% |
| googlenet | `1024×8, 19200×7` | `−384×2, 19200×2` | 6% |
| shufflenet_v2_x0_5 | `512×59, 256×17` | `512×14, 256×2` | 56% |
| efficientnet_b0 | `−320×3, −4608×2` | `3507648×1, −320×1` | 10% |
| regnet_x_400mf | `256×1039, 3328×30` | `256×35, 7680×1` | 93% |
| densenet121 | `−3917312×3, −3893760×3` | `−4014592×1, −3772928×1` | 1% |

**⇒ 只有 2/9 个模型「段内差值集中」（shufflenet 56%、regnet 93%），其余 7 个段内本身就散。**
**⇒ 跨界的差值分布与段内**没有可区分**的特征。**

**⇒ 「段边界 = 缓冲复用边界（可由 tensor 地址识别）」这条**不成立**。**

## 3. ★★★ 顺带修正 docs/134 的一处**外推**

[docs/134](134-每个task映射回算子-模型被复制3份每核一份权重.md) §1 我写过：

> `CNA(513).4368`（输入张量地址）随 task 单调递增，且约等于上一个 task 的 RDMA 输出地址（差 512）
> ⇒ **地址链独立印证了算子顺序**

**现在全量看：**

| resnet18 的「下一输入 − 上一输出」分布 | 次数 |
|---|---|
| 512 | 13 |
| 1024 | **13** |
| 2048 | 5 |
| 其余各种值 | 42 |

**⇒ 差 512 只占 13/73 ≈ 18%，不是普遍规律。**
**⇒ 我当时只看了**前 8 对**（112/56 那两段恰好都是 512），就写成了「地址链」。**

**⚠️ 修正：docs/134 §1 的「地址链」应改为「前若干个 task 的地址恰好相邻；
   全量看差值分布很宽（512/1024/2048/…，都是 256 的倍数）」。**
**⇒ 这不影响 docs/134 的**主要结论**（3 份副本、权重不同输入相同 —— 那条被 docs/136 修正为 surface），
   但「地址链」这个**论据**要撤掉。**

## 4. 这个负结果说明什么

**⇒ 段边界**不是**由 tensor 地址（缓冲布局）直接标记的。**
**⇒ 结合 docs/136/137 已知的三点：**

1. 提交划分**依赖 `core_mask`**（1 核 1 个提交、2 核 5 个、3 核 5 个）
2. task 列表由**运行期**生成（`task_number` ≠ 核数 × 算子数）
3. 段结构**跟着模型的块结构走**（docs/137 §2 的序列规律）

**⇒ 三条合起来指向同一个结论：**
**「切段」是 `librknnrt` 的**调度器**在 `init_runtime(core_mask=...)` 时做的决策，
   它既不看（我能看到的）tensor 地址，也不由编译器固定。**

**⇒ 所以目标②的正题应该是：**
**对 **`librknnrt`（板子上的运行库）** 的调度器建模，而不是继续在 `librknnc`（编译器）里找。**

## 5. 下一步（新方向，可检验）

| # | 动作 | 判据 |
|---|---|---|
| 1 | **在板子上看 `librknnrt.so` 是否也带 RTTI/符号** | 与 `librknnc` 同样的手段（`src/compiler/rtti_find.py` 可复用，改 SO 路径） |
| 2 | 找调度器相关符号（如 `task`/`schedule`/`subgraph`） | 有符号就能下断点看决策 |
| 3 | **换 `core_mask` 抓 `tasks_*.bin` 更多组合**（0/auto、0x3、0x5、0x6） | 逼出「核数 → 段划分」的映射表；纯黑盒也能建表 |
| 4 | 把段结构与**内存占用**对照（IR 表的 `RW(KB)` 列） | 若段边界处 RW 累积跨过某个阈值 ⇒ 内存约束驱动 |

**#3 是最便宜、且**不依赖任何逆向**的路子**：黑盒建表（模型 × core_mask → 段划分）。
**#1 是最有上限的路子**：若 `librknnrt` 有符号，调度规则可以直接读。
