> 接 [docs/126](126-编译器骨架是ONNC-全部67个pass一次枚举完.md)。
> docs/126 §4 给出了「用 vptr 在堆里找回非多态对象」的方法；

## 1. ★★★★ 为什么在**析构器**上读

`RKNNOperatorTilingInfo` 由 `make_shared` 管理，销毁时走控制块的 `_M_dispose`
= 库内偏移 **`0x391510`**（docs/126 §3 已由反汇编判定）。

**⇒ 在 `0x391510` 下断，`rdi` = 控制块 ⇒ 对象就在 `rdi+0x10`。**
**⇒ 而 `0x391510` 的第一件事就是遍历那个「tile 表」⇒ 表头就在 `rdi+0x58`。**

**这条比堆扫描好**：不用扫 1.4 GiB 内存，而且**每个对象必然经过这里**（一个不漏）。

## 2. ★★★★★ 反汇编 `0x391510`：**tile 记录的结构直接写在析构代码里**

```asm
391510: push %r12 ; mov %rdi,%r12 ; push %rbp ; push %rbx ; sub $0x10,%rsp
39151b: mov 0x60(%rdi),%rbx        ; rbx = 表尾
39151f: mov 0x58(%rdi),%rbp        ; rbp = 表头     ← std::vector 头在 +0x58
391523: cmp %rbp,%rbx ; je done
391530: mov 0x130(%rbp),%rdi ; ... call _ZdlPv     ; 删 +0x130
391541: mov 0x118(%rbp),%rdi ; ... call _ZdlPv     ; 删 +0x118
391552: mov 0x100(%rbp),%rdi ; ...                 ; 删 +0x100
391563: mov 0xe8(%rbp),%rdi  ; ...
391574: mov 0xd0(%rbp),%rdi  ; ...
391585: mov 0xb8(%rbp),%rdi  ; ...
391596: mov 0xa0(%rbp),%rdi  ; ...
3915a7: mov 0x88(%rbp),%rdi  ; ...
3915b8: mov 0x70(%rbp),%rdi  ; ...
3915c6: mov 0x58(%rbp),%rdi  ; ...
3915d4: mov 0x40(%rbp),%rdi  ; 删 +0x40
3915e2: add $0x1a8,%rbp      ; ★★★ 元素**步长 = 0x1a8 = 424 字节**
3915e9: cmp %rbp,%rbx ; jne 391530
3915f2: mov 0x58(%r12),%rbp ; ... call _ZdlPv      ; 最后删表本身
```

### 结构（**从析构代码读出来的，不是猜的**）

```
RKNNOperatorTilingInfo
  +0x58: std::vector<Tile>            begin / end / cap   （对象内偏移；控制块视角 +0x58）
    Tile = 0x1a8 = 424 字节
      +0x00 .. +0x3f   头部 8 个 quadword（数值字段）
      +0x40 +0x18*k    k = 0..10 ⇒ **11 个 std::vector**（每个 24 字节：begin/end/cap）
      偏移依次 0x40 0x58 0x70 0x88 0xa0 0xb8 0xd0 0xe8 0x100 0x118 0x130
      +0x148 .. +0x1a7  尾部 0x60 字节
```

**⇒ 「一个算子一张 tile 表，表里每个 tile 带 11 个子向量」。**
**⇒ tile 个数 = `(end − begin) / 0x1a8`。**

## 3. ★★★ 实测：一个 depthwise conv 模型（`ab_dw.onnx`）

```
3 个 RKNNOperatorTilingInfo 对象，tile 数分别 = 3 / 6 / 6

对象 #1（3 tiles）:
  tile[0] 头部: 0x100000001 0x0 0x100000000 0x1 0x0 0x1 0x100000000 0x0
  tile[1] 头部: 0x100000001 0x0 0x100000000 0x1 0x0 0x1 0x100000000 0x7fff00000000
  tile[2] 头部: 0x100000001 0x0 0x100000000 0x1 0x0 0x1 0x100000000 0x0

对象 #2（6 tiles）:
  tile[0] 头部: 0x100000001 0x0 0x100000000 0x1 0x0 0x1 0x100000000 0x0
  tile[1] 头部: 0x100000001 0x0 0x200000000 0x1 0x0 0x2 0x100000000 0x0
                 ↑ 第 3 个 u32 从 1 变 2          ↑ 第 6 个 u32 从 1 变 2
```

**⇒ 头部里有一对随 tile 序号递增的 u32**（对象 #2 里 tile[1] 是 2，tile[0] 是 1）
   ⇒ 很可能是 **tile 的序号 / 分组号**。

**每个 tile 的 11 个子向量（实测尺寸）**：

| 子向量 | 偏移 | 实测 diff | 推测 |
|---|---|---|---|
| vec0/1/2 | 0x40/0x58/0x70 | `0x10` | 1 个 16 字节元素（或 2 个 8 字节） |
| vec3 | 0x88 | `0x100` | 2 个 0x80 或 4 个 0x40 |
| vec4/5/6 | 0xa0/0xb8/0xd0 | `0x10` | 同 vec0 |
| vec7 | 0xe8 | `0x100` | 同 vec3 |
| vec8/9 | 0x100/0x118 | `0x8` | 1 个 u64 |
| vec10 | 0x130 | `0x10` | 同 vec0 |

（**注意：这些是「析构时」的尺寸**；`std::vector` 的 cap 往往大于 size，
 但这里 begin/end 是 size ⇒ 上面 diff 就是 size。子向量**元素类型未知**，此处只记尺寸。）

**★★ 关键猜想（待验证）：`3` = RK3588 的 3 个 NPU core。**

   ⇒ 这正好对上 `RKNNMultiSurfacePass`（docs/126 §2）。

⚠️ **这是猜想，不是结论。** 判定方法写在 §5。

## 6. 教训（本轮新增）

1. **★★★ 析构函数是「结构说明书」。** 我不需要猜 `Tile` 的布局 ——
   **编译器为了销毁它，必须把每个成员都写出来**（11 个 `delete`，步长 `0x1a8`）。
   **⇒ 想知道一个结构有哪些成员，先看它的析构函数。**
2. **★★★ 找「读数点」优先于「扫内存」。** docs/126 §4 的堆扫描能用，
   但**析构器是一个必然经过、且直接给出结构布局的点** —— 更省、更全、更准。
   **⇒ 有多个观测手段时，先挑「语义上必经」的那个。**
3. **★ 我明确标了「这是猜想」。** tile 数 = 3 对上 3 个 core 很诱人，
   但**诱人正是危险信号**（本项目 docs/101 就是被一个「诱人的因果链」误导）。
   **⇒ 猜想必须附判据（§5 #2）。**
4. **★ 数据先记全，再谈规律。** §4 的表只有 5 个模型，
   **列出来是为了让下轮的对照有基准，而不是为了现在就下结论。**
