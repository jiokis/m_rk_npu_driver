# 30 · DRAM 流量模型的交叉验证，与「67% 往返」的修正

> 承接 docs/29。上轮用**跨度法**（相邻 tile 地址差）量出单次推理 ≥143.86 MB，
> 并据此推断"67% 是 DPU→DPU_RDMA 的同一趟往返"。
>
> 本轮做了一件必须做的事：**用第二种独立方法交叉验证**。结论是流量总量可信，
> **但那个 67% 是错的** —— 严格逐地址配对只有 11%。
>
> ⚠️ **本篇第三节与第五节的"优化方向修正"已被 [docs/31](31-撤回方向修正-读的确实就是写过的.md) 撤回。**
> 本篇据"91% 的读与写地址不相等"推断"存在大量搬运/重排浪费"，但那是**判据过严**的假象：
> 生产者和消费者的 tiling 粒度不同（例如 op0 的 DPU 输出 19 tile 步长 0x15400、
> op1 的 CNA 输入 5 tile 步长 0x55000，**基址却完全相同**），于是"地址相等"判据失效。
> 改用**区间重叠**判据后，**95.2% 的读流量落在生产者写过的区间内** —— 不存在额外搬运。
>
> 本篇其余内容（流量交叉验证 160.89 MB、严格配对的 9.5%、非纯带宽受限）仍然成立。

## 一、为什么要交叉验证：一个自相矛盾的数字

docs/29 里跨度法给出的明细中，最刺眼的一行是：

```
DPU_RDMA 0x5018   缓冲#4(7.42MB)   读 63.53 MB   段数 95   算子 44
```

`0x5018` 总共只有 **39 个不同地址**，却算出读了 **63.53 MB** —— 平均每个地址 1.63 MB。
而容纳它的缓冲区只有 7.78 MB。

一开始我把它当成 bug（"39 个 1.63MB 的 tile 装不进 7.78MB"），加了容量校验。
但校验加上去总量几乎没变（143.86 → 142.68 MB），说明**这个数字其实可以是对的**：

> **缓冲区会被反复复用。** 44 个算子轮流用同一个 7.78 MB 缓冲区，每个算子用其中
> 约 1.4 MB 的不同区域 —— 那么"单次推理经过该缓冲区的总流量"当然可以远超缓冲区容量。
> 63.53 MB 是**流量**，不是**占用**。我一开始把这两个概念混了。

这提醒我不能靠"看起来不合理"来否定一个数字，**得用第二种方法独立算一遍**。

## 二、第二种方法：只用「确证」字段算，不用任何启发式

跨度法依赖"相邻地址步长"这个启发式（在地址稀疏时会失真）。所以换一个**完全不依赖地址**的算法：

```
CORE 0x3014 低16 = 输出宽−1      （docs/17 确证级：319/159/79/39/19 ↔ 320/160/80/40/20）
CORE 0x3018     = 输出通道−1     （docs/17 确证级：31/63/127/255/511 ↔ 32/64/128/256/512）
```

yolov5s 的特征图 H = W（都是方的），所以单算子输出字节数 = `W × W × C`。
一个算子的输出被切成多个 tile，但**总和仍是 W×H×C**，不用乘 tile 数。
输入则用链式关系：**本算子的输入 = 上一个算子的输出**（首个算子是 640×640×3）。

```bash
python3 src/analysis/dram_model.py shapes
```

### 结果

```
输入图像             1,228,800 B =   1.17 MB
中间+最终输出       80,230,400 B =  76.51 MB
各算子输入合计      88,473,600 B =  84.38 MB
特征总量(读+写)    168,704,000 B = 160.89 MB
```

### 两种方法对比

| 方法 | 依据 | 特征流量 | 性质 |
|---|---|---|---|
| 跨度法 | 相邻 tile 地址差（启发式） | 142.68 MB | 实测地址，但地址稀疏时失真 |
| **形状法** | `CORE 0x3014/0x3018`（**确证**字段） | **160.89 MB** | 纯字段推算，无启发式 |

**两者相差 13%，且跨度法偏低** —— 完全符合预期（跨度法在多处因地址稀疏被容量校验剔除，
必然偏低）。**两条独立路径互相印证，流量总量这个结论站住了。**

### 顺带的自证：字段解对了

形状法输出的序列是 `320²×32 → 160²×64 → 80²×128 → 40²×256 → 20²×512`，
**正是 yolov5s 骨干的公开结构**（通道 32/64/128/256/512，特征图逐级减半）。
这不是循环论证 —— CORE 字段是我从命令流里抠出来的，而它独立地重合了公开架构。
这同时验证了 docs/17 对 `0x3014`/`0x3018` 的字段判定。

## 三、修正：那个「67% 往返」是错的

### 上轮的推断错在哪

docs/29 的推理是："DPU 往 buf#4 写 48.07 MB、DPU_RDMA 从 buf#4 读 63.53 MB，
两者量级对称、落在同一缓冲区 → 这就是同一趟往返 → 占 67%"。

**这个推理有问题**：同一缓冲区 + 量级相当，只能说明"都用了那块内存"，
**不能说明读的就是写下去的那些字节**。

### 严格判据：逐地址配对

正确的判据很硬：**同一个地址，先被某个写寄存器写、后被某个读寄存器读**。

```bash
python3 src/analysis/dram_model.py fusion
```

```
参与配对的写地址数      39
被读过一次的写字节数         7,988,480 B =  7.62 MB
对应往返流量（写+读）       15,976,960 B = 15.24 MB

  占总流量（160.89 MB）的  9.5%

── 按流水级对的明细 ──
   写寄存器      读寄存器    配对数    字节 MB
  0x4020        0x1070      118      4.39     ← DPU 写 → CNA 读（下一层的输入）
  0x4020        0x5018       55      3.13     ← DPU 写 → DPU_RDMA 读回
  0x4020        0x5038        3      0.10
```

**只有 9.5%，不是 67%。**

### 但这个 9.5% 反而指向一个更值得注意的事实

反过来说：**160.89 MB 的中间特征流量里，只有 15.24 MB 是"写到某地址、再从同一地址读回"。
剩下约 91% 的读，读的是跟生产者写入地址不一样的地方。**

这意味着什么？**中间结果在 DRAM 里被搬来搬去、或者做了双缓冲/重排。**
换句话说，实际的数据搬运量比"生产者写一次、消费者读一次"的理论最小值还要多 ——
**这本身就是一块额外的浪费**，而且这块浪费比分块融合能省的多得多。

所以「融合」在这块硬件上的真正收益方向，不是"把中间结果留在片上"（RK3588 的 NPU
`GET_TOTAL_SRAM_SIZE = 0` —— **根本没有可用片上 SRAM**，docs/06 已确认，这条路物理上堵死），
而是：**减少地址重排/双缓冲带来的额外搬运**。

> 这是个方向性的修正：上轮把"融合"当成头号手段，本轮的数据说明
> ① 片上根本没有 SRAM 可用（融合无处可留）；② 真正的浪费在于 91% 的读落在
> 与写不同的地址上（重排/双缓冲）。**手段应该从"融合"改为"减少重排"。**

## 四、修正后的有效带宽

用更可信的 160.89 MB（特征）+ 权重（yolov5s w8a8 约 7.2 MB，每 tile 可能重读，未计入）：

| DMC 频率 | 实测耗时 | 反推有效带宽（仅特征） |
|---|---|---|
| 534 MHz | 46.00 ms | 3.50 GB/s |
| 2400 MHz | 28.91 ms | **5.57 GB/s** |

RK3588 的 DMC 2400 MHz、若按 32-bit LPDDR4x/5 估，峰值约 9.6 GB/s
（2400 MT/s × 4 B）→ **实测效率约 58%**。访存密集型负载的典型效率区间是 50~70%，
所以"瓶颈里有相当一部分是 DRAM"这个判断成立。

但 **docs/29 的发现 B 依然有效**：DMC 频率 4.5× 只换来带宽 1.59×，
说明 NPU **不是纯**带宽受限 —— 另一半在流水串行（对应 docs/19 的核内天花板 16%）。

## 五、本轮结论汇总

| 问题 | 上轮说法 | 本轮修正 | 证据 |
|---|---|---|---|
| 单次推理 DRAM 特征流量 | ≥143.86 MB | **≈160.89 MB**（形状法，确证字段）；跨度法 142.68 MB 交叉印证 | 两种独立方法差 13% |
| DPU→DPU_RDMA "同一趟往返" | 67% | **9.5%**（逐地址严格配对） | `fusion` 子命令 |
| 融合是头号优化手段吗 | 是 | **不是**。RK3588 的 NPU 无可用片上 SRAM（`TOTAL_SRAM_SIZE=0`），融合物理上无处可留；真正的浪费是 91% 的读与写地址不同（重排/双缓冲） | docs/06 + 本轮配对结果 |
| NPU 是纯带宽受限吗 | 不是 | **仍然不是**（DMC 4.5× → 带宽 1.59×） | docs/29 发现 B |
| 有效带宽 | 5.22 GB/s | **5.57 GB/s**（约峰值 58%） | 形状法流量 / 实测耗时 |

## 六、下一步

方向越来越清楚了 —— **两个瓶颈各占一半，且都在"搬运"这一侧**：

1. **查清那 91% 的地址错位**：为什么消费者读的地址跟生产者写的地址不一样？
   这可能是 ① 运行时确实做了 copy ② ping-pong 双缓冲 ③ 分块边界重排。
   做法：把某个算子的输出地址集合与它的消费者输入地址集合做**区间包含关系**分析
   （不是等值，而是"消费者的读落在生产者写过的区间内"）。工具只需给 `fusion`
   加一个"区间包含"判据即可。
2. **量化重排带来的额外搬运**：有了 ① 就能算出"理论最小搬运 vs 实际搬运"的差额。
3. **流水串行那一半**：用纯软件的 per-core busy/idle 插桩（安全，不碰寄存器）
   去定位 docs/19 说的 CNA 串行瓶颈。

> 方法论备注：本轮是**同一类错误第二次出现**（第一次是 docs/25 的 DDR 2×，
> 第二次是这个 67%）。两次的共同点都是 **用"看起来对称/合理"代替了严格判据**。
> 应对办法已经固化：任何关键数字都要有**第二种独立方法**，且判据要写成可复跑的脚本。
