> 本轮（第 6 轮）做的是**纠偏**：docs/41 里两个数字（提交地板、三核算术效率）是

> `RKNPU_DUMP_SLACK=64` 的稳态语料，把两个数字都变成了**点估计 + 可证**。

## 0. 修正摘要（先说改了哪两个数）

| 量 | docs/41 的说法 | **本轮修正** | 为什么 |
|---|---|---|---|
| 提交地板 `FLOOR` | 74 ~ 89 µs（**上界**，因为读不到 `OP_ENABLE`） | **67.4 µs**（144 个样本的中位，**可证**） | 新语料段尾完整，`OP_ENABLE` 全部可读；且只挂 timer、不挂 dump，无写文件干扰 |

## 1. 为什么要重抓：docs/41 那份语料的两个硬伤

### 硬伤一：段尾全被截断，`OP_ENABLE` 读不到

```
align1（SLACK=0）:  856/856 个 segment 的 end 全是 "uncaptured"，chain/enable 全为 None
align2（SLACK=64）: 428 个 segment，end = {chain: 425, end: 3}，enable 全部可读
```

后果：在 align1 上**无法**判定「这个 tile 该不该有算术」，于是地板只能给**上界**
（「即使那些 tile 真带算术，70~89 µs 也只能是地板的上界」）。docs/41 §5 明确写了这个限制。

新语料里 `OP_ENABLE` 全部可读，分类干净：

```
cm=7 稳态：OP_ENABLE = {0x1d: 1778, 0x60: 609, 0x18: 609}
           0x1d = CNA|CORE|DPU|DPU_RDMA  ⇒ 走算术
           0x60 = PPU|PPU_RDMA           ⇒ 池化，天然无算术
           0x18 = DPU|DPU_RDMA           ⇒ 逐元素，天然无算术
```

⇒ **只由 `0x60`/`0x18` 组成的提交，其 hw 时间就是提交地板**，不需要任何假设。

### 硬伤二：冷启动 ≠ 稳态，差 15%

`capture-run.py` 只跑**一次**推理，实测 cm=7 = **9.615 ms/趟**；
`capture-steady.py`（3 预热 + 4 测量）给出 **11.056 ms/趟**。
同一份工作、同一套命令流（ΣMAC 一模一样），差 15%。
**只跑一次就报数会把地板和吞吐都算歪。**

## 2. ★ 抓取工具本身会改变被测对象（这一条以前没意识到）

同一台板子、同一个模型、cm=7、各 15 次中位：

| 测量方式 | 墙钟/趟 | 硬件 hw/趟 |
|---|---|---|
| 无插桩 | **25.02 ms** | —（量不到） |
| 只挂 `rknpu_submit_timer.so` | — | **8.742 ms** |
| 同时挂 `rknpu_capture.so`（写 ~500 个 bin/趟） | **36.25 ms** | 11.056 ms |

⇒ **dump 探针给每趟加了约 2.3 ms 的 hw 时间、给墙钟加了 31%。**
原因不难猜：每趟要往 tmpfs 写 ~500 个文件，DDR 与 CPU 都被占用，
而 NPU 是**访存延迟敏感**的（docs/32），于是被拖慢。

**所以本轮的分工是**：
* **报时间**用「只挂 timer」的低开销测量（§3 的表）；
* **报工作量**用带 dump 的语料（只有 dump 才有寄存器）。

这也是为什么 `steady.py` 里那两节被明确分开，并写清楚「报数用低开销那一节」。

## 3. ★ 三个配置的干净数字

`python3 src/analysis/steady.py`（低开销节）：

```
★ 零算术量提交（144 个样本，按 task_start 对齐）地板中位 = 67.4 µs   min 30.9  max 201.0

配置          提交/趟    ΣMAC/趟     hw/趟(ms)   地板合计   算术(ms)   算术效率   占峰值
cm=7（3 核）      77   8.251e+09      8.742     5.188     3.554    2.322    75.6%
cm=3（2 核）      77   8.251e+09     12.964     5.188     7.776    1.061    51.8%
cm=1（1 核）       4   1.485e+10     15.405     0.269    15.136    0.981    95.8%
```

几点值得单独说：

1. **`cm=7` 与 `cm=3` 的 `ΣMAC` 完全相同**（8.2512e9，五位有效数字），
   而两者 tile 数不同（428 vs 413）—— **两种不同的分块给出同一个工作量**。
   这是 MAC 模型「与分块无关」的最强验证：不是自洽，是**两条独立路径撞在一起**。
2. **七趟之间 `ΣMAC` 一模一样**（8.2512e9 × 7），耗时 10.874 ~ 11.319 ms（dump 语料）。
   工作量确定性极好，波动全在时间侧。
3. **2 核（51.8%）反而比 3 核（75.6%）低** —— 非单调。同地板、同提交数下，
   2 核的算术时间 7.776 ms vs 3 核 3.554 ms，即 1.5 倍核数换来 2.19 倍加速。
   ⇒ 2 核模式另有额外开销（分块策略不同），值得单独追。

### 3.1 模型检验（一个实测地板 + 一个物理常数）

```
cm=7:  77 × 67.4µs + 8.251e9/(3×1.024e12) = 5.190 + 2.686 = 7.876 ms   实测 8.742   −9.9%
cm=1:   4 × 67.4µs + 1.485e10/1.024e12     = 0.270 + 14.505 = 14.775 ms 实测 15.405  −4.1%
```

两行都**低 4~10%**，方向一致 ⇒ 说明真实提交的平均地板比「零算术量提交」的地板高约 10%。
这很合理：零算术量的提交大多只有 3 个 tile，而含算术的提交有的多达 21 个。
**这是一个可解释的系统性偏差，不是模型形式错了。**

## 5. ★ 一个还没解释清楚的异常：单核路径的 `ΣMAC` 是 3 核的 1.80×

```
cm=7（3 核）: 428 tile / 趟，ΣMAC = 8.2512e9
cm=1（1 核）: 615 tile / 趟，ΣMAC = 1.4853e10      ⇒ 比值 1.800
```

两者都是**同一次 `capture-steady.py` 单趟**、同一个模型、同一个输入，且各自 7 趟都完全重复。

**这不是 MAC 公式的问题** —— 用最干净的算子核对（op1，首层卷积，输出必须是 320×320）：

```
cm=7: op1 共 21 个 tile，Σ out_px = 1.024e5 = **恰好 320×320** ✓ 分块恰好铺满输出一次
cm=1: op1 共 39 个 tile，Σ out_px = 2.048e5 = **640×320**      ✗ 是应有输出的 2 倍
      39 个 tile 的 dst 地址各不相同（37 个不同值），cub_o 都是 12，kern 都是 12
```

⇒ **单核路径的 op1 确实产生了 2 倍的输出行数，写到了 39 个不同地址上。**

### 两种解释，目前**没有定论**

| 解释 | 支持 | 反对 |
|---|---|---|
| (a) 单核分块真的**重复计算**了约 44% 的算术 | `Σ out_px` 就是 2 倍；`ΣMAC` 就是 1.8 倍；两者方向一致 | 一个量产运行时不至于这么浪费 |
| (b) **两种 core_mask 下 RKNN 走了不同的算子融合**，`op_idx` 在两条路径上不一一对应 | op45 在 cm=7 是 `cub_o=192/160`、在 cm=1 是 `512/256` —— **同一个 `op_idx` 通道数都不同**，强烈提示 `op_idx` 不是稳定标识 | 那为什么总量也是 1.8 倍？ |

**倾向 (b)**：`op_idx` 很可能只是「连续同值就视为一个算子」的启发式（docs/14），
两条路径的图不同，编号自然不同；总量差 1.8 倍则可能来自不同的融合/切分策略。

**这不影响本轮的结论**，因为：
* §3 的效率表里，cm=7 与 cm=3 用的是**同一份工作量**（8.2512e9，两条路径互证）；
* cm=1 那一行用的是它自己的工作量，报的是「寄存器可见工作的算术效率」，与分块无关。

### 5.1 已经查到一半：**有 5 个算子被字面重复编程，但不全是重复**

把每个 tile 的**指令内容**（`(block, reg, value)` 三元组的集合，**不含地址**）做哈希：

```
cm=1 第 0 趟：588 个 tile → 522 种不同内容 ⇒ 重复率 11.2%
cm=7 第 0 趟：428 个 tile → 343 种不同内容 ⇒ 重复率 19.9%
              （其中一种内容出现 81 次 —— 是一类恒定的琐碎配置，不是真重复）
```

⇒ **cm=1 的重复率反而比 cm=7 低**，所以「1.8 倍」**不能**用重复来解释。
但重复确实存在，而且是最硬的那种重复 —— op82 在 cm=1 的**同一次提交**里出现两遍：

```
cm=7:  task765 (dst=0xfff0a580, 1×1,  ch=16)   task766 (dst=0xfed83000, 40×32, ch=256)   task767 (dst=0xfed88000, 40×8, ch=256)
cm=1:  task198 ……与 task765 逐字段相同          task199 ……与 task766 逐字段相同            task200 ……与 task767 逐字段相同
       task413 ……与 task765 逐字段相同          task414 ……与 task766 逐字段相同            task415 ……与 task767 逐字段相同
```

**连目标地址都一样**（`0xfed83000` / `0xfed88000`）—— 也就是同一份结果被算了两遍、写到同一个地方。
被这样重复的算子有 **5 个：op47 / op56 / op80 / op82 / op84**。

所以 §5 的 1.8 倍要拆成两部分，目前只能给到这个程度：

| 成分 | 证据 | 占比 |
|---|---|---|
| **字面重复**（同内容 + 同目标地址） | 5 个算子成对出现；全局重复率 11.2% | 已知存在，**量级 ~11%**，不足以解释 1.8× |
| **不同的分块**（cm=1 编程了 ~1.5× 更多的**不同** tile 配置） | 522 vs 343 种不同内容 | 剩下的 ~60% 在这里 |
| 哪个是「模型真正需要的工作」 | cm=7 的 op1 `Σout_px` 恰好 = 320×320（分块恰好铺满一次） | **cm=7 侧是 work-preserving 的** |

⇒ 结论收窄为：**cm=7/cm=3 的分块是「恰好铺满」的；cm=1 的分块既含字面重复、
又含更多不同的 tile 配置，两者叠加成 1.80×。** 具体机制（是重复计算还是不同融合）
**仍未定论**，但「cm=7 侧工作量可信」这一点已经被 op1 的精确铺满独立证实。

**下一轮继续查**（见 §7）。

## 8. 教训（本轮新增）

1. **★ 抓取工具本身会改变被测对象。** dump 探针让每趟 hw 多 2.3 ms、墙钟多 31%。
   以前所有基于 dump 语料的**时间**数字都要重新审一遍（工作量数字不受影响）。
   **正确的做法：时间用低开销探针，工作量用高开销探针，两份分开报。**
2. **★ 冷启动 ≠ 稳态，差 15%。** 只跑一次就报数是错的。
   `capture-steady.py` 现在是标准做法（3 预热 + 4 测量 + 按 `task_start` 回绕切趟）。
3. **★ 报数之前先检查语料的完整性指标**（`end` 分布、`OP_ENABLE` 可读率）。
   `SLACK=0` 的语料看起来「有 1010 个 bin」，实际上一个段尾都没抓到。
   **文件多不等于数据全。**
4. **同一个工作量数字来自两条不同分块路径时，可信度会跳一个台阶。**
   cm=7 与 cm=3 的 `ΣMAC` 五位有效数字相同 —— 这比任何单路径的自洽都强。
5. **异常要写下来并给出竞争性解释**，不要急着挑一个。§5 的 1.8 倍我倾向 (b)，
   但把 (a) 的证据也列全了，并写明「没有定论」。**假确定的解释比承认不知道更有害。**
