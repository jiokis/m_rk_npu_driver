## 1. 结论速览

| # | 问题 | 结论一句话 |
|---|---|---|
| 1 | 社区已有逆向项目 | **有很多，而且 2025–2026 年爆发**。regcmd/单算子层面已被至少 4 个独立项目做透；但**没有**开源项目做到 rknn-toolkit2 的端到端 op 覆盖 |
| 2 | 微架构 / IP 归属 | **NVDLA 衍生**（非 VeriSilicon/Vivante）。3 核，每核 2 TOPS，每周期 1024 int8 MAC / 512 fp16 MAC；**无原生 matmul**，matmul = 1×1 卷积 |
| 3 | regcmd 格式 | **已完整公开**：64-bit `(op/block, value, reg)` 三元组；块 ID、任务 trailer、PC 链均有文档；Mesa 自带 dump+decode 工具链 |
| 4 | 内核 UAPI | Vendor（闭源 BSP）6 个 RKNPU ioctl，结构体已完整逆向；**mainline 走另一套 4 个 ioctl（`drm/rocket_accel.h`）** |
| 5 | 主线 / Mesa / DRM | **已完成上游化**：`drivers/accel/rocket` 自 **Linux v6.18** 起在主线；Mesa 侧 Gallium `rocket` 驱动 + `teflon`(TFLite delegate) **Mesa 25.3** |
| 6 | 逆向动机 | op 不支持/CPU 回退、自定义算子只能跑 CPU、量化受限、`rknn_matmul_api` ~150 context 上限、调度不透明、无编程化 kernel |
| 7 | GPU/VPU 区分 | Mali-G610 → **Panthor**（Linux v6.10 起主线）；VPU → **MPP**（开源）+ 主线 rkvdec/rkvenc。二者与 NPU 无关，**不要混用** |

**最重要的一句话：**"逆向 RK3588 NPU" 这件事的**价值重心已经从"搞懂 regcmd"转移到"在已公开的 regcmd 之上写编译器和调度器"**。前者是重复劳动，后者仍是空白。

### 2.3 哪些方向**已经被做透**（避免重复劳动）

1. **regcmd 编码格式本身** —— 至少 4 个独立来源给出一致结论（mtx512 / StarryOS / ork / Mesa `registers.xml`，另 gregordinary 独立复核）。**不要再做。**
2. **fp16 / int8 / int4 单算子 matmul regcmd 从零合成** —— ork-driver、gregordinary/librocketnpu、mtx512、allbilly 各自独立完成。**不要再做。**
3. **寄存器地址映射与字段名** —— Mesa `registers.xml` + `rocket_registers.h`(4404 行) + TRM Table 1-1 三方齐备。
4. **内核驱动 + 用户态上游化** —— `drivers/accel/rocket` 已在主线（v6.18+），Mesa Gallium/Teflon 已在 25.3。**不要去写新的内核驱动**（除非目标是 RK3576，见 §8）。
5. **regcmd dump/解码工具** —— Mesa 自带 `intercept.c` + `decode.py`，不需要新造（见 §4.4）。
6. **weight packing / NC1HWC2 布局** —— Mesa `rkt_coefs.c`/`rkt_ml.c` 是 ground truth，多个项目已实现。

## 3. Q2：RK3588 NPU 的微架构与 IP 归属

### 3.1 IP 来源：NVDLA 衍生（**不是** VeriSilicon / Vivante）✅已验证

三条独立一手/近一手证据：

1. **主线驱动作者 Tomeu Vizoso 的定调句**（v8 cover letter，最初 2024-06-12）：
   > "This series adds a new driver for the NPU that Rockchip includes in its newer SoCs, **developed by them on the NVDLA base**."
   > 来源：<https://lkml.org/lkml/2025/7/13/107>；更早版本 <https://lkml.org/lkml/2024/6/12/713> ✅已验证
2. **Mesa MR 29698 描述**：
   > "The programming model matches very closely to that of NVIDIA's NVDLA."
   > 来源：<https://gitlab.freedesktop.org/mesa/mesa/-/merge_requests/29698> ✅已验证
3. **内核官方文档**：
   > "The accel/rocket driver supports the Neural Processing Units (NPUs) inside some Rockchip SoCs such as the RK3588. Rockchip calls it RKNN and sometimes RKNPU. **The hardware is described in chapter 36 in the RK3588 TRM.**"
   > 来源：<https://docs.kernel.org/accel/rocket/index.html>（页面标注内核 7.3.0-rc6）✅已验证

旁证：Jasbir Matharu 2024-02 原文称其为 "NVDLA 架构的**远亲**（distant relative）"（中文全文 <https://blog.csdn.net/gggi520/article/details/138198375>）✅已验证。

> **关于 VeriSilicon / Vivante：❓未找到任何一手证据表明 RK3588 的 NPU 使用 VeriSilicon VIP / Vivante IP。** Vivante/VeriSilicon 在 RK3588 上出现是 **GPU 无关**的另一条线（Mesa `etnaviv` 面向 Vivante GPU，与 `rocket` 并列存在于 Mesa；`teflon` 同时支持两者——**这是极易混淆的陷阱**，见 §7）。
> 老一代 **RK3399 的 NPU（`rknpu1` / `librknn_api.so`）是与 RK3588 NPU 不同的 IP**，本项目不覆盖；其 IP 供应商归属 ❓未找到可引用的一手来源。

### 3.2 块结构与管线 ✅已验证 / 🔶

```
                ┌──── PC (0x0xxx) — Rockchip 自研，非 NVDLA：寄存器程序取指引擎
                │
feature ─→ CNA (0x1xxx)  ─→ CORE (0x3xxx) ─→ DPU (0x4xxx) ─→ PPU (0x6xxx)
          卷积/DMA/CBUF       MAC+CACC        SDP 后处理        PDP 池化
weight  ─→ (含 CSC 时序控制器)                ↑ DPU_RDMA(0x5xxx) ↑ PPU_RDMA(0x7xxx)
                                    DDMA(0x8xxx)=MCIF  DDMA  SDMA(0x9xxx)=SRAMIF  GLOBAL(0xF008)
```
- 寄存器基址（来源：Mesa `registers.xml`，被 [rockchip-npu-notes/hardware-overview.md](https://github.com/gregordinary/rockchip-npu-notes/blob/main/hardware-overview.md) 与 [StarryOS 寄存器图](https://qc-gpu-driver.github.io/starryos-pulsar/documents/register-map.html) 独立复核）✅已验证：

| 模块 | 基址 | 大小 | 功能 |
|---|---|---|---|
| PC | `0x0000` | 4KB | 任务控制器 / 命令流引擎（**Rockchip 自研，NVDLA 没有**）|
| CNA | `0x1000` | 4KB | 卷积加速（含 NVDLA 的 CDMA/CBUF/CSC）|
| CORE | `0x3000` | 4KB | MAC 核心（NVDLA CMAC+CACC）|
| DPU | `0x4000` | 4KB | 后处理（NVDLA SDP）|
| DPU_RDMA | `0x5000` | 4KB | DPU 读 DMA（NVDLA SDP_RDMA）|
| PPU | `0x6000` | 4KB | 池化（NVDLA PDP）|
| PPU_RDMA | `0x7000` | 4KB | PPU 读 DMA（NVDLA PDP_RDMA）|
| DDMA | `0x8000` | 4KB | Data DMA（NVDLA MCIF）|
| SDMA | `0x9000` | 4KB | System DMA（NVDLA SRAMIF）|
| GLOBAL | `0xF000`–`0xF004` | 4B | 全局使能掩码 |

  来源：<https://qc-gpu-driver.github.io/starryos-pulsar/documents/register-map.html>（注明取自 RK3588 TRM Table 1-1）✅已验证

- **NVDLA 有、RK3588 没有的块**（对逆向结论很关键，来源 [rockchip-npu-notes/nvdla-lineage.md](https://github.com/gregordinary/rockchip-npu-notes/blob/main/nvdla-lineage.md)，🔶AI 生成但逻辑自洽且与多个现象一致）：
  - **CDP**（跨通道 LRN）缺失 → 通道轴归约只能做成 ones-matmul
  - **BDMA**（bridge DMA）缺失 → 没有片内 memory-to-memory 拷贝引擎
  - **RUBIK**（reshape 引擎）缺失 → **host 侧 de-tiling 无法消除**
- **RK3588 有、NVDLA 没有的块**：**PC**（寄存器程序取指器）→ "一个硬件 layer" 变成一个内存 buffer，而不是 CPU 写寄存器序列。✅已验证（同来源 + Tomeu 的驱动设计）

## 4. Q3：regcmd（register command）格式

### 4.1 编码 ✅已验证（三个独立来源一致）

**64-bit 一条命令**，字段布局：

```
 63        48 47              16 15       0
┌────────────┬──────────────────┬──────────┐
│  op/block  │      value       │   reg    │
│  (16-bit)  │     (32-bit)     │ (16-bit) │
└────────────┴──────────────────┴──────────┘
```

来源（三者可互相换算，实为同一编码的两种表述）：
- mtx512 风格宏（StarryOS 文档同）：<https://qc-gpu-driver.github.io/starryos-pulsar/documents/rknnlibso/internals.html>
  ```c
  #define NPUOP(op, value, reg) \
    (((uint64_t)(op & 0xffff)) << 48) | \
    (((uint64_t)(value & 0xffffffff)) << 16) | (uint64_t)(reg & 0xffff)
  ```
- ork-driver 的 u32 对表述（<https://github.com/oRKLLM/ork-driver/wiki/regcmd-ISA-Reference>）：
  ```
  reg_offset = word0 & 0xffff
  block_id   = word1 >> 16
  value      = ((word1 & 0xffff) << 16) | (word0 >> 16)
  ```
  🔶 两种写法数学等价：`word0 = (value_low16 << 16) | reg`，`word1 = (op << 16) | value_high16`。

### 4.2 命令类型（opcode）与块 ID ✅已验证

```
BLOCK_PC       0x0100        PC_OP_01    0x01   ← 寄存器写入
BLOCK_CNA      0x0200        PC_OP_40    0x40   ← 用途未完全解明
BLOCK_CORE     0x0800        PC_OP_EN    0x80   ← 使能
BLOCK_DPU      0x1000
BLOCK_DPU_RDMA 0x2000   组合后的常用 op：
BLOCK_PPU      0x4000     OP_REG_CNA  = 0x0201
BLOCK_PPU_RDMA 0x8000     OP_REG_CORE = 0x0801
                          OP_REG_DPU  = 0x1001
                          OP_ENABLE   = 0x0081
```
来源：<https://qc-gpu-driver.github.io/starryos-pulsar/documents/rknnlibso/internals.html> ✅已验证（与 ork wiki 的 `0x0201/0x0801/0x1001/0x0101/0x0041/0x0081` 一致）

**任务尾部（trailer）四条命令**（来源 <https://github.com/gregordinary/rockchip-npu-notes/blob/main/encodings/regcmd-task-model.md>，🔶AI 生成）：
```
NPUOP(OP_NONE,   0,    0)                      # 收尾
NPUOP(OP_REG_PC, 0,    PC_REGISTER_AMOUNTS)    # 驱动会用 regcmd_count 回填 PC_DATA_AMOUNT
NPUOP(OP_40,     0,    0)
NPUOP(OP_ENABLE, 0x1D, PC_OPERATION_ENABLE)    # 0x1D = bit0,2,3,4 = PC+CNA+DPU+DPU_RDMA
```
- 池化程序的 trailer 用 `0x60`（bit5,6 = PPU+PPU_RDMA），**不含 bit0**。
- ⚠️ **`PC_OPERATION_ENABLE` 是"块参与位图"，但 TRM 和 Mesa 的 `registers.xml` 都把它描述为只有 bit0 有效**（TRM: `31:1 RO reserved`）。两者都错。若按文档读，池化程序将"什么都不使能"。这是**一个已被证伪的文档**，逆向时要注意经文档校验会误导。🔶（来源同上，标 `[HW sweep]`）

### 4.3 任务描述符与 task list

- 一个 RPUOP 程序 = 一条 task；`rknpu_task.regcmd_addr` 指向它，`regcfg_amount` 指明字数。
- **`regcfg_amount` 的算法**（✅ 由内核驱动源码确认，StarryOS 给出逆向证据）：
  ```
  regcfg_amount = total_ops - RKNPU_PC_DATA_EXTRA_AMOUNT(4) - 4;
  // 内核侧 rknpu_job_subcore_commit_pc():
  amount = task->regcfg_amount + rknpu->config->pc_data_extra_amount;
  ```
  来源：<https://qc-gpu-driver.github.io/starryos-pulsar/documents/rknnlibso/internals.html> ✅
- 典型 matmul 命令流结构（108 条）：DPU_S_POINTER → 28 条 CNA → 12 条 CNA 权重解压 → 2 条 CNA 补充 → CNA_S_POINTER → 6 条 CORE → CORE_S_POINTER → 56 条 DPU → PC_OPERATION_ENABLE。🔶（同上；Mesa 侧的 int8 全长 task 报 **126** words）
- `S_POINTER`（偏移 `0x_004`，四个块各一）是**乒乓寄存器组选择器**，值 `0xE` = `PP_MODE|EXECUTER_PP_EN|POINTER_PP_EN`；bit 定义与"寄存器状态跨 task 持续"的实测见 <https://github.com/gregordinary/rockchip-npu-notes/blob/main/encodings/regcmd-task-model.md> 🔶
- **PC 链（跨 task 续接）**：`0x0101:0x10` = PC_DATA_ADDR，`0x0101:0x14` = PC_DATA_AMOUNT（`0x37` 非末 / `0` 末）。ork-driver 明确记录：**NPU 不会自动串起 task list，task 链必须编码在 regcmd 的 PC-control 条目里**，这是 ork 与 gregordinary 都仍在推进的"最深调度层"。<https://github.com/oRKLLM/ork-driver/wiki/Reverse-Engineering-Roadmap> 🔶

### 4.4 能 dump regcmd 的工具（这是 Q3 里最实用的一节）✅已验证

## 5. Q4：内核驱动的 UAPI

RK3588 上有**两套互不相同的 UAPI**，逆向选型时必须先决定用哪套。

### 5.1 Vendor BSP 驱动（`drivers/rknpu`，GPL，随 linux-6.1 vendor 内核）✅已验证

**6 个 ioctl**，走 DRM 私有命令空间：

| 名字 | nr | 结构体 | 大小 |
|---|---|---|---|
| `DRM_IOCTL_RKNPU_ACTION` | `DRM_COMMAND_BASE + 0x00` | `struct rknpu_action {u32 flags; u32 value;}` | 8 |
| `DRM_IOCTL_RKNPU_SUBMIT` | `+ 0x01` | `struct rknpu_submit` | 96 |
| `DRM_IOCTL_RKNPU_MEM_CREATE` | `+ 0x02` | `struct rknpu_mem_create` | 40 |
| `DRM_IOCTL_RKNPU_MEM_MAP` | `+ 0x03` | `struct rknpu_mem_map` | 16 |
| `DRM_IOCTL_RKNPU_MEM_DESTROY` | `+ 0x04` | `struct rknpu_mem_destroy` | 16 |
| `DRM_IOCTL_RKNPU_MEM_SYNC` | `+ 0x05` | `struct rknpu_mem_sync` | 32 |

（另有非 DRM 前缀的 `IOCTL_RKNPU_*` = `_IOWR('r', nr, type)` 变体）
完整头文件（可直接编译）：<https://raw.githubusercontent.com/phhusson/rknpu-reverse-engineering/main/rknpu-ioctl.h> ✅已验证
逐字段偏移表（含 `__packed` 说明）：<https://qc-gpu-driver.github.io/starryos-pulsar/documents/ioctl-protocol.html> ✅已验证

**关键结构体**（`rknpu_task`，36 字节 `__packed`）：
```c
struct rknpu_task {
  u32 flags; u32 op_idx; u32 enable_mask; u32 int_mask; u32 int_clear;
  u32 int_status; u32 regcfg_amount; u32 regcfg_offset; u64 regcmd_addr;
} __packed;
struct rknpu_submit {           // 96 字节
  u32 flags; u32 timeout; u32 task_start; u32 task_number; u32 task_counter;
  s32 priority; u64 task_obj_addr; u64 regcfg_obj_addr; u64 task_base_addr;
  u64 user_data; u32 core_mask; s32 fence_fd;
  struct rknpu_subcore_task subcore_task[5];
};
```
**枚举（逆向必需）** ✅：
- `e_rknpu_mem_type`（位掩码）：`CONTIGUOUS 0` / `NON_CONTIGUOUS 1<<0` / `NON_CACHEABLE 0` / `CACHEABLE 1<<1` / `WRITE_COMBINE 1<<2` / `KERNEL_MAPPING 1<<3` / **`IOMMU 1<<4`** / `ZEROING 1<<5` / `SECURE 1<<6` / `NON_DMA32 1<<7` / **`TRY_ALLOC_SRAM 1<<8`**；`MEM_MASK = 0x1FF`
- `e_rknpu_mem_sync_mode`：`SYNC_TO_DEVICE 1<<0`（flush）/ `SYNC_FROM_DEVICE 1<<1`（invalidate）
- `e_rknpu_job_mode`：`SLAVE 0` / `PC 1<<0` / `BLOCK 0` / `NONBLOCK 1<<1` / `PINGPONG 1<<2` / `FENCE_IN 1<<3` / `FENCE_OUT 1<<4`
- `e_rknpu_action`：0..23（`GET_HW_VERSION`, `GET/SET_FREQ`, `ACT_RESET`, 带宽 4 项, `ACT_CLR_TOTAL_RW_AMOUNT`, 三个计数器 `GET_DT_WR_AMOUNT`/`GET_DT_RD_AMOUNT`/`GET_WT_RD_AMOUNT`, `GET_TOTAL_RW_AMOUNT`, **`GET_IOMMU_EN`**, `SET_PROC_NICE`, `POWER_ON/OFF`, `GET_TOTAL/FREE_SRAM_SIZE`）
  - **带宽/读写计数器是"硬件真干了活没有"的判据** —— gahingwoo 用它揭穿"job done 但输出全零"（`dt_wr=wt_rd=0`）。见 §7.3 引用。
  - StarryOS 扩展了 24/25：`GET/SET_IOMMU_DOMAIN_ID` ✅

**任务提交模型** 🔶（来源 ork wiki + StarryOS + Mesa）：
- `submit.core_mask` = bit0/1/2 三核；`subcore_task[i] = {task_start, task_number}` 做核间切分；`subcore_task[1]` 起是哨兵 `{N,0}`（单核模式）。
- `enable_mask=0xd`、`int_mask=0x300`、`int_clear=0x1ffff` 是 matmul 的典型值。
- **`regcmd` 内是绝对 IOVA，内核不做重定位** —— 每个地址寄存器（`0x1070` feature / `0x1110` weight / `0x4020` 输出 / `0x40c0` SURFACE_ADD）都必须填有效 IOVA，填错会 wild-write 导致 AXI hang。🔶（ork wiki，`[HW sweep]` 语境）
- **设备节点坑**：NPU 暴露为 DRM 设备；ork 记录 **裸 `RKNPU_SUBMIT` 只在 `card1`（primary node）上有效**，`renderD129` 不行。phhusson 的 strace 也只见 `/dev/dri/card1`。⚠️ 但主线 rocket 是标准 accel 节点 `/dev/accel/accel0`。✅/🔶

**内存模型** ✅：
- GEM 对象：`MEM_CREATE`（返回 `handle`/`obj_addr`/`dma_addr`/可选 `sram_size`）→ `MEM_MAP`（返回 DRM **fake offset**）→ `mmap(fd, size, PROT_RW, MAP_SHARED, fd, offset)` → `MEM_SYNC`（显式 cache 维护）→ `MEM_DESTROY`。
- **IOMMU**：`RKNPU_MEM_IOMMU` 位启用；一个 IOMMU domain 对应一个 **32-bit IOVA 窗口（~4 GiB）**。分配返回的是 IOVA（启用 IOMMU）或物理地址（未启用，需物理连续）。`iommu_domain_id` 需为真实 domain（`-1` 会被拒）。
- **CMA / dma-heap**：`RKNPU_MEM_NON_CONTIGUOUS` / `NON_DMA32` 控制物理连续性；ork 记录 dma-heap（`ork_dma_import`）可零拷贝导入。
- **片上 SRAM**：`RKNPU_MEM_TRY_ALLOC_SRAM`（flags `0x503`）；需内核 `CONFIG_ROCKCHIP_RKNPU_SRAM=y` + DT 里把 `sram@ff001000`（956KB）从 `rkvdec` 改配给 `rknpu`。**默认不启用，报 0 字节。** 🔶
- **已知驱动缺陷**：`rknpu` 的 IOMMU 域引用计数/切换在多 domain（模型 >4GiB）场景会 wedge；修复提在 <https://github.com/rockchip-linux/kernel/pull/390>。🔶（ork 自述）

### 5.2 Mainline `rocket` UAPI（**这是应该优先选的一套**）✅已验证

头文件：<https://git.kernel.org/pub/scm/linux/kernel/git/torvalds/linux.git/plain/include/uapi/drm/rocket_accel.h>（192 行，本次已完整读取）

| ioctl | 结构体 | 语义 |
|---|---|---|
| `DRM_IOCTL_ROCKET_CREATE_BO` (`0x00`) | `drm_rocket_create_bo` | `size`→ 返回 `handle`/`dma_address`/`offset`。**`dma_address` 是该 fd 私有的 NPU 地址空间地址，仅在 handle 生命周期内有效**（隐含每 fd 一个 IOMMU 域）|
| `DRM_IOCTL_ROCKET_SUBMIT` (`0x01`) | `drm_rocket_submit` | `{jobs, job_count, job_struct_size, reserved}` |
| `DRM_IOCTL_ROCKET_PREP_BO` (`0x02`) | `drm_rocket_prep_bo` | 开始 CPU 持有：等待 NPU job 完成 + cache 同步（`timeout_ns`）|
| `DRM_IOCTL_ROCKET_FINI_BO` (`0x03`) | `drm_rocket_fini_bo` | 结束 CPU 持有：为 NPU 访问同步 cache |

```c
struct drm_rocket_task { u32 regcmd; u32 regcmd_count; };   // regcmd = regcmd buffer 的 DMA 地址
struct drm_rocket_job {
  u64 tasks; u64 in_bo_handles; u64 out_bo_handles;
  u32 task_count; u32 task_struct_size;
  u32 in_bo_handle_count; u32 out_bo_handle_count;
};
```
- **设计语义（内核文档原话）**："All tasks in the same job will be executed **sequentially on the same core**, to benefit from memory residency in SRAM."、"The kernel will schedule the execution of these jobs in **dependency order**." ✅
- 与 vendor 的差别：**没有 `regcfg_amount`/`enable_mask`/`core_mask`/`subcore_task`/绝对 IOVA 语义**；依赖用 BO handle 列表显式声明，由内核维护；job 内多 task 串行同核。
- **`/dev/accel/accel0`**，红黑树/调度由 DRM accel 框架托管。
- 设备树绑定：`Documentation/devicetree/bindings/npu/rockchip,rk3588-rknn-core.yaml`，`compatible` **仅** `rockchip,rk3588-rknn-core`，`reg-names = pc, cna, core`。✅已验证

### 7.3 调度 / 运行时的不透明与硬约束

| 限制 | 说明 | 来源 |
|---|---|---|
| **~150 个 matmul context 上限** | 闭源 `rknn_matmul_api` 每个 matmul 一个 context（自带缓冲 + IOMMU 映射），约 150 个即死；而一个模型有 ~200 个权重矩阵 | 🔶 <https://github.com/oRKLLM/ork-driver/wiki/Reverse-Engineering-Roadmap> |
| **每 context 重新上传权重** | 即使绕过上限也无用，做不到"权重常驻" → prefill 落后闭源 `librkllmrt` | 🔶 同上 |
| **无编程化 kernel** | Jasbir 原文：*"I was hoping to be able to use programmable kernels to perform custom operations. Unfortunately, this is not the case, you can only use OpenCL as an alternative. This creates challenges if you need to shift data between OpenCL and NPU."* | ✅ <https://blog.csdn.net/gggi520/article/details/138198375> |
| **调度不透明** | 核间切分/层间依赖/CBUF 冲突避免是"闭源库核心竞争力"（StarryOS 逆向结论），用户无法干预 | 🔶 <https://qc-gpu-driver.github.io/starryos-pulsar/documents/rknnlibso/internals.html> |
| **6 TOPS 存疑** | Jasbir 分析 SDK 数据流后认为**三核协同从未被使用**；且 DPU/PPU 无对应多核机制。他自己也没有做成多核。**但 2026 年的 gregordinary 与 ork 都声称已实现多核 N-split** | ✅（他的质疑）/ 🔶（2026 年的反例） |
| **32-bit 地址空间** | 所有指针为 32-bit 物理/IOVA → **单 domain 上限 4GB**，16/32GB 板子的内存对 NPU 无用（除非多 IOMMU domain，而多 domain 在 vendor 驱动上有 wedge 缺陷） | ✅（Jasbir）/ 🔶（domain 缺陷来自 ork） |
| **版本强绑定** | `rknn_server` / `librknnrt.so` / `rknn-toolkit2` 三者版本必须一致；`.rknn` 与 `.rkllm` 格式随版本变化（ezrknpu README 明确列出兼容性坑） | ✅ <https://github.com/Pelochus/ezrknpu> |
| **TRM 质量差** | Jasbir 原文（TRM v1.0）："包含 RKNN 的许多差距和不一致"；且**TRM 对 `PC_OPERATION_ENABLE` 的描述被实测证伪**（§4.2） | ✅ + 🔶 |
| **"job done" ≠ 算了** | 硬件计数器 `dt_wr`/`wt_rd` 全 0 而 job 报完成 —— 闭源栈没有暴露这种可观测性；gahingwoo 靠读硬件带宽计数器才定位 | ✅ <https://gahingwoo.github.io/posts/rk3576-npu-mainline/> |
| **静默错误** | #574 与 #549：转换成功、运行成功、输出全零/相似度 0.63。**没有任何 source 级断言** | ✅ |

## 8. Q7：必须区分的三条加速器线（**不要混用成果**）

| 加速器 | IP | 开源状态 | 与你项目的关系 |
|---|---|---|---|
| **NPU（RKNPU2）** | **Rockchip 基于 NVIDIA NVDLA 衍生**（3 核，6 TOPS） | 内核 `drivers/accel/rocket`（**Linux v6.18+ 主线**）；用户态 Mesa Gallium `rocket` + `teflon`（Mesa 25.3）；vendor 侧闭源 `librknnrt` / `rknn-toolkit2` | **本项目目标** |

| **VPU** | Rockchip 视频编解码 | **MPP (Media Process Platform) 开源**：<https://github.com/rockchip-linux/mpp>（1086★，镜像 <https://github.com/HermanChen/mpp>）；主线侧有 V4L2 `rkvdec`/`rkvenc`（Hantro 系） | **无关**，但有**真实的资源耦合**见下 |

来源：
- Panthor：<https://www.collabora.com/news-and-blog/news-and-events/release-the-panthor.html>（"merged into drm-misc … we expect this driver to land in Linux v6.10"，Mesa MR 26358，"enabling GPUs on Rockchip's RK3588"）✅已验证
- MPP：<https://github.com/rockchip-linux/mpp>（**1086★**，2016→2026-09 仍在更新；镜像 <https://github.com/HermanChen/mpp>，310★）✅已验证（GitHub API）
- FFmpeg 侧 MPP/RGA 支持：<https://github.com/nyanmisaka/ffmpeg-rockchip>（1.3k★）✅

**⚠️ 唯一的真实交叉点（值得注意的坑）**：NPU 想用 **片上 SRAM（956KB）**，而该 SRAM 在标准 vendor DT 里是**分给 `rkvdec` 的**。要启用 NPU SRAM 必须改 DT 把 `rkvdec0_sram` 让给 `rknpu`，**代价是硬件视频解码**。🔶 <https://github.com/oRKLLM/ork-driver/wiki/NPU-on-chip-SRAM>

- Mesa `teflon` 还支持 **Arm Ethos-U65**（Mesa 25.3 release notes: `ethos: Initial commit of a driver for the Arm Ethos-U65 NPU.`）✅
- `allbilly/tinygrad-npu` 针对的是 **ARM China Zhouyi X2 NPU（CIX P1 / Radxa Orion）**，与 RK3588 无关 ✅

**老一代 NPU**：RK3399 的 `rknpu1` / `librknn_api.so` 是**另一颗 IP**（Jasbir 也提到他从 **V831 NPU** 的逆向经验受益）。不要把 rknpu1 的资料套到 RK3588（反之亦然）。

> **"逆向 regcmd" 已不是研究课题，是已完成的基础设施。你的投入应该放在它之上：编译器（op 覆盖）、调度（PC 链/跨算子融合）、量化（混合精度）。**

### 10.2 ✅ 值得投入（按性价比排序）

**① 先选边：主线 rocket 还是 vendor rknpu？—— 建议主线 rocket**
- 理由：UAPI 已定稿且有文档（`include/uapi/drm/rocket_accel.h`）、内核调度/依赖/IOMMU 隔离由 DRM accel 框架托管、有 Mesa `decode.py`/`intercept.c` 调试链、有 `librocketnpu` / `ork-driver` 两个可站在肩上的用户态库。
- 但要接受两个现实：**(a) 主线 rocket 目前只支持 RK3588**（RK3576 未合入）；**(b) 主线不支持 `TRY_ALLOC_SRAM` 等 vendor 特性**（allbilly 明确抱怨"mainline rocket kernel npu driver has limitation on submit and cannot implement according to the reverse engineering results"，被迫回退到 `rknpu_driver`）。
  🔶 <https://github.com/allbilly/rk3588>
- **务实做法**：核心实现基于主线 rocket；用 `gregordinary/rknpu-submit` 的 "submit seam" 思路做一层抽象，让同一套上层逻辑也能跑在 stock vendor 内核上（无需刷机）。

**② 真正的空白 #1：ONNX → regcmd 的端到端编译器（op 覆盖）**
- 现状：Mesa/Teflon **只做 TFLite int8 子集、以 conv 为主**；ork 只做 matmul + 少数 op；librocketnpu 覆盖较广但仍是"手写 op 库"而非编译器。
- 差异点：`rknn-toolkit2` 有 484 行的 op 表（含大量 `Not Supported`），**你要做的是把那些 `Not Supported` 变成可用**（Einsum→matmul 重写、GridSample→host 索引、F.pad→conv padding 等），或者做一个 **ONNX 前置重写层**（把图改写为 NPU 友好的等价图）。后者工程上更短平快，价值也明确。
- 可复用：Mesa `registers.xml`（寄存器真相源）+ 内核 `rocket_registers.h` + ork 的 ISA reference。

**③ 真正的空白 #2：PC 链 / 跨算子融合 / 单提交多 task 调度**
- 这是**所有项目都还没完全解决**的"最深调度层"：PC 链（`0x0101:0x10`/`0x14`）、乒乓寄存器组、delta task、跨算子 fusion。
- 已知硬约束（免得踩坑）：① NVDLA 数据通路单向（MAC→SDP→PDP→CDP），activation→matmul 方向违反数据流；② **寄存器组跨 task 会残留状态**——"as shipped, the group a task lands in is the one written **two tasks back**"，所以 delta task 要"前两个 task 写全、后续用 delta"；③ LUT 激活 op 会**污染共享 task descriptor**（`regcfg_amount` 1097→69 未还原）导致后续 single-core matmul 超时。🔶 <https://github.com/gregordinary/rockchip-npu-notes/blob/main/encodings/regcmd-task-model.md> · <https://github.com/oRKLLM/ork-driver/wiki>
- 这一块有真实性能收益（ork 测到 per-submit 稳态开销 ~32ms，把 N 次提交压成 1 次是主要收益）。🔶

**④ 真正的空白 #3：量化自由度**
- NPU 硬件支持 int4/int8/int16/fp16/bf16/tf32（🔶 需你自行 HW 验证）。
- `rknn-toolkit2` 只暴露 int8（per-tensor/per-channel）+ int16 + w4a16 的**固定组合**，且用 MMSE 算法（`examples/functions/quantize_algorithm_mmse/`）。
- 可做的：**per-channel + importance matrix + NF4 + stochastic rounding + Hadamard 旋转**（ork 已有 `ork_i4a8_mm_pack_im`、`ORK_NF4`、`ORK_SR`、Hadamard 实验）。这是一个**纯软件、可量化收益、不依赖硬件 RE** 的方向，性价比最高。
- DPU 的 **out-cvt 片上 requant**（整数 multiplier+shift，BS 级 per-output-channel 可承载 TFLite per-axis scale）意味着**int8 卷积可以在片上直接输出 int8，无需 host requant**。🔶 值得复用。

**⑤ 差异化场景：做闭源栈做不好的 workload**
- **MoE**：edge NPU 静态 shape 编译 vs MoE 动态稀疏路由 —— 硬件层面的 group GEMM / multi-batch 是明确空白（ork 与 gregordinary 都在攻）。
- **Attention / KV-cache / 长上下文 K-split**：Mesa 完全没覆盖。
- **线性注意力 / 状态空间模型的 scan**（cumsum + 广播乘）：硬件无 gather/scatter，需 matmul-with-ones 的等价变换。
- 这些是"提升模型部署自由度"最直接的落地。

**⑥ RK3576 / RK3566 porting（如果硬件在手）**
- 上游缺位（未合入），但方法学已有：`PC_TASK_CON` 位宽这类 SoC 差异必须逐位实测；`chips/porting-patterns.md` 给了"哪些 IP 固有、哪些 per-SoC"的划分思路。🔶
- **警告**：gahingwoo 在一个开发分支上因 15 个寄存器/缓冲生成错误 + 一个位宽错误，浪费了约两个月，且一度得出"错误结论"并发表。**任何"硬件在寄存器以下拒绝工作"的结论，先怀疑自己的寄存器字段宽度。**

### 10.3 ❌ 死路 / 强烈建议不要做

| 方向 | 为什么是死路 |
|---|---|
| **重新逆向 regcmd 编码格式** | 至少 4 个独立项目 + Mesa 官方实现已做透。**直接读 `registers.xml`。** |
| **从零合成 fp16/int8/int4 单算子 matmul** | ork、librocketnpu、mtx512、allbilly 各自独立完成；Mesa 已上游。重复劳动。 |
| **新写一个 NPU 内核驱动** | `drivers/accel/rocket` 已在主线且被维护；除非目标是新 SoC。 |
| **自研 regcmd dump 工具** | Mesa `intercept.c`+`decode.py` 已完备（且复用 `registers.xml` 才能保证字段名正确）。 |
| **期望从 RK3588 TRM 拿到"语义"** | TRM 只有寄存器表，**且已知有错**（`PC_OPERATION_ENABLE` 的"reserved"位实际是块位图）。TRM 只能用于对地址，不能用于对语义。 |
| **做 `librknnrt` 的 ABI 兼容层** | 障碍是 op 语义与调度，不是函数签名。兼容层只是把闭源限制一起继承下来，收益接近零。 |
| **在 vendor 内核上做多 IOMMU domain（>4GB 模型）** | 已知 wedge 缺陷（`rockchip-linux/kernel#390`）；单 domain 上限 4GB 是硬件约束（32-bit 地址）。要么多进程（每 fd 一域），要么流式换页。 |
| **把 GPU/VPU 的成果当 NPU** | Panthor/Panfrost（Mali-G610）与 MPP/rkvdec（VPU）与 NPU **零共享代码**。看到 `etnaviv`/`teflon`/`ethos` 出现在同一份 Mesa release notes 里，不要误读成 NPU。 |
| **无保护的硬件 register fuzzing** | 一次非法写就能 wedge NPU 甚至内核 panic。若要做，必须像 ork 记录的那样上 **OOB 恢复**（写日志→重启→黑名单→网络智能插座断电）。而且注意：**"读回值"与"写进去的值"不同**（寄存器自清零），不要用 readback 判断写入是否生效。 |
| **引用 `jas-hacks.blogspot.com` 原文之外的二手转述** | 原文不易访问，市面转述有细节漂移（例如把"远亲"说成"就是 NVDLA"）。 |
| **直接采信 `rockchip-npu-notes` / `rocket-userspace` 的数字** | 作者自己声明 **AI 生成、准确性不保证**。可以当"待验证假设库"用，**不能当引用来源**。 |
| **围绕 `rknn-toolkit2` 做二次开发/打补丁** | 闭源 .so；issue 生态显示改不动（#32 悬了两年）。你要的自由度只能来自绕过它。 |

### 10.4 建议的第一步（低成本、高信息量）

1. **在板子上跑通主线 rocket + Mesa `teflon` 跑 MobileNetV1**（官方文档给了完整步骤）。这一步会一次性验证：内核版本、IOMMU、`/dev/accel/accel0`、Teflon delegate、你的工具链。约 1 天。
2. **用 Mesa `intercept.c` + `decode.py` 抓一条真实 regcmd 并解码**，与 ork wiki 的 ISA reference 对一遍。**确认你能读懂** —— 这是后面所有工作的前提。约 1 天。
3. **判据搭建（最重要的一步）**：在做任何优化前，先按 gahingwoo 的教训建好"能区分『算了』和『没算却被报完成』"的可观测性 —— 读硬件带宽计数器（`RKNPU_GET_DT_WR_AMOUNT` / `GET_WT_RD_AMOUNT`）、写数值 oracle（脚本化的 CPU 参考 + 逐元素比对），不要依赖单一的"输出像不像"。**这一步能省掉两个月。**
4. **然后才选方向**（§10.2 的 ②③④⑤ 中挑一个），并优先选**不依赖硬件 RE** 的那个（量化/图重写）。
