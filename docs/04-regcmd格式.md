# regcmd 格式已破解 ★

> **里程碑**：2026-10-11，用 `LD_PRELOAD` 拦截 ioctl，从闭源 `librknnrt.so` 手里
> 抓到了 **615 条真实命令流**，格式已解出。
> 抓取工具：[`src/probes/rknpu_capture.c`](../src/probes/rknpu_capture.c) ·
> 原始样本：[`data/dumps/`](../data/dumps/)

## 一、指令格式

**每 8 字节 = 1 条指令**，小端：

```
┌────────────────┬──────────────────┬─────────────────┐
│  u16  寄存器地址 │  u32  写入的值    │  u16  操作码     │
│      (LE)      │      (LE)        │  几乎恒为 0x0201 │
└────────────────┴──────────────────┴─────────────────┘
  offset 0         offset 2           offset 6
```

一条真实指令的例子（`regcmd_000_task0.bin` 第 0 条）：

```
字节: 40 10 | 1b 00 00 00 | 01 02
解出: 0x1040   0x0000001b    0x0201
含义: 向寄存器 0x1040 写入 0x1b
```

## 二、寄存器地址分 bank

抓到的地址全部落在几个规整的 bank 里：

| Bank | 出现的偏移 | 说明 |
|---|---|---|
| **0x10xx** | 0x0c, 0x10, 0x14, **0x20–0x38**, 0x40–0x88 | **PC / 主控制 bank**，与 UAPI 头文件的偏移表完全对上 |
| **0x11xx** | 0x00, 0x04, 0x10, 0x40–0x6c | 第二个 bank（疑似张量描述符） |
| 0x40xx / 0x50xx | 0x04 | 只见过 `0x4004` / `0x5004` 各写 `0x0e` |

**与 UAPI 头文件的对照（这是铁证）**：

| regcmd 里的地址 | UAPI 宏 | 偏移 |
|---|---|---|
| `0x1010` | `RKNPU_OFFSET_PC_DATA_ADDR` | 0x10 |
| `0x1014` | `RKNPU_OFFSET_PC_DATA_AMOUNT` | 0x14 |
| `0x1020` | `RKNPU_OFFSET_INT_MASK` | 0x20 |
| `0x1024` | `RKNPU_OFFSET_INT_CLEAR` | 0x24 |
| `0x1028` | `RKNPU_OFFSET_INT_STATUS` | 0x28 |
| `0x102c` | `RKNPU_OFFSET_INT_RAW_STATUS` | 0x2c |
| `0x1030` | `RKNPU_OFFSET_PC_TASK_CONTROL` | 0x30 |
| `0x1034` | `RKNPU_OFFSET_PC_DMA_BASE_ADDR` | 0x34 |
| `0x1038` | 未在头文件里 | 0x38 |

高 12 位是 bank/前缀，低 12 位是 bank 内偏移。所以 **`0x1010` = bank `0x10` 的寄存器 `0x010`**。

## 三、★ 关键架构发现：命令流是自延续的

抓到的指令里有这一对：

```
[7]  0x1010 ← 0x00000220     # PC_DATA_ADDR   ← 下一次取指的数据地址
[8]  0x1014 ← 0x00000012     # PC_DATA_AMOUNT ← 下一次取指的数据长度
```

**`PC_DATA_ADDR` / `PC_DATA_AMOUNT` 不只是驱动初始化时写的两个寄存器，
它们本身就是 regcmd 里的指令。**

这意味着 NPU 的执行模型是：

```
取指 → 解码 → 执行
        ↓
   若指令写了 PC_DATA_ADDR/AMOUNT
        ↓
   硬件去新地址继续取指   ← 链式、自延续
```

**推论**：一条命令流可以在执行中途"跳转"到另一块数据继续执行。
这既是理解的钥匙（解释了为什么驱动只写 7 个寄存器就够），
也是**优化的抓手**（可以把长命令流分段、按需加载，减少一次性 DMA）。

## 四、同算子不同形状的差异分析

同一个 `op_idx` 的多条命令流做 diff，差异通常只有 **2–6 处** ——
说明**每个算子有固定模板，少数槽位是变量**。变化的槽位正好对应：

| 变化地址 | 观测到的变化 | 含义推断 |
|---|---|---|
| `0x1070` | `0x7fcb5000` → `0x7fcc4f00` | **张量设备地址**（与我们在 ioctl 里见过的 dma_addr 同一地址空间） |
| `0x1010` | `0x100` → `0xf0` | **数据长度**（每次 0x10 递减，疑似按 16 字节对齐递减） |
| `0x1014` | `0x12` 不变 | 长度相关 |
| `0x1020` / `0x1084` | `0x01400022` → `0x01400023` | **计数器 +1**（低 12 位是数量） |
| `0x1040` | `0x1b` → `0x201b` | **标志位**（`0x2000` 位切换） |

这条规律对**自己造命令流**极其有利：不需要从零构造，
**拿一条真实模板改几个变量槽位**就能得到新的算子配置。

## 五、第三个字段是 block_id，不是操作码（已修正）

初版把最后一个 u16 叫"操作码"，**这个命名是错的**。经与第三方逆向成果
（[`oRKLLM/ork-driver`](https://github.com/oRKLLM/ork-driver/wiki/regcmd-ISA-Reference)）
对照，它独立给出的解码公式是：

```
reg_offset = word0 & 0xffff;
block_id   = word1 >> 16;
value      = ((word1 & 0xffff) << 16) | (word0 >> 16);
```

代入我们自己抓到的第一条指令 `40 10 1b 00 | 00 00 01 02`：

| 字段 | 三方公式 | 我们的解析 | 一致性 |
|---|---|---|---|
| `reg_offset` | `0x001b1040 & 0xffff` = **0x1040** | 0x1040 | ✅ |
| `block_id` | `0x02010000 >> 16` = **0x0201** | 0x0201 | ✅ |
| `value` | `(0<<16) \| 0x001b` = **0x1b** | 0x1b | ✅ |

**三个字段逐一吻合，而这是两条完全独立的路径得到的**（他们靠资料+上板试错，
我们靠 LD_PRELOAD 抓真实运行时）。所以格式无误，只是把 `block_id` 误叫成了操作码。

### 5.1 从真实数据反推出的硬件模块拓扑

把 615 条样本按 `block_id` 归类，模块划分一目了然：

| block_id | 次数 | 观测到的寄存器偏移 | 推断 |
|---|---|---|---|
| **0x0201** | 9431 | 0x100c, 0x1040–0x1088, 0x1100–0x1168 | **主计算单元**（三方命名为 CNA/卷积），占绝对多数 |
| **0x1001** | 2371 | 0x4004 ← 0x0e | 同构单元 A |
| **0x2001** | 470 | 0x5004 ← 0x0e | 同构单元 B |
| **0x4001** | 544 | 0x6004 ← 0x0e, 0x600c, 0x6010, 0x6014 | 同构单元 C |
| **0x8001** | 243 | 0x7004 ← 0x0e, 0x700c, 0x7010, 0x7014 | 同构单元 D |
| **0x0101** | 110 | 0x10 ← **下一段命令流地址**，0x14 ← 链长度 | **PC 链控制** |
| 0x0041 / 0x0081 | 55 / 55 | 0x0000 / 0x0008 ← 0x60 | op_en 前置与总使能（TRM 要求） |
| 0x0000 | 138 | 0x0000 ← 0 | 空操作/填充 |

**四个同构单元（0x1001/0x2001/0x4001/0x8001）的寄存器基址依次是 0x4004 / 0x5004 /
0x6004 / 0x7004** —— 步长整齐的 0x1000。它们被写入同一个值 `0x0e`，
行为像是**并联的数据通路被一起使能**。这暗示硬件里有多组对称的处理通道。

> 注：三方的 block 命名（0x0801=DPU、0x1001=PPU）与 TRM 的位表**存在系统性错位**，
> 谁的命名对**尚未确认**。我们只采信「编号→寄存器偏移」这个可观测的对应关系，
> 不采信名字。

### 5.2 自延续模型（由真实数据证实）

我在第 3 节从 `PC_DATA_ADDR`/`PC_DATA_AMOUNT` 推断出"命令流是自延续的"，
现在在 `0x0101` block 里抓到了直接证据：

```
block 0x0101, 偏移 0x0010 ← 0x80c5c640   ← 下一段命令流的设备地址
block 0x0101, 偏移 0x0014 ← 0x0000000e   ← 该段的长度
```

**命令流可以在执行中途跳到另一块内存继续执行**，形成链。
这解释了为什么内核驱动只写 7 个寄存器就够，也提供了"长命令流分段按需加载"的优化路径。

## 八、下一步

1. **模板化**：把 615 条命令流按 `op_idx` 聚类，为每个算子生成"模板 + 变量槽位表"
2. **最小可运行**：取一个最简单的 op（如 9 字节的），只在变量槽位改值，提交给硬件
3. **边界探测**：故意写坏一条指令，看硬件报哪个中断位 → 反推中断语义
4. **SRAM 实验**：用 `RKNPU_MEM_TRY_ALLOC_SRAM` 分配，看 SRAM 有多大、命中后快多少
