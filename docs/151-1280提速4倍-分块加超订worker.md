# docs/151 — 1280 YOLO11 提速 4.09×：6.50 → 26.6 FPS

> 目标：只谈速度。把已验证的三条（分块 / 多实例 / C 运行时）合起来，并加一条新发现
> ——**必须超订 worker**。最终 1280 从 6.50 FPS 干到 26.6 FPS。

---

## 0. 结果

| 配置 | ms/帧 | FPS | 相对 |
|---|---|---|---|
| native 1280（单实例，绑 3 核） | 153.76 | **6.50** | 1.00× |
| 4×640 分块，单实例串行（3 核） | 123.72 | 8.08 | 1.24× |
| 4×640 分块，3 worker（每核 1 个） | 50.71 | 19.72 | 3.03× |
| 4×640 分块，4 worker | 47.05 | 21.25 | 3.27× |
| **4×640 分块，6 worker（每核 2 个）** | **37.4** | **26.6** | **4.09×** |
| 4×640 分块，8 worker | 43.26 | 23.12 | 3.56× |
| 4×640 分块，12 worker | 47.60 | 21.01 | 3.23× |

三个独立 100 帧长跑：**26.76 / 26.54 / 26.46 FPS**（偏差 <1.2%）。

---

## 1. 架构

```
输入 1280×1280
   │
   ├─ 切成 4 块 640×640（无需缩放，直接零拷贝喂）
   │
   ├─ 6 个 worker 线程抢 tile 队列（动态负载均衡）
   │     ├─ worker 0,3 → ctx0（绑 core0）
   │     ├─ worker 1,4 → ctx1（绑 core1）
   │     └─ worker 2,5 → ctx2（绑 core2）
   │
   └─ 每个 ctx 用 rknn_dup_context 复用同一份模型权重
```

要点：
- **ctx 用 `rknn_dup_context`**：3 个上下文共享权重，省内存
- **每个 ctx 单独 `rknn_set_core_mask`**：0/1/2 各绑一个核
- **worker 数 = 核数 × 2**：这是关键，见下
- tile 队列用互斥锁保护的自增下标，动态分配，实测负载极均衡（54/53/53）

## 2. ★ 新发现：worker 必须超订

| worker 数 | FPS | tile 吞吐 |
|---|---|---|
| 2 | 15.37 | 61.5/s |
| 3（=核数） | 19.72 | 78.9/s |
| 4 | 21.25 | 85.0/s |
| **6（=核数×2）** | **26.6** | **107/s** |
| 8 | 23.12 | 92.5/s |
| 12 | 21.01 | 84.0/s |

**worker = 核数时只有 19.7 FPS，加到 2 倍才 26.6 FPS。** 再多（8/12）开始退化。

### 为什么

因为**单次推理要发 99 次 ioctl**（`docs/144` ftrace 实测）。
3 个推理并发时，每秒要打 ~10,400 次 ioctl，**CPU 侧的内核路径先饱和了**，
NPU 反而在等。多开一个 worker 就是在轮转里把等待时间填掉。

> 反证：改用 `rknn_inputs_set`（缓存拷贝路径）替代 memcpy 直写，**19.94 vs 20.41 FPS 没区别**
> ⇒ 瓶颈不在数据拷贝，在提交路径。

## 3. 已经到多核天花板了

单个 tile 的推理耗时 28.5 ms，3 个核并行 ⇒ 理论上限：

```
3 core / 28.5 ms = 105.3 tile/s = 26.3 帧/s（每帧 4 tile）
```

实测 **107 tile/s = 26.6 FPS**，**已经贴在理论上限上**（100%）。

⇒ 想再快，只能减少单个 tile 的耗时（28.5 ms），而不是继续加并发。

## 4. 为什么不用 native 1280

| 问题 | 数值 |
|---|---|
| 耗时 | 153.76 ms（是分块方案的 4.1 倍） |
| 寄存器字段溢出 | 转换时报 30 次 `offset 0x4038/0x5048 limit 0x1fff` |
| 编译器模型 | cycle 数正好是 640 的 4.00×，但实测墙钟 5.04× |
| 提交数 / 核利用率 | 94 次 / 单核 56.4% —— 和 640 完全一样 |

⇒ native 1280 既没效率优势，又撞了寄存器边界；分块方案两头都占。

## 6. 边界（必须说清楚）

| 项 | 状态 |
|---|---|
| **精度** | **完全未验证**。所有 rknn 模型都是随机噪声标定的，检出恒为 0。这份只证明速度。 |
| 长时热稳定 | 未测。26.6 FPS 是 100 帧（约 3.8 s）的短跑，产线要压 30 分钟看降频。 |
| 边界目标 | 2×2 无重叠会在接缝切断目标；这属于精度问题，不是速度问题。 |
| 640 场景 | 单实例 35.2 FPS；3 实例并发 82.84 FPS（`docs/149/150`）。 |
