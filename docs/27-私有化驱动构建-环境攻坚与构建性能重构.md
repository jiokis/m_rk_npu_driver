> 承接 docs/26（私有化驱动构建方案）。本篇记录**实际动手构建时**踩到的环境问题、
> 对构建机的性能剖析结论，以及据此重构出的构建/部署链路。
>
> 状态：内核构建中（`6.1.99-rockchip-rk3588-priv1`），产物尚未上板。

## 1. 构建机是什么——先认清机器，再谈优化

之前一直假设这是一台普通笔记本。实测发现它是一台**虚拟机**：

| 项目 | 实测值 | 影响 |
|---|---|---|
| CPU | AMD Ryzen 9 8945H，8 物理核 / 16 vCPU（SMT） | 并发上限 16 |
| cpufreq | **`/sys/devices/system/cpu/cpu*/cpufreq/` 完全不存在** | 虚拟机不暴露调频；无法钉频，也无法靠 governor 加速 |
| 内存 | 7582 MB + 2048 MB swap | |
| 磁盘 | `/dev/sdd`，`lsblk -o ROTA` = **1**（机械盘虚拟盘） | 随机小文件写入慢 |
| 温度 | `sensors` 无输出 | 虚拟机不透传 |

这条直接推翻了「靠调 governor / 钉频来提速」的思路——**没有可调的东西**。

## 2. 免 root 补齐主机工具链（flex / bison / m4 / mkimage / dtc）

内核构建需要一堆主机工具，而这台机器上 **`flex`、`bison`、`m4`、`mkimage`、`dtc` 全都没有**，
`sudo` 又要密码（本会话审批关闭，`apt install` 不可用）。

解法：`apt-get download` 普通用户就能用，`dpkg-deb -x` 可以把 deb 解到任意目录。

```bash
mkdir -p ~/.local/kbtools/debs && cd ~/.local/kbtools/debs
apt-get download flex bison m4 libsigsegv2 u-boot-tools device-tree-compiler
mkdir -p ~/.local/kbtools/root
for d in ~/.local/kbtools/debs/*.deb; do dpkg-deb -x "$d" ~/.local/kbtools/root/; done
```

**两个必须知道的坑**（否则解出来也用不了）：

1. **bison 找不到 m4**：Debian 把 m4 路径编译成写死的 `/usr/bin/m4`，而我们解到了 `~/.local`。
   症状是 `bison: m4 subprocess failed: No such file or directory`。
   用环境变量覆盖：`export M4=~/.local/kbtools/root/usr/bin/m4`
2. **bison 找不到 skeleton**：skeleton 在 `/usr/share/bison`。
   覆盖：`export BISON_PKGDATADIR=~/.local/kbtools/root/usr/share/bison`

flex 反而不需要覆盖（skeleton 编译进二进制了）。这些都固化在
`scripts/build/host-tools-env.sh` 里，任何构建脚本 `source` 它即可。

验证：`flex 2.6.4` + `bison 3.8.2` + `m4 1.4.19` + `mkimage 2025.10` + `dtc 1.7.0`，
`make olddefconfig` 一次通过——**bison 3.8.2 与 6.1 内核的 kconfig 没有不兼容问题**。

> 附带收获：`mkimage` 本来只是为了让 dtb overlay 的 `fixup.scr` 能编出来，
> 而它正好也是后面做**双启动 `boot.scr`** 和**打包 `uInitrd`** 的必需工具。
> 我们还额外下了一份 **arm64** 的 `u-boot-tools` deb，作为板子离线时的兜底。

### 构建依赖预检结论（省掉了很多白等）

读板子原厂 `.config` 逐项确认，以下**都不需要**：

| 潜在依赖 | 结论 | 原因 |
|---|---|---|
| `pahole` | 不需要 | `CONFIG_DEBUG_INFO_BTF` 根本没开 |
| `libssl` / `openssl` 开发头 | ⚠️ **判断错了，实际需要** | 见下面第 2.1 节 —— `CONFIG_SYSTEM_TRUSTED_KEYRING=y` 会强制编译 `certs/extract-cert`，跟签不签名无关 |
| `objtool` / `libelf` | 不需要 | `CONFIG_OBJTOOL`、`CONFIG_STACK_VALIDATION` 均未开（那是 x86 的机制） |
| `cpio` | 不需要 | `CONFIG_INITRAMFS_SOURCE=""`，走内核自带的 `gen_init_cpio` |
| `lz4` / `lzo` | 不需要 | arm64 产出未压缩的 `Image`；且 `CONFIG_MODULE_COMPRESS_NONE=y` |

### 2.1 三个「解包 deb」才会遇到的坑（都实际踩了）

**坑 A：架构同名覆盖（最阴险，会静默坏事）**
arm64 的 `u-boot-tools` 与 amd64 的**文件名同名**。我把两个 deb 放在同一个目录里批量
解包，aarch64 的 `mkimage` 覆盖掉了主机的 x86-64 版本 —— 构建会在毫无提示的情况下
走到一个莫名其妙的失败。现在物理隔离：`~/.local/kbtools/debs/`（amd64，解包到本机）、
`~/.local/kbtools/board-debs/`（arm64，只打包送板子，绝不在本机解包）。

**坑 B：`certs/extract-cert` 需要 openssl 头文件**
第一次构建跑到这里炸：

```
certs/extract-cert.c:21:10: fatal error: openssl/bio.h: No such file or directory
make[2]: *** [scripts/Makefile.host:114: certs/extract-cert] Error 1
make: *** [Makefile:2009: .] Error 2
```

我原来的预检结论"MODULE_SIG 没开就不需要 libssl"是**错的**：
`CONFIG_SYSTEM_TRUSTED_KEYRING=y` 会让 `certs/Makefile` 无条件编译 `extract-cert`
这个主机工具。解法照旧免 root 解包 `libssl-dev`，并把 `.pc` 的 `prefix` 改到解包目录。

**坑 C：`openssl/opensslconf.h` 在 multiarch 目录里**
补完 libssl-dev 后 `bio.h` 能编到了，但它 `#include <openssl/opensslconf.h>` 又找不到。
原因：这个头不在 `/usr/include/openssl/`，而在
`/usr/include/x86_64-linux-gnu/openssl/`。真机上 gcc 默认就搜 multiarch 目录，所以
libcrypto.pc 里那句 `Cflags: -I${includedir}` 够用；我们解到别处之后这个默认路径没了。
→ 往 `.pc` 的 `Cflags` 显式补 `-I<root>/usr/include/x86_64-linux-gnu`。

这两个 openssl 的坑现在都由 `scripts/build/setup-host-tools.sh` 自动处理，
而且脚本最后会**真的编译一个用到 openssl 的小程序**并检查链接通过 ——
不是只看 `command -v` 存在就算数。


## 3. 性能剖析：真正的瓶颈不是内存，是「没人让路」

第一次用 `make -j14 Image dtbs modules` 直接把整机冻住，用户反馈「卡死了」。
按经验第一反应是内存打爆——**实测证明这个判断是错的**：

```
并发 gcc（-j8）：7 个 cc1，合计 RSS 369 MB，**均值只有 53 MB**
swap：138 MB，全程不增长
iowait：0.1%          ← 磁盘并没有在拖住 CPU
idle：49.1%
进程 %CPU 合计：约 1000%（可用 1600%）
```

- **内存从来不是瓶颈**：内核 .o 很小，8 个并发 gcc 才 400 MB 出头。
  真实内存消耗的是**链接 vmlinux 那一步**，而不是编译。
- **磁盘也不是 CPU 侧的瓶颈**：iowait 0.1%。
- 冻死的真正原因：**16 个线程被占满，且编译进程优先级与前台完全平等**，
  前台（桌面/我的 SSH/工具链调用）抢不到 CPU 时间片，表现就是「整机卡死」。

### 三重护栏

```bash
nice -n 15 ionice -c 3 make -j"$JOBS" LOCALVERSION="$LV" Image dtbs
```

1. `nice -n 15` —— 编译让出 CPU，前台永远是第一优先级
2. `ionice -c 3` —— 编译走 idle I/O 类，机械盘的带宽优先给前台
3. `-j8` —— 不发满 16 线程（实测 `-j8` 已能拿到 2.46 个 .o/秒）

效果（编译进行中实测）：**`bash -c true` 的启动延迟 0.02 s，机器完全可用。**

## 4. 最大的优化：砍掉 99.5% 的模块编译

翻板子原厂配置时发现一个决定性的事实——**所有启动关键驱动本来就全是 `=y`**：

```
MMC_DW_ROCKCHIP=y      MMC_SDHCI_OF_DWCMSHC=y   MMC_BLOCK=y    BLK_DEV_NVME=y
EXT4_FS=y              PCIE_ROCKCHIP_HOST=y     PCIE_DW_ROCKCHIP=y
PHY_ROCKCHIP_SNPS_PCIE3=y   PHY_ROCKCHIP_NANENG_COMBO_PHY=y
CFG80211=y             MAC80211=y               RFKILL=y       ← 连无线协议栈都是内置
```

整份配置里有 **792 个 `=m`**。板子实际加载了几个？**`lsmod` 说了算，不能靠猜**。
第一次我只想到 rtw89（因为它最显眼），上板一查发现是 **10 个模块**：

```
pwm_fan  rtw89_8852be  rtw89_8852b  rtw89_pci  rtw89_core  sch_fq_codel  fuse  ip_tables  pgdrv  r8125
```

差点漏掉的几个都是有用的：`r8125`（2.5G 有线网卡）、`pwm_fan`（风扇）、
`pgdrv`（Realtek 网卡 PG 工具）、`fuse`、`ip_tables`、`sch_fq_codel`。

再用 `modinfo -F depends` 把依赖闭包算出来，结论是**完全是平的**：

```
pwm_fan       depends:
fuse          depends:
ip_tables     depends:          ← 连依赖都没有，说明 x_tables 是内置的
sch_fq_codel  depends:
pgdrv         depends:
r8125         depends:
rtw89_8852be  depends: rtw89_pci,rtw89_8852b
rtw89_8852b   depends: rtw89_core
rtw89_pci     depends: rtw89_core
rtw89_core    depends:
```

也就是说**没有任何模块依赖自己目录之外的模块**。于是这 10 个模块恰好落在 7 个目录里，
可以只编这 7 个目录：

```
drivers/net/wireless/realtek/rtw89        → rtw89_core/pci/8852b/8852be（+ 配置里另外几个变体）
drivers/net/ethernet/realtek/r8125        → r8125
drivers/net/ethernet/realtek/realtek_pgtool → pgdrv
drivers/hwmon                             → pwm-fan
fs/fuse                                   → fuse, cuse
net/ipv4/netfilter                        → ip_tables 等
net/sched                                 → sch_fq_codel 等
```

所以构建目标从

```bash
make -j14 Image dtbs modules      # 编 792 个用不上的模块
```

改成

```bash
make -j8 Image dtbs                                       # 全部内置代码
for d in <上面 7 个目录>; do make -j8 M="$d" modules; done  # 只编这 7 个目录
```

**收益是双份的**：① 少编绝大部分用不上的模块；② 顺带省掉
`modules_install` → `depmod` → 打 200 MB 模块包 → 传给板子 → 装 `/lib/modules` → 重建 initramfs
一整条链路，最终只搬 **82 个 `.ko`**。

> 教训记下来：**「只有 4 个模块」是我凭印象推的，上板 `lsmod` 一查就是 10 个。**
> 涉及"板子到底依赖什么"的判断，必须上板实测，不能靠推理。

> 注意：这是**构建范围**的优化，**没有改配置**。`.config` 相对原厂仍然只差 8 行
> （`DEBUG_INFO` 关闭 + pahole 版本号这类装饰项），`RTW89_8852BE` 依然是 `=m`。
> 保持配置忠实，插桩改动才是唯一的显式 diff。

### DEBUG_INFO 为什么关掉

本机 7.6 GB 内存，arm64 vmlinux 带 DWARF 链接要吃 4–8 GB，而我们要反复迭代插桩构建。
关闭后：**运行行为零差异**，`CONFIG_KALLSYMS=y` 保留，oops/panic 回溯照样有符号名。
原始配置完整保留在 `build/.config.vendor`（**从未被改动**），想还原只需删掉
`prepare-kernel.sh` 里的两行 `set_kv`。

## 5. LOCALVERSION：模块目录绝不重叠

厂商侧是 `LOCALVERSION=-${LINUXFAMILY}`，即 `-rockchip-rk3588`。
我们用 **`-rockchip-rk3588-priv1`**（保留家族名 + 私有后缀）：

- 新内核模块落在 `/lib/modules/6.1.99-rockchip-rk3588-priv1/`，**与现有目录物理隔离**
- 即使新内核完全起不来，旧内核 + 旧模块目录毫发无损，双启动回退随时可用
- 版本号来源已查清：源码树里没有 `localversion*` 文件，`EXTRAVERSION` 为空，
  `CONFIG_LOCALVERSION=""` —— 所以 `-rockchip-rk3588` 是 orangepi-build 在
  make 命令行上传的，不是配置里的

## 6. 部署设计：安装与切换分离

`/boot/boot.scr`（由 `boot.cmd` 编译）里**写死了三个固定名字**：`Image`、`dtb/${fdtfile}`、`uInitrd`。

因此双启动用**符号链接切换**实现，而不是改 U-Boot：

| 做法 | 是否采用 | 理由 |
|---|---|---|
| 改 `boot.cmd` 做启动菜单 | ✗ | 要碰 U-Boot，有刷砖风险，还得改 `boot.scr` |
| U-Boot `bootcount`/`altbootcmd` 自动回退 | 待评估 | 最稳，但依赖 U-Boot 编译选项，需上板查环境 |
| **改 `/boot/{Image,dtb,uInitrd}` 符号链接** | ✓ | U-Boot 环境一点不动；旧内核文件原封不动；SSH 一条命令切换 |

配套脚本：

- `scripts/board/install-kernel.sh` —— **只新增带版本号的文件**，
  绝不碰 `Image`/`dtb`/`uInitrd` 三个符号链接。装完做完整性自检并明确说「尚未切换」。
  → 「装到一半失败」永远不会让板子起不来。
- `scripts/board/kernel-select` —— 切换/回退。首次运行会记录原厂指向到
  `/boot/.kernel-orig.targets`，`kernel-select orig` 一键回退。
- `scripts/build/deploy-to-board.sh` —— 笔记本侧：传输 + 触发板子侧安装，
  `--switch` 可以顺带切换重启并等板子回来做自动验收。

回退路径（按可行性排序）：
1. 还能进系统 → `kernel-select orig && reboot`
2. 完全起不来 → 串口进 U-Boot，或重刷 boot 分区 / SD 卡（D 盘有完整镜像 + RKDevTool）

## 7. 板子第 5 次假死，与两味「料」

构建期间板子**第 5 次失联**，症状：

```
ping 192.168.31.128     → 100% packet loss
ip neigh                → MAC 在表里（cc:21:9d:b0:5d:a2），状态 DELAY
并发 ping 扫 192.168.31.0/24 → 只有 .1/.8/.74/.104/.223/.237，板子没换 IP
```

「链路层有影子、网络层全丢」= 典型的 **WiFi 关联着但流量不通**，而不是内核挂死
（内核挂死的话 ARP 也不会应答，而且之前有过自愈记录）。这次需要断电重启。

针对这个毛病准备了两味料，**已上板安装并验证**：

| 脚本 | 治什么 | 原理 | 实测结果 |
|---|---|---|---|
| `scripts/board/setup-watchdog.sh` | **内核真挂住** | 不自己写喂狗程序，直接用 systemd 的 `RuntimeWatchdogSec=60`。由 PID 1 负责喂狗，没有「喂狗进程自己被饿死导致误重启」的风险 | ✅ 已激活：`RuntimeWatchdogUSec = 1min29s` |
| `scripts/board/setup-net-watchdog.sh` | **内核活着但 WiFi 假死** | 网关连续 3 次探测失败 → 分级自愈：重启 NetworkManager → 重装 rtw89 模块（重置固件状态机）→ 网卡 down/up → 连续 15 分钟不可达则重启板子。有冷却时间，全程写 journald | ✅ 服务 active + enabled |
| `scripts/board/setup-network.sh` | 从源头减少假死 | 关掉 WiFi 省电（`wifi.powersave=2`）。RTL8852BE 的 PS-Poll 状态机是假死的头号嫌疑；同时把连接设为无限重试 + 高优先级自动连接、启用 SSH 开机自启、清掉 apt 里那个已经死掉的 Docker 代理 | ⚠️ 见下 |

### 7.1 装看门狗时又踩的两个坑

**坑 D：判断"有没有看门狗"不能用属性文件**
`/dev/watchdog0`、`/sys/class/watchdog/watchdog0` 都在、设备树 `watchdog@feaf0000` 也是
`status=okay`，但脚本报「没找到硬件看门狗」直接退出。原因是我用
`/sys/class/watchdog/watchdog0/identity` 是否存在来判断 —— 而这个 `dw_wdt` 驱动
**一个 sysfs 属性都不暴露**（目录里只有 `dev/device/power/subsystem/uevent`，
`identity/state/timeout/nowayout` 全部不存在）。
→ 判断设备存在要认 `/dev/watchdog*` 和设备目录本身，不能认可选属性。

**坑 E：探测时报 EBUSY 其实是成功**
systemd 接管后会**独占持有** `/dev/watchdog0`，我们再去 `open()` 会拿到 `EBUSY`。
我一开始把它当失败，而且 `set -e` 让脚本在成功报告前就退出了。
**那个 EBUSY 本身就是"看门狗确实被 PID 1 拿着"的铁证** —— 现在把它当作成功信号打印。

顺带记下一个反直觉的细节：硬件只支持离散的超时档位，我们请求 60 s，
实际生效的是 **1min29s**（systemd 向上取到硬件支持的档位）。
所以"设了 60 秒"不等于"60 秒"，要读 `systemctl show -p RuntimeWatchdogUSec` 确认。

> 硬件看门狗只治「内核挂住」；假死那种「内核还活着」的情况它无能为力 —— 两个都要有。
> 另外硬件看门狗有个前提：`CONFIG_DW_WATCHDOG=y` 已在，但**现在没有任何人喂它**，
> 所以内核真挂住时板子只能等人工断电。这就是之前多次失联本可自愈却没自愈的原因。

## 8. 构建完成：实际产物与账目

**构建成功，0 报错。**

```
release         6.1.99-rockchip-rk3588-priv1
Image           41,402,880 字节
                ↑ 与板子上原厂 vmlinuz-6.1.99-rockchip-rk3588 的 41,402,880 **字节数完全相同**
                  （配置一致 → 内置代码一致；DEBUG_INFO 只影响 vmlinux，而 Image 是 objcopy
                   掉调试段后的产物，所以尺寸对得上。这正是"等价内核"的直观证据）
设备树          9 个，含 rk3588-orangepi-5-plus.dtb（282,629 字节）
模块            82 个 .ko，覆盖板子实际加载的全部 10 个模块
配置差异        相对原厂 8 行，全部是有意的（DEBUG_INFO 关闭 + pahole 版本号装饰项）
构建目标        Image dtbs + 7 个模块目录
构建并行        -j8  nice=15  ionice=idle
实测速率        2.46 个 .o/秒；编译全程 bash 启动延迟 0.02 s、swap 不增长、机器可正常使用
驱动源码        与板子在跑的 v0.9.8 **逐字节一致**（diff -rq 为空）→ 首版运行行为 = 现状，零回归
```

`diff -rq` 的结论值得单独强调：**内核树里的 `drivers/rknpu/` 与板子上正在运行的驱动源码完全一致**。
也就是说这份新内核的 NPU 行为与现状**完全相同**。「私有化驱动构建」这一步先把
「能自己编译出等价内核并成功上板」这件事做扎实，插桩再作为显式 diff 叠上去 ——
这样万一出问题，能立刻分清是"构建链路的问题"还是"插桩的问题"。

### 构建过程时间线（含三次失败）

| 阶段 | 结果 |
|---|---|
| `make olddefconfig` | 第 1 次失败：缺 `flex`/`bison`/`m4` → 免 root 解包补齐 |
| `make Image dtbs modules`（-j14） | 第 1 次失败：缺 `mkimage`（dtb overlay 的 fixup.scr）；**且把整机拖死** |
| 性能重构后 `make Image dtbs`（-j8） | 第 2 次失败：缺 `openssl/bio.h`（`certs/extract-cert`） |
| 补 openssl 后重跑 | ✅ 通过；随后 7 个模块目录全部编出 |

三次失败的共同点：**都是主机侧工具缺失，不是内核代码或配置的问题**。
这也说明那套"预检"做得还不够 —— 我预检了 `pahole/libelf/cpio/lz4`（结论正确，都不需要），
却漏了 `mkimage` 和 openssl 头文件。教训是：**预检不能只靠读配置推理，要真跑一遍**。
现在 `build-kernel.sh` 与实际构建已经跑通，下次改动只需增量重编。
