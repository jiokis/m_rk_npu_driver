## 一、为什么要多手段

前面几轮我基本只用了**一种**手段：`LD_PRELOAD` 抓运行时行为 + 统计。
那位用户提醒得对 —— 逆向不能技术单调。这条路做不动的地方，换一条：

| 手段 | 能回答什么 | 本轮进展 |
|---|---|---|
| **动态抓取**（LD_PRELOAD） | 硬件实际收到什么 | ✅ 已产出 615 条样本 |
| **静态反汇编**（本文件） | **代码为什么这么构造** | ✅ 找到类层次与 vtable |
| **参考模型比对**（NVDLA） | 寄存器语义是什么 | ⬜ 待做 |
| **可执行模拟**（自写模拟器） | 假设自不自洽 | ⬜ 待做（见第五节） |
| **差分实验**（改一个变量） | 哪个字段管什么 | ⬜ 需硬件 |

静态反汇编的价值：**它不依赖硬件、不依赖抓包，直接读代码意图。**
而且我们的目标（能不能自己造算子配置）本质上就是"读懂那段构造代码"。

## 二、RTTI 泄露了完整的发射器类层次 ★

二进制虽然 stripped（无 `.symtab`），但 **C++ RTTI 类型名还在**，这是第一个突破口。

```
rknn::runtime::RKNPUEmitter        ← 基类
rknn::runtime::RKNPUEmitterF2      ← 各代 NPU 一个
rknn::runtime::RKNPUEmitterT4
rknn::runtime::RKNPUEmitterV2
rknn::runtime::RKNPUEmitterLite
```

配套的目标名字符串：`RKNPU F2 / F3 / Lite / T3 / T4 / V2 / W1 / W2`

### 2.1 定位 typeinfo → vtable → 虚函数

| 类 | typeinfo | vtable | [2] | [3] |
|---|---|---|---|---|
| RKNPUEmitterF2 | `0x750940` | `0x74a8a8` | `0x5b9bf0` | `0x5b5780` |
| RKNPUEmitterLite | `0x750958` | `0x74a8d8` | `0x5b6a40` | `0x5b4ee0` |
| RKNPUEmitterT4 | `0x750970` | `0x74a908` | `0x5b6500` | `0x5b5bf0` |
| **RKNPUEmitterV2** | `0x750988` | `0x74a938` | **`0x5b8290`** | **`0x5b5300`** |

**方法 [0] 和 [1] 在四个类里完全相同**（`0x5b2a30` / `0x5b3390`，基类的构造/析构），
**[2] 和 [3] 是各自的重写** —— 那两个就是**目标相关的 regcmd 构造代码**。

> 关键含义：**regcmd 格式是"每代 NPU 一套"的**。
> 这解释了为什么不同 SoC 的 block 映射会不一样，也说明我们的 615 条样本
> 只代表 RK3588 这一套（V2 目标）。

### 2.2 确定 RK3588 用哪个

模型自己打印过：`target: RKNPU v2, target platform: rk3588`
（见 [04](04-regcmd格式.md) 的抓取日志）→ **RK3588 = `RKNPUEmitterV2`**。

## 三、目标名方法的定位（验证方法有效）

用**字符串交叉引用**找到了目标名 `name()` 实现：

```
0x562abc  → "RKNPU F2"    (add x3, x3, #0x4a8 → 0x6114a8)
0x562b24  → "RKNPU W2"    (0x6114b8)
0x562bdc  → "RKNPU V2"
```

每个都是 ~0x20 字节的小函数：取字符串地址 + `mov x4, #8`（长度 8）+ 调 `string::assign`。
这是**虚函数 `name()` 的标准形态**，说明定位方法有效。

## 四、★ 三个方法论教训（都是踩出来的）

### 4.1 搜小常量 = 假阳性地狱

我一开始直接搜 block_id 立即数（`0x41`/`0x81`/`0x201`），结果：

| 搜到的 | 真相 |
|---|---|
| `0xb7f04: mov w24, #0x41` | **ASCII 'A'**。那一段在组建字符表（0x41='A', 0x42='B', 0x43='C', 0x3e='>', 0x47='G'…） |
| `.rodata` 里 `0x0201` 成簇出现 | 是字节对 `01 02` 的巧合。同样 `0x0101` = `01 01` |

**教训**：`0x41`/`0x81`/`0x201` 这类小值在二进制里到处都是（ASCII、枚举、尺寸、对齐）。
**搜常量不可靠，要搜唯一的东西** —— 比如字符串地址、vtable 槽位、RTTI 指针。

### 4.2 编译器会调度 `adrp`/`add`，不能假设相邻

AArch64 取字符串地址是 `adrp` + `add` 两条，但**编译器会把 `add` 排在后面几条**：

```
0x000b7f14  adrp  x10, #0x5ec000
0x000b7f18  str   x6, [sp, #0x7e98]      ← 中间插了别的指令
0x000b7f1c  add   x6, x10, #0xa28        ← 而且用的是 x10，不是紧邻的 adrp
```

我第一版要求"相邻的 adrp+add"，结果 **0 命中**，白反汇编了 134 万条指令。

**正解**：**按寄存器跟踪** —— `adrp Rd, #page` 记 `pending[Rd]=page`，
遇到 `add Rd, Rn, #imm` 且 `Rn` 在表里就算目标；其它写 `Rd` 的指令清掉表项；
`blr/br/ret` 清空。改完立刻命中。

### 4.3 stripped 不等于没线索

`.symtab` 没了（`nm` 只能看到 482 个动态符号），但：
- **RTTI 类型名还在** → 能枚举出所有有虚函数的类
- **`.rela.dyn` 里有 28643 条 `R_AARCH64_RELATIVE` 重定位** → 应用后能正确读出
  `.data.rel.ro` 里的 vtable 指针（否则读到的是 0）

**这两条合起来，就能在没有符号表的情况下恢复出类的虚函数表。**

## 五、下一步（按可行性排序）

### 5.1 写一个 regcmd 软件模拟器（不需要硬件）★

用户建议的"搭配仿真"是对的方向，而且**本机就能做**：

把 NPU 的寄存器空间建模成一张表，写一个执行器：
```
输入：一条 regcmd 字节流
处理：逐条解码 → 写进虚拟寄存器表 → 追踪"哪些寄存器被写过、写了什么"
输出：寄存器时序、依赖关系、可疑写法
```

**它能直接回答我们卡住的问题**：
- 拿 615 条真实样本喂进去，看**寄存器写的顺序与重复模式**
- 检查"同一寄存器被写多次"的位置 → 那些就是分阶段配置（印证 PC 链）
- 把 `regcfg_amount` 与模拟器算出的"实际指令条数"对比 → **直接判定它的单位**
  （比等硬件做实验快得多，而且零风险）

### 5.2 找发射器本体

方法：从 vtable 的 `[2]`/`[3]`（`0x5b8290` / `0x5b5300`）往下追，
或找"把 8 字节写进缓冲"的循环 —— 特征是 `str x?, [x?, #imm]` 配合 8 的步长。

### 5.3 参考模型比对（NVDLA）

外部资料确认 RK3588 NPU 是 **NVDLA 衍生**。NVDLA 的寄存器规格是公开的，
可以把我们观测到的 CNA 寄存器（窗口 `0x1xxx`）与 NVDLA 的 CNA 块逐偏移比对，
**用公开规格去解释私有寄存器**。

### 5.4 硬件差分实验（有风险，需先解决安全问题）

只有在 5.1 的模拟器把假设收敛到很小范围之后再考虑。
