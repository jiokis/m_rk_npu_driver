# 37 · 字段级对撞：偏移全对，但字段语义没有完全对上

> docs/36 证明了**指令编码**与**寄存器偏移**与上游开源实现完全一致。
> 本篇是继续下钻到**字段级**的结果 —— 结论是：**偏移对上了，字段语义没有完全对上。**
>
> 这是个重要的边界：它决定"能不能直接照抄上游开源驱动的寄存器语义来驱动这块硬件"。
> 答案是 **不能**，必须用厂商自己的数据重新推导。
>
> 相关：[36](36-上游对撞与片上缓冲微架构.md)（偏移级对撞）

---

## 一、先确认偏移级是吻合的

对 CNA 域做逐条核对：

```
上游定义 43 个 CNA 寄存器 → 厂商写了其中 39 个（91%）
从未写的 4 个：S_STATUS / S_POINTER / OPERATION_ENABLE / CLK_GATE
              （都是状态与开关类，本来就由驱动代劳）
```

**所以寄存器"地址"层面是同一个硬件。** 这排除了"厂商用的是另一套寄存器布局"这个可能。

## 二、但字段解出来的值不合理

用上游 `registers.xml` 的位域去解厂商写的真实值（每个算子取第一段）：

| op | `DATA_SIZE0` | 解出 WIDTH | 解出 HEIGHT | `DATA_SIZE2` OUT_W | `DATA_SIZE1` CH_REAL | CH | `WEIGHT_SIZE0` 字节 | `WEIGHT_SIZE2` W×H×K |
|---|---|---|---|---|---|---|---|---|
| 1 | 0x02800022 | **640** ✓ | 34 ✗ | **320** ✓ | 2 ✗ | 16 | 768 | 2×2×12 |
| 2 | 0x01400046 | **320** ✓ | 70 ✗ | **320** ✓ | 11 ✗ | 16 | 4608 | 3×3×32 |
| 3 | 0x01400022 | **320** ✓ | 34 ✗ | **160** ✓ | 31 | 32 | 18432 | 3×3×64 |
| 4 | 0x00a00023 | **160** ✓ | 35 ✗ | **160** ✓ | 63 | 64 | 2048 | 1×1×32 |
| 9 | 0x00a00023 | **160** ✓ | 35 ✗ | **160** ✓ | 63 | 64 | 4096 | 1×1×64 |
| 10 | 0x00a0001c | **160** ✓ | 28 ✗ | **80** ✓ | 63 | 64 | 73728 | 3×3×128 |

### 解对的

- **`DATAIN_WIDTH`（0x1020 bits 16..26）**：640 / 320 / 160 / 80 —— **正是 yolov5s 的宽度降采样序列**
- **`DATAOUT_WIDTH`（0x1028 bits 0..10）**：320 / 320 / 160 / 80 —— **正是各层输出宽度**
  （顺带纠正我们的逆向：我们曾把 CORE `0x3014` 记为"输出宽**−1**"、`0x3018` 记为"通道**−1**"，
  这里 0x1028 是**直接宽度**、无 −1）
- **`WEIGHT_KERNELS`（0x1038 bits 0..13）**：12 / 32 / 64 / 128 —— **正是通道序列的形态**
- **内部自洽**：`WEIGHT_SIZE0(768) = WEIGHT_BYTES_PER_KERNEL(64) × WEIGHT_KERNELS(12)` ✓

### 解不对的

| 字段 | 上游位域 | 解出的值 | 合理值（yolov5s） |
|---|---|---|---|
| `DATAIN_HEIGHT` | 0x1020 bits 0..10 | 34 / 70 / 34 / 35 / 28 | 640 / 320 / 160 … |
| `DATAIN_CHANNEL_REAL` | 0x1024 bits 16..29 | 2 / 11 / 31 / 63 | 3 / 32 / 64 … |

而且注意一个可疑的巧合：

```
0x1010 CONV_CON2 = 544  →  上游位域 FEATURE_GRAINS[4..13] = 34
0x1020 DATA_SIZE0 低位  = 34
                            ↑ 两者完全同值
```

**"高度"字段的值恰好等于 `FEATURE_GRAINS`** —— 这更像说明这个字段**不是高度**，
而是某个与"粒度/条带数"相关的东西。也就是说：**上游对这两处的位域定义，与厂商的用法不符。**

## 三、这意味着什么

**结论：同一个硬件、同一套寄存器地址，但字段打包（field packing）与配置约定不同。**

可能的原因（当前无法用现有数据区分）：

1. **厂商运行时用的是不同 HW 修订版的位域** —— 地址相同、位布局不同。
   （Rockchip 的 vendor kernel 与 mainline 支持的硅版本可能不同。）
2. **厂商把一层拆成了"条带/粒度"为单位**，于是同名寄存器在不同阶段承载不同含义。
3. 上游 `registers.xml` 的位域本身就不完整/有误
   （证据：docs/36 里上游把 `op_en` 的 6 个有效位标成 `RESERVED`，还往里写 14）。

### 对"二次开发"的直接含义

| 想做的事 | 能不能照抄 Mesa | 说明 |
|---|---|---|
| 指令编码格式 | ✅ **可以** | docs/36 已逐位确证 |
| 寄存器地址 / 块归属 | ✅ **可以** | 39/43 CNA 寄存器被厂商实际使用，偏移吻合 |
| 状态位、中断、时钟开关 | ✅ 可以 | 驱动侧，上游有完整实现 |
| **写配置寄存器（尺寸/通道/权重布局）** | ❌ **不能** | 字段语义需从厂商数据重新推导 |
| **分块与 CBUF bank 分配策略** | ⚠️ 部分 | CBUF_BANKS=12 已被我们的数据独立确证（`DATA_BANK+WEIGHT_BANK ≡ 12`）；但具体分配公式待验证 |

**一句话**：**想自己生成命令流，编码层可以直接照抄上游；配置层必须重新逆向。**

## 四、下一步怎么把字段啃下来

字段语义是可以实证推出来的，方法已经在手（本项目的"字段自证"套路）：

1. **用相关性代替假设**：把 decoded 值按算子分组，看哪个字段与**已知量**（yolov5s 的
   通道序列、分辨率序列、tile 数）单调相关。docs/17 就是这么解出 12 个字段的。
2. **优先解 `DATA_SIZE0` 低位**：它等于 `FEATURE_GRAINS`，而 grains 是"输入被切成几条"，
   用 `输入高度 / grains` 应该得到一个整齐的条带高度 —— 用它反推该字段的真实含义。
3. **权重字段用内部自洽约束**：`WEIGHT_BYTES = BYTES_PER_KERNEL × KERNELS` 恒成立，
   再叠加 `BYTES_PER_KERNEL = W×H×CH`，就能反解出真实的三元组。
   op1 解得 2×2×16 vs 期望 3×3×3 —— 差得很远，说明**要么权重被重排/补零，
   要么这个 tid 的 WEIGHT 区不是按层组织的**。这条要单独查。
4. **拿 RKLLM 的 13383 条样本做交叉**：LLM 的全连接层权重布局简单得多，
   在那里验证权重字段的语义会比在 CNN 里容易。

## 五、诚实总结

- **接口层（指令编码、寄存器地址、块拓扑、段结构、调度 ABI）**：逆向完成，且有上游交叉确证。
- **字段层**：**部分完成**。尺寸/宽度/输出宽度/权重总量这类"整值"字段解对了；
  高度、输入通道、权重三维布局这类"打包相关"字段**没解对**。
- **微架构层**：拿到了片上缓冲的真实参数（384 KB / 12 bank）与使用情况
  （`WEIGHT_REUSE` 40%、`DATA_REUSE` 0%），但**命令流如何精确编排流水**仍未完全掌握。

要继续往下，最有效的一步是把 **RKLLM 的 13383 条样本**拿来解权重/通道字段 ——
那里布局更简单，能先把字段语义的"锚点"钉住，再回来啃 CNN 的分块。
