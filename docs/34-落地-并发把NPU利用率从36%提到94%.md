# 34 · ★★★ 落地：并发把 NPU 利用率从 36% 提到 94%（零代码改动）

> 这是本目标（"最大化 NPU 利用率"）**第一个真正落地的手段**，而且不需要改驱动、
> 不需要碰闭源运行时、不需要重新编译任何东西。
>
> 本篇还记录了内核 CPU 到底花在哪（结论：不在驱动里，所以驱动插桩救不了它）。

## 一、先排掉一个假方向：内核 CPU 不在驱动里

docs/33 量出一次推理 `sys CPU = 9.5~10 ms`，而 NPU 硬忙只有 `9.0~10.5 ms`。
看起来"驱动自己烧了不少内核时间"。但那是把两件不同的事混在一起了：
**阻塞等 NPU 完成的墙钟不算 CPU 时间。**

于是写了个探针（`src/probes/rknpu_ioctl_cpu.c`），按 ioctl 类型统计
**线程 CPU 时间**（`CLOCK_THREAD_CPUTIME_ID`，阻塞不计入）：

```
# 23 次推理累计
类型           次数     CPU_ms   CPU/次_us     占比
SUBMIT         1771    21.36      12.1        42.0%
MEM_CREATE        7    10.83    1546.7        21.3%   ← 一次性（7 个缓冲区）
MEM_DESTROY       7    11.76    1679.6        23.1%   ← 一次性
MEM_SYNC        194     6.60      34.0        13.0%
合计           2023    50.85            = 2.21 ms/推理
```

**稳态下 RKNPU 的 ioctl 只吃 1.2 ms/推理**（SUBMIT 0.93 + MEM_SYNC 0.29）。
而实测 `sys` 是 10 ms ⇒ **8.8 ms 的内核 CPU 根本不在 RKNPU 驱动里。**

### 那 8.8 ms 在哪：`strace -c` 全量系统调用

```
3 次推理合计 104.6 ms：
  ioctl      20.3 ms   735 次   ← 含阻塞等 NPU
  read       12.8 ms   931 次
  munmap      6.5 ms   236 次  ┐
  mmap        3.9 ms   381 次  │  内存管理类
  mprotect    2.9 ms   200 次  │  ≈5.4 ms/推理、308 次调用
  brk         2.5 ms   107 次  ┘
  pread64     3.1 ms   616 次
  openat      2.0 ms   705 次   ← 235 次/推理
```

**每推理数百次 mmap/munmap/mprotect/openat 的内存抖动**，全部来自闭源 librknnrt。
结论很清楚：**给驱动程序插桩救不了这 8.8 ms**，那部分不归我们管。

> 这个判断很重要 —— 它让我**没有**去做那个本来排在第一优先级、但实际收益很小的
> "驱动 submit 路径分段计时"。省下了整整一轮构建-部署-测量。

## 二、换个角度：宿主开销能不能与 NPU 工作重叠？

既然 2/3 的时间是宿主侧（CPU 在算）、只有 1/3 是 NPU（硬件在算），那么
**把多个推理并发起来，一个的宿主开销就能盖住另一个的 NPU 时间。**

这正是"提高 NPU 利用率"最直接的思路，而且完全不需要改代码。

### 实验

`scripts/board/bench-concurrency.sh`：跑 N 个并发进程，每进程做 M 次推理，
测**聚合吞吐**。

> ⚠️ 第一版测错了：`t0` 取在 launch 进程**之前**，于是 Python 启动 + 模型加载
> （约 1 秒的固定偏移）也被算进墙钟。单路时这个偏移占比最大，
> 结果**把 1 路的吞吐压低、虚高了并发的相对收益**。
> 改成由每个 worker 自报「推理循环」的绝对起止时间（打 `WINDOW` 标记行），
> 父进程取所有 worker 的最早开始与最晚结束 —— 这才排除掉启动开销。

### 结果

| 并发 | 总吞吐（次/s） | 相对 1 路 | **占 NPU 理论上限** |
|---|---|---|---|
| 1 路 | 34.65 | 1.00× | **36%** |
| 2 路 | 51.71 | 1.49× | 54% |
| **4 路** | **84.59** | **2.44×** | **89%** |
| **6 路** | **89.28** | **2.57×** | **94%（饱和）** |
| 8 路 | 87.65 | 2.52× | 92% |

NPU 理论吞吐上限 = `1 / NPU单次硬忙(10.51 ms)` ≈ **95 次/s**。

### ★★ 三重独立验证

| # | 方法 | 说的事 | 数字 |
|---|---|---|---|
| 1 | docs/33：读驱动回写的 `hw_elapse_time` | 单进程时 NPU 硬件忙碌占比 | **32~36%** |
| 2 | 并发吞吐曲线 | 单进程吞吐占 NPU 上限的比例 | **36%** |
| 3 | **6 个进程全挂探针，把各自的 `hw_elapse_time` 加总除以并发窗口** | 并发下的 NPU 利用率 | **90.7%** |

第 3 项的实测明细：

```
探针日志数 6/6   并发窗口 2.079 s
6 进程 NPU 硬忙合计 1.885 s  ->  NPU 利用率 90.7%
6 进程 ioctl 墙钟合计 7.359 s
```

注意最后一行：`7.359 s > 2.079 s` 窗口 —— 多个进程的 ioctl 墙钟之和**远超**并发窗口，
说明它们在 NPU 上**排队**。这正是"NPU 被喂饱"的直接证据（若 NPU 没饱和，各进程的
ioctl 应当并行完成，墙钟之和不会超出窗口这么多）。

三个方法来源完全不同（驱动回写的硬件计时 / 端到端吞吐 / 多进程累加硬件时间），
**1↔2 一致到 1 个百分点内，3 独立确认并发下确实饱和**。按本项目定下的规矩，这种交叉印证才算数。

## 三、落地的建议

```
单进程吞吐   34.65 次/s   ← NPU 只用 36%，2/3 时间在等宿主
4 路并发     84.59 次/s   ← 2.44×
6 路并发     89.28 次/s   ← 2.57×，已饱和
8 路并发     87.65 次/s   ← 略降（CPU/内存竞争开始反噬）
```

**建议：4~6 个并发推理进程/线程。** 超过 6 路不再有收益，8 路反而略降。
6 路时实测 NPU 利用率 **90.7%**（单进程只有 32~36%）。

工程上对应到常见做法：
- 多路视频流分析：每路一个 worker，4~6 路并行
- 服务化：4~6 个 worker 进程 + 队列
- 单进程内：4~6 个线程各自持有一个 `RKNNLite` 实例（**不能共用一个实例**，
  运行时是同步的）

### 边界条件（必须说清楚）

- **这是吞吐收益，不是延迟收益。** 单次推理的端到端延迟不变（仍然 26~33 ms）。
  对延迟敏感的单路场景，这个手段无效。
- 前提是应用可以并行化。
- 需要注意的是多进程各自加载一份模型（内存占用 ×N）。可用共享内存/多实例复用缓解。

## 四、把已知手段按"端到端收益"排个总账

| 手段 | 端到端收益 | 代价/前提 | 状态 |
|---|---|---|---|
| **4~6 路并发** | **2.44~2.57×** | 应用可并行；内存 ×N | ✅ **本轮落地，零代码** |
| DDR 钉频 | ~1.16× | 功耗/发热上升 | ✅ 已做（`rknpu-perf.service`） |
| 三核（core_mask=7） | ~1.10× | 无 | ✅ 已开 |
| 加 DDR 带宽 | ≈1.0× | 带宽只用 26% | ❌ 无效 |
| 改驱动 submit 路径 | ≈1.0× | 只占 1.2ms/推理 | ❌ 已用测量排除 |
| 非阻塞提交 | 上限很低 | 提交间空档仅 ~6~13% | ⚠️ 降级 |
| 减少宿主内存抖动 | 潜在可观 | **在闭源 librknnrt 里** | ⚠️ 不可控（除非 shim） |

> 这张表本身是本次逆向的一个结论：**"最大化 NPU 利用率"这件事，
> 在当前这块板子上，最大的杠杆既不在 NPU、也不在驱动，而在"怎么用"**——
> 把宿主开销与 NPU 工作重叠起来。

## 五、下一步

1. **验证并发下 NPU 真的饱和了**：在 6 路并发运行时，用 LD_PRELOAD 探针在其中一个
   进程里读 `hw_elapse_time` 累积值 —— 若它接近 95 次/s 对应的硬件时间，就坐实了饱和。
2. **多实例能否共享模型权重**：4~6 路各加载一份 7 MB 模型是浪费。
   看 rknn 是否支持多 context/共享权重；这属于工程优化。
3. **回到 NPU 本身**：并发已经把它喂饱到 94%，说明剩下的空间只有 6%。
   **继续挖 NPU 微结构（指令集/流水）的边际收益已经很小** ——
   除非目标是"降低单次延迟"，那才需要回到 docs/19 的流水串行问题。
   这个判断值得明确记下来，避免后面把力气花在只有 6% 空间的方向上。
