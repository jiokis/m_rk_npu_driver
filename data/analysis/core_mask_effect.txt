# ★★★★★ 换 core_mask 重抓：**「3 次重复」与核数无关**（docs/136，修正 docs/134/135）
#
# 抓取（板子）：
#   LD_PRELOAD=~/rknpu_capture.so RKNPU_DUMP_DIR=/tmp/tvcapN RKNPU_DUMP_BUFS_MAX=0 \
#     python3 -c "RKNNLite: load resnet18.rknn; init_runtime(core_mask=...); inference 一次"
#
# ── 3 核（core_mask=0x7 / NPU_CORE_0_1_2）──
#   5 个 submit，Σtask = 74；tasks_*.bin = 240+40+2400+40+240 = 2960 B
#   submit 3 的 op_idx:  7..23 | 1..23 | 1..17      ← op_idx **两次从 1 重启**
#   f14 取值：0 / 1024 / 2048
#
# ── 1 核（core_mask=0x1 / NPU_CORE_0）──
#   **1 个 submit**，75 个 task；tasks_000.bin = 3000 B
#   op_idx: 1,1,1,2,3,...,23 | 1,1,1,1,2,...,23 | 1,1,1,1,3,...,20
#           ← op_idx **仍然两次从 1 重启** ⇒ 仍然是 3 遍！
#   f14 取值：0（74 个）/ 512（1 个）
#
# ── ★★★ 结论（修正 docs/134/135）──
#   ① 「3 遍算子序列」**在单核下依然存在** ⇒ **它不是 3 个核**！
#      而是编译期就烘进模型的 **3 个 surface**（对应 pass 清单里的 RKNNMultiSurfacePass）。
#      ⇒ docs/134/135 里「3 次重复 = 3 个核」的说法**错误**，现修正为「3 个 surface」。
#   ② core_mask 改变的是**提交调度**，不是模型内容：
#        1 核：1 个 submit / 75 个 task
#        3 核：5 个 submit / 74 个 task
#      ⇒ **提交数依赖 core_mask**，不是纯编译期量。
#      ⇒ 这也说明 .rknn 是固定的，调度在 init_runtime(core_mask=...) 时决定。
#   ③ f14 随 core_mask 变（3 核：0/1024/2048；1 核：0/512）
#      ⇒ f14 与核数/缓冲布局有关，但**不是简单的「核序号」**（1 核时出现 512）。
#   ④ 每份权重的 3 个副本 = 3 个 surface 各自的权重切片（docs/134 的地址证据仍然成立），
#      但「每核一份」的解释**错了** —— 是**每个 surface 一份**。

# ── ★★★★ 三种核数的完整对比（同一个 resnet18.rknn）──
#   核数   submits   Σtasks   submit1        submit2   submit3          submit4    submit5
#   1 核      1        75      全部(ops1-23,75个)   —        —              —          —
#   2 核      5        54      8个 ops1-5     1个 op6   40个 ops7-19     1个 op20   4个 ops21-23
#   3 核      5        74      6个 ops1-5     1个 op6   60个 ops7-17     1个 op18   6个 ops19-23
#
#   ★★★★ 段边界在**算子编号**上几乎一样：[ops 1-5] [单个算子] [中段] [单个算子] [尾段]
#     2 核：1-5 | 6 | 7-19 | 20 | 21-23
#     3 核：1-5 | 6 | 7-17 | 18 | 19-23
#   ⇒ **图的切分位置不随核数变**（只有中段/尾段的分界挪了 2 个算子）
#   ⇒ 变的是**每段里放多少个 task**
#
#   ★★★ 每段 task 数 ≠ 核数 × 算子数：
#     3 核段1：ops 1-5 但只有 6 个 task（3×5=15 不对）
#     2 核段1：ops 1-5 但只有 8 个 task（2×5=10 不对）
#   ⇒ task 数是**运行期规划**的结果，不是简单的乘法
#
#   ★★★ 结论：**task 列表由 librknnrt 在 init_runtime(core_mask=...) 时规划生成**
#     （.rknn 固定，但提交划分与 task 数随 core_mask 变）
#     ⇒ 「提交数预测模型」= 对 **librknnrt 调度器**建模，而不是对编译器建模
#     ⇒ 这是目标②的问法修正：不再是「模型 → 提交数」，而是「模型 × core_mask → 提交数」
#
#   ★ f14 与核数相关：1 核 {0,512}；2 核 {0,1024}；3 核 {0,1024,2048}
#     且 3 核时只在「同算子多 task」处出现非零 ⇒ 与**分片/缓冲布局**有关，不是核序号

# ── ★★★★★ 再补一轮：干净重抓 1 核（NPU_CORE_0 与 NPU_CORE_1 各一次）──
#   1 核（core 0）：1 个 submit，75 个 task，op_idx 从 1 重启 2 次 ⇒ **3 遍**（25/28/22）
#   1 核（core 1）：1 个 submit，75 个 task，op_idx 从 1 重启 2 次 ⇒ **3 遍**（25/28/22）
#   2 核          ：5 个 submit，54 个 task，重启 1 次           ⇒ **2 遍**（28/26）
#   3 核          ：5 个 submit，74 个 task，重启 2 次           ⇒ **3 遍**（26/24/24）
#
#   ★★★ 遍数 = 3 / 2 / 3（1/2/3 核）—— **既不是恒为 3，也不等于核数**
#   ⇒ 「遍数」由运行期调度器决定；它把图切成若干**含全部算子的切片**（surface）
#   ⇒ 每片都包含从算子 1 到最后一个算子的完整序列（所以 op_idx 会重启）
#   ⇒ **docs/134/135 的「3 遍 = 3 个核」被彻底否定**（1 核也是 3 遍；2 核只有 2 遍）
#   ⇒ 但「3 遍 ≠ 3 核」这个**修正方向**是对的，只是遍数本身也不是常数
