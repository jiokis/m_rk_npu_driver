# docs/146 — 40 字节 task 描述符：三个未解字段一次结案

> `docs/135/136/137` 一直挂着三个字段没定性：`f08`（29 或 96）、`f0c`（768 或 3072）、
> `f18`（122 或 26）。这份把它们钉死，并说明**哪些是已有的、哪些是本轮新增的**。

---

## 0. 结论

| 偏移 | 曾经叫 | 真实含义 | 证据强度 |
|---|---|---|---|
| `+0x08` | `f08` | **`enable_mask`** —— 本次要跑的流水级位图 | struct 定义 + **983/983** 形式化验证 |
| `+0x0c` | `f0c` | **`int_mask`** —— 哪个级发完成中断，**2 bit / 级** | **本轮新增**，**983/983** |
| `+0x18` | `f18` | **`regcfg_amount`** —— 指令条数（每条 8 字节） | `docs/145` 已结案 |

**关键点：这三个不是寄存器，是 task 描述符里的字段。** 之前一堆猜测都建立在
「寄存器」的前提上，方向就错了。

---

## 1. 字段来源：驱动里的 `struct rknpu_task`

`artifacts/rknpu-module/src/include/rknpu_ioctl.h`：

```c
struct rknpu_task {
    __u32 flags;          /* +0x00 */
    __u32 op_idx;         /* +0x04 */
    __u32 enable_mask;    /* +0x08  ← f08 */
    __u32 int_mask;       /* +0x0c  ← f0c */
    __u32 int_clear;      /* +0x10 */
    __u32 int_status;     /* +0x14 */
    __u32 regcfg_amount;  /* +0x18  ← f18 */
    __u32 regcfg_offset;  /* +0x1c */
    __u64 regcmd_addr;    /* +0x20 */
} __packed;               /* 合计 40 字节 ✓ 与实测一致 */
```

抓取库每 40 字节存一份 `tasks_NNN.bin`，直接按这个结构解即可。

---

## 2. `enable_mask`（f08）—— 语义早已记录，本轮是**大规模验证**

`src/analysis/ppu_path.py` 里其实已经写下了三条：

```
0x1d = CNA|CORE|DPU|DPU_RDMA   → 卷积
0x18 = DPU|DPU_RDMA            → 逐元素/激活
0x60 = PPU|PPU_RDMA            → 「池化」（这个标签是错的，实际是张量搬运/切片）
```

**所以位含义不算新发现。** 本轮做的是两件此前没做的事：

### 2.1 在 983 条**完整**命令流上做形式化验证

```
enable_mask 的位集合  ==  该流里实际出现的 block 集合
一致 983 / 不一致 0
```

不是抽样、不是推断 —— 逐条比。

### 2.2 全语料只有 3 种取值

| `enable_mask` | 流水级 | 出现次数 |
|---|---|---|
| `0x1d` | CNA + CORE + DPU + DPU_RDMA | **688** |
| `0x60` | PPU + PPU_RDMA | **173** |
| `0x18` | DPU + DPU_RDMA | **122** |

四个模型（resnet18 / mobilenet_v2 / shufflenet / mnasnet）加起来只有这三种组合。
⇒ **这些网络只用到 3 种流水配置**，没有第四种。

## 3. `int_mask`（f0c）—— ★本轮新增

### 3.1 编码：每一级占 2 bit

```
0x0300 = bits 8,9    → 级 4
0x0c00 = bits 10,11  → 级 5
```

`级号 = 最低置位 / 2`。

### 3.2 规则：指向「执行顺序上最后一个**非 PPU_RDMA** 的级」

```
predicted = 该流中执行顺序上最后一个 stage != 6 (PPU_RDMA) 的级
实测 int_mask 的级 == predicted      → 983 / 983 全中
```

三个组合逐一对照：

| `enable_mask` | 流里的级 | `int_mask` | int 级 |
|---|---|---|---|
| `0x1d` | 0, 2, 3, 4 | `0x0300` | 4（DPU_RDMA） |
| `0x18` | 3, 4 | `0x0300` | 4（DPU_RDMA） |
| `0x60` | 5, 6 | `0x0c00` | 5（PPU） |

### 3.3 `0x8001`（PPU_RDMA）**从不发中断**

这是那条「最后一个非 PPU_RDMA」规则的来源：PPU_RDMA 是纯写回级，
完成信号由它上一级（PPU / DPU_RDMA）发出。

## 4. 编号公式（两条，零反例）

### 4.1 block id

```
block = ((0x02 << stage) << 8) | 0x01
```

| stage | block | 谁 |
|---|---|---|
| 0 | `0x0201` | CNA |
| **1** | **`0x0401`** | **从未出现** |
| 2 | `0x0801` | CORE |
| 3 | `0x1001` | DPU |
| 4 | `0x2001` | DPU_RDMA |
| 5 | `0x4001` | PPU |
| 6 | `0x8001` | PPU_RDMA |

### 4.2 寄存器窗口

```
reg >> 12 == stage + 1
```

983 条流、十几万条指令，**0 个反例**：

| 级 | 窗口 | 实测寄存器范围 |
|---|---|---|
| 0 CNA | 0x1 | `0x100c .. 0x1184`（48 个） |
| 2 CORE | 0x3 | `0x3010 .. 0x3030`（5 个） |
| 3 DPU | 0x4 | `0x4004 .. 0x412c`（51 个） |
| 4 DPU_RDMA | 0x5 | `0x5004 .. 0x506c`（18 个） |
| 5 PPU | 0x6 | `0x6004 .. 0x60dc`（18 个） |
| 6 PPU_RDMA | 0x7 | `0x7004 .. 0x7030`（8 个） |

⇒ **这是一条 7 级流水线**（stage 0–6），其中 **stage 1 从没被用过**
（窗口 0x2xxx、block `0x0401` 完全空白）。

## 5. 对 SD 部署的意义

`docs/144` 测到 SD 的 806 次提交里 **55% 是单核**。现在能对上一条：
单核提交对应的是「`N % 3 != 0` 的算子组」，而算子组的大小由**算子类型**决定 ——
上面的三种 `enable_mask` 组合里，`0x60`（PPU 张量搬运）占 173/983，
这类算子天然任务数少，最容易凑不满 3 的倍数。

## 6. 诚实边界

| 事 | 状态 |
|---|---|
| `enable_mask` 位含义 | 项目里早有（`ppu_path.py`），本轮只是 983/983 验证 |
| `int_mask` 规则 | **拟合极好（983/983），但「为什么是最后一级非 PPU_RDMA」没有机理证明** |
| stage 1 是什么、为什么不用 | **未知**。窗口 0x2xxx 完全空白 |
| 「最后一个非 PPU_RDMA」 | 这是**观察到的规律**，不是从硬件文档推出来的 |
| `int_clear = 0x1ffff` | 全语料恒定，含义未追（清全部中断位） |

**没有做的验证**：改 `int_mask` 的某一位看会不会少一次中断 —— 那要动硬件，
需要先设计安全的对照实验（`docs/09` 的边界）。
