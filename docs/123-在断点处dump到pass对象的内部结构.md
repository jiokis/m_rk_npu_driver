## 3. ★ 三个可继续追的指针

| 槽位 | 指向 | 解引用后 |
|---|---|---|
| `[5]` | `0x64edc88` | 首 8 字节 `0x0000000046495245`（含 ASCII `ERIF`，**疑似类型标签/magic**）+ `0x65210e8` |
| `[7]` | `0x6256900` | `0x6332f56` + 一个看起来像随机数的值 |
| `[12]`/`[13]` | `0x6510eb0` / `0x65130c0` | 都以 `0x0` + `0x161`（=353）开头 ⇒ **同构对象**，`0x161` 可能是**数量/大小** |
| `[18]` | `0x63bd1d8` | 指向**自身内部**（+0x158）⇒ 可能是某个**链表/容器头**（自引用） |

**⇒ 这些是找 IR/Module 的线索。**

⚠️ **我**不**推断 `0x46495245` 是什么** —— 它看起来像 ASCII（`ERIF`），
但**在没有验证前只能记为「疑似类型标签」**。（这个项目里我因为「猜结构」吃过多次亏。）

## 5. 教训（本轮新增）

1. **★★★ 验证可以分层做，而且每层都便宜。**
   docs/122 验证了「vtable **地址**对」；本轮验证了「vtable **内容**对（前两项 = 提取的地址）」。
   **两层都做了，才敢说「地址确实属于这个类」。**
2. **★ 我不推断 `0x46495245` 是什么。** 它像 ASCII、像 magic，但**没有验证**。
   在这个项目里，「猜结构」已经让我栽过多次（docs/63/76/92/93）。
   **观测到的东西要按「观测到的」记录，推断部分要显式标注。**
3. **★ dump 内存时要「先看指针、再看内容」。** 24 个 quadword 里大部分是 0；
   **先把非零的挑出来解引用，比逐个解释每个槽位高效得多**（本轮就是这么做的）。
