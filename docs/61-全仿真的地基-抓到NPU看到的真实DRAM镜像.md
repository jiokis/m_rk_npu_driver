# 61 · 全仿真的地基：把 NPU 看到的**真实 DRAM 镜像**抓下来了

> 用户判断：「**尽量直接把 NPU 的全仿真做出来，没有仿真环境终究不能高自由度开发**」。
> 这个判断是对的 —— 前六轮我们在硬件上试错（而且历史上手写命令流挂过板两次），
> 没有仿真就只能「改一点、上板、看结果」，自由度上不去。
>
> **本轮把仿真器最硬的前置条件解决了：拿到 NPU 实际读写的 DRAM 字节。**
> 没有它，执行器无论怎么写都无法验证 —— 因为你不知道权重在内存里长什么样。

---

## 0. 本轮拿到的三样东西

### 1. NPU 看到的完整 DRAM 镜像（新能力）

扩展了 `src/probes/rknpu_capture.c`：新增 `RKNPU_DUMP_BUFS` / `RKNPU_DUMP_BUFS_MAX`
两个环境变量，在**每次提交时**把已登记的缓冲区内容落盘。

```
RKNPU_DUMP_BUFS=2  ⇒ 每次提交都 dump      （mode 1 = 只 dump 首个提交）
RKNPU_DUMP_BUFS_MAX=33554432              （单缓冲区上限，默认 32 MB）
文件名：buf_<提交序号>_dma<设备地址>.bin
```

实测（`tiny_cnn`，6 次提交）：

```
[BUFS] 落盘 5 个缓冲区，共 786432 字节（seq=0）   × 6
61 个 .bin（含 regcmd），4.7 MB
```

### 2. ★ 识别出了**量化权重缓冲区**

`tiny_cnn` 的 5 个缓冲区（`dma_addr` / 大小 / 头部字节）：

| 缓冲区 | 大小 | 头部 | 判读 |
|---|---|---|---|
| `0xfff40000` | 4,096 | 全 0 | 参数/控制块 |
| `0xfff41000` | **151,552** | 全 0 | **输入**（224×224×3 = 150,528 + 对齐） |
| `0xfff66000` | **552,960** | 全 0 | 暂存/中间特征 |
| `0xfffed000` | **73,728** | `4f 46 eb 06 06 06 06 …` | ★ **量化权重**（非零，且是唯一有内容的） |
| `0xfffff000` | 4,096 | `00…01 00 00 00 1d 00 00 00 00 03 00 00` | ★ **控制块**，偏移 8 处正是 `op_en = 0x1d` |

**权重缓冲区 73,728 B vs 真实参数量 24,112 个（INT8 ≈ 24 KB）⇒ 约 3 倍** ——
这正是 docs/44 记的**对齐/分块布局**（`align(in_ch,32)`、`kernels` 对齐到 2、
以及 Mesa 公式里那个 `×2`）。**现在可以用真实字节去验证布局假设了。**

### 3. 一个现成的**黄金参照**：rknn-toolkit2 自带模拟器

实测（本机 x86）：

```
r.config(target_platform='rk3588', ...); r.load_onnx(...); r.build(...)
r.init_runtime()            # ← 不传 target
  → "I Target is None, use simulator!"
  → 推理 0.01 s，输出 [1,10] = [0.571, 1.102, -0.619, 0.738, 1.372, ...]
```

**⇒ 板子实测 + 官方模拟器 = 两个独立参照。** 我们的命令流执行器可以同时对着两个校验。

## 1. 全仿真的分阶段方案

| 阶段 | 内容 | 验证方式 | 状态 |
|---|---|---|---|
| **①** | **DRAM 镜像抓取**（权重/输入/暂存/控制块） | 文件大小与缓冲区表一致；权重缓冲区非零 | ✅ **本轮完成** |
| **②** | 地址→缓冲区映射 + 逐 tile 配置解析 | 已有（`src/sim/rknpu/` 的 regcmd 解码 + tiling 验证） | ✅ 已有 |
| **③** | **权重布局解码**（把 73,728 B 拆成各层的量化权重） | **用已知的 ONNX 浮点权重量化后比对字节** | ⬜ 下一步 |
| **④** | 算子执行器（conv/depthwise/pool/elementwise + INT8 定点语义） | 与**板子实测输出** + **官方模拟器输出**双向比对 | ⬜ |
| **⑤** | 结构级时序模型（提交地板/每轮=每核一个 tile/阵列 32×32/CBUF banking） | 与 `hw_elapse_time` 逐提交比对 | ⬜ |
| **⑥** | **离线实验**：去掉冗余拷贝、合并提交、改 tiling | 先在仿真里验证**正确性 + 收益**，再考虑上板 | ⬜ |

### 为什么 ③ 是**可验证**的（这是本方案能成立的关键）

我们**自己生成了这些 ONNX 模型**，所以知道浮点权重。于是：

```
假设一种权重布局  →  按该布局把浮点权重量化成 INT8  →  与 buf_000_dmafffed000.bin 比对
```

**布局假设错了，字节对不上；对了，就能逐字节吻合。**
这比「猜格式」强得多 —— 它把一个逆向问题变成了**可证伪的比对问题**。

而且 docs/44 已经给出了布局的强线索（上游 `rkt_coefs.c` 的最内两层 `oc2×ic2` 32×32 块、
`align(in_ch,32)`、`kernels` 对齐到 2），docs/38 也验证过 `WEIGHT_SIZE0/1/2` 的语义 ——
**布局的先验知识已经不少了。**

## 2. 这个仿真器能换来什么（对「高自由度开发」）

| 现在只能这样做 | 有了仿真之后 |
|---|---|
| 想试「去掉冗余拷贝」⇒ **改驱动、上板、可能挂** | 在仿真里改命令流，**先验证正确性**，再上板 |
| 想试「合并提交」⇒ 只能靠 `optimization_level` 这种现成旋钮 | 自己拼提交，仿真里直接看**正确性 + 时序** |
| 想试「改 tiling / CBUF bank 分配」⇒ 无法试 | 仿真里改寄存器值，立即出结果 |
| 想知道「某个算子为什么慢」⇒ 只能推断 | 逐 tile 执行，**每一级的耗时/数据量都在手上** |

**并且有安全底线**：docs/07/09 两次挂板都是因为**未经仿真就手写命令流提交**。
仿真器正是这件事的前置条件。

## 4. 教训（本轮新增）

1. **★ 「拿不到真实数据」是仿真器的真障碍，而不是「算法难」。** 我一直以为
   写执行器的难点在算子语义；实际上**卡点是「不知道权重在内存里长什么样」**。
   把这件事解决（抓 DRAM 镜像），整个方案才成立。
   **先找「哪一步让后面所有事都无法验证」，先解决它。**
2. **★ 自己生成的模型是逆向的最大资产。** 因为 ONNX 是我们自己造的，
   所以**知道浮点权重** ⇒ 权重布局假设可以**逐字节证伪**。
   如果只有别人的 `.rknn`，这一步就只能靠猜。
   **「可控的输入」把逆向问题变成了比对问题。**
3. **★ 现成的参照要主动找。** 官方模拟器一直在 wheel 里（`rknn/api/simulator.*.so`），
   字符串里也写着「想用模拟器就用 load_xxx & build」。**先花十分钟找有没有现成的，
   再决定要不要自己写。**
4. **★ 抓取能力要一次做够。** 本轮把「dump 缓冲区内容」一次做进探针
   （含 mode/上限两个环境变量），而不是等到需要时再改一遍 ——
   **每次改探针都要重新编译、上板、跑，成本远高于一次做全。**
