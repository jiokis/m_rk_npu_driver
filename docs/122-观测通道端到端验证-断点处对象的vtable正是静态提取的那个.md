## 1. ★ 观察结果

```
命中（0x391420，RKNNTilingPass 的虚函数之一）
#0  0x7fffaf1913f0 in ?? ()   from librknnc.so
#1..#3 ?? ()
#4  0x7fffaf07cfb1 in rknn::RKNNCompiler::build() ()

rdi = rsi = 0x658ff70        ← this 与第 1 参数是同一个指针
rdx = 0xbab010

rsi 指向的对象 @0x658ff70:
  0x658ff70: 0x00007fffb0c090d0    ← ★★ vtable 指针
  0x658ff78: 0x0
  …
  0x658ff98: 0x00000000064f1da8
```

### ★★ 关键校验：vtable 地址**正是** docs/120 静态提取的那个

```
运行时 vtable      = 0x7fffb0c090d0
库基址（本次运行） = 0x7fffaf1913f0 − 0x391420 ≈ 0x7fffaeE00000
⇒ vtable 的库内偏移 ≈ 0x1e090d0
```

**而 docs/120 静态提取的 `rknn::RKNNTilingPass` vtable 正是 `0x1e090d0`。**
（同一份输出里还有 `0x1e09098` = typeinfo 指针位置、`0x1e090a0` = typeinfo。）

**⇒ 完全吻合。**

## 2. ★ 这条链现在是**端到端验证过的**

```
① 静态：RTTI 名 → typeinfo → vtable @0x1e090d0 → 10 个虚函数地址   （docs/120）
② 动态：在 0x391420 断下，栈里是 RKNNCompiler::build()             （docs/121）
③ 校验：断点处对象的 vtable = 0x1e090d0 = ①里提取的那个            （本轮）
```

**⇒ 三个环节互相印证 ⇒ 「这些地址属于 RKNNTilingPass」不再是推断，而是验证过的事实。**

## 5. 教训（本轮新增）

1. **★★★ 「验证闭环」比「成功一次」重要得多。**
   断点命中（docs/121）只说明「地址能断下」；
   **本轮的 vtable 校验才说明「这个地址确实属于 RKNNTilingPass」**——
   因为**断点处对象的 vtable 与静态提取的 vtable 是同一个地址**。
   **做了逆向推断后，要找一个独立观测去印证它。**
2. **★★ 静态与动态两条路互证，可信度最高。**
   静态（读 ELF）给出 vtable 地址；动态（gdb）给出运行时的 vtable；
   **两者相等 ⇒ 中间没有假设。**
3. **★ 我这一轮没有急着「读业务数据」，而是先做验证。**
   因为**如果地址错了，后面读到的所有东西都是错的**。
   **先证明工具对，再用工具。**
