## 0. 一句话结论

**上游 Mesa 驱动里有一个完整的、可证伪的「分块（split task）」结构模型。把它逐字段撞在我们的
真实 dump 上：15 项预测命中 13 项 100%，另 2 项的非命中原因也查清了。**

有了这个模型，每个 tile 的 **输出宽/高/通道、输入通道、卷积核尺寸全部可读**，
于是 **MAC 数是可算的**（已用一个形状无歧义的 1×1 卷积算子核对到 **0.4%**）。
把 MAC 数对实测 hw 时间拆开，就得到结构级耗时模型：

```
t_total ≈ n_submit × FLOOR  +  MAC_total / THROUGHPUT
```

两个系数都被**实测**锚住，不需要拟合：

```
FLOOR ≈ 74 ~ 89 µs        ← 在「零算术量」的提交上直接量出来
                            （零算术量提交 74.4 / 75.0 / 88.7 µs）
```

而模型给出两条**互相夹逼**的结论，这是本轮最重要的收获：

| 喂法 | 提交数 | 每次提交的 tile | 算术效率（占物理峰值） |
|---|---|---|---|
| 单核 + 一个 **588-tile 大提交** | 1 | 588 | **≥ 98.1%** |
| 三核 + **77 次细碎提交** | 77 | 3（每核 1 个） | **50 ~ 65%** |

> **同一块硬件的同一批乘法器，效率差 1.5~2 倍，唯一变的是提交粒度。**
> ⇒ **RK3588 NPU 的乘法器不是瓶颈，提交粒度才是。** 把 77 次提交合并成一次，
> NPU 侧理论上快约 **1.8×** —— 结构性的，不改硬件、不加带宽、不改驱动。

**这一次不再是「哪个变量相关」，而是「给定工作量能算耗时」。**

## 1. 上游到底给了我们什么（这是本轮最大的杠杆）

上一轮（docs/36）我们只用了上游的**寄存器表**。本轮去读上游的**代码**，发现了
`mesa/rkt_task.c`：

```
rkt_split_tasks()      ← 完整的分块（split task）模型，注释写着 "Function mostly taken from NVDLA"
calc_input_banks()     ← 片上缓冲的 bank 分配
calc_weights_banks()
calc_entries_per_slice()
fill_task()            ← 每个 tile 的每个字段怎么算
```

以及 `mesa/rkt_regcmd.c` 里每个寄存器**具体填什么值**。这是一份可以直接拿来对撞的
**结构级规格**，而不是猜。它给出的可证伪预测有 15 条（见 §2）。

### 关键的三条（后面全靠它们）

| 上游代码 | 含义 |
|---|---|
| `EMIT(REG_CNA_DATA_SIZE0, DATAIN_WIDTH(op->input_width) \| DATAIN_HEIGHT(task->input_height))` | 宽度用**整层**、高度用 **tile** |
| `EMIT(REG_CNA_FC_DATA_SIZE0, DMA_WIDTH(op->input_width) \| DMA_HEIGHT(task->input_height))` | **同一个寄存器里再次**：宽度整层、高度 tile |
| `EMIT(REG_CNA_DATA_SIZE3, DATAOUT_ATOMICS(task->atomic_count))`，而 `atomic_count = output_width × output_height` | **输出高度可以白拿** |

第二条是最漂亮的：**一次寄存器写入里，宽度字段用整层、高度字段用 tile** —— 上游代码本身
就把这个不对称写死了。这独立证明了「高度字段是 tile 级」，不依赖我们自己的任何推理。

### 两项非 100% 的原因都查清了

**L（99.2%，4 个反例）**：反例全在 task 702 / 717，`WEIGHT_KERNELS=1` 而真实输出通道是
256 / 128。而 `rkt_task.c` 里有：

```c
if (operation->depthwise)
   task->weights_kernels = 1;
```

⇒ **这 4 个反例是深度卷积**，非命中反而**证实**了上游的 depthwise 分支。
教训重申：把判据定得太严会制造假阴性，而假阴性会把正确的方向带偏。

**D（18.5%）**：`FEATURE_GRAINS` 并不是 tile 输入高度。而且——

```c
EMIT(REG_CNA_CONV_CON2,
     CNA_CONV_CON2_FEATURE_GRAINS(
        50 + task->stride_y + 1)); /* Magic: Seems to pass the most tests */
```

**上游自己也不知道这个字段是什么，写的是一个注释为「Magic」的魔数。**
这不是我们逆向失败，这是一个**上游同样未解**的字段。我们还顺手排除了一个可能：

> 它**不是**输出几何的函数。反例：op5 与 op6 的输出几何完全相同
> （out_w=160, out_h=54, ch_align=32），但 grains 分别是 14 和 16。
> 差别在输入侧（in_h 54 vs 55）和核尺寸（1×1 vs 3×3）。

## 3. 本轮钉住的字段（解决 docs/17 / 37 / 38 的悬案）

### 3.1 `DATA_SIZE0[0..10]` **就是** tile 输入高度 —— 悬案结案

docs/17 记录「`DATA_SIZE0[0..10]` 解出 34/70/28，不是高度」；docs/37/38 把它列为唯一未解字段。
**34 / 70 / 28 确实是高度 —— 是 `bottom_slice − top_slice + 1`，即本 tile 处理的输入行带高度，
不是整层高度。** 整层高 640 的第一层，tile 带高 34；第二层整层高 320，tile 带高 55。

三条独立证据：
1. 上游代码 §1 的不对称写法（宽度整层、高度 tile）。
2. `FC_DATA_SIZE0`（0x1084）同一次写入里，高半字 = 640（整层宽）、低半字 = 32/30（tile 高）
   —— 856 个 tile 里 508 个可查，**100% 一致**。
3. 与 tile 的 `out_h` 自洽：op1 每个 tile `in_h=34, kw=kh=2, stride=2 → out_h=(34−2)/2+1=17` ✓。

### 3.2 `DATA_SIZE3`（0x102c）＝ `DATAOUT_ATOMICS` ＝ out_w × out_h

**输出高度从此白拿**，并且有两条**互相独立**的寄存器路径可以对撞：

```
 путь 1:  out_h = DATA_SIZE3[0..21] / DATA_SIZE2[0..10]
 путь 2:  out_h = CORE_DATAOUT_SIZE_0[16..31] + 1
```

508/508 一致。第三条路：DPU `DATA_CUBE_HEIGHT`（0x4034），也 100% 一致。

顺带修正 docs/38 的一个标签错误：`CORE 0x3014` 不是「输出宽−1 / 通道−1」，
而是 **`(out_h−1)<<16 | (out_w−1)`**；通道在 `0x3018`。

### 3.3 `WEIGHT_KERNELS` 是 `align(out_ch, 2)`，不是 `out_ch`

docs/38 写的是「= out_ch」。上游是 `align(operation->output_channels, 2)`。508 个 tile 里
504 个吻合，4 个反例是深度卷积（`kernels=1`）。**稀疏性/奇数通道时会差 1，做预算推算时要按 align 算。**

## 4. ★ 修正 docs/36：「39 个上游未定义寄存器」是错的，实际只有 2 个

docs/36 声称「我们观测到 39 个上游未定义的寄存器，全以 `0xc` 结尾」。
本轮把上游**内核头文件**（`rocket_registers.h`，199 个 `#define REG_`）正确解析后重算：

```
上游头文件定义的寄存器数: 199
本次语料观测到的不同寄存器数: 148
  交集 146   上游有我们未见 53   我们见上游无 2
```

**只有 2 个**：

| 偏移 | 观测次数 | 上游实际上是什么 |
|---|---|---|
| `0x003030` | 508 | `emit_raw(regs, CORE \| 0x1, 0x3030, 0)` —— Mesa **也写它**，只是头文件没给名字 |
| `0x0040c4` | 682 | `emit_raw(regs, DPU \| 0x1, 0x40c4, 0)` —— 紧跟在 `DPU_SURFACE_ADD(0x40c0)` 之后，是它的**高 32 位**（低字 mask 是 `0xfffffff0`，低 4 位保留） |

⇒ **上游覆盖了我们观测到的 100% 的寄存器。** docs/36 的错误来源：它拿的是
Mesa 的 `registers.xml`（154 条，是个子集）当「来源 A」，而不是内核头文件（199 条）。

这不是坏消息，是好消息：**我们对上游的依赖度比想象中高，也就是说二次开发可以直接站在
上游的命名体系上**，不必自造一套。

另外那 53 个「上游有、我们从没见过」的寄存器也有信息量：它们集中在
**DDMA / SDMA / 中断 / S_STATUS / S_POINTER / CLK_GATE** —— 即我们全程没碰过的路径
（多核同步、独立 DMA、功耗门控）。这是后续可以攻的方向。

## 5. ★ 提交地板：在「零算术量」的提交上直接量出来

docs/39 提出「66% 是固定开销」，docs/40 修正为「31–54%，欠定」。
本轮找到了**理想的测量对象**：cm=7 语料里有若干提交的 3 个 tile 全是纯 PPU 算子
（`OP_ENABLE = 0x60`，一个 MAC 都不做；docs/46 已证明这条通路的实际功能是**张量搬运**）。

```
task 663 / 666 / 714 等：3 个 tile，Σ MAC = 0，实测 hw = 88.7 / 75.0 / 74.4 µs
```

⇒ 这些提交的 tile **连一个 CNA 尺寸寄存器都没有**，所以
**提交地板 ≤ 74.4 / 75.0 / 88.7 µs**（保守方向：即使那些 tile 真带算术，
70~89 µs 也只能是地板的**上界**，不会低估地板）。

与 docs/40 的独立结果（60–115 µs）一致。**FLOOR ≈ 74 ~ 89 µs。**

⚠️ 注意 `align1` 的段尾被截断，读不到 `OP_ENABLE`，所以**没法**按位图证明
「这些 tile 天然无算术」。真正**可证**的地板现场是下面 §5.1 的 LLM decode ——
那里的几何 100% 可读、形状毫无歧义。

### 5.1 一个更干净的地板现场：LLM decode

`/tmp/llm_timer.log` 有 4056 条记录，`task_start` **全部为 0**、`task_number` 全部为 3
（4032 条），`core_mask` 轮转 ∈ {0x1, 0x2, 0x4}，各 1352 条。
也就是说：**同一份工作，在三个核上各跑了 1352 次，且是交错随机排序的。**

工作量的形状**毫无歧义**（`data/rkllm` 全部 13383 个 tile 寄存器完整，覆盖率 100%）：

```
3 个 tile:  2px / 4px / 6px  ×  in_ch=896  ×  out_ch=320  ×  1×1 核
Σ MAC = 12 × 896 × 320 = 3.44 M-MAC        （无 padding 歧义：1×1 核，ch 已是 896 对齐）
```

按单核标称峰值 1 T-MAC/s，**这 3.44 M-MAC 只要 3.4 µs**。而实测：

| core_mask | 样本 | hw **中位数** | hw 均值 |
|---|---|---|---|
| `0x1`（核 0） | 1352 | **77.3 µs** | 114.8 µs |
| `0x2`（核 1） | 1352 | **61.0 µs** | 109.6 µs |
| `0x4`（核 2） | 1352 | **60.7 µs** | 109.5 µs |

⇒ **≥94% 的提交时间与算术量无关，而且这个「无关的部分」是按「提交次数」计的，不是按「工作量占比」计的。**
这就是 docs/39 想说的东西，现在有了干净的证据。

**为什么这个现场比 §5 更硬**：这里的几何是 100% 可读的（`data/rkllm` 13383 个
tile 全部读到 `DATA_SIZE2/3` 与权重三元组），`OP_ENABLE = 0x0d` 明确含 CNA 位
（⇒ 确实在做乘法），所以「算术量 = 3.44 M-MAC」这句话本身没有缺口可以争议。
§5 那个现场只能给出地板的**上界**，这个现场给出的是一个**可证的比值**。

### 5.2 ★ 副产物：核 0 比核 1/2 慢 27%

同一份工作、同一批 1352 个样本、交错执行：

```
核 0: 77.3 µs      核 1: 61.0 µs      核 2: 60.7 µs
```

**核 0 的固定开销比另两个核多 ~16 µs（+27%）。** 这与「核 0 同时承担 PC/全局控制路径
（PC、DDMA、中断）」的架构猜想一致，也解释了一个此前没解释的现象：
**`core_mask=0x1`（只用核 0）比 `core_mask=0x2`/`0x4` 慢**。
⇒ 多核调度时应**优先避开核 0**，或至少不要把它当普通核用。

### 5.3 `OP_ENABLE` × 「算不算得出 MAC」交叉表 —— 证明缺口是真的缺口

把 `data/dumps2`（段尾完整）的 615 个 tile 按 `OP_ENABLE` 位图 × 能否算出 MAC 交叉：

| `OP_ENABLE` | 流水组成 | MAC>0 | MAC==0 | 结论 |
|---|---|---|---|---|
| `0x1d` | CNA\|CORE\|DPU\|DPU_RDMA | 402 | **66** | 卷积通路，66 个是**几何寄存器读不到**的真缺口（14.8%） |
| `0x0d` | **CNA\|CORE\|DPU**（无 DPU_RDMA） | 13383 | 0 | ★ **LLM GEMM 通路**，见下 |
| `0x18` | DPU\|DPU_RDMA | 0 | 89 | 逐元素/激活，**天然无乘法**，不是缺口 |
| `0x60` | PPU\|PPU_RDMA | 0 | 58 | **实为张量搬运/切片引擎，不是池化**（docs/46：93% 是退化的 1×1×32 拷贝），**天然无乘法**，不是缺口 |

**⇒ 147 个「零 MAC」tile 里有 147 个是天然无算术的（0x18 / 0x60），只有 66 个（0.1d 通路）是真缺口。**
这一张表同时干掉了两个错误猜测：既不是「34% 的 tile 都丢了数据」，也不是「PPU 也算乘法」。

**★ 新观测：`OP_ENABLE = 0x0d` = `CNA|CORE|DPU`，缺 `DPU_RDMA`（bit4）。**
`data/rkllm` 里 13383 个 tile **全部**是这个位图，而 CNN 通路用的是 `0x1d`（带 `DPU_RDMA`）。
⇒ 这是**又一种流水组成**：LLM 的 GEMM 路径**跳过了 DPU_RDMA 这一级**。
结合 docs/36 记的 DPU 数据通路（`BS_*`→`BN_*`→`EW_*`→`LUT_ACCESS_*`），
`DPU_RDMA` 正是把 DPU 结果读回来喂 PPU/EW 的那一级 —— **GEMM 不需要那一级，所以关掉它**。
这是「流水构建」层面一条很实的新证据：**位图不是「用了哪几级」的标签，而是可以按算子类型裁剪的开关。**

## 6. ★ 结构级模型：两个锚点把「硬件满不满速」和「损耗在哪」分开了

```
t_total ≈ n_submit × FLOOR  +  MAC_total / THROUGHPUT
```

**锚点 1：单核 + 一个 588-tile 的大提交（地板可以忽略）**
`data/dumps2` 的 `seq 0`（`cm=0x1`，`task_number=588`，实测 hw = **14.107474 ms**）：

```
走算术的 tile 447 个，其中几何可读 381 个（缺口 66 个 = 14.8%）
Σ MAC(可读)              = 1.417e10
物理上限 = 1.024 T-MAC/s × 14.107 ms = 1.445e10     ← 不可能超过它
⇒ 可读部分已占物理上限的 98.1%
⇒ 那 66 个「读不到几何」的 tile，最多只能承载剩下的 1.9%
⇒ ★ 单核算术效率 ≥ 98.1%
```

「1.9%」这个界是**被物理夹出来的**，不是假设：如果那 66 个 tile 拿平均权重，
算出来会超过 1.024 T-MAC/s × 14.107 ms 这个天花板，物理上不可能。
**这一条同时干了两件事**：验证了整套 MAC 账（否则不可能恰好贴到天花板上 98%），
并且证明 **RK3588 的 NPU 乘法器在喂饱的情况下几乎满速**。

**锚点 2：三核 + 77 次小提交（aligned1，cm=7，每趟 77 次提交）**

```
每趟 hw = 22.156 / 2 = 11.078 ms，77 次提交
Σ MAC(可读) = 8.25e9/趟（几何缺口 14.8% ⇒ 真值约 9.4~9.7e9）
FLOOR = 74 µs（实测）  ⇒ 地板 5.70 ms，算术 5.38 ms ⇒ 1.53 T-MAC/s = 峰值 49.9%
FLOOR = 80 µs          ⇒ 地板 6.16 ms，算术 4.92 ms ⇒ 1.68 T-MAC/s = 峰值 54.6%
FLOOR = 115 µs         ⇒ 反解 3.71 T-MAC/s > 3.072 T-MAC/s 峰值 ⇒ **该取值被物理排除**
```

⇒ **三核算术效率落在 50% ~ 65%（含 15% 几何缺口修正后上限约 64%）**。

### 6.1 把两个锚点放在一起看 —— 本轮最有价值的一句话

| | 提交数 | 单次提交的 tile 数 | 算术效率（占峰值） |
|---|---|---|---|
| 单核，一个大提交 | **1** | 588 | **≥ 98%** |
| 三核，细碎提交 | **77** | 3（每核 1 个） | **50 ~ 65%** |

**同一块硬件、同一批乘法器，效率差 1.5~2 倍，唯一变的是提交粒度。**
再加上一张干净的地板账单（零算术量提交 74.4 / 75.0 / 88.7 µs），
结论就闭合了：

> **RK3588 NPU 的算术单元不是瓶颈，提交粒度才是。**
> 把 77 次提交合并成 1 次，NPU 侧理论上能快约 **1.8×**（三核满载 3.072 T-MAC/s）。
> 这个 1.8× 是**结构性**的，不需要改硬件、不需要加带宽、不需要改驱动。

### 6.2 一个干净的单算子核对（证明 MAC 账不是自欺欺人）

op82（40×40 输出、256 通道、1×1 核）在**两份完全独立的抓取**里：

```
cm=1/dumps2:  out = 40×32 + 40×8 = 40×40，ch = 256，kern = 256
              ⇒ MAC = 1600 × 256 × 256 = 1.0486e8
实测每份 Σ MAC = 8.356e7 + 2.089e7 = 1.0445e8        ⇒ 误差 0.4%
```

### 6.3 已知局限（必须说清楚）

* **`align1` 整份语料段尾都被截断**（856/856 个 segment 的 `end` 都是 `uncaptured`，
  `chain`/`enable` 全为 None）—— 因为抓取时 `RKNPU_DUMP_SLACK=0`。
  ⇒ 在 align1 上**无法**按 `OP_ENABLE` 分类，只能用 dumps2 的比例去估缺口。
  这也解释了 §2 表里 `D`/`L` 两项的样本数少于 856。
* 因此 §6 的**三核数字仍是区间**（50~65%），不是点估计。
  唯一的收紧办法是**用非零 slack 重抓一份**（见 §8 第 4 条）。
* `rkllm` 那份覆盖率 100% 但**提交地板远大于算术量**（地板 74 µs vs 算术 3.4 µs），
  反解吞吐无意义 —— `submit_budget.py` 在那里输出 `nan`/12.8%，
  这是**模型在正确地说「这个负载的地板比算术量大一个数量级」**，不是 bug。
* 上游分块模型只覆盖 **CNA/DPU/CORE** 这条路。PPU 那条路（实为搬运，见 docs/46）没有等价的上游规格，
  只能拿到地板。

### 6.4 ★ 预测检验（这才是「模型」该干的事）

`python3 src/analysis/submit_budget.py predict`。
**两个常数全部来自别的实验，没有在被预测的数据上拟合**：

```
FLOOR = 80 µs              ← 零算术量提交实测 74.4 / 75.0 / 88.7 µs 的中位
PEAK  = 1.024 T-MAC/s/核   ← 板上 devfreq 实测 NPU = 1.0 GHz（performance 档，已是最高档）
```

| 负载 | 提交数 | 地板(ms) | MAC | 算术(ms) | **预测(ms)** | **实测(ms)** | 误差 |
|---|---|---|---|---|---|---|---|
| `dumps2 seq0` 单核 588-tile | 1 | 0.080 | 1.417e10 | 13.834 | **13.914** | **14.107** | **−1.4%** |
| `align1` 三核 154 提交 | 154 | 12.320 | 1.65e10 | 5.372 | **17.692** | **22.156** | −20.1% |

* **单核那一行没有任何自由参数**，−1.4% 就是「MAC 模型 + 峰值常数」的总误差。
* 三核那一行按纯峰值预测低 20.1% —— 这**恰好是**「三核效率只有 50~65%」
  这同一件事的另一种说法。把有效吞吐换成实测反解出的 1.68 T-MAC/s，
  预测变成 12.320 + 9.836 = **22.156 ms**，与实测**完全重合**。

⇒ **模型在一份数据上标定，在另一份数据上预测到 1.4% 以内。目标 ③ 达成。**

## 7. 对「最大程度利用 NPU」的直接含义

按本轮结论重排优化杠杆（前面是**已实测**的，后面是**本轮新推出**的）：

| 杠杆 | 依据 | 量级 |
|---|---|---|
| 4–6 路并发 | docs/34 | **2.44–2.57×**（NPU 36%→90.7%） |
| **减少提交次数** | 本轮：77 次提交 × 80 µs = 6.2 ms，占 11.08 ms 的 56% | **理论天花板 ~1.8×** |
| 避开核 0 | 本轮：核 0 慢 27% | 提交地板上限 +16 µs/次 |
| DDR 定频 | docs/28 | 1.59× |
| 3 核并用 | docs/22 | 1.10× |
| 加 DDR 带宽 / 改驱动提交路径 | docs/32 / docs/33 | ≈1.0× |

**「减少提交次数」第一次有了量化依据**：提交粒度由闭源 librknnrt 决定，但
`docs/24`（调度逻辑解剖）已经说明驱动侧怎么拼 job，而本轮的
`DATA_SIZE3 = out_w × out_h` 让**每个 tile 的工作量可读** ——
这就为「自己重排 tile → 自己决定提交粒度 → 绕开 runtime 的细碎提交」提供了完整的
输入。**这是提高二次开发上限的最具体的一条路。**

## 9. 教训（本轮新增）

1. **读上游的代码，不只是上游的表。** docs/36 只用了寄存器表，得出「上游不知道很多」的结论；
   读了 `rkt_task.c` / `rkt_regcmd.c` 之后，上游给的是一份**完整的结构级规格**。
2. **对自己的旧结论要主动怀疑。** 「39 个未定义寄存器」听起来很漂亮（显得我们挖得深），
   实际是拿错了参照物。漂亮结论要额外验一遍。
3. **单位的教训再来一次**：`rkt_regcmd.c` 里 `FC_DATA_SIZE0 = DMA_WIDTH(w) | DMA_HEIGHT(h)`，
   我先按「低半字=宽」去解，得到 E/F 两项 5.9% 的惨状；查头文件 mask 才发现
   `DMA_WIDTH` 在 bit16-29。**先读 mask，再读代码顺序。**
4. **「零工作量」的样本是量固定开销的最佳实验设计。** 找纯 PPU 提交比做回归外推可靠得多。
5. **下游要能自己解释自己**：`submit_budget.py` 在 `rkllm` 那行输出 `nan`，
   这不是缺陷，是模型在说「这个负载的地板比算术量大一个数量级，反解无意义」。
6. **判据别定太严**：检查 L 的 4 个「反例」其实是深度卷积的证据；检查 D 的非命中
   其实是上游未知字段。**每一次非 100% 都要当成线索而不是失败。**
7. **★ 用物理上限去夹，比用回归去拟合硬得多。** 「可读 tile 已占物理天花板的 98.1%」
   这句话同时验证了 MAC 模型、给出了未读数 tile 的**上界 1.9%**、还证明了硬件满速 ——
   三件事一句话。**当一个量有已知的物理上界时，先算「我算出来的占到上界的百分之几」，
   再考虑做回归。** 回归可以骗人，天花板不会。
8. **★ 先查语料质量，再谈结论。** 本轮跑完才发现 `align1` 的 **856/856 个 segment 段尾全被截断**
   （`RKNPU_DUMP_SLACK=0` 的副作用），`chain`/`enable` 全为 None ⇒ 在那份语料上根本
   无法按 `OP_ENABLE` 分类。**指标不好看的时候，第一嫌疑应该是数据，不是现象。**
9. **同一个结论要在两份独立抓取上复现。** §2 那张双列表（align1 / dumps2）比任何单份
   语料上的「100%」都有说服力 —— 连非命中的项目和数量级都一样。

## ⚠️ 修正（由 [docs/43](43-稳态重抓-提交地板可证实测与三核效率修正.md) 给出）

本篇的模型**形式**（`t = n_submit × FLOOR + MAC/PEAK`）与核心结论
（**瓶颈是提交粒度、不是乘法器**）在 docs/43 上板重抓后**依然成立，而且更硬**。
但有两个**数字**需要修正，原因是本篇用的 `align1` 语料 `SLACK=0`，
**856/856 个 segment 的段尾全被截断**（`chain`/`enable` 全为 None）：

| 量 | 本篇（区间/上界） | **docs/43（点估计，可证）** |
|---|---|---|
| 提交地板 `FLOOR` | 74 ~ 89 µs（**上界**） | **67.4 µs**（144 个零算术量提交的中位，`OP_ENABLE` 全部可读） |
| 三核算术效率 | 50 ~ 65% | **75.6%** |
| 单核算术效率 | ≥ 98.1%（带 14.8% 几何缺口） | **95.8%** |

两个额外发现（本篇写作时不知道）：
1. **dump 探针本身会给每趟加 ~2.3 ms hw / +31% 墙钟**（每趟写 ~500 个文件到 tmpfs，
   而 NPU 是访存延迟敏感的）⇒ **时间要用低开销探针量，工作量才用 dump 量**。
2. **`capture-run.py` 只跑一次推理是冷启动**，比稳态快 15%（9.615 vs 11.056 ms/趟）。

另外，本篇 §6.3 说「几何缺口 14.8%」只对 `dumps2`（cm=1）成立；
`align1` 与 `align2` 的 cm=7 语料里，走算术的 tile **几何全部可读，缺口为 0**。

## ⚠️ 撤回（由 [docs/49](49-撤回核0慢27%的说法-两条独立理由.md) 给出）

**§5.2「核 0 比核 1/2 慢 27% ⇒ 调度优先避开核 0」撤回，两条独立理由：**

1. **换负载不成立、方向相反。** 同一个模型、同一种低开销探针，在 **yolov5s** 上：

   ```
   cm=1（核 0）: 15.410 ms/趟      cm=2（核 1）: 15.833      cm=4（核 2）: 15.829
   ⇒ 核 0 反而**快 2.7%**
   ```

   本篇那个 27% 来自 **RKLLM 的 3-task 小提交**，是**实测**的（1352×3 交错样本），
   但**不可推广** —— 两个负载给出相反的符号。
2. **这个杠杆根本不可用。** `init_runtime(core_mask=5/6)`（只用核 0+2 / 核 1+2）
   直接 **`INIT_FAIL ret=-1`**。支持的只有 `1/2/4/3/7`，
   **所有多核配置都必须包含核 0**，无法排除。

⇒ 修正后的说法：**「核 0 慢」是负载相关观察，不可推广；且没有 API 能利用它。**
本篇其余结论（提交地板、单核 98%、模型形式）不受影响。
