## 一、调度 ABI：`subcore_task[]` —— 调度决策就在这里

驱动 `rknpu_ioctl.h` 的提交结构（104 字节）：

```c
struct rknpu_submit {
    __u32 flags; __u32 timeout;
    __u32 task_start;      /* 总区间起点 */
    __u32 task_number;     /* 总区间长度 */
    __u32 task_counter; __s32 priority; __u64 task_obj_addr;
    __u32 iommu_domain_id; __u32 reserved;
    __u64 task_base_addr; __s64 hw_elapse_time;
    __u32 core_mask; __s32 fence_fd;
    struct rknpu_subcore_task subcore_task[5];   /* ★ 每核的 {start, number} */
};

struct rknpu_subcore_task { __u32 task_start; __u32 task_number; };
```

**⇒ 用户态（运行时）显式指定每个核负责哪个 task 区间。硬件不做负载均衡 —— 分片是编译期/运行期算好的。**

### 1.1 一个 ABI 怪癖：3 核时索引从 2 开始

```c
static int rknpu_get_task_number(struct rknpu_job *job, int core_index)
{
    if (job->use_core_num == 1 || job->use_core_num == 2)
        task_num = job->args->subcore_task[core_index].task_number;
    else if (job->use_core_num == 3)
        task_num = job->args->subcore_task[core_index + 2].task_number;  /* ← +2 ! */
}
```

**3 核时读的是 `subcore_task[2]`、`[3]`、`[4]`**，而不是 `[0][1][2]`。
实测数据完全吻合 —— 运行时把 `[0][1]` 也填成了核 0/1 的值（冗余填写）：

```
core_mask=0x7  总区间 [618, +21)
  subcore[0]: start=618 number=7     ← 核0（冗余）
  subcore[1]: start=772 number=7     ← 核1（冗余）
  subcore[2]: start=618 number=7     ← 核0（驱动实际读这个）
  subcore[3]: start=772 number=7     ← 核1（驱动实际读这个）
  subcore[4]: start=909 number=7     ← 核2（驱动实际读这个）
```

`use_core_num` 的算法：`(core_mask & 0x1) + ((core_mask & 0x2) >> 1) + ((core_mask & 0x4) >> 2)`。

## 二、实测的调度结构：每核一条独立的任务流

### 2.1 任务数组被划成 N 个连续区域

| 配置 | 核 0 区域 | 核 1 区域 | 核 2 区域 | 每核 task 总数 |
|---|---|---|---|---|
| **cm=7**（3 核） | `618..761` | `772..907` | `909..1044` | **137 / 137 / 137** |
| **cm=3**（2 核） | `205..409` | `420..616` | — | **198 / 198** |

**⇒ 三核的工作量精确相等。任务数组按核切成连续区域。**

### 2.2 每次提交给每核的 chunk 大小**完全相同**

```
cm=7: 71/71 次提交中，三个核的 chunk 大小完全一致  ✅
cm=3: 71/71 次提交中，两个核的 chunk 大小完全一致  ✅
```

**⇒ 每个批次内部都是完美均衡的。**

chunk 大小分布（cm=7 每核）：

| chunk | 1 | 2 | 3 | 4 | 5 | 7 |
|---|---|---|---|---|---|---|
| 次数 | 34 | 16 | 17 | 2 | 1 | 1 |

**这正好对应层的分块数**（见 [docs/20](20-分块结构与并行粒度.md)：1 分块的层 68 个、2 分块 67 个、3 分块 48 个…）
——**一个层有 k 个分块时，每核分到约 k/N 个**。

### 2.3 这也解释了"为什么 task_number 总是核数的倍数"

```
cm=7: task_number ∈ {3(×35), 6(×17), 9(×17), 12(×2), 21, 15}   ← 全是 3 的倍数
cm=3: task_number ∈ {6(×23), 4(×21), 2(×18), 10(×4), 20(×3)…}  ← 全是偶数
```

因为 `task_number = 核数 × 每核 chunk`。

## 三、提交是**同步屏障**

```c
RKNPU_JOB_BLOCK    = 0 << 1,     /* flags bit1 = 0 → 阻塞模式 */
RKNPU_JOB_NONBLOCK = 1 << 1,
```

实测 `flags = 0x5 = PC(0x1) | PINGPONG(0x4)` → **bit1 = 0 → BLOCK 模式**，
且 `fence_fd = -1`（无 fence）。

**⇒ 每次 `SUBMIT` 的 ioctl 会阻塞到该批全部完成。**

所以 **77 次提交 = 77 个同步屏障**。每个屏障处：
- 三个核都要排空（快的核要等慢的核）
- **乒乓流水被打断**（`PINGPONG` 让硬件把下一 task 的配置加载与当前 task 的计算重叠；
  屏障处这个重叠必然中断）

## 四、开销估算（诚实标注不确定性）

**可排除的因素：负载不均。** §2.1 已证明三核工作量精确相等（137/137/137），
所以 1.76× 不是不均衡造成的 —— **只能是每个屏障的固定代价。**

### 4.1 保守估算（假设 cm=1 的提交开销可忽略）

```
cm=1:  44.8 ms ≈ 纯计算 W
cm=7:  25.5 ms = W/3 + 77·O  →  14.9 + 77·O = 25.5
                            →  O ≈ 0.138 ms/次
                            →  屏障开销合计 ≈ 10.6 ms，占 cm=7 总时的 42%
```

### 4.2 双参数拟合（把 cm=1 的开销也解出来）

```
W +  4·O = 44.8
W/3 + 77·O = 25.5      →  W ≈ 28.9 ms · O ≈ 0.206 ms
                       →  屏障开销合计 ≈ 15.9 ms，占 62%
```

### 4.3 两种估算的取舍

**4.2 的 W=28.9ms 意味着三核理论上能到 44.8/9.6 ≈ 4.7×（超线性）—— 这不物理。**
所以 **4.1 更可信**：W ≈ 44.8ms、O ≈ 0.14ms、屏障开销约 42%。

> 但两种估算都只有 2 个数据点，**欠定**。
> 要定论需要更细的测量（性能计数器，或改变提交次数的对照实验）。

### 4.4 如果不确定性成立，减少提交次数能带来什么

按 4.1 的模型外推（**这是上界估计，不是预测**）：

| 提交次数 | 预计耗时 | 相对 cm=1 加速 |
|---|---|---|
| 77（现状） | 25.5 ms | 1.76× |
| 40 | 20.4 ms | 2.20× |
| 20 | 17.7 ms | 2.53× |
| 8 | 16.0 ms | 2.80× |
| 4 | 15.5 ms | 2.89× |

**⇒ 即使把提交次数压到最低，上限也只有约 2.9×** —— 因为纯计算部分（W/3）就是 14.9ms。
**真正的 3× 需要同时解决"屏障开销"和"计算本身的可并行度"。**

## 五、完整的调度模型（一图）

```
编译期/运行期:
  把整个图切成 task 序列
  按核数 N 把 task 数组划成 N 个【连续区域】   ← 工作量尽量均分
  每个区域内部再按层切成若干 chunk

运行期:
  for 每个批次:
      填充 subcore_task[0..4]（N=3 时驱动读 [2][3][4]）
      ioctl(SUBMIT, core_mask=0x7, flags=0x5)   ← 【阻塞】，同步屏障
      → 三个核并行执行各自 chunk
      → 全部完成后返回

硬件:
  每个核: PC_DATA_ADDR = 该核首个 task 的 regcmd_addr
          PC_DATA_AMOUNT = 按 regcfg_amount 算（见 docs/15）
          PC_TASK_CONTROL = (0x6|pp_en)<<12 | 该核的 task_number
          → 顺链（或遍历数组）执行该核的 chunk
          → 乒乓：把下一 task 配置的加载与当前计算重叠
```

## 六、可行动的方向

| 方向 | 依据 | 预期 |
|---|---|---|
| **减少提交次数**（合并相邻批次） | 77 次屏障、每次约 0.14ms | **上界 2.9×** |
| **让屏障可重叠**（用 fence / NONBLOCK） | `RKNPU_JOB_NONBLOCK` 与 `RKNPU_JOB_FENCE_*` **都定义了但实测从未使用** | 可能消除大部分屏障代价 |
| 让分块数 < 核数的层也能并行 | 6 次提交退回 `core_mask=0x1` | 补上长尾 |
| 用 CMAC/PPU 等闲置单元 | PPU 仅占 10% 段 | 有限 |

> **最有意思的一条**：驱动定义了 `NONBLOCK`、`FENCE_IN`、`FENCE_OUT` 三种模式，
> **而实测 4152+77 次提交里 flags 只有 `0x5` 和 `0x1`** —— 运行时**从来没用过异步提交**。
> 如果屏障是主要开销，这正是一个现成的、未被利用的机制。
