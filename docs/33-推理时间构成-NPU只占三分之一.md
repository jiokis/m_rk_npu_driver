# 33 · ★★★ 推理时间的真实构成：NPU 只占三分之一

> 本篇把"一次推理到底把时间花在哪"拆开了。结论是一个此前没人量过的分配：
> **NPU 硬件忙碌 ≈ 1/3、内核 ioctl ≈ 1/3、用户态 CPU ≈ 1/3。**
>
> 由此定量解开了 docs/22 的"三核只有 1.28×"之谜，也修正了 docs/32 对
> "非阻塞提交"的期望值。
>
> 相关：[19](19-利用率实验计划.md) · [22](22-多核实验结论.md) · [24](24-调度逻辑解剖.md) · [32](32-定论-不是带宽墙是延迟墙.md)

## 一、怎么量出来的

三个独立的量，各有各的来源，互不依赖：

| 量 | 来源 | 说明 |
|---|---|---|
| **墙钟** | `time.perf_counter()` 包住 20 次 `inference()` | 用户看到的推理耗时 |
| **NPU 硬忙** | LD_PRELOAD 拦 `ioctl(0xc0686441)`，读回 `hw_elapse_time` | 驱动回写的 NPU 侧耗时 |
| **CPU 时间** | `time.process_time()`（user+sys） | 进程真正烧了多少 CPU |

外加 `strace -c` 做旁证（按系统调用类型统计耗时）。

## 二、结果：三分天下

```
3 核（core_mask=7），DDR 2400MHz，yolov5s 640：

  单次推理墙钟      33.23 ms
  ├─ NPU 硬件忙碌   10.51 ms   (32%)
  ├─ 内核 ioctl     11.48 ms   (35%)   ← 77 次提交，含驱动侧同步/缓存维护
  └─ 用户态 CPU     ~10.7 ms   (32%)   ← librknnrt 的簿记、数据准备、取输出
```

校对：`process_time()` 合计 22.19 ms = 内核 ioctl（11.48，计入 sys）+ 用户态（~10.7）。
三者加起来正好覆盖墙钟 —— **没有神秘的空白时间，确实花在这三件事上。**

### 旁证：`strace -c`

```
% time     seconds  usecs/call     calls    errors syscall
100.00    0.025916          35       735       414 ioctl
```

3 次推理共 735 次 ioctl（245 次/推理），耗时合计 25.9 ms（8.6 ms/推理，均值 35 µs）。
其中提交类只有 77 次/推理 —— **另外约 168 次是 MEM_CREATE/MEM_SYNC/MEM_MAP 之类的簿记**。

### 旁证二：CPU 占比

```
单次墙钟 33.79 ms   单次 CPU 时间 23.12 ms   → CPU 占比 68%
```

进程在推理期间有 68% 的时间在烧 CPU。这与"NPU 占 1/3"互相印证。

## 三、定量解开「三核只有 1.28×」之谜

同一套方法跑 `core_mask=1` 与 `core_mask=7`：

| | 墙钟 | CPU | ioctl | **NPU 硬忙** | 提交数/次 |
|---|---|---|---|---|---|
| **1 核** (cm=1) | 36.51 ms | 20.51 ms | 15.64 ms | **15.39 ms (42%)** | **4** |
| **3 核** (cm=7) | 33.23 ms | 22.19 ms | 11.48 ms | **10.51 ms (32%)** | **77** |

### 关键对比

- **NPU 侧的加速比 = 15.39 / 10.51 = 1.46×** —— 三核机制本身**是有用的**
- **墙钟加速比 = 36.51 / 33.23 = 1.10×** —— 用户只看到 1.1×
- 差在哪？**NPU 只占总时间的三分之一**。按 Amdahl 定律，
  即使 NPU 侧无限快，总时间也只能降到 2/3（即最多 1.5×）；NPU 侧拿到 1.46× 之后，
  剩下的瓶颈完全落在宿主侧。

> **所以 docs/22 里"三核只有 1.28×、多核性价比低"这个判断需要改口径：**
> 不是三核机制不行（它做到了 1.46×），**是宿主侧的开销把收益吃掉了。**
> 先修宿主侧，多核才能兑现。

### 另一个刺眼的发现：提交粒度随 core_mask 变化

```
cm=1:   4 次提交，每次 ioctl 约 3.9 ms
cm=7:  77 次提交，每次 ioctl 约 0.15 ms
```

**同一个模型，core_mask 从 1 换成 7，提交粒度差 19 倍。** 这说明运行时里有两条
不同的提交策略（1 核走"少量大批"，多核走"每层一提交"）。
这是个此前完全没被注意到的结构性差异，也是一个明确的优化入口：

**如果多核路径能用更少、更批量的提交，就能把那 35% 的内核开销压下去。**

## 四、修正 docs/32 对「非阻塞提交」的期望值

docs/32 提出"同步提交屏障把访存延迟完整暴露，改成非阻塞/fence 串联可以填掉等待"。
本轮数据**削弱**了这个期望：

- 提交之间的空档其实很小：`hw_ratio = 86.9~94%`（在 ioctl 内部，NPU 忙碌占 87~94%），
  说明**连续两次提交之间几乎没留气泡**。
- 真正的浪费不在"提交之间"，而在：
  ① 每次提交的内核侧开销（11.48 ms 里，NPU 只占 10.51，其余是驱动簿记）
  ② **用户态那 10.7 ms**（librknnrt 的簿记 —— 触发 245 次 ioctl/推理）

所以"非阻塞提交"的收益上限**远低于** docs/32 的预期，不该作为主攻方向。
**主攻方向应该是"减少提交次数与每次提交的簿记"**，因为这两项加起来占了约 2/3 的时间。

## 五、修正后的优化优先级

| 手段 | 收益上限（按本轮数据估） | 可行性 |
|---|---|---|
| DDR 钉频 | 已吃：NPU 侧 1.59×，但 NPU 只占 1/3 ⇒ 总收益约 **1.16×** | ✅ 已做 |
| **减少提交次数 / 每次提交开销** | 内核 35% + 用户态 32% 里可压掉相当一部分 ⇒ **潜在 1.3~1.5×** | ⚠️ 大部分在闭源 librknnrt 里，但**驱动侧能减少每次提交的成本**（见下） |
| 三核 | NPU 侧 1.46×，兑现后总收益约 **1.1×** | ✅ 已开 |
| 非阻塞提交 | 空档只占 ~6~13% ⇒ **上限很低** | ⚠️ 降级 |
| 加 DDR 带宽 | 带宽只用 26%（docs/32）⇒ **接近零** | ❌ |

> 顺带修正一个之前的说法：docs/28 把"DDR 钉频 1.59×"当成"单点最大收益"。
> 那个 1.59× 是**NPU 侧**的；映射到端到端推理时间只有约 **1.16×**
> （28.91 → 24.4 ms 量级，与实测吻合）。**这是"局部优化 ≠ 端到端收益"的一个典型例子。**

### 驱动侧具体能做什么

1. **降低每次提交的固定成本**：`ioctl` 均值 35 µs，11.48 ms/推理分摊到 77 次提交。
   驱动里每次提交要做 IOMMU domain 的 get/put、任务数组映射、内存同步检查等。
   可以统计哪一段占大头（用 ftrace 或驱动内计时），再针对性削减。
2. **支持批量提交**：一次 ioctl 提交多层任务（驱动已有 `task_number` 与
   `subcore_task[]` 机制，本来就是为批量设计的）。
3. 这两条都在我们**已经能改的驱动里**，不需要碰闭源运行时。

## 六、下一步

1. **量每次提交的内核侧成本花在哪**：给驱动的 submit 路径加分段计时
   （进入 → iommu get → 任务映射 → 内存同步 → 硬件提交 → 等待完成），
   找出那 11.48 ms 的构成。这是安全、纯软件的插桩，收益直接。
2. **验证"批量提交"能省多少**：`cm=1` 天然就是 4 次大批提交，
   而它的 NPU 硬忙（15.39 ms）比 `cm=7`（10.51 ms）大、内核开销（15.64 ms）也更大 ——
   所以不能简单照搬。需要拆开看"单次提交的成本 vs 提交内容"。
3. 宿主侧那 10.7 ms 用户态 CPU 在闭源库里，能动的不多；但**减少 ioctl 次数**
   （245 次/推理里只有 77 次是提交）是可以从驱动侧配合的。
