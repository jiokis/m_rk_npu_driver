# 模拟器与修正后的 NPU 执行模型

> 代码：[src/sim/](../src/sim/)（纯 Python，无第三方依赖）
> 上一版结论的更正：[13-算子真实结构](13-算子真实结构.md) 里的「算子 = task 链」**是错的**，
> 本文件给出修正后的模型。

---

## 一、修正：PC 链不是算子边界

`docs/13` 当时的判断是「链值 0 = 算子结束，链 = 算子分组」。**那是错的**，
错因是**扫描方法**：我当时在**整份 dump** 里找"最后一条链指令"，
而 dump 会重叠到下一个 task 的槽位，于是扫到的是**别人的**链指令。

改成精确提取（只取本段 `amount` 之后那条）后，结论完全变了：

| 实测 | 数量 |
|---|---|
| 链目标 == 某个已知 task 的地址 | **610 / 611** |
| 链值 == 0 | **4**（罕见） |
| 链目标不在 task 列表里 | 1 |

而且链的目标**就是下一个 task 的地址**（task 0 → task 1 → task 2 → …）。

### 正确的执行模型

```
PC 链 = 「下一个 task」的指针（一条链表）
硬件执行多少个 task，由 PC_TASK_CONTROL 里的 task_number 决定 —— 不是靠链值为 0 终止
```

**算子边界不是链**，而是 **`op_idx` 的变化**：连续若干个 op_idx 相同的 task 构成一个算子。

## 二、修正后的算子统计

| | 值 |
|---|---|
| task 总数 | 615 |
| **真实算子数** | **229** |
| 每个算子的 task 数 | 1:69 · 2:69 · 3:50 · 4:12 · 5:14 · 6:2 · 7:3 · 8:1 · 10:8 · 19:1 |
| 完整算子指令数 | 最少 **27** · 平均 **314** · 最多 **1479** |

`op_idx` 会重复出现（82 个 op_idx 出现多次）→ **它是算子「类型」，不是实例**。
例如 op1 出现 5 次，各实例指令数 `[1311, 1230, 1230, 246, 984]`。

### 与两版旧结论的对比

| | 第一版 | 第二版（docs/13） | **本版（正确）** |
|---|---|---|---|
| 算子数 | 588（= task 数） | 395 | **229** |
| 边界依据 | — | PC 链 | **连续相同 op_idx** |
| op1 规模 | 47 条 | 24 task / 1588 条 | **19 task / 1311 条** |
| 最大算子 | 137 条 | 4252 条 | **1479 条** |

> **教训**：扫描窗口没对齐"本段边界"时，会读到邻居的数据并得出完全错误的拓扑。
> 两次修正都源于同一个根因 —— **没有严格按 `regcfg_amount` 切段**。

## 三、★ CPU 侧 RKNPU 模拟开发环境

用户要求"逆向出一整套 CPU 模拟 RKNPU 的开发环境与工具"。已建好：

```
src/sim/
├── README.md
├── rknpu/
│   ├── __init__.py
│   ├── regcmd.py     指令编解码（8 字节三字段）+ RegcmdBuilder 构造器
│   ├── regmap.py     寄存器空间模型（153 个实测寄存器，自动生成）
│   ├── machine.py    结构级模拟器（内存 / 寄存器 / 段 / 链 / 算子）
│   ├── loader.py     从抓取语料载入 task 与内存
│   └── cli.py        命令行入口
└── tests/
```

### 3.1 它能做什么

| 能力 | 说明 |
|---|---|
| **跑真实 dump** | 615 条样本全部执行，验证我们对结构的理解是否自洽（**当前 72044 条指令全通过**） |
| **反汇编 / 汇编** | `decode` / `encode` 往返一致；`RegcmdBuilder` 能从头构造命令流 |
| **寄存器状态机** | 完整记录 150 个寄存器地址的写入历史与次数 |
| **链与算子分析** | 自动算链指向统计、按 op_idx 划算子、算指令数分布 |
| **未知寄存器告警** | 写入未观测过的寄存器会记录（当前 0 个未知 → 我们的寄存器表是全的） |
| **hook 机制** | 每条指令可挂回调，为后续**功能级**建模留接口 |

### 3.2 定位：结构级，不是功能级

**它不算卷积结果。** DMA 与算子字段的语义还需 NVDLA 对照才能确定，
在此之前做功能级建模是无源之水。

但它已经能替代硬件做大量验证工作 —— 而且**零风险**（板子被我搞挂过两次，
这条路线的价值已经被证明了）。

### 3.3 用法

```bash
cd rk3588-npu-re
export PYTHONPATH=src/sim

python3 -m rknpu.cli verify          # 全量验证（615 样本）
python3 -m rknpu.cli chains          # 列出重建出的算子
python3 -m rknpu.cli trace 0         # 跟踪 task 0 的完整执行
python3 -m rknpu.cli state           # 转储寄存器状态
python3 -m rknpu.cli regs            # 打印已知寄存器表
```

### 3.4 开发过程中修掉的两个自身 bug

| Bug | 现象 | 根因 |
|---|---|---|
| **重叠块查找错误** | 379 个段读不出来 | dump 之间重叠（`amount*8+64` 伸进下一个槽位），`find` 返回"第一个包含"的块，读到的是上一个块剩的十几字节 → 应选**起始地址最大**的块 |
| **段定义漏一条** | 链指令永远看不到 | 链指令在 `index == amount`，而我只解码了 `amount` 条 → 段是 **`amount + 1`** 条（体 + 链） |

> 第二个 bug 也再次确认了 `regcfg_amount` 的语义：**它数的是"体"，链是额外一条。**
> 这与"`regcfg_amount` 精确等于链指令索引"（611/611）完全一致。
