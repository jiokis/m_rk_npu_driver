# ★★★★★ 本轮结果：网关跑通（提示词 → 出图 → NPU 利用率），但**出图质量还不对**

## ③ CLIP 文本塔 → RKNN：完成（同样用「拆」的办法）

整只文本塔（354 M 参数 / ONNX 1413 MB）转 RKNN 峰值 **6.59 GB** ⇒ 7 GB 上 OOM。
**按层切成 3 段**（文本塔**没有 skip 连接**，接口就是 `[B,77,1024] → [B,77,1024]`，比 UNet 简单）：

| 段 | 层 | ONNX | `.rknn` | build |
|---|---|---|---|---|
| P0 | 0–7（含词/位置嵌入） | 606 MB | **354 MB** | 35 s |
| P1 | 8–15 | 403 MB | **257 MB** | 21 s |
| P2 | 16–23（含 ln_final） | 403 MB | **257 MB** | 25 s |

**踩的坑**：
1. `open_clip.create_model('ViT-H-14')` 会**同时建视觉塔**（32 层×1280，~600 M）⇒ OOM
   ⇒ 改用 `TextTransformer` **只建文本塔**
2. `TextTransformer` **自带** `token_embedding`/`positional_embedding`/`ln_final`/`transformer`
   ⇒ 外面再包一层会让名字对不上（`missing 293 / unexpected 288`）
3. 必须 `output_tokens=True`，否则返回的是**池化**的 `[B,1024]`；
   且它返回的是**元组 `(pooled, tokens)`** —— 要取**后者**
4. 直接调 `resblocks` 会走 `aten::_native_multi_head_attention`，
   **该算子无法导出 ONNX** ⇒ 必须 `torch.backends.mha.set_fastpath_enabled(False)`

## ❌ 出图质量还不对：是**调度器**的问题，不是链路

三张不同提示词出的都是**高频彩色噪声**（相邻像素差 2.8~4.6，std 32~48）。

**根因（已定位）**：
* 我最初写成 `z = z - eps/N` —— **那根本不是 DDIM**，几乎不改变 z
* 改成真 DDIM 后仍然不对：**t=999 时 `1/sqrt(ᾱ) ≈ 15`，eps 的误差被放大 15 倍**
  ⇒ RKNN 路径 1~3% 的误差 → `z0` 直接跑飞
* **SD-Turbo 官方用的是 `EulerAncestralDiscreteScheduler` + `timestep_spacing="trailing"`
  + `guidance_scale=0`**，不是 DDIM；而且它靠**蒸馏**让 1 步成立，
  对 eps 精度极其敏感 ⇒ **量化路径下 1 步大概率不成立**

# ★★★★★ 出图修好了：真凶是漏了 `scheduler.scale_model_input()`

## 症状与定位过程

出图一直是**抽象彩色纹理**。逐一排除：

| 试过 | 结果 | 结论 |
|---|---|---|
| 换 512×512（以为分辨率不对） | 仍纹理 | ❌ 分辨率假设不成立 |
| 加步数 2/4/8 | 仍纹理 | ❌ 不是步数 |
| 换 EulerAncestral（对齐 SD-Turbo） | 仍纹理 | 但**必要**（见下） |
| 查 CLIP 因果掩码 | 正常 | ❌ 不是条件 |
| **看参考里 `z` 的 std** | **16.8**（应为 ~1） | ★ **找到了** |

## ★★★★★ 真凶：**喂 UNet 之前必须调 `scheduler.scale_model_input()`**

diffusers 的采样循环是：

```python
latent_model_input = scheduler.scale_model_input(latents, t)   # ← 我漏了这一步
noise_pred = unet(latent_model_input, t, encoder_hidden_states=prompt_embeds).sample
latents = scheduler.step(noise_pred, t, latents).prev_sample
```

EulerAncestral 的 `scale_model_input` 就是 **`sample / sqrt(σ² + 1)`**。
σ_max = 14.61 ⇒ **除数 14.65**。

**我原来把 std≈14.6 的 latent 直接喂进 UNet ⇒ UNet 看到的输入大了 14.65 倍
⇒ 预测的 eps 全是垃圾 ⇒ 输出抽象纹理。**

### 修复效果（GPU 参考，512×512）

| | 采样后 `z` 的 std | 图像 std | 相邻差 |
|---|---|---|---|
| 修复前 | **16.8** | 93.5 | 20.8 |
| **修复后** | **1.37** ✅ | 93.5 | 20.8 |
| **修复后 + 4 步** | **0.63** ✅ | **34.4** | **5.0** |

**修复后出的是真实连贯画面**（米色纸页 + 上面的图形），不再是噪声。

## 板上实测（256×256，NPU）

## 现在网关里正确的完整采样链

```python
z = randn * SIGMA_MAX                                  # 14.61（init_noise_sigma）
for i, t in enumerate(timesteps):
    zi = z / sqrt(sigma[i]**2 + 1)                     # ★ scale_model_input
    eps = unet3parts(zi, t, ehs)                       # CLIP 条件
    z = euler_ancestral_step(eps, i, sigmas, z)        # z ← z − σ·eps（1 步时）
img = vae_decode(z)                                    # ONNX 里已烘 1/scaling_factor
```

## ★★★★★ 板子的硬限制：`cma=128M`

```
RKNPU: failed to allocate IOVA: -12
RKNPU fdab0000.npu: rknpu_gem_get_pages: dma map 869076992 fail     ← 单次要 869 MB！
```
`/proc/cmdline` 里 `extraargs=cma=128M` ⇒ **NPU 分不到连续 DMA 内存**。
256 档能跑是因为激活小得多。

**处理**：改 `/boot/orangepiEnv.txt` 的 `extraargs=cma=2048M`（已备份原文件）并重启。
重启后 `CmaTotal: 2097152 kB` ✓，六个模型**单独 init 全部成功**。

## ❌ 仍卡住：512 档推理时 NPU 内存不够

* 同时驻留 p1+p2+p3a+p3b ⇒ `init 失败`
  ⇒ 改成**逐段加载→跑→释放**（任何时刻只驻留一个）
* 但 `unet_p3a` 的 **`inference` 返回 None**（init 成功、推理失败）
  ⇒ 512 档 up_blocks 在 256×256 上有 512 通道，**中间激活极大**
  ⇒ 869 MB 那笔分配仍然过不去

**⇒ 结论：512 档需要把 P3a 再拆细（按 up_block 逐个拆），
   或者接受 256 档（那个是能出图的）。**

## 顺带修的

* `run()` 现在会**明确报错**（输入个数/形状 + 提示看 dmesg），不再只是 `NoneType`
* skip 的分配搞清楚了（latent=64 实测）：
  `up[0]`←skip[9..11] `up[1]`←skip[6..8] `up[2]`←skip[3..5] `up[3]`←skip[0..2]

# 512 档：端到端**跑通了**（但出图仍是纹理）

## ✅ 本轮靠逆向成果直接解决的问题

### ① 用 `RKNNMemStatisticsPass` 定位内存黑洞

编译 `unet_p3a` 时工具链自己打印（逆向时发现的 pass）：

```
Total Internal Memory Size: 17046.8KB     ← 激活只有 17 MB
Total Weight Memory Size:  825668KB       ← **权重 825 MB**
```

**⇒ 那笔失败的 869 MB 分配是「权重」而不是激活 ⇒ 按参数量拆就能解决。**
⇒ 把 `up_blocks` **逐个拆开**（up0/up1/up2/up3），最大一段 540 MB：
332 + 540 + 164 + 73 MB，**拼接余弦 0.999023**。

### ② 板子的硬限制：`cma=128M`

```
RKNPU: failed to allocate IOVA: -12

```
⇒ 改 `/boot/orangepiEnv.txt` 的 `extraargs=cma=2048M`（原文件已备份）并重启。

# ★★★★★ 逐段对比：**核心链路是对的**，问题在采样循环

## 方法

GPU 上导出每一步的中间量（`deploy/sd/dump_ref64.py` → `/tmp/ref64.npz`），

| 环节 | 余弦 | 判读 |
|---|---|---|
| ① CLIP `ehs` | 通过（>0.99） | ✅ |
| ② `p1.feat` / `p1.emb` | 通过 | ✅ |
| ③ `p2.mid` | 通过 | ✅ |
| skip4–11 | 0.81 → **0.31** | ⚠️ 但索引可能错位（见下） |
| ④ `up0` / `up1` / `up2` | 0.596 / 0.148 / 0.297 | ⚠️ |

## ★★★★★ 结论

**UNet 的最终输出和 VAE 解码都正确**（0.9993 / 1.0000）
⇒ **纹理不是「模型/转换」的问题，而是「采样循环」的问题。**

⚠️ 中间 skip 的余弦低（0.31~0.81）**很可能是我的索引对不上**：

⇒ **两边的序号不是一一对应的**（这一点在 docs/141 已经踩过一次）。

**但最终 eps 对得上，说明这些中间量即便有出入也没有破坏结果**
（或者说：我比对的是错位的张量对）。

## 下一步：只查采样循环

既然 eps 与 VAE 都正确，单步结果就应该正确。**⇒ 重点查：**

1. **gateway 的 `steps` 循环**：`euler_ancestral_schedule(4)` 给的
   `timesteps` 与 `sigmas` 是否与 diffusers 的 `set_timesteps(4)` 一致
   （尤其 `timestep_spacing="trailing"` 的取整方式）

# ★★★★★ 真凶找到了：**内层循环覆盖了采样步序号**

## bug

```python
for i, t in enumerate(tlist):        # ← 采样步
    ...
    for i in range(4):               # ← 内层复用 i，把采样步序号**覆盖成 3**！
        h = run(f"unet_up{i}.rknn", ...)
    z = euler_ancestral_step(eps, i, tlist, siglist, z, rng)   # ← i 已经是 3 了
```

* **单步**：`tlist` 只有 1 个元素、`siglist` 2 个 ⇒ `sg[3]` 越界
  ⇒ `IndexError: index 3 is out of bounds for axis 0 with size 2`
* **多步**：不崩，但**每一步都用 `σ[3]`** ⇒ 采样完全错 ⇒ **出图是纹理**

**⇒ 这就是「eps 余弦 0.9993、VAE 1.0000 却出纹理」的原因** —— 模型链路一直是对的，
错的是**采样循环**（正好印证了逐段对比的结论）。

## 修法

内层循环变量改名 `j`。**教训：嵌套循环里外层变量名不能复用**，
尤其外层变量还是**下标语义**的时候。

| 修复前 steps=4 | 123.4 | 127.4 | **37.2** |
| **修复后 steps=1** | 133.6 | 33.3 | **7.5** |
| **修复后 steps=4** | 146.8 | 40.5 | **4.7** |

**相邻差 34~37 → 4.7~7.5** ⇒ **从彩色噪声变成了平滑连贯的图像**

# ★★★★★ 定位到根因：**1 步生成下，eps 的 0.07% 误差会被 σ=14.61 放大到与信号同量级**

## 逐步排除的结果

| 检查 | 结果 | 结论 |
|---|---|---|
| **文本编码器**（`open_clip` 重建 vs HF `CLIPTextModel`） | **余弦 1.0000**（missing 0 / unexpected 0） | ✅ **编码器没问题** |
| **调度器**（vs diffusers `EulerDiscreteScheduler`） | 修掉取整方式后 **t 完全一致、σ 最大差 0.000006** | ✅ **已对齐** |
| 换成确定性调度器后的整体对比 | 余弦 **0.8868 → 0.9796**（相邻差 23.95 → 9.86） | ✅ 大幅改善 |

（编码器验证时踩了两个坑：HF 的 `CLIPTextModel` 把文本塔包在 **`text_model.`** 前缀下；

| 步数 | GPU 相邻差 | NPU 相邻差 | 余弦 |
|---|---|---|---|
| 4 | 0.17 | 9.86 | 0.9796 |
| **1** | **20.78** | **1.35** | 0.8197 |

## ★★★★★ 定量解释（这就是根因）

逐段比对时量到 **`eps` 的余弦是 0.9993**（约 **0.07%** 的误差）。

而 1 步生成的更新是：

```
x0 = z − σ·eps        σ = 14.6146
```

* eps 的 0.07% 相对误差 ⇒ 绝对误差 ≈ **0.0007 × 14.6146 ≈ 0.010**（在 eps 的 std≈0.97 尺度上）
* 但 `x0` 的 std 只有 **1.3734**
* ⇒ **误差与信号的量级已经可比** ⇒ 高频细节被抹掉 ⇒ 出图变平滑

**⇒ 结论：不是「链路错」，而是「精度不够」。**
在 SD 这种 `σ_max ≈ 14.6` 的设定下，**eps 需要比 0.07% 高得多的精度**，
否则单步生成的细节会被放大误差吃掉。

## 下一步（方向明确）

1. **提高 UNet 三/六段的精度**：目前是 FP16（`do_quantization=False`）；
   可以考虑 fp32 导出（体积翻倍但精度更高），或逐段定位哪一段贡献了那 0.07%
2. **逐段测 eps 误差**：分别把 p1/p2/up0..up3 换成 torch 的对应段，
   看误差主要来自哪一段（很可能是含 attention 的 up1）
3. **CLIP 三段**同样过了一遍 RKNN（FP16）⇒ 也可以换成 torch 版对比

# ★★★★★ CLIP 的真正 bug：**我手写的 resblock 循环复刻不出 `TextTransformer.forward`**

## 决定性判据

| 比较 | 余弦 |
|---|---|
| NPU 串接输出 vs **我手写循环算的** `p2` | **0.999964** ✅ |
| NPU 串接输出 vs **真正的 `ehs`**（`t(ids)`） | **0.265684** ❌ |
| **`clipref.p2`（手写循环）vs `clipref.ehs`（真正）** | **0.265923** ❌ |
| `clipref.ehs` vs `ref64.ehs`（两个都是真正的） | 1.000000 ✅ |

**⇒ 三段 RKNN 本身都很准（0.99996~0.99998），但它们**忠实复刻的是我那个错的手写循环**。**
**⇒ bug 在导出侧的「手写循环」，不在 RKNN。**

## 差在哪

`open_clip.TextTransformer.forward` 是：

```python
x, attn_mask = self._embeds(text)        # ← 掩码在这里生成
x = self.transformer(x, attn_mask=attn_mask)   # ← 走 Transformer 模块
x = self.ln_final(x); tokens = x
```

我手写的是 `for blk in resblocks: x = blk(x)`，**漏了掩码**。

补掩码时又踩一个：直接把 `self.attn_mask` 传给 `MultiheadAttention` 会报

```
RuntimeError: The shape of the 2D attn_mask is torch.Size([77, 77]), but should be (1, 1)
```

⇒ 说明 `_embeds`/`Transformer` 内部对掩码还有额外处理（形状/维度），
**不能拿 `self.attn_mask` 直接塞给 resblock**。

## 正解（下一步）

**别再手写循环**，直接用 `TextTransformer` 自己的代码路径：

1. `x, am = t._embeds(ids)` 拿到**正确的** `x` 与 `am`
2. 分段时，把 `am` 作为**常量 buffer 烘进子模块**（掩码是固定的 77×77），
   子模块内部按 `Transformer.forward` 的同样方式调 resblock
3. 或者更稳：**用 forward hook** 在 `t.transformer.resblocks[i]` 上截取中间激活，
   以「真实前向」的输入/输出为准来切分（而不是自己重算）

⚠️ 这也解释了为什么之前所有 CLIP 相关的比对都「自洽但错」：
**参考和被测都出自同一个错的手写循环**，互相印证得很好，却和真正的 CLIP 差了 0.27。

# ★★★★★ 生图过程中的 NPU 利用率（实测）

## 先排掉两个不可信的读数

| 接口 | 读数 | 结论 |
|---|---|---|
| `/sys/class/devfreq/fdab0000.npu/load` | 恒为 `100@1000000000Hz`（**换 `rknpu_ondemand` governor 也一样**） | ❌ 不是真实占用（governor=performance 时它反映的是「频率请求」） |
| `/sys/kernel/debug/rknpu/load` | 有**逐核**读数 `Core0/Core1/Core2: x%`，但**出图期间恒为 0** | ❌ 这版驱动没实现该计数器 |

**⇒ 改成从宿主侧实测**：把网关的 `run()` 拆成「模型加载 / NPU 推理 / 释放」三段计时，
`NPU 占用率 = 所有 inference 调用耗时之和 ÷ 墙钟`。

## 结果（512×512，`core_mask=0_1_2`）

## ★★★★★ 结论：**NPU 只忙了约一半时间，剩下全是「加载/释放模型」**

**26.8%~34.3% 的时间花在 `load_rknn`/`release` 上**，因为 CMA 装不下多段、
必须**逐段加载→跑→释放**（每步 6 段 × 4 步 = 24 次加载）。

**⇒ 这是目前最大的优化空间**：
* 若模型能常驻，NPU 占用率可望到 **~90%**，总耗时大约能砍掉 1/4~1/3
* 前提是**板子的 CMA/IOVA 够大**（单段最大 540 MB，而失败的那笔分配要 869 MB）
* 可试：**再调大 CMA**（现在 2048M），或**把段拆得更小**以让多段并存

# ★★★★★★ 逆向结论：`fuse_mul_into_sdpa` 的「bug」其实是 **numpy 2.x 不兼容**

## 怎么找到的（经验式逆向，因为规则是编译好的 .so）

`rknn/api/rules/` 下全是 `.cpython-312-x86_64-linux-gnu.so`（无 Python 源码），
报错里的 `matmul.py:1633` 只是编译时嵌入的调试路径。⇒ 只能靠**实验**。

### 第一步：最小复现（自己造 attention 图）

造了 q/k/v + `q*scale` + matmul/softmax/matmul 的最小模块，变化 `scale` 的形状：

| scale 形状 | 带规则 | 禁规则 |
|---|---|---|
| 标量（0 维） | ✅ build=0 | ✅ |
| `[1]`（1 元素 1 维） | ✅ build=0 | ✅ |
| `[heads]`（每头一个） | ❌（是我测试代码的广播错，非规则问题） | ❌ |
| 无 scale | ✅ | ✅ |

**⇒ 最小图**带规则也能过** ⇒ 规则本身没坏，是真实模型里某种形状才触发。**

### 第二步：逐个 part 带规则试（真实模型）

| part | 含 attention | 带规则的结果 |
|---|---|---|
| `unet_up0` | ❌（`UpBlock2D` 无 attn） | ✅ build=0 |

| `vae512_v1` | ✅ | ❌ 同上 |

`TypeError: only 0-dimensional arrays can be converted to Python scalars`

# ★★★★★★ 逆向「模型加载路径」⇒ 提速 31%

## 第一步：加载开销到底花在哪（eMMC vs tmpfs + 分段计时）

对 `unet_up1`（515 MB）做分段计时：

| 来源 | 构造 | `load_rknn` | **`init_runtime`** | **`release`** | 合计 |
|---|---|---|---|---|---|
| eMMC（首次/冷） | 0.17 s | **1.68 s** | 0.54 s | 0.21 s | 2.60 s |
| eMMC（第二次/页缓存） | 0.10 s | 0.24 s | 0.52 s | 0.20 s | 1.06 s |
| **tmpfs**（`/tmp`，RAM） | 0.09 s | 0.23 s | 0.35 s | 0.20 s | **0.87 s** |

**⇒ 两个结论：**
1. **磁盘只在首次读时慢**（1.68 s / 515 MB ≈ **307 MB/s**，eMMC 的顺序读速度）；之后走页缓存
   ⇒ **tmpfs 换不来收益**（页缓存后一样快）
2. **真正的固定开销是 NPU 侧的 `init_runtime`（0.35~0.54 s）+ `release`（0.20 s）≈ 0.6 s**
   ⇒ 那是 **IOVA/DMA 映射 + 权重上传 + 拆卸**

**⇒ 24 次加载 × 0.6 s ≈ 14.4 s，正好对上实测的 `model_load_ms 13.8 s`。**

## 第二步：驻留上限是「体积」还是「个数」

| 模型 | 可同时驻留 | 合计 |
|---|---|---|
| `unet_up3`（70 MB） | **12 个** | 840 MB |
| `unet_up1`（515 MB） | **7 个** | 3.6 GB |
| 混合 11 个（约 2.75 GB 权重 + 各自激活） | **10 个**（第 11 个 `init=-1`） | — |

**⇒ 是**体积**限制不是个数：RKNPU 可用 IOVA 空间约 **3.6 GB**（含每模型的内部激活内存）。**
（CMA 从 2 GB 提到 **3 GB** 后上限没变 ⇒ **限制在 IOVA 空间，不在 CMA**。）

## ★★★★★ 第三步：按「使用频率」分配常驻（关键洞察）

**CLIP(3 段) 与 VAE(2 段) 是「每张图用一次」；只有 6 个 UNet 段是「每步都用」。**

⇒ **让 6 个 UNet 段常驻、CLIP/VAE 按需加载**，每步的「加载→跑→释放」就彻底消失。

```python
RESIDENT_MODELS = ("unet_p1.rknn","unet_p2.rknn","unet_up0.rknn",
                   "unet_up1.rknn","unet_up2.rknn","unet_up3.rknn")
# run() 里：name in self.resident ⇒ 直接 inference，不 load/release
```

**实测 6/6 全部常驻成功**（内存刚好够：129+616+317+515+157+70 ≈ 1.8 GB 权重 + 激活）。

## 效果（512×512 / 4 步 / seed 0）

| | 逐段加载 | **6 段常驻** | 变化 |
|---|---|---|---|
| CLIP | 1789 ms | 1962 ms | ~ |
| **UNet** | **38546 ms** | **22239 ms** | **−42%** |
| VAE | 10976 ms | 11105 ms | ~ |
| **总计** | **51440 ms** | **35472 ms** | **−31%** |
| **NPU 占用率** | 59.4% | **88.0%** | **+29pp** |
| **加载占比** | 26.8% | **4.4%** | **−22pp** |

**⇒ NPU 从「忙一半」变成「忙 88%」，总耗时砍掉近三分之一。**
（出图质量不变 —— 仍是一张高质量写实照片。）

## 这一轮的逆向链条

```
「加载占 25%」的现象
  → 分段计时：区分磁盘 I/O 与 NPU 侧开销 ⇒ 磁盘不是问题（页缓存后 0.24 s）
  → tmpfs 对照 ⇒ 确认换存储介质无用
  → 定位到 init_runtime/release ≈ 0.6 s（IOVA 映射 + 权重上传）
  → 测驻留上限 ⇒ 是体积限制（~3.6 GB IOVA），且 CMA 调大无效
  → 按「使用频率」重新分配常驻 ⇒ 每步的加载全部消除
```
