> 从真实图进去，到最终检测框出来，速度和一致性都实测。

## 0. 结果

| 指标 | 值 |
|---|---|
| **吞吐** | **14.27 FPS**（27 帧 / 1.89 s） |
| 单帧延迟 | 中位 **69.14 ms**，p90 80.17 ms |
| **检出总数** | RKNN **1419** vs ONNX-FP32 **1490** |

纯推理（C 基准，无后处理）能到 26.6 FPS；Python 流水线 14.3 FPS，
差的 12 FPS 是 Python 侧的后处理 + GIL（见 §5）。

## 1. 架构

```
1280 输入图
   │  切成 2×2 = 4 块 640×640（ascontiguousarray，不缩放）
   ├─ 6 个 worker 抢 tile 队列（动态负载均衡）
   │     worker i → 独立 rknn 上下文，绑核 MASK[i % 3]
   ├─ 每个 tile：640 双输出 INT8 模型 → (1,64,8400) logits + (1,80,8400) 分数
   ├─ DFL：只对 score>0.25 的候选锚点算（numpy，~0.6 ms/tile）
   ├─ 坐标回映：tile 内框 += (x0, y0)
   └─ 跨 4 个 tile 做一次 NMS
```

三个关键点，每一个都是踩出来的：

1. **模型必须是双输出**（`docs/152`）——单输出会让 INT8 把分数压成 0
2. **每个 worker 必须持有独立的 rknn 上下文**——见 §2 的 bug
3. **喂 RGB 不喂 BGR**——RKNN 的 mean/std 按 RGB 配

---

## 2. ★ 踩到的坑：共用上下文会把输出互相踩烂

第一版流水线里我图省内存，**3 个上下文让 6 个 worker 共用（每核 2 个 worker）**。

结果：**每帧 412 个检出**（正确值约 55）。不报错、不崩、框坐标也都在合理范围，
**只是数字多了一个数量级** —— 典型的"看着像在工作"的坏法。

改成**每个 worker 一个独立上下文**（6 个 ctx，按 `i % 3` 绑核）后：

```
共用 ctx : 412.9 检出/帧   ← 错
独立 ctx :  52.6 检出/帧   ← 对（ONNX 参考 55.2）
```

> `rknnlite` 的上下文**不是线程安全的**。C API 有 `rknn_dup_context` 用于多线程，
> 但那也是"每个线程一份句柄"，不是多线程共用一份。
> 内存代价很小（4.06 MB × 6 = 24 MB）。

### 排查过程（可复用）

先用一个 tile 单独跑 → 0 检出，正常（那是个空地裁剪）；
再手工把一帧 4 个 tile 串起来跑 → **46 原始框 / NMS 后 15 个**，完全正常；
⇒ 差异只在"多线程"这一层 ⇒ 锁定上下文共享。

## 3. 另一个坑：BGR / RGB

`cv2.imread` 读进来是 **BGR**，而 RKNN 的 `mean_values/std_values` 是按 **RGB** 配的。
标定和验证脚本里我都写了 `bgr[:,:,::-1]`，但第一版流水线漏了，喂的是 BGR。

颜色通道错位后：单 tile 的 `cls max` 从 0.18 变成 0.25，检出数直接翻倍。
**这种错不会报错，只会让精度悄悄变差。**

## 4. 一致性验证（27 张真实 COCO 图）

同一条 2×2 分块流程，RKNN-INT8 vs ONNX-FP32：

| | 检出总数 | 平均/帧 |
|---|---|---|
| ONNX FP32 | **1490** | 55.2 |
| RKNN INT8 | **1419** | 52.6 |
| 一致度 | | **95.2%** |

> 注意这里比的是"分块后的 640 模型"，不是 native 1280 —— 因为我们的架构就是分块，
> 要和同架构的 FP32 比才有意义。

## 5. 速度还能再挤

| 环节 | 耗时 | 说明 |
|---|---|---|
| 4×640 纯推理 | ~37 ms/帧 | C 基准实测（`docs/151`，6 worker） |
| **Python 流水线实测** | **69 ms/帧** | 多出的 ~32 ms 在 DFL 尾部 + NMS + GIL |

优化方向（未做）：

1. **后处理移出 GIL**：DFL/NMS 用 C 或 `numpy` 原地操作；或者把 worker 改成多进程
2. **DFL 阈值先粗筛**：先用 `cls.max(0) > 0.25` 的布尔掩码减少候选
3. **C 里做整条链路**：把 DFL 和 NMS 也写进 `bench1280.c`，理论上能贴近 26.6 FPS
