# 31 · 撤回 docs/30 的方向修正：读的确实就是写过的（覆盖率 95.2%）

> "存在大量搬运/重排浪费，优化手段应从「融合」改为「减少重排」"。

## 一、错在哪：把"地址不相等"当成了"没复用"

docs/30 里的严格配对判据是**地址完全相等**：同一地址先被写、后被读。
算出来只有 9.5%，于是有了那个推断。

但我漏看了一个直接的数据：

```
op0（19 个 tile）:  DPU 0x4020 输出基址  0xff1cf000  步长 0x15400
op1（ 5 个 tile）:  CNA 0x1070 输入基址  0xff1cf000  步长 0x55000
                        ↑ 基址完全相同
```

**基址是一样的，只是 tiling 粒度不同**（一个算子切 19 块，下一个算子把同样的数据
当 5 块读）。这种情况下"地址集合相等"根本不成立，但数据明明是同一份。

**"地址相等"是个过严的判据 —— 它把 tiling 边界差异误判成了"没复用"。**
正确判据是：**消费者的读区间，落不落在某个生产者写过的区间里（区间重叠）。**

## 二、正确的判据与结果

```bash
python3 src/analysis/dram_model.py overlap
```

```
  缓冲   容量MB   写占用MB   读占用MB   写流量MB   读流量MB   被覆盖MB   覆盖
   1     0.39     0.04     0.00     0.16     0.00     0.00   0.0%
   2     1.56     0.13     0.00     0.51     0.00     0.00   0.0%
   3     1.17     0.00     1.23     0.00     3.52     0.00   0.0%
   4     7.42     5.78     5.92    48.07    90.42    89.39  98.9%

  写流量合计 48.74 MB / 读流量合计 93.93 MB
  读被写覆盖 89.39 MB = **95.2%**（按读流量计）
```

**95.2% 的读流量落在生产者写过的区间内。** 剩下来的 4.8% 主要是：
- 输入图像（从没被 NPU 写过，是 CPU 填的）
- 权重（0x1110 指向只读区）
- 最终输出（写了但没人读）
- 少量测量误差

这些本来就**应该**不被覆盖。所以真实结论是：

> **消费者读的就是生产者写过的数据，不存在额外的搬运、双缓冲或重排浪费。**
> DRAM 流量就是"生产者写一次 + 消费者读一次"的最小值，没有水分。

## 三、被迫撤回的结论，以及被迫接受的结论

| docs/30 的说法 | 本轮结论 |
|---|---|
| 91% 的读与写地址不同 ⇒ 有大量搬运/重排 | ❌ **撤回**。那是 tiling 粒度差异造成的假象；区间重叠判据下覆盖率 95.2% |
| 手段应从「融合」改为「减少重排」 | ❌ **撤回**（前提不成立） |
| 融合是头号优化手段 | ⚠️ **部分恢复但要打折**：见下 |

### 那"融合"到底还有没有用

必须接受一个物理事实：**RK3588 的 NPU 没有可用片上 SRAM**（`GET_TOTAL_SRAM_SIZE = 0`，docs/06）。

所以"把中间结果留在片上"这件事，在这块芯片上**没有地方可留**。既然流量已经是最小值
（95.2% 覆盖率高），那么：

- **减少 DRAM 往返的次数** —— 唯一办法是让相邻算子在**分块级别**上融合
  （生产者的一个 tile 算完就地喂给消费者，中间结果只停留在流水级之间的 line buffer 里）。
  这是**编译器/工具链层面**的事（命令流是 rknn-toolkit 生成的），**驱动改不了**。
- **提高带宽** —— DDR 钉频已做（1.59×）。这是驱动能碰的部分，也已经吃掉了。
- **剩下的一半** —— docs/29 的发现 B 说得很清楚：DMC 频率 4.5× 只换来带宽 1.59×，
  说明还有一半时间不在等 DRAM，而在**流水串行**（对应 docs/19「核内天花板仅 16%」）。
  **这一半是驱动和调度能碰的**，也是下一步该花力气的地方。

## 四、这个错误值得单独记一笔

这是本项目**同类错误的第三次**：

| 次数 | 出处 | 错误 | 共同点 |
|---|---|---|---|
| 1 | docs/25 | DDR 钉频收益报成 1.8~2.5×（实际 1.59×） | 用"看起来合理"代替严格测量 |
| 2 | docs/29 | "67% 是同一趟往返"（实际 9.5%） | 用"同一缓冲区+量级对称"代替严格判据 |
| 3 | docs/30 | "91% 地址不相等 ⇒ 有重排浪费" | 用"地址不等"代替"区间不重叠" |

三次都是**判据选错**，而不是数据错。而且第 3 次尤其值得记：**我是在"修正"第 2 次的过程中
引入第 3 次错误的** —— 纠错动作本身也需要被交叉验证。

已固化成两条做法：

1. **关键数字必须有第二种独立方法**（本轮：形状法 vs 跨度法，差 13% 互相印证）。
2. **判据要往"物理上必然成立"的方向放宽，而不是收紧**：
   "同一地址" → "区间重叠" 就是一次正确的放宽。判据过严会产生**假阴性**，
   而假阴性比假阳性更危险 —— 它会让你把本来正确的方向当成错的去改。

## 五、现在的完整图景

```
单次推理（yolov5s 640，3 核，DDR 2400MHz）
├─ 特征 DRAM 流量      ≈160.89 MB（形状法，确证字段）／142.68 MB（跨度法）互相印证
├─ 流量的构成          写 48.07 MB + 读 90.42 MB，**95.2% 的读落在写过的区间内**
│                     ⇒ 没有任何搬运/重排水分，已是"写一次读一次"的最小值
├─ 实测耗时            28.91 ms  ⇒ 有效带宽 5.57 GB/s（约峰值 58%）
└─ 瓶颈拆解
   ├─ DRAM 侧：DMC 频率 4.5× 只换来 1.59× ⇒ DRAM 只解释了一部分
   └─ 流水侧：另一半在流水串行（docs/19：核内天花板 16%）← ★ 驱动能碰，下一步主攻
```

## 六、下一步（修正后）

1. **主攻流水串行那一半**：纯软件 per-core busy/idle 插桩（安全，不碰寄存器）。
   目标是把 docs/19 说的"核内天花板 16%"定位到具体流水级（CNA 串行？CORE 等待？）。
2. **验证"分块级融合"是否已在工具链里**：既然 95.2% 的读覆盖写、且占用峰值只有
   5.92 MB（远小于 7.78 MB 缓冲），说明命令流已经在做较紧凑的分块复用。
   可以算一条曲线：**占用峰值 vs 流量**，看还有多少压缩空间。
3. 权重流量单独量化（0x1110 是只读区，目前没算尺寸）—— 如果权重被每个 tile 重读，
   那会是一块可观且**可优化**的流量（比如让工具链把权重留在片上）。
