# 39 · ★★★ 结构级耗时模型：`t = work + 90µs × submit数`（66% 是固定开销）

> 目标第 ③ 条要"建立能预测给定工作量的结构级模型"。本轮把模型建出来了 ——
> 而且它的形式出乎意料：**耗时的主要项不是工作量，而是"提交次数"。**
>
> ⚠️ **本篇的模型与「66%」这个比例已被 [docs/40](40-提交地板直接实测与docs39修正.md) 修正/加强**：
> ① **「每次提交有约 70 µs 固定地板」被两个独立工作负载直接测到**（yolov5s 与 RKLLM 的
>    3-task 提交都落在 60~115 µs）—— 这部分结论加强；
> ② 但 `t = work + c×n` 用两套配置是**欠定**的：k=3 解出 c=78 µs（占比 54%），
>    k=2 解出 c=45 µs（占比 31%）。**「66%」是把拟合截距当唯一解，过强了**，
>    应收窄为「31%~54%，取决于并行度假设」。
> ③ 模型形式更可能是 `t = max(地板, work)` 而不是加法。
>
> 相关：[33](33-推理时间构成-NPU只占三分之一.md)（时间构成）· [34](34-落地-并发把NPU利用率从36%提到94%.md)（并发）· [38](38-字段语义实证钉住.md)（字段语义）· [40](40-提交地板直接实测与docs39修正.md)（修正）

## 一、先纠一个数据格式错误

计时探针的逐条记录表头写的是 `wall_us hw_us overhead_us`，
**但实测逐列求和的单位是纳秒**：

```
逐条 hw 求和 = 22,155,640  →  若 ns 则 22.156 ms
TOTAL 行        hw_us=22156 →  22.156 ms          ✓ 吻合
```

后续所有分析按 ns 处理。**这个错不改会得出"每次 submit 只要 0.15 µs"的荒谬结论。**

## 二、对齐数据集：让"内容"和"计时"来自同一次运行

之前的 `dumps2` 是 **cm=1、单个 588-task 大 submit** 抓的，
而计时日志是 **cm=7、大量小 submit** —— 两者结构不匹配，无法对齐。

所以重新跑了一次**双探针同时挂载**的采集（`rknpu_capture.so` + `rknpu_submit_timer.so`），
让 task 内容与 submit 计时来自同一次运行：

```
计时日志第 N 条  ↔  capture 的 seq N-1      （task_number 逐一吻合）
154 条记录（2 次推理 × 77 submit）
```

## 三、否定结果：**任何结构量都解释不了单次 submit 耗时**

用 154 组对齐数据做单变量回归（因变量 = 实测 `hw_elapse_time`）：

| 特征 | R² | 截距 |
|---|---|---|
| tile 数 | 0.015 | 121.7 µs |
| 权重流量 | 0.001 | 146.3 µs |
| 输入访存 | 0.009 | 137.5 µs |
| 输出访存 | 0.007 | 139.1 µs |
| **MAC 数** | **0.002** | 139.4 µs |

再把 ~20 个特征全跑一遍（含**权重解压 DCOMP 量**、**激活 LUT 装载次数**、
各流水级的寄存器写入数……），最好的是 DPU 寄存器数 R² = 0.026。

**全部约为 0。每个拟合的截距都落在 90~146 µs。**

而且拿板子上遗留的 **2677 条历史记录**独立验证：

```
core_mask=0x7: 2467 条，task 数 3..21，hw 中位 89.5 µs，task数–hw 相关 r = 0.011
```

**task 数从 3 到 21（7 倍），耗时几乎不变。** 结论稳。

## 四、正解：两参数模型，且两套配置同时吻合

否定结果指向了正解：耗时 = 工作量 + **固定的每次提交开销**。

拿两次已知测量联立（work₁ = 单核工作量，work₃ = 三核工作量，c = 每次提交固定开销）：

```
cm=1:  work₁ +  4c = 15.39 ms
cm=7:  work₃ + 77c = 10.51 ms
```

取 **c = 90 µs**（上面所有拟合的截距，也是大日志的中位数）：

```
→  work₁ = 15.0 ms   （单核）
→  work₃ =  3.6 ms   （三核，约 4× 加速 —— 3 核上限 3× 加上更好的流水重叠，合理）
```

**两式都吻合**（15.0 + 0.36 = 15.36 ≈ 15.39；3.6 + 6.93 = 10.53 ≈ 10.51）。

用 154 组对齐数据再校验一次：`Σwork = Σhw − 154 × 90µs = 22.156 − 13.86 = 8.30 ms`
（2 次推理）→ 单次 4.15 ms，与上面推的 3.6 ms 同量级 ✓。

### 模型

```
t_hw  ≈  work(核数)  +  90 µs × submit 数
         │                │
         │                └─ cm=7 时 77 × 90µs = 6.9 ms  ← 占全部的 66%
         └─ cm=7 时约 3.6 ms（三核并行后的真实计算+访存时间）
```

## 五、这个模型的三个直接推论

### 5.1 **cm=7 下 66% 的 "NPU 时间" 是固定开销**

```
cm=7 的 10.51 ms = 3.6 ms 工作量 + 6.9 ms 提交固定开销
```

**换句话说：运行时的 77 次小提交策略，把三分之二的时间花在了"每次提交的固定成本"上。**

### 5.2 改写 docs/33/34 对 `hw_elapse_time` 的解读

docs/33 据 `hw_elapse_time` 得出"NPU 硬件忙碌只占推理时间 32%"。
现在要精确化：**那个 10.51 ms 里只有约 3.6 ms 是真正的计算/访存，其余 6.9 ms 是每次提交的固定开销。**

所以：
- "NPU 忙碌 32%" 更准确的说法是 **"每次提交的占用"**
- **真正的计算占比更低**（3.6/26 ≈ 14%）
- 但 docs/34 的**落地方案不受影响** —— 并发之所以有效，正是因为它把"提交固定开销 + 计算"整体与其它进程重叠，
  利用率照样从 36% 提到 90.7%（那是在"NPU 占用"口径下测的，一致）

### 5.3 这是一个**可落地的优化目标**

对二次开发：**减少 submit 次数是第一优先级的结构性优化。**

```
cm=7 现在:  77 submit × 90µs = 6.9 ms 固定开销
若合并到 10: 10 submit × 90µs = 0.9 ms 固定开销
             → t_hw 从 10.5 ms 降到约 4.5 ms（NPU 侧 2.3×）
```

而且这不是空想：**同一份模型的 cm=1 路径只用了 4 次提交**（把 588 个 task 打包成一个 submit）。
说明"大批量提交"在硬件上是**被支持的**，只是 cm=7 路径的运行时没这么干。

> ⚠️ 但要注意：合并提交**不能牺牲多核并行**（cm=1 的那 4 次提交虽然少，但只用一个核，
> 工作量 15.0 ms 全靠单核）。理想策略是**大批量 + 多核**：
> 把 3 个核的工作各自打包成少量提交，或用驱动已支持的 `subcore_task[]`
> 机制在**一次提交里**分散到 3 个核 —— 后者正是驱动本就是为此设计的接口。

## 六、诚实标注的不确定性

1. **`c = 90 µs` 是从两次配置反解 + 拟合截距得来的**，不是直接测出的。
   要直接验证，需要做"同一工作量、只改 submit 次数"的对照实验（下一轮）。
2. `hw_elapse_time` 是 commit→completion 的墙钟，**它同时包含工作量与固定开销**，
   无法单独分离。所以模型是"两项之和"的经验形式，不是机理模型。
3. 那个 138 ms 的异常样本（cm=7, task=6）没解释 —— 可能是偶发 stall，已用中位数规避。
4. 90 µs 这个固定开销的**物理来源**仍未确定（候选：流水填充/排空、DMA 建立、
   中断往返、CBUF 重配置）。要定位它需要驱动侧插桩（submit 路径分段计时）。

## 七、下一步

1. **对照实验验证 c**：同一模型/同一 core_mask，只改变 submit 次数
   （例如用不同版本的运行时、或构造不同提交粒度的测试），看耗时是否按 `c × ΔN` 变化。
   这是把模型从"反解"变成"实测"的关键一步。
2. **定位 90 µs 的来源**：给驱动的 submit 路径加分段计时
   （进入 → iommu → 任务映射 → 内存同步 → 硬件提交 → 等待完成）。
   ⚠️ 注意 docs/34 已经测过：驱动侧 ioctl 只吃 1.2 ms/推理，所以 90 µs 很可能**不在驱动簿记里**，
   而在硬件侧（那就只能靠命令流优化，改不了）。
3. **把模型接上 bank/CBUF 约束**：docs/38 已经能把每层的 bank 需求算出来，
   可以进一步问"给定 bank 约束，最优的分块与提交打包方案是什么"。
