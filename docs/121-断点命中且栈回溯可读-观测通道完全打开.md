
## 3. 可复现的做法

```bash
# 1) 装 gdb（无需 root）
bash tools/get-gdb.sh

# 2) 提取内部 pass 的虚函数地址
python3 src/compiler/rtti_find.py RKNNTilingPass RKNNLayoutMatchPass …

# 3) 用 gdb 断点观察（gdb 脚本要点：先 catch load，再算基址，再 break）
cat > g.gdb <<'G'
set pagination off
catch load librknnc.so
run b.py
python
import gdb, re
out = gdb.execute("info sharedlibrary librknnc", to_string=True)
text_load = int(re.search(r"(0x[0-9a-f]+)\s+0x", out).group(1), 16)
base = text_load - 0x11b260          # .text 的 ELF vaddr
for off in [0x391450, 0x391420, …]:
    gdb.execute(f"break *{hex(base+off)}")
end
continue
bt 8
G
```

**关键点（踩过）**：**必须先 `catch load` 拿到基址再 break** ——
因为 ASLR 每次不同（实测两次运行基址分别是 `0x7fffaeC00000` / `0x7fffaeE00000`）。

## 5. 教训（本轮新增）

1. **★★★ 「符号表被剥离」是个**程度问题**，不是布尔值。**
   我检查了 `.symtab` 缺失、`nm` 查不到 pass 符号 ⇒ 判定「无符号」。
   **但 `.dynsym` 里仍有可用的 C++ 符号（导出层）。**
   **⇒ 判断「有无符号」时要**分层**看（导出层 vs 内部），不能一票否决。**
2. **★★★ 我连续三轮（docs/117/118 + 隐含在 119/120）低估了可达性。**
   * docs/117：「没有 Python 回调」→ 对（那条路闭），但**不等于整体闭**
   * docs/118：「gdb 不可行」→ 错（可装）
   * docs/120：「符号表剥离」→ 只对内部成立
   **⇒ 根因是同一个：我把「某一手段不行」放大成「问题不可解」。**
   **这是本项目最该记住的一条。**
3. **★ gdb 脚本的「先 catch load 再算基址」是必需步骤，不是优化。**
   ASLR 使基址每次不同（实测两轮不同）⇒ **硬编码地址会失败**。
   **踩过一次就要写成模板（本文 §3）。**
