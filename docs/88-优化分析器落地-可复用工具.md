## 1. ★ 设计原则：把这几轮踩过的坑写进代码

| 坑 | 写进代码的方式 |
|---|---|
| 用全局地板会让 `shufflenet` 算出 102%（docs/84） | `--floor-us` **必填项**，且报告里打印出来 |
| `tile × 地板` 会算出比总时间还大的数（docs/86） | **只按轮算**，并在输出里显式标注 |
| 上界/可达值分不清（docs/85） | 合并提交只给**参数化曲线**，不给单个「可达值」 |
| 数字依赖未验证假设（docs/82） | 每个数字后面跟 `[依据]` 标注 |

**⇒ 教训写进代码，比写在文档里更能防止重犯。**

## 2. 验证：复现 docs/83/86/87 的全部数字

```
模型                 纯搬运轮  期望   可删   期望   省ms    期望
densenet121             11    11    362   362   0.745  0.741
shufflenet_v2_x0_5       0     0    143   143   0.000  0.000
regnet_x_400mf           4     4    269   269   0.233  0.270
efficientnet_b0         15    15     65    65   0.922  1.011
```

**⇒ 结构量（纯搬运轮、可删数）全部精确复现；时间量有小数差。**

### 差异的原因（而且工具更准）

`regnet` 0.233 vs 0.270、`efficientnet` 0.922 vs 1.011 ——
**docs/83 用的是全局地板 67.4，而工具用的是逐模型实测地板**（58.3 / 61.5）。

```
合计：逐模型地板 2.11 ms   vs   全局 67.4 → 2.22 ms
```

**⇒ docs/83 的 2.22 ms 应修正为 2.11 ms**（差 5%，方向正确：`regnet`/`efficientnet` 的地板低于全局值）。

**这不是错误，是精度提升** —— 而且它正好印证了 docs/84 那条教训
（「全局常数在逐模型计算里会露馅」）在**同一个量上**又出现了一次。

## 4. 教训（本轮新增）

1. **★★ 教训要写进代码，不只是写进文档。**
   我把「地板必须逐模型给」「时间只按轮算」这两条**写成了代码约束**
   （必填参数 + 只按轮算 + 输出里标注依据）。
   **文档里的教训会被忘记，代码里的约束不会。**
2. **★ 沉淀工具时会顺带发现精度问题。** 复现验证暴露出 docs/83 用了全局地板
   ⇒ 修正为 2.11 ms。**重跑一遍旧结论是低成本的检查。**
3. **★ 同一个教训在同一类量上反复出现，说明它是结构性的。**
   「全局常数露馅」我在 docs/84（102%）和本轮（2.22→2.11）都遇到 ⇒
   **凡是逐模型计算的量，都不该用全局常数。** 这条值得写成默认规则。
