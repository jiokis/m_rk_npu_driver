## 一、计时结果

同一模型（yolov5s-640-640）、同一输入，各 15 次取平均：

| core_mask | 平均 (ms) | 最快 | 最慢 | **加速比** |
|---|---|---|---|---|
| **1**（单核） | 44.8 | 34.5 | 54.2 | 1.00× |
| **3**（双核） | 42.8 | 27.6 | 70.5 | **1.05×** ← 几乎无提升 |
| **7**（三核） | 25.5 | 22.4 | 30.3 | **1.76×** |
| auto | 30.1 | 26.5 | 34.2 | 1.49× |

> ⚠️ **可复现性说明**：本次测量有噪声（cm=1 在两次运行中分别测得 44.8ms 与 39.5ms，
> 板子是 WiFi 连接、ping 抖动达 141ms）。**趋势可信，绝对数值需多次复测。**

## 二、★ 多核到底怎么分工（结构证据）

抓取三套完整命令流后，`SUBMIT` 层面的差异是决定性的：

| 配置 | SUBMIT 次数 | task 总数 | 每 submit 平均 task |
|---|---|---|---|
| **cm=1** | **4** | 615 | 153.8 |
| **cm=3** | **77** | 413 | 5.4 |
| **cm=7** | **77** | 428 | 5.6 |

### 2.1 cm=1：整个模型当成一条链

```
[SUBMIT] flags=0x5 core_mask=0x1 task_start=0 task_number=588   ← 整个图，一次提交
[SUBMIT] flags=0x1 core_mask=0x1 task_start=196 task_number=6
[SUBMIT] flags=0x1 core_mask=0x1 task_start=198 task_number=9
[SUBMIT] flags=0x1 core_mask=0x1 task_start=201 task_number=12
```

**588 个 task 一次提交**，硬件顺着链走完。

### 2.2 cm=3 / cm=7：重组成大量小批次

```
cm=7 首批: [SUBMIT] flags=0x5 core_mask=0x7 task_start=618 task_number=21
cm=3 首批: [SUBMIT] flags=0x5 core_mask=0x3 task_start=205 task_number=20
```

**77 次提交，每次 1~21 个 task。**

### 2.3 ★ 分批规律：**每批 task 数 = 启用的核数**

看两组的 task 数分布：

| 配置 | task 数分布 | 规律 |
|---|---|---|
| **cm=3**（2 核） | `{6:23, 4:21, 2:18, 10:4, 20:3, 8:3, 14:1, 12:1}` | **全是偶数** |
| **cm=7**（3 核） | `{3:35, 6:17, 9:17, 12:2, 21:1, 15:1}` | **全是 3 的倍数** |

**⇒ 运行时的策略是「一批 = N 个 task，N = 启用核数」，一个核分一个 task。**

### 2.4 小活退回单核

cm=3 与 cm=7 各有 **6 次 `core_mask=0x1`** 的提交（task 数 1~4）——
**当工作量不足以拆成 N 份时，运行时退回单核**。

## 三、为什么只有 1.76× 而不是 3×

### 3.1 提交开销被放大了

| | SUBMIT 次数 | 平均 task/submit |
|---|---|---|
| cm=1 | **4** | 153.8 |
| cm=7 | **77** | 5.6 |

**提交次数增加约 19 倍。**

粗估每次提交开销（设 cm=1 的提交开销可忽略）：
```
cm=1 总时 44.8 ms ≈ 纯计算 W
cm=7 总时 25.5 ms ≈ W/3 + 77·O  →  14.9 + 77·O = 25.5
                                    → O ≈ 0.14 ms/次提交
                                    → 提交开销合计 ≈ 10.6 ms，占 cm=7 总时的 **42%**
```

**⇒ 近一半的三核耗时花在提交上，而不是计算上。**
（注：也可能是负载不均导致，两者无法从当前数据分离 —— 这是估算不是结论。）

### 3.2 分块粒度天然不足

回顾 [docs/20](20-分块结构与并行粒度.md) 的分块分布：

| 每层分块数 | 1 | 2 | 3 | 4 | 5 | 6 | 7 | 10 | 19 |
|---|---|---|---|---|---|---|---|---|---|
| 层数 | 68 | 67 | 48 | 10 | 14 | 2 | 3 | 8 | 1 |

**68 + 67 = 135 / 221 层只有 1~2 个分块 ⇒ 根本拆不出 3 份**，只能退回 1~2 核。

### 3.3 cm=3 的反常（未解决）

**2 核（cm=3）几乎零加速（1.05×），而 3 核有 1.76×** —— 这不合理，因为两者的
submit 次数完全相同（都是 77）。

**已尝试的排查**：
- 确认 `core_mask=0x3` 真的生效（71 次提交用的是 0x3，不是 0x1）✅
- 用 `/sys/kernel/debug/rknpu/load` 采样三核负载 → **读数不可靠**
  （cm=2/cm=4 都显示 "Core0 17%"，明显不对；30~40ms 的推理对 4ms 采样太短）

**结论：原因未定。** 候选：① 2 核时负载严重不均；② 0x3 的两核有共享资源冲突；
③ 驱动在 0x3 下的调度有别的问题。**需要更细的测量手段（如性能计数器）。**

## 四、对"最大程度利用 NPU"的更新结论

| 杠杆 | 实测/估算上限 | 依据 |
|---|---|---|
| **多核（3 核）** | **1.76×（实测）** | 而非理论 3× |
| ├ 提交开销 | 吃掉约 42% | 77 次提交 × ~0.14ms |
| └ 分块不足 | 135/221 层拆不出 3 份 | 分块数分布 |
| 核内调度 | ~16% | docs/19 |
| 利用闲置 PPU | 小 | PPU 仅占 10% 段 |

### 可行动的方向

1. **减少提交次数**：若能合并相邻批次（例如一次提交 6~9 个 task 而非 3 个），
   提交开销可显著下降 —— 这属于运行时/驱动层，**需要改 librknnrt 或驱动**
2. **提高分块粒度可控性**：让少于 3 块的层也能 3 核并行（拆通道维而非空间维）
3. **先弄清 cm=3 为何不加速** —— 这可能指向一个更大的问题（如两核共享带宽瓶颈）

## 五、数据与复现

```
data/multicore/
├── cm1/   615 样本 · 4 submit    · core_mask 全 0x1
├── cm3/   413 样本 · 77 submit   · 71×0x3 + 6×0x1
└── cm7/   428 样本 · 77 submit   · 71×0x7 + 6×0x1
```

复现：
```bash
LD_PRELOAD=~/rknpu_capture.so RKNPU_DUMP_DIR=/tmp/x RKNPU_DUMP_SLACK=64 \
  python3 capture-run.py /opt/rknn-models/yolov5s-640-640.rknn <core_mask> /tmp/x tag
```

> ⚠️ 踩坑：`LD_PRELOAD` 必须在 **shell 里**设好再启动 python。
> 在已运行的 Python 进程里改 `os.environ` **无效**（只对新 exec 的进程生效）。
> 这个坑让我第一次抓取拿到 0 个样本。
