> docs/39 用两套配置（cm=1 / cm=7）联立出 `t_hw ≈ work + 90µs × submit数`，

## 一、先补一个模型识别问题：两套配置**不足以定解**

docs/39 的模型是 `t = work + c × n_submit`。用两套配置联立：

```
cm=1:  work₁ +  4c = 15.40 ms
cm=7:  work₃ + 77c = 11.02 ms
```

三个未知量（work₁、work₃、c），两个方程 —— **欠定**。c 取决于并行加速比 k：

| 假设 k | 解出的 c | work₁ | 固定开销占比（77c / 11.02） |
|---|---|---|---|
| k = 3（理想三核） | **78 µs** | 15.03 ms | 54% |
| k = 2 | **45 µs** | 15.16 ms | 31% |

**两个解都自洽。** 所以 docs/39 里那句「66% 是固定开销」是把「拟合截距 90 µs」当成了唯一解，
**这是个过强的表述，需要收窄为「固定开销占比在 31%~54% 之间，取决于并行度假设」。**

## 二、但有件事被**直接测到**了：~70 µs 的提交地板

不再依赖反解，而是直接看"最小提交"要花多久。用两个内容完全不同的工作负载交叉：

### yolov5s（CNN）

```
cm=7：2467 条样本，task 数 3..21
     task≤3 的提交 中位 113.6 µs     （大日志里 task=3 中位 79.6 µs）
     与 task 数的相关 r = 0.011
cm=1：4 次提交里最小的是 6 task → 77 µs
```

### RKLLM（LLM，内容几乎统一）

```
4056 条记录：
  core_mask=1:  task=3 共 1344 条 → hw 中位 77 µs
  core_mask=2:  task=3 共 1344 条 → hw 中位 60 µs
  core_mask=4:  task=3 共 1344 条 → hw 中位 61 µs
  （另各有 8 条 task=21 的，见下节）
```

**两个毫不相干的工作负载、两个不同的运行时（librknnrt / librkllmrt），
在"3 个 task"这个规模上都落在 60~115 µs。** 这就是**每次提交的固定地板**，
不依赖任何模型假设。

而同一份单核数据也显示了地板之外的部分：

```
cm=1 的 4 次提交（yolov5s）：
  task_start   task数    hw_ms    每 task
         0       588    14.107    24.0 µs
       196         6     0.077    12.8 µs
       198         9     0.241    26.8 µs
       201        12     0.917    76.4 µs
```

588 个 task 的大提交做到 **24 µs/task**，而小提交是 12.8~76.4 µs/task（内容差异大）。
**说明提交做大之后，每个 task 的边际成本远低于小提交的均摊成本 —— 地板的效应。**

## 三、cm=3 与 cm=7 几乎相同：一个干净的自洽性检验

模型预测：**cm=3 与 cm=7 应该几乎一样**（都是 77 次提交、都是三核工作量；具体是哪三个核不重要）。

```
core_mask=1  12 次提交（3 次推理）  hw 46.19 ms → 单次 15.40 ms
core_mask=2  12 次提交               hw 47.46 ms → 单次 15.82 ms
core_mask=4  12 次提交               hw 47.48 ms → 单次 15.83 ms
core_mask=3  231 次提交（77/次）     hw 35.09 ms → 单次 11.70 ms
core_mask=7  231 次提交（77/次）     hw 33.05 ms → 单次 11.02 ms
```

- **单核三个 mask（1/2/4）结果一致（15.40/15.82/15.83）** ⇒ 只取决于**核数**，与是哪个核无关
- **cm=3 与 cm=7 差 6%（11.70 vs 11.02）** ⇒ 与模型预测一致（同为 77 次提交、同为三核）
- 而且单核路径的**提交次数固定 4 次**、多核路径固定 **77 次** ⇒ 运行时有两条截然不同的提交策略

## 四、★ 意外收获：RKLLM 的解码耗时几乎就是提交地板

LLM 那 4056 条记录的构成：

```
task=3  : 4032 条（8 个 token × 约 504 次）  hw 中位 60~77 µs
task=21 :    8 条（prefill）                  hw 中位 4.156 ms
```

**每次 token 解码要提交约 504 次，每次只有 3 个 task。**

```
504 次 × ~70 µs  ≈  35 ms/token  的纯提交地板
实测每 token     ≈  34~59 ms
```

**⇒ RKLLM 的解码速度几乎完全由"每次提交的固定地板"决定。**

这个结论对用户直接有用：板子上跑 0.5B 模型约 29~34 tok/s，
**而理论上如果能把 504 次提交合并成几十次，解码速度有数倍的提升空间**。

### 但要注意：这个杠杆**不在驱动手里**

- docs/34 已测：驱动侧 ioctl 的 CPU 只占 1.2 ms/推理，`wall − hw` 的 per-submit 开销只有约 10 µs
- 那 70 µs 是 **`hw_elapse_time`（commit→completion）**，即**硬件侧**的提交延迟
- 提交粒度由运行时（闭源 librkllmrt）决定，驱动不知道哪些提交可以合并

所以可行的路径是：
1. **比较不同版本的 librkllmrt**：板子上有 `rkllm_bench_114/123/130` 等多个版本
   —— 如果新版本批得更好（每次提交的任务更多），那就是现成的升级路径。**这是最省事的验证。**
2. 自己接管命令流生成（docs/36/37/38 已经把编码层和配置层都摸清了），
   把每 token 的 1500+ 个 task 合并成少量提交 —— 但这条要自己写提交，有风险（见 docs/09）。

## 五、本轮修正/加强的结论汇总

| 项 | docs/39 的说法 | 本轮 |
|---|---|---|
| 提交地板 | 反解出 90 µs | ✅ **直接测到 60~115 µs**（两个独立负载）—— 结论加强 |
| 固定开销占比 | 66% | ⚠️ **收窄为 31~54%**（取决于并行度假设 k=2~3）—— 结论修正 |
| 模型形式 | `t = work + c×n`（加法） | 更可能是 `t = max(地板, work)`（地板由 3-task 提交直接显现） |
| cm=3 vs cm=7 | 未测 | ✅ 几乎相同（差 6%），自洽性检验通过 |
| 具体是哪个核 | 未测 | ✅ 不影响（单核 1/2/4 结果一致） |
| **LLM 解码** | 未涉及 | ✅ **约 504 次提交/token，地板 ≈ 全部耗时** |

## 六、试图验证"换运行时版本能不能改善"—— 本轮没做成

这条本来是最省事的路径：板子上同时存在两版 librkllmrt，

```
/lib/librkllmrt.so              = 1.1.4   （系统在用）
~/rkllm/lib130/librkllmrt.so    = 1.3.0   （7.6 MB，比 1.1.4 的 6.2 MB 大）
```

用 `LD_LIBRARY_PATH` 覆盖即可切换。想法是：若 1.3.0 每次提交的 task 数更多
（批得更好），那"提交地板"这个瓶颈就有现成答案。

**实测结果：做不成 —— 模型文件是版本绑定的。**

```
lib130 (1.3.0) + Qwen2.5-0.5B   →  [INIT] ret=-1     载入失败
系统库 (1.1.4) + qwen3.5-2b      →  failed to load model
lib130 (1.3.0) + qwen3.5-2b      →  [INIT] ret=-1     载入失败
```

而运行时自己会报出版本关系：

```
", but current librkllmrt.so is support model version <= "
1.3.0
```

**板上现有的 `.rkllm` 模型没有一个能与 1.3.0 配对**（0.5B / qwen3.5-2b 在 1.3.0 下都失败）。
所以"换版本批得更好"这个假设**本轮无法验证**。

> **给用户的直接建议**：如果想要这个可能数倍的解码加速，
> 需要先弄到一个 **1.3.0 格式的模型**（用对应版本的 rkllm-toolkit 转换，或下载官方 1.3.0 示例模型），
> 然后用同一个探针比"每次提交的 task 数"。这个实验本身只要几分钟。

## 七、下一步

1. **比不同版本的 librkllmrt 的提交粒度**（最省事、收益可能最大）：
   `rkllm_bench_114` / `_123` / `_130` + 探针，看每次提交的 task 数有没有变化。
   如果新版本来每 token 只提交几十次，那用户的解码速度问题就有现成答案。
2. **把模型形式确定下来**：`max(地板, work)` 还是 `work + c`？
   判据：找"地板与 work 相当"的工作点（约 5~20 task），看时间是否在两者之间平滑过渡。
   LLM 的 task=21 提交（4.156 ms）就是一个 work 远大于地板的点，可用于定标。
3. **把地板接进结构模型**，给出一张"提交预算表"：
   给定一个模型，算出最少需要多少次提交、预测耗时 —— 这就是目标第 ③ 条的最终产物。
