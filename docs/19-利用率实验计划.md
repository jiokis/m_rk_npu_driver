## 步骤 2 离线结论（已完成，不需要硬件）

### 2.1 ★ CNA 是串行瓶颈 —— 核内优化的天花板只有 16%

对全部 **587 对相邻段**做资源冲突分析（资源占用来自 `ENABLE` 位图，已确证）：

```
✅ 资源不冲突（理论可重叠）:  94 / 587 = 16.0%
❌ 有资源冲突（必须串行）  : 493 / 587

冲突明细：
   403×  四级全开 ↔ 四级全开      ← 相邻两个卷积层，都在抢 CNA
    79×  DPU+DPU_RDMA ↔ 同样      ← 相邻两个逐元素层
    25×  四级全开 ↔ PPU（池化）    ← ✅ 不冲突
    24×  PPU ↔ 四级全开            ← ✅ 不冲突
    23×  PPU ↔ DPU+DPU_RDMA       ← ✅ 不冲突
    22×  DPU+DPU_RDMA ↔ PPU       ← ✅ 不冲突
    11×  PPU ↔ PPU                ← 冲突
```

**结论很硬**：
- 卷积段占 468/615（76%），而**相邻卷积层互相争抢同一个 CNA**
- **核内调度优化的理论上限只有 16%** —— 费大力气也就这么多
- **真正的大杠杆在多核**：每个核有自己独立的 CNA/CORE/DPU
- 且**池化层（PPU）几乎不参与竞争**（只占 10%），是天然的"可并行填充物"

> 这条结论把步骤 1 的动机量化了：**要提升利用率，优先做多核，而不是核内调度。**

### 2.2 各流水级占用率

| 流水级 | 被多少段占用 |
|---|---|
| DPU / DPU_RDMA | 530 段（90%） |
| CNA / CORE | 447 段（76%） |
| **PPU / PPU_RDMA** | **58 段（10%）** |

**PPU 是明显闲置的硬件（10%）**。池化/后处理通路在 yolov5s 里用得很少。

### 2.3 配置冗余度

| 指标 | 数值 | 解读 |
|---|---|---|
| 段内重复写同值 | **4.2%** | 发射器不浪费，配置基本是新值 |
| **相邻段之间：同值占比** | **89%**（41588 同 / 5306 异） | 相邻段配置高度相似，**几乎完整重写一遍** |

**待验证**：硬件是否有配置缓存。若没有，这 89% 的重写就是真实的**配置带宽成本**
（588 段 × 平均 66 条 × 8 字节 ≈ 310 KB/次推理）。

## 步骤 3：跨模型验证（脚本已就绪）

**动机**：目前所有结论都基于 yolov5s。**要排除"过拟合到单个模型"的风险。**

用 `mobilenet_ssd.rknn`（300×300，SSD 检测）重抓，对比：

| 待验证结论 | 若跨模型成立 |
|---|---|
| 段 = 体 + 链(2) + 使能(2) | 布局是硬件约定，不是模型特有 |
| `block_id = target \| 写位`，target 是 2 的幂 | 同上 |
| 使能位图只有 3 种取值 | 若出现第 4 种，说明位图语义还有分支 |
| 每级一个张量地址寄存器（10 个） | 寄存器语义与模型无关 |
| `0x0014` 的内核公式 | 链机制与模型无关 |

**脚本**：`scripts/npu/capture-run.py /opt/rknn-models/mobilenet_ssd.rknn 7 /tmp/mb mb`
