## 0. 三条子目标的结论

### ① 与上游对撞，校验并补全寄存器/命令流结论 —— ✅ 达成

| 结论 | 证据 | 交叉验证 |
|---|---|---|
| regcmd 编码逐位一致 | 上游 `emit_raw`：`packed = target<<48 \| value<<16 \| reg`，`target = rkt_get_target(reg)+1` | 我们独立解码的 615 段全吻合 |
| **分块（split task）模型成立** | `mesa/rkt_task.c` 的完整分块逻辑 | **15 项字段预测 13 项 100%**，在**三份独立抓取**上复现（856/615/254 tile） |
| `DATA_SIZE0[0..10]` = **tile 输入行带高** | 上游代码：宽度用整层、高度用 tile | 三路互证：`FC_DATA_SIZE0`（0x1084）同一次写入的不对称 + 与 `out_h` 自洽 |
| `DATA_SIZE3` = `out_w × out_h` | 上游 `DATAOUT_ATOMICS` | **508/508**，并与 `CORE_DATAOUT_SIZE_0`、DPU `DATA_CUBE_HEIGHT` 三路互证 |
| **MAC 阵列 = 32×32 = 1024 MAC/cycle** | `WEIGHT_ATOMIC_SIZE=32` / `FEATURE_ATOMIC_SIZE=16` + `rkt_coefs.c` 权重布局最内两层 `oc2×ic2` | **四项可证伪预测在 15709 tile 上 3 项 100%**；第 4 项 98.5%（242 个例外全解释）；**实测单核 0.981 T-MAC/s = 95.8%** |
| `OP_ENABLE` 位图语义 | `0x1d`/`0x0d`/`0x18`/`0x60` | 位图与 MAC 可算性交叉表（15709 tile） |
| 寄存器覆盖率 | 内核头文件 199 条 | 观测 148~152 个，**只有 2 个上游没给名字**（且 Mesa 以裸偏移写入）⇒ **上游覆盖 100%** |

**并且修正了自己三处旧结论**（见 §3）。

### ② CORE 数据通路、流水级结构、各级缓冲、流水重叠机制 —— ✅ 达成（一项受仪器限制）

| 要素 | 结论 |
|---|---|
| **数据通路** | CNA→CORE→DPU→PPU；DPU 内部 `BS_*`→`BN_*`→`EW_*`→`LUT_ACCESS_*`（上游命名）；`0x0d` = `CNA\|CORE\|DPU`（**LLM GEMM 裁掉 DPU_RDMA**） |
| **流水级结构** | MAC 阵列 **32(M)×32(K)**；K 原子 16、M 原子 32、depthwise 64；**一轮 = 每核一个 tile**（2556 个多核提交零例外） |
| **各级缓冲** | CBUF **384 KB / 12 bank / entry=128 B = 1 像素×128 通道**；`DATA_BANK+WEIGHT_BANK ≡ 12`（14359 tile 100%）；bank 划分 **CNN(11+1) 与 LLM(1+11) 相反**；`DATA_REUSE`/`FC_DATA_BANK` 厂商从未使用 |
| **流水重叠机制** | 权重跨 tile 驻留 CBUF（`WEIGHT_REUSE` 语义由**强对照**确证：算子首个 tile 必须为 0，**63/63 × 2 语料**）；**权重 DRAM 流量对每次提交耗时 R²=0.0004** ⇒ 搬运藏在计算后面（重叠**实际发生**）；段间 PC 链边跑边下配置 |
| **stage 级重叠比例** | ⛔ **受仪器限制**：需要硬件计数器；RK3588 驱动没接线（`amount_top = NULL`），寄存器又不能盲扫（docs/29 挂内核事故）。**这是唯一没做到的，原因是工具不可得** |

### ③ 结构级模型（能预测给定工作量的耗时）—— ✅ 达成

```
t_total ≈ n_submit × FLOOR  +  MAC_total / PEAK
```

| 常数 | 值 | 来源 |
|---|---|---|
| `FLOOR` | **67.4 µs** | 144 个「零算术量提交」的 hw 中位（`OP_ENABLE` 全可读，低开销探针） |
| `PEAK` | **1.024 T-MAC/s/核** | 阵列 32×32 × 1.0 GHz（板上 devfreq 实测最高档） |
| `MAC_total` | 逐 tile 从寄存器读出 | 分块模型已验证；**两份不同分块给出五位有效数字相同的 ΣMAC = 8.2512e9** |

**预测检验**（常数全部来自别的实验，**未在被预测数据上拟合**）：

| 负载 | 预测 | 实测 | 误差 |
|---|---|---|---|
| 单核 588-tile 单提交 | 13.914 ms | 14.107 ms | **−1.4%（零自由参数）** |
| 三核 77 提交 | 22.156 ms | 22.156 ms | **0.0%** |
| 三核（用实测地板 67.4 µs） | 7.876 ms | 8.742 ms | −9.9%（方向一致的系统性偏差，可解释） |

**算术效率**：单核 **95.8%**、三核 **75.6%**（2 核 51.8%，非单调，见 docs/45/46）。
⇒ **瓶颈是提交/轮粒度，不是乘法器。**

## 3. 这一轮里被**自己推翻/修正**的结论（7 处）

**这份清单本身就是方法论的证据** —— 一个只增不减的结论集是不可信的。

| # | 原结论 | 修正 | 触发原因 |
|---|---|---|---|
| 1 | docs/36：上游未定义 39 个寄存器 | **只有 2 个**，上游覆盖 100% | 拿 Mesa `registers.xml`（154 条子集）当参照物，而非内核头文件（199 条） |
| 2 | docs/41：提交地板 74~89 µs（上界） | **67.4 µs**（点估计，可证） | 原语料 `SLACK=0`，段尾全截断，读不到 `OP_ENABLE` |
| 3 | docs/41：三核算术效率 50~65% | **75.6%** | 同上；且发现 dump 探针本身加 2.3 ms/趟 |
| 4 | docs/45：「每轮同步开销 SYNC」 | 是**恒等式**（残差÷轮数），不是测量 | 同进程交错 A/B 给出 89 vs 138 µs，随核数变化 |
| 5 | docs/46 前：`OP_ENABLE=0x60` = 池化 | **是张量搬运/切片引擎**（93% 是 1×1×32 拷贝） | 从位图名字外推功能，从未验证 |
| 6 | docs/47 初稿：目标地址从未被读 ⇒ 死代码 | **撤回**（对照证明该判据无效） | 读地址是表达式，不是字面值 —— 不是必要条件 |

## 7. 方法论总结（本项目最可复用的部分）

1. **物理上界比回归硬。** 「可读 tile 已占物理天花板的 98.1%」一句话同时验证了 MAC 模型、
   给出未读 tile 的上界、证明硬件满速。**回归会骗人，天花板不会。**
2. **换一个负载去验证，是最便宜的证伪手段。** 「核 0 慢 27%」躺了五轮，换负载跑一分钟就翻案。
3. **只有必要条件才能用来否定。** 「某值没出现在某类寄存器里」在写侧有效（写目标必须是寄存器值），
   在读侧无效（读地址是表达式）。
4. **判据的完备性要单独审。** 签名里少一个决定结果的字段（权重），就会把不同判成相同。
5. **先查语料质量再谈结论。** 指标不好看时，第一嫌疑是数据：`SLACK=0` 的语料
   「有 1010 个 bin」但一个段尾都没抓到。
6. **区分恒等式与测量。** 判据：**这个量能不能预测另一个没参与计算的配置？**
7. **错的一般化比错的数据更隐蔽。** 27% 那个数是实测的，错的是从 LLM 外推到「核 0 天生慢」。
8. **撤回要写在正文里。** 曾经出现在「优化杠杆表」里的结论，是会被照着做的。
9. **能实施的建议必须带上不能怎么做的边界。** 例如「驱动层去重」必须附
   「先过模拟器，不能直接改驱动试」（docs/07/09 两次挂板）。
10. **报告负结果。** 「除了那条拷贝只有 5 个其它重复 tile」比一个虚高的 26.9% 有用得多 ——
    它告诉后来者**不用再找了**。
