## 2. ★★★ 但发现了两件更有价值的事

### ① 两个类型的名字**在 `.rodata` 里紧邻**

```
rknn::RKNNTilingPass        的 RTTI 名 @ 0x1a8d760
rknn::RKNNOperatorTilingInfo 的 RTTI 名 @ 0x1a8d780     ← 只差 0x20 字节
```

### ② 两个类型的**方法地址交错**

```
RKNNTilingPass:         0x3913f0  0x391420  0x391450  0x3914d0  …
RKNNOperatorTilingInfo: 0x3913e0  0x391400  0x391410  0x391480  0x391510  …
                        ↑ 完全交错在同一段（0x3913e0 ~ 0x391510）
```

**⇒ 两个类定义在**同一个翻译单元（源文件）**里 ⇒
`RKNNOperatorTilingInfo` 就是 `RKNNTilingPass` 的**配套数据结构**。**

**⇒ 这与 docs/105 从 RTTI 里看到它们的名字相邻**完全一致**。**

---

## 3. ★ 因此 dump 到的对象是 `RKNNTilingPass`（或其基类），而且内容自洽

**上轮 dump 到对象里含字符串 `"Conv"` + 参数（129 / 32 / 48 / -1）。**

**现在能解释了**：docs/99 的 `hardware_rules` 里，
`tiling_depthwise_conv` 的 `ops = ['Conv']` —— **这个 pass 对象持有它处理的算子模式 `"Conv"`。**

**⇒ 「对象 = `RKNNTilingPass` 实例，持有 op 模式 `"Conv"` + 尺寸参数」是一个**自洽且被验证**的图像。**

## 6. 教训（本轮新增）

1. **★★★ 一个「可检验的预测」比一段「合理的推断」有用得多。**
   上轮我只能说「像是 `RKNNOperatorTilingInfo`」；本轮一句命令就**证伪**了它，
   **同时顺带发现了两个类型同源这个更有价值的事实**（名字相邻 + 方法交错）。
   **推断要给成预测，因为预测会带来额外信息。**
2. **★ 地址的**邻接关系**是强信息。** 两个 RTTI 名只差 `0x20`、方法地址完全交错 ⇒
   **同源文件** ⇒ **配套数据结构** —— **这个结论不是猜的，是从地址布局读出来的。**
3. **★ 「预测错了一半」也是收获。** 我预测「对象不是 `RKNNOperatorTilingInfo`」——
   **这一半对了**；但我原本期待它「是 tiling 结果的载体」——**那一半需要修正**
   （它是 pass，载体是另一个类型）。**部分正确也要把修正写清楚。**
