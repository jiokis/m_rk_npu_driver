# docs/144 — 抓到驱动了：一次 SD 生成的 806 次提交，和 62.7% 的空转

> 上一份 `docs/143` 的结论是「板子的驱动不是黑盒：85 个 `rknpu_*` 符号 + `CONFIG_FUNCTION_TRACER=y`，
> 可以 ftrace」。这份是把这条路走通之后的实测结果。

---

## 0. 一句话

一次 512×512 单步生成的 **18.9 秒**里，用户态向内核发了 **806 次 `submit_ioctl`**，
每一次都恰好由一次 `rknpu_core0_irq_handler` 完成；而 **62.7% 的墙钟时间里 NPU 一个提交都没有** ——
其中 **4.3 秒的大空洞**已经逐事件分解清楚，**主因是 VAE 模型的加载，不是推理**。

---

## 1. 怎么抓的（含一个把数据全清掉的坑）

板端 `ftrace` 只有 `blk / function / function_graph / nop` 四种 tracer，`CONFIG_KPROBES` 未开。
所以拿不到 ioctl 的参数，只能看**函数级时序与调用者**。

### 用的配置

```bash
T=/sys/kernel/tracing
echo 0 > $T/tracing_on
echo nop > $T/current_tracer
echo > $T/trace
echo > $T/set_graph_function
echo > $T/set_ftrace_filter
echo 65536 > $T/buffer_size_kb
echo "rknpu_*" > $T/set_ftrace_filter        # 展开成 83 个函数
echo 1 > $T/options/func_stack_trace          # 每次调用附调用栈（体积 ×3，但能看到调用者）
echo function > $T/current_tracer
echo 1 > $T/tracing_on
#   …触发一次推理…
echo 0 > $T/tracing_on
cp $T/trace out.txt                           # ★★ 必须先落盘
echo nop > $T/current_tracer                  # ★★ 后关 tracer
```

### ★ 坑：`echo nop > current_tracer` 会清空环形缓冲区

前三次采集全部得到 **12 行**（只有表头），一度以为「这个内核的 tracer 是坏的」。

真相是我在 `cp $T/trace` **之前**就把 `current_tracer` 切成了 `nop` ——
**切换 tracer 会重置 ring buffer**，数据在落盘前就没了。

对照实验（改一个变量）立刻暴露：

| 配置 | 结果 |
|---|---|
| `function`，无过滤，先取后关 | **1,563,972 行** |
| `function` + `vfs_read`，先取后关 | 45 行 ✓ |
| `function_graph` + `__arm64_sys_openat`，先取后关 | 1,594 行 ✓ |
| `function_graph` + `rknpu_debugfs_open`，先取后关 | 4 行 ✓（驱动函数能挂上） |
| 同样配置，但**先关后取** | **12 行**（全空） |

这是 `docs/142` 教训 5（「测量手段的偏差会伪装成结论」）的又一次复现：
**三次「观测不到」全部是我自己的采集顺序造成的。**

### 顺带否掉两条路

- `function_graph` + `set_graph_function='rknpu_*'`、深度不限：**一次推理产出 1.5 GB**，不可用。
  深度限 5 也不行（根函数 83 个，每个都带完整子树）。
- `set_ftrace_filter` 对 `function_graph` **不起作用**，graph tracer 只认 `set_graph_function`。

⇒ 最终选型：**扁平 `function` + `rknpu_*` 过滤 + `func_stack_trace`**，8 MB，信息最全。

## 2. 结构：806 次提交，1:1 完成中断，只有 1 核或 3 核

| 量 | 实测 |
|---|---|
| `rknpu_submit_ioctl` | **806** |
| `rknpu_job_schedule` | 806（每个提交恰好一个 job） |
| `rknpu_job_free` | 806 |
| `rknpu_core0_irq_handler` | **833** |
| `rknpu_core1_irq_handler` | 354 |
| `rknpu_core2_irq_handler` | 354 |
| `rknpu_get_task_number` | **4,569**（每次提交被轮询 5.7 次） |
| `rknpu_job_next.part.0` | 3,028（3.8 次/提交） |
| `rknpu_gem_sync_ioctl` | 186 |
| `rknpu_gem_create_ioctl` | 25（每个新建 buffer 都配一个 `iommu_dma_map_sg`） |

### ★ 每个提交要么用 1 核，要么用 3 核，**没有 2 核**

按「一个提交到下一个提交之间各核 IRQ 出现几次」统计：

```
core0=1 core1=0 core2=0  →  444 次 (55.1%)   单核执行
core0=1 core1=1 core2=1  →  354 次 (43.9%)   三核齐发
其他（core0=5 / 2 / 3）  →    8 次 ( 1.0%)
```

- `core0 : submit = 833/806 = 1.03` ⇒ **每个提交恰好由一次 core0 完成中断收尾**，
  驱动不是轮询收尾的。
- 不存在 2 核的中间态 —— 说明 `core_mask` 是**用户态按次指定的**，取值只有「单核」和「全三核」两种。
- 这修正了我此前对「3 核」的模糊认识：**三核并行在 job 级是真实存在的**，
  只是只用在 44% 的提交上。

同时也修正一条旧假设：**`rknpu_job_subcore_commit` 全程 0 次调用**，
所以「每次提交走 subcore_commit」这个推断是错的，实际路径是
`submit_ioctl → job_schedule → job_next → IRQ`。

## 3. 时间：62.7% 的时间 NPU 没有提交

提交流只覆盖 17.85 s 里的 **6.65 s**，其余 **11.20 s（62.7%）一个提交都没有**。

### 3.1 空洞清单（>200 ms）

```
 0.26→ 0.75   0.485s     4.67→ 5.18   0.507s
 0.80→ 1.20   0.393s     5.37→ 5.73   0.368s
 1.43→ 1.78   0.356s     5.98→ 6.35   0.368s
 1.98→ 2.35   0.367s     6.58→ 6.95   0.369s
 3.43→ 3.64   0.209s     7.11→ 7.54   0.433s
 8.73→13.02   4.295s ★  14.08→14.29   0.219s
 …
```

### 3.2 ★ 那个 4.3 秒的空洞，逐事件分解

窗口 8.722s → 13.025s，其间**只有 300 来个驱动事件**，其余全是静默：

| 时刻 | 发生什么 | 耗时 |
|---|---|---|
| 8.99 → 9.41 | `gem_sync_ioctl`×3 → `gem_destroy_ioctl`×5 → `gem_free_object`×5 | 0.42 s　**释放 6 个 UNet 常驻段** |
| 9.60 → 9.79 | `action_ioctl`×4 → `gem_create_ioctl` → `gem_map_ioctl` → `gem_sync_ioctl` | 0.19 s　**加载 VAE 第 1 段** |
| 9.99 → 10.41 | `gem_object_create` → `iommu_dma_map_sg` → `iommu_dma_alloc_iova`，**两轮各 200 ms** | 0.42 s　**IOVA 映射** |
| 10.408 | `power_off_delay_work` → `power_off`；16 ms 后 `power_get` → `power_on` | 0.02 s　白白掉电一次 |
| **10.47 → 12.59** | **没有任何驱动调用** | **2.12 s**　纯 CPU 侧（rknn 读文件 / init 解析） |
| 12.59 → 12.64 | 又一轮 `gem_create` + `iommu_dma_map_sg`（20+20 ms） | 0.05 s |
| **12.64 → 13.02** | **没有任何驱动调用** | **0.37 s** |
| 13.017 | `gem_sync_ioctl`×3 → 第一个 `submit_ioctl` | — |

**结论：这 4.3 秒里，NPU 真正在算的时间是 0。** 拆开看：
- **2.5 s 是 `rknn_init` 的 CPU 侧开销**（读 ~198 MB 的 VAE 权重 + 解析），
  驱动完全没参与 —— 这部分连 `model_load_ms` 都没记全（只报了 1466 ms）。
- 0.42 s 是 IOVA 映射，**单个大 buffer 的 `iommu_dma_map_sg` 就要 200 ms**。
- 0.42 s 是把 6 个 UNet 段踢出常驻再换 VAE 进来。

### 3.3 VAE 尾段的节奏：4 个提交 + 420 ms 空，周期 0.51 s

13 秒之后提交非常规整：

```
间隔(ms): 17 49 68 | 420 | 17 49 71 | 422 | 17 49 67 | 424 | …
```

即 **每周期 4 个提交（前三个挤在 ~0.09 s 内，第四个单独）+ 0.42 s 完全空闲**，
共 11 个周期 ≈ 5.6 s。那 0.42 s 的静默同样**没有任何驱动调用** ⇒ 又是 CPU 侧。

## 4. 三个可操作结论

1. **把 VAE 也做成常驻，直接省 4.3 s（占全程 23%）**
   常驻池现在只放了 6 个 UNet 段。VAE 两段合计 ~198 MB，
   按 `docs/142` 测过的 IOVA 上限（~3.6 GB）大概率放得下 —— 需要实测确认。
   省掉的正是「释放 UNet + 加载 VAE + IOVA 映射」这 0.85 s 加上 **2.5 s 的 CPU init**。

2. **`iommu_dma_map_sg` 单次 200 ms 是个独立的成本项**
   25 个 buffer 创建里，大 buffer 的映射明显更贵。如果模型常驻，这项就摊销掉了；
   否则应该考虑**复用已映射的 buffer**，而不是每次 `gem_create`。
   这一项以前完全不在成本模型里（`docs/140` 只算了 MAC 和通道）。

3. **NPU 在 10.408 s 掉电，16 ms 后又上电**
   `power_put_delay` 的延迟太短，CPU 侧一忙它就 suspend 了。
   虽然单次只有 16 ms + resume 开销，但它出现在每个空洞里 ——
   把 `power_put_delay` 调大可以直接消掉这类抖动。

## 5. 边界（这次没拿到的）

- **ioctl 参数**：没有 kprobes，拿不到 `rknpu_submit_ioctl` 的 `task_number` / `core_mask` 实参。
  「1 核 vs 3 核」是从 IRQ 次数**推断**的，不是直接读到的。
- **单个 job 的 NPU 执行时间**：只有「提交→完成中断」的间隔（中位 977 µs），
  其中含驱动调度开销；不是纯 NPU 时间。
- **`10.47→12.59` 那 2.12 s 到底在干什么**：只能确定「没有驱动调用」。
  要定位到具体是读文件还是 `rknn_init` 解析，得在网关进程里打点（下一步）。
- 15 个函数（`<stack>` 之外的 35 个里）本次一次没调用，包括 `rknpu_job_subcore_commit`、
  `rknpu_soft_reset`、`rknpu_job_abort` —— 正常路径不碰它们。
