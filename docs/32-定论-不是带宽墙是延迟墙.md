# 32 · ★★★ 定论：不是「带宽墙」，是「延迟/并行度墙」

> 本篇推翻一个从 docs/25 沿用至今的**框架性标签**。之前把 NPU 的瓶颈叫「DRAM 带宽瓶颈」，
> 本轮用一个**独立于 NPU 的**参照系证明：**NPU 在最高频下只用掉约 26% 的 DRAM 带宽。**
> 它压根没把带宽用满 —— 卡住它的是**访存延迟 / 并行度**，不是带宽。
>

## 一、之前那个论证的漏洞

docs/25 的核心论证是："DDR 默认只有 534 MHz（上限 2400），钉到 performance 实测 1.59× ⇒ DRAM 带宽是瓶颈。"

**这个论证有个洞**：它只证明了 **「降频会变慢」**，没有证明 **「NPU 把带宽用满了」**。

这两件事完全不同，导向的优化手段也完全相反：

| 真实瓶颈 | 加带宽有用吗 | 该做什么 |
|---|---|---|
| **带宽饱和** | 有用 | 提频率、加通道、减少总流量 |
| **延迟 / 访存并行度受限** | **没用** | 提高访存并行度、重叠计算与访存、减少依赖链 |

所以必须补一个**独立于 NPU 的**参照：这台机器到底能跑多少带宽？

## 二、独立参照：纯 CPU memcpy 基准

```bash
sudo scripts/board/bench-dram-cpu.sh
```

64 MB × 4 次 memcpy（读 N + 写 N = 2N 字节），取 3 轮最快：

```
  DDR   534 MHz      7.72 GB/s   (70 ms)
  DDR  2400 MHz     23.84 GB/s   (23 ms)

  频率比 4.49×（534→2400 MHz），带宽比 3.09×
```

**两个要点：**

1. **成功解掉了 docs/31 第六节挂起的那个矛盾**：DMC 频率确实真实影响 DRAM 吞吐
   （带宽比 3.09×，不是 1×）。所以 1.59× 的收益是真实的 DRAM 侧效应，
   不是"devfreq 名字变了但硬件没变"。
2. **它还顺手纠正了一个我自己估错的数**：我在 docs/29 里按"32-bit LPDDR4x/5 @2400MHz
   峰值约 9.6 GB/s"估算，而**实测可达 23.84 GB/s** —— 说明这个接口远比我以为的宽
   （大概是 64-bit、且数据率高于 DMC 时钟的 2 倍）。**估算被实测打掉，这正是要独立基准的原因。**

## 三、核心结论：NPU 只用了 26% 的带宽

用完整的流量账（docs/31：特征 160.89 MB + 权重 15.81 MB = 176.70 MB）：

| | 可达带宽（实测） | NPU 实际需求 | **占用率** |
|---|---|---|---|
| DDR 2400 MHz | 23.84 GB/s | 176.70MB / 28.91ms = **6.11 GB/s** | **25.6%** |
| DDR 534 MHz | 7.72 GB/s | 176.70MB / 46.00ms = 3.84 GB/s | 49.8% |

**→ NPU 在最高频下只用掉约 26% 的 DRAM 带宽。它没有被带宽卡住。**

### 那为什么降频会变慢 1.59×？

因为**它卡在延迟上**：频率降低 → 访存延迟上升 → 每个流水级等数据回来的时间变长。
降频带来的损失来自延迟，不是带宽。

而且注意这个漂亮的规律：**NPU 拿到的带宽跟着频率走，但只走了 1.59×，而可达带宽走了 3.09×。**
说明 NPU 能达到的访存吞吐被某个**与频率无关的上限**卡住了 —— 那就是它能同时挂起的
访存请求数（memory-level parallelism, MLP）。频率越高，同样数量的在途请求能搬运的
数据越多，所以有提升；但请求数封顶，所以提升不到带宽比那么多。

## 四、这个框架一次性解释了三个此前互不相干的怪现象

| 现象 | 出处 | 延迟/MLP 框架下的解释 |
|---|---|---|
| **三核只有 1.28×**（而非 3×） | docs/22 | 加核只是加并行**计算**单元，不增加在途访存请求的深度 → 大家一起等同样的延迟 |
| **核内天花板仅 16%** | docs/19 | "CNA 串行" 的本质是流水级串行等待访存返回 → 利用率低是因为在等，不是因为算不动 |
| **DDR 降频损失 1.59× / 加带宽没用** | 本篇 | 降频抬高延迟所以变慢；但带宽本身远远富余 |

**三个现象原本是三条独立线索，现在收敛到同一个根因。**

## 五、这对优化方向意味着什么（重要修正）

| 手段 | 之前以为 | 现在判断 |
|---|---|---|
| DDR 钉频 | 头号手段（2×） | ✅ 仍然要做（已做，1.59×），但它是**缓解延迟**，不是"补带宽" |
| 继续加 DDR 频率/通道 | 值得投入 | ❌ **性价比很低** —— 带宽只用了 26%，加带宽解决不了延迟 |
| 减少 DRAM 总流量 | 头号方向 | ⚠️ 部分有效：流量确实已是"写一次读一次"的最小值（docs/31），但省流量省不到延迟上 |
| **提高访存并行度 / 重叠访存与计算** | 没被考虑过 | ✅ **★ 这才是主攻方向** |

### 落到具体动作：那个同步提交屏障

docs/24 已经查清：驱动定义了 `RKNPU_JOB_NONBLOCK` / `FENCE_IN` / `FENCE_OUT`，
但**两个运行时（librknnrt / librkllmrt）从来不用**，所有提交都是
`flags=0x5`（PC|PINGPONG，bit1 NONBLOCK=0）→ **BLOCK 模式同步屏障**。

**同步屏障 = 一次提交要等完，下一批任务才开始。**
在延迟受限的硬件上，这等于把每一次的访存延迟**完整暴露**出来，没有任何重叠。

如果能支持**非阻塞提交 / fence 串联**，让第 N+1 批任务的计算与第 N 批任务的访存重叠，
就有机会把那些等待时间填掉 —— **这正好打在"延迟墙"上，而且这是驱动侧能做的事。**

这也和 docs/24 的另一条观察对上了：subcore 机制 + `todo_list` 的存在说明驱动**本来就
为异步/排队准备过**，只是当前路径没走。

## 六、下一步（方向已改）

1. **先验证"同步屏障暴露延迟"这个假设**：用一个纯 CPU 侧能做的小实验 ——
   连续跑 N 次单算子推理（每次一个 submit），与跑 1 次更大的推理对比，
   看"每次提交的固定延迟开销"有多大。如果 N 次小推理的总时间里有一大块是
   与计算量无关的固定项，那就坐实了延迟暴露。
2. **驱动插桩（安全、纯软件）**：per-core busy/idle + 每次 submit 的
   `hw_elapse_time` 分布。要看的不是平均耗时，而是**提交之间的空档** ——
   如果 NPU 在两次提交之间是空闲的，那就是屏障造成的气泡。
3. **驱动侧尝试非阻塞提交**：这是有风险的改动（要动 job 生命周期），
   所以在做完 1、2 拿到证据之后再做，且先只读不写地跑通一次。

## 七、方法论：这次是"框架"错了，不是数字错了

前三次错误（docs/25 的 2×、docs/29 的 67%、docs/30 的 91%）都是**数字或判据**错。
这次不同：**数字基本都对，是给现象起的"名字"错了** ——
把"降频会变慢"直接命名为"带宽瓶颈"。

代价是：如果没做这个独立基准，接下来几个月可能会去追"加带宽"这条路，
而那条路的收益上限只有 26% 里的一点点。

> **教训：给瓶颈起名字，需要比给数字做验证更严的证据。**
> 具体做法固化：任何"X 是瓶颈"的论断，都必须配一个**独立测量 X 的利用率**的基准 ——
> 不能只靠"去掉 X 会变慢"来证明 X 饱和。
