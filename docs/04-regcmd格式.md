> 抓取工具：[`src/probes/rknpu_capture.c`](../src/probes/rknpu_capture.c) ·
> 原始样本：[`data/dumps/`](../data/dumps/)

## 一、指令格式

**每 8 字节 = 1 条指令**，小端：

```
┌────────────────┬──────────────────┬─────────────────┐
│  u16  寄存器地址 │  u32  写入的值    │  u16  操作码     │
│      (LE)      │      (LE)        │  几乎恒为 0x0201 │
└────────────────┴──────────────────┴─────────────────┘
  offset 0         offset 2           offset 6
```

一条真实指令的例子（`regcmd_000_task0.bin` 第 0 条）：

```
字节: 40 10 | 1b 00 00 00 | 01 02
解出: 0x1040   0x0000001b    0x0201
含义: 向寄存器 0x1040 写入 0x1b
```

## 二、寄存器地址分 bank

抓到的地址全部落在几个规整的 bank 里：

| Bank | 出现的偏移 | 说明 |
|---|---|---|
| **0x10xx** | 0x0c, 0x10, 0x14, **0x20–0x38**, 0x40–0x88 | **PC / 主控制 bank**，与 UAPI 头文件的偏移表完全对上 |
| **0x11xx** | 0x00, 0x04, 0x10, 0x40–0x6c | 第二个 bank（疑似张量描述符） |
| 0x40xx / 0x50xx | 0x04 | 只见过 `0x4004` / `0x5004` 各写 `0x0e` |

**与 UAPI 头文件的对照（这是铁证）**：

| regcmd 里的地址 | UAPI 宏 | 偏移 |
|---|---|---|
| `0x1010` | `RKNPU_OFFSET_PC_DATA_ADDR` | 0x10 |
| `0x1014` | `RKNPU_OFFSET_PC_DATA_AMOUNT` | 0x14 |
| `0x1020` | `RKNPU_OFFSET_INT_MASK` | 0x20 |
| `0x1024` | `RKNPU_OFFSET_INT_CLEAR` | 0x24 |
| `0x1028` | `RKNPU_OFFSET_INT_STATUS` | 0x28 |
| `0x102c` | `RKNPU_OFFSET_INT_RAW_STATUS` | 0x2c |
| `0x1030` | `RKNPU_OFFSET_PC_TASK_CONTROL` | 0x30 |
| `0x1034` | `RKNPU_OFFSET_PC_DMA_BASE_ADDR` | 0x34 |
| `0x1038` | 未在头文件里 | 0x38 |

高 12 位是 bank/前缀，低 12 位是 bank 内偏移。所以 **`0x1010` = bank `0x10` 的寄存器 `0x010`**。

## 三、★ 关键架构发现：命令流是自延续的

抓到的指令里有这一对：

```
[7]  0x1010 ← 0x00000220     # PC_DATA_ADDR   ← 下一次取指的数据地址
[8]  0x1014 ← 0x00000012     # PC_DATA_AMOUNT ← 下一次取指的数据长度
```

**`PC_DATA_ADDR` / `PC_DATA_AMOUNT` 不只是驱动初始化时写的两个寄存器，
它们本身就是 regcmd 里的指令。**

这意味着 NPU 的执行模型是：

```
取指 → 解码 → 执行
        ↓
   若指令写了 PC_DATA_ADDR/AMOUNT
        ↓
   硬件去新地址继续取指   ← 链式、自延续
```

**推论**：一条命令流可以在执行中途"跳转"到另一块数据继续执行。
这既是理解的钥匙（解释了为什么驱动只写 7 个寄存器就够），
也是**优化的抓手**（可以把长命令流分段、按需加载，减少一次性 DMA）。

## 四、同算子不同形状的差异分析

同一个 `op_idx` 的多条命令流做 diff，差异通常只有 **2–6 处** ——
说明**每个算子有固定模板，少数槽位是变量**。变化的槽位正好对应：

| 变化地址 | 观测到的变化 | 含义推断 |
|---|---|---|
| `0x1070` | `0x7fcb5000` → `0x7fcc4f00` | **张量设备地址**（与我们在 ioctl 里见过的 dma_addr 同一地址空间） |
| `0x1010` | `0x100` → `0xf0` | **数据长度**（每次 0x10 递减，疑似按 16 字节对齐递减） |
| `0x1014` | `0x12` 不变 | 长度相关 |
| `0x1020` / `0x1084` | `0x01400022` → `0x01400023` | **计数器 +1**（低 12 位是数量） |
| `0x1040` | `0x1b` → `0x201b` | **标志位**（`0x2000` 位切换） |

这条规律对**自己造命令流**极其有利：不需要从零构造，
**拿一条真实模板改几个变量槽位**就能得到新的算子配置。

## 五、操作码字段的疑点（未确认）

第三个 u16 字段绝大多数是 `0x0201`，但有例外：

```
[4]  0x4004 ← 0x0000000e   op=0x1001
[5]  0x5004 ← 0x0000000e   op=0x2001
```

三条不同的值：`0x0201` / `0x1001` / `0x2001`，而它们**写入的值都是 0x0e**，
只是目标寄存器不同（0x4004 vs 0x5004）。

猜测（**未经证实**）：该字段编码**目标模块或核选择**，而非纯操作码。
`0x02` / `0x10` / `0x20` 可能是模块编号，低字节 `0x01` 恒定为"写"操作。
要证实需要做**写不同 bank 的对照实验**。

## 七、还有哪些没解决

| 问题 | 怎么查 |

| 操作码字段的真实语义 | 写不同 bank 做对照实验 |

| 能否手工构造最小可用命令流 | **下一步就是干这个** |

## 八、下一步

1. **模板化**：把 615 条命令流按 `op_idx` 聚类，为每个算子生成"模板 + 变量槽位表"
2. **最小可运行**：取一个最简单的 op（如 9 字节的），只在变量槽位改值，提交给硬件
3. **边界探测**：故意写坏一条指令，看硬件报哪个中断位 → 反推中断语义
4. **SRAM 实验**：用 `RKNPU_MEM_TRY_ALLOC_SRAM` 分配，看 SRAM 有多大、命中后快多少

> 到这一步，"不能自定义算子/调度"的约束已经开始松动了：
> 我们手里有真实模板、有变量槽位、有提交通路、有复位兜底。
