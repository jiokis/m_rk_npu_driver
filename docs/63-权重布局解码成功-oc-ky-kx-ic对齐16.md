# 63 · ★ 权重布局解码成功：`[oc][ky][kx][ic对齐16]`

> 接 [docs/62](62-权重布局探针-抓到结构特征但one-hot不够.md)（one-hot 探针不够）。
> 本轮换了两件事，**一次就把布局读出来了**：
> ① 探针改成「**每通道一个常数值**」；② **不再靠猜位置，直接用寄存器里的权重基址定位**。

---

## 0. 结论（先给结果）

```
权重布局：offset(oc, ky, kx, ic) = ((oc * kh + ky) * kw + kx) * align(in_ch, 16) + ic

  · 最内层是 **ic，对齐到 16**（FEATURE_ATOMIC_SIZE，docs/44）
  · 对齐的 16 里：**前 in_ch_real 个是真实权重，其余是填充**
  · 填充值 = `128`（= zero_point）；真实权重按 per-channel 量化
```

**两项独立验证**：
1. **尺寸吻合**：`16 oc × 3×3 × 16 = 2304`，而寄存器 `WEIGHT_SIZE0 = 2304` —— **完全一致**。
2. **填充模式吻合**：每个 16 字节组是 `3 个真实值 + 13 个填充`，实测 `W[0:16]` = `127,127,127,128×13` ✓

---

## 1. 怎么做到的：**用寄存器里的权重基址定位，不猜**

上一轮我盯着整个缓冲区找模式，**方向错了** —— 权重只是缓冲区的一小部分。

**正确做法**：`CNA 0x1110`（`DCOMP_ADDR0`）就是**权重基址**。探针（`probe2`：conv 3→16 k3 + 一个 7×7 池化）的寄存器直接给出：

```
op1  权重基址=0xffff9000   WEIGHT_SIZE0=2304  WEIGHT_SIZE1=144  kw=3 kh=3 kernels=16 ch_align=16 ch_real=3
op2  权重基址=0xffff9a40   WEIGHT_SIZE0=784   WEIGHT_SIZE1=784  kw=7 kh=7 kernels=1  ch_align=16 ch_real=16
```

* `0xffff9000` **正好是缓冲区基址** ⇒ op1 的权重 = 该缓冲区 **偏移 0，长 2304**
* op2 在 `+0x9a40 − 0x9000 = 0xa40 = 2624` ⇒ 与 2304 之间有 320 字节间隔（对齐）
* `WEIGHT_SIZE1 = 144 = 3·3·16 = kw·kh·ch_align` ✓ 又一次确认 docs/38 的公式
* `WEIGHT_SIZE0 = 144 × 16(kernels) = 2304` ✓

**⇒ 从此不必猜：读 `0x1110` + `WEIGHT_SIZE0`，就能精确切出任一算子的权重。**

## 2. 探针设计的改进（这是上一轮缺的东西）

| | one-hot（docs/62） | **每通道一个常数值（本轮）** |
|---|---|---|
| 权重 | 每 oc 一个 `1.0`，位置各异 | `W[oc] = oc+1`（整通道同值） |
| 得到 | 「非零在哪」——只有位置 | 「每个 oc 占哪块」——**直接看出块边界** |
| 与填充的区分 | ❌ padding 也写 zero_point ⇒ 混在一起 | ✅ 权重全非零、填充是 zero_point ⇒ **天然分开** |

**实测**：每个 oc 的 144 字节块（`kw·kh·ch_align = 3·3·16`）里
**恰好 27 个非填充字节**（= `3×3×3 = kw·kh·ic_real`）+ **117 个填充**（`13×9`）。

**⇒ 27 与 117 这两个数直接锁死了「ic 是内层且对齐到 16」。**

## 3. 两个附带结论

### 3.1 填充值 = `128`，且它是 **zero_point**

探针的权重**全部非零**（`oc+1`，1..16），所以：
* 字节 `127` = 真实权重（per-channel 量化后每通道的常数都落在 127）
* 字节 `128` = **填充** = `zero_point`（浮点 `0.0` 的映射值）

**⇒ 与 docs/62 的推断一致**：`zero_point = 128`（有符号 INT8 的 −128）。
反量化必须是 `w_float = (w_int8 − zero_point) × scale`。

（注：16 个通道的常数**都**量化成 127，符合「常值通道」的 per-channel 量化行为 ——
尺度由该通道的 min=max 决定，退化到最大表示值。这一点下一轮用非恒值权重再确认。）

### 3.2 op2 不是我的 FC，是**被实现成 7×7 的全局池化**

`op2: kw=kh=7, kernels=1, ch_align=16, WEIGHT_SIZE1=784=7·7·16`
—— 我的探针里没有 7×7 卷积。**⇒ RKNN 把 `GlobalAveragePool` 实现成了 7×7 的 depthwise 算子**
（输入 32×32 经若干下采样后正好 7×7）。

**这是个有用的结构事实**：池化在 RKNN 里走的是**深度卷积通路**（`kernels=1`，
即 docs/41 记的那条 depthwise 分支）。

## 6. 教训（本轮新增）

1. **★ 不要从「整个缓冲区」里找模式，要用寄存器把区域切出来。**
   上一轮我盯着 24 KB 的缓冲区找结构，而权重只占开头 2 KB —— **方向错了半小时**。
   寄存器里本来就有权重基址（`0x1110`）和长度（`WEIGHT_SIZE0`）。
   **先问「有没有现成的定位信息」，再动手找模式。**
2. **★ 探针的取值设计决定能读出什么。** one-hot 只能读「位置」；
   **每通道一个常数值**直接给出「块边界」—— 而且因为权重全非零，
   与填充（zero_point）**天然可分**。**设计探针时先想「哪个量与填充不同」。**
3. **★ 两个数就能锁死一个维度。** 「27 个真实 + 117 个填充」= `3·3·3` 与 `13·9`
   —— 这两个数同时出现，就把「ic 内层 + 对齐 16」定死了，不需要再做实验。
   **找这种「只有一种解释能同时满足」的数字组合。**
4. **★ 顺带发现也值钱。** `GlobalAveragePool` 被实现成 7×7 depthwise 不是本轮目标，
   但它解释了池化为什么走 `kernels=1` 那条分支，对执行器是必需的。

## ⚠️⚠️ 修正（由第 10 轮的**斜坡探针**给出）：**只锁定了「块结构」，没锁定「块内排列」**

本文标题写的是「布局解码成功」，**这个说法过强了**。斜坡探针（权重 = 逻辑序号，`probe3`）
把内层顺序的问题暴露出来：

```
按本文假设的 offset(oc,ky,kx,ic) 取回 432 个权重字节，与浮点斜坡对照：
  浮点 0.000000 → 字节 128      ← ✅ 与 zero_point=128 一致
  浮点 1.000000 → 字节 127
  前 12 个（按本文假设的顺序）字节: [128, 216, 49, 2, 45, 89, 44, 73, 102, 65, 86, 108]
                                    ↑ 完全**不单调**
  线性拟合 q ≈ 101.4 + f × 13.8，残差中位 11.0（±1 内只占 7.6%）
```

**⇒ 内层排列与本文的假设不符。**

### 为什么会「验证通过」却仍然错

我用的是「**每通道一个常数值**」的探针（`W[oc] = oc+1`）。**通道内所有值相同**
⇒ 无论块内怎么排列，读出来都是同一个值 ⇒ **这个探针在原理上无法区分块内排列**。

**本文实际验证到的是（这部分仍然成立）**：
* 每个 `oc` 占 **144 字节**（`kw·kh·ch_align`），共 16 个 ⇒ `16×144 = 2304 = WEIGHT_SIZE0` ✅
* 每个 144 块里**恰好 27 个真实值 + 117 个填充**（`3·3·3` / `13·9`）✅
* 对齐宽度是 **16** ✅
* 填充值 = `128` ✅

**没验证到的是**：`oc` / `ky` / `kx` / `ic` 在块内的**先后与排列**。

### 教训

**「验证通过」也可能是因为探针没有分辨力。** 我用的探针恰好对「块内排列」不敏感，
于是我把「块结构对」误当成了「整个布局对」。
**做验证时要问：这个探针能区分开我关心的那些可能性吗？**
（这与 docs/56 的教训同族：判据的强度必须匹配结论的强度。）

## ✅ 最终结论（[docs/68](68-权重布局最终确定-ky-kx-oc-ic-每tap步长256.md)）

**本文的 `[oc][ky][kx][ic]` 是错的。真正的布局是：**

```
offset(ky, kx, oc, ic) = (ky*kw + kx) * 256  +  oc * 16  +  ic
```

**kernel tap 在最外层（步长 256），`oc` 第二（步长 16），`ic` 最内。**
本文把 `oc` 放最外层，所以后续探针永远对不上。
（本文的「计数级事实」仍然成立：2304 = WEIGHT_SIZE0、对齐 16、不存在的通道填 128。）
