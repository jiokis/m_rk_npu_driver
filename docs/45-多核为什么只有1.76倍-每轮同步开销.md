# 45 · 多核为什么只有 1.76×：运行时的「一轮 = 每核一个 tile」

> docs/43 留下一个非单调的谜：**三核算术效率 75.6%、单核 95.8%，但 2 核只有 51.8%**。
> 核多了效率应该升，为什么 2 核最差？
>
> 本轮从「提交里的 tile 怎么分到核上」把这件事拆开了。
> 工具：`src/analysis/round_model.py`（产物 `data/analysis/round_model.txt`）

---

## 0. 结论

```
多核提交的 task_number 永远是核数的整数倍  ⇒ 一轮 = 每个核一个 tile
⇒ 提交耗时由最慢的核决定 ⇒ 一轮耗时 = max(该轮内各 tile 的工作量)

t_总 = Σ_轮 [ max_work(该轮) / 单核峰值 ]  +  轮数 × SYNC

单核  SYNC ≈ 1.5 µs/轮    ← 基本没有每轮开销 ⇒ 算术效率 95.8%
3 核  SYNC ≈ 22.3 µs/轮   ← 每轮都要付一次同步/派发代价
2 核  SYNC ≈ 36.7 µs/轮   ← 且轮数是 3 核的 1.43 倍（同一批 tile，核少就轮多）
```

**「单核满速、多核掉效率」的差额，就是每轮的同步开销；单核不用付这笔钱。**

---

## 1. ★ 结构事实：多核提交的 tile 数永远是核数的整数倍

在 **2556 个多核提交**（两份日志 × 18 趟 × 71 次提交）上验证，**零例外**：

| 配置 | `core_mask` | 提交数 | `task_number % 核数 == 0` | 例外 |
|---|---|---|---|---|
| `cm=7`（3 核） | `0x7` | 1278 | **1278 / 1278** | **无** |
| `cm=7` | `0x1`（单核兜底） | 108 | 36 | `1,1,2,4,…` |
| `cm=3`（2 核） | `0x3` | 1278 | **1278 / 1278** | **无** |
| `cm=3` | `0x1`（单核兜底） | 108 | 54 | `1,1,3,1,…` |

⇒ **只要开了多核，运行时就把 tile 按核数**整轮**下发：一轮 = 每核一个 tile。**
⇒ 单核时没有这个约束，`task_number` 随意（所以 cm=1 能出现 588-tile 的巨型提交）。

这个事实同时解释了 docs/43 的一个观察：`cm=7` 的 `task_number ∈ {3,6,9,12,15,21}`、
`cm=3` 的 `∈ {2,4,6,8,10,14,20}` —— 都是核数的倍数，因为都是整轮。

## 2. 模型与反解

```
t_总 = Σ_轮 [ max_work(该轮) / 1.024 T-MAC/s ]  +  轮数 × SYNC
```

`max_work(该轮)` 可以**逐轮精确算出来**（把每个提交的 tile 按核数分组、取组内最大），
不需要任何假设。然后 SYNC 由实测 hw 反解：

| cm | 核 | 提交 | **轮数** | Σ每轮 max | 算术(ms) | 干净 hw(ms) | 残差(ms) | **SYNC (µs/轮)** |
|---|---|---|---|---|---|---|---|---|
| 7 | 3 | 77 | **145** | 5.3526e9 | 5.227 | 8.461 | 3.234 | **22.3** |
| 3 | 2 | 77 | **208** | 6.0174e9 | 5.876 | 13.501 | 7.624 | **36.7** |
| 1 | 1 | 4 | **615** | 1.4853e10 | 14.504 | 15.419 | 0.914 | **1.5** |

注意几个附带信息：

* **`Σ每轮 max` 比总工作量小**（3 核：5.35e9 vs 8.25e9）—— 因为一轮里三个核并行，
  提交只等最慢的那个。**这才是多核的真实算术时间**（5.23 ms），而不是 8.25e9/3.072 = 2.69 ms。
  后者假设了完美并行，实际每轮都在等最慢的核。
* **单核的 SYNC 只有 1.5 µs/轮** —— 所以单核能把阵列跑到 95.8%（docs/44）。
* 干净 hw 用低开销探针（只挂 timer），不用带 dump 的那份（dump 会加 ~2.3 ms/趟，docs/43）。

---

## 3. 这个模型解释了什么

✅ **为什么单核 95.8%、3 核只有 75.6%** —— 差的就是「每轮 22 µs × 145 轮 = 3.23 ms」。
不是乘法器变慢了，是**多核每轮都要同步一次**。

✅ **为什么 2 核反而比 3 核差** —— 两个因素叠加：
1. 同一批 tile，**核少就轮多**：208 轮 vs 145 轮（1.43×）；
2. 每轮同步还更高（36.7 vs 22.3 µs）。
⇒ 2 核既付更多次、每次还更贵，所以效率掉到 51.8%。

✅ **为什么「减少提交次数」不是唯一杠杆** —— 提交数在 cm=3 和 cm=7 下都是 77，
但耗时差 1.6×。**真正的粒度是「轮」**：减少轮数（= 提高每轮的工作量密度）
和减少提交数是两件事。这修正了 docs/41/43 里「地板是按提交计的」这个说法。

## 4. 这个模型**没有**解释什么（如实记录）

⛔ **SYNC 为什么随核数变化**（22.3 → 36.7 µs/轮）。
如果「每轮一次同步」是硬件固定代价，它应该是常数。现在不是。
可能是：核数少时每轮的 tile 更大（cm=3 平均 413/208 = 1.99 tile/轮，
cm=7 平均 428/145 = 2.95 tile/轮），单 tile 的处理时间更长，
同步的相对代价不同。**但这是猜测，没有证据。**

⛔ **把「每提交地板」和「每轮开销」同时放进模型，方程组无解**：
```
cm=7: 77·F_s + 145·F_r = 3.234 ms
cm=3: 77·F_s + 208·F_r = 7.624 ms
cm=1:  4·F_s + 615·F_r = 0.914 ms
```
前两式解出 `F_r = 69.7 µs`，代回得 `F_s = −89 µs` —— **负的每提交地板，不可能。**
⇒ **地板与轮开销在现有数据上不可分离**，三个配置的自由度不足以同时定两者。
要定下来，需要**同一个核数下、不同轮数**的一组配置（比如人为构造轮数不同的模型）。
这是下一轮可以做的事（换一个 op 数不同的模型即可，不需要碰硬件）。

## 5. 对「最大程度利用 NPU」的更新

| 杠杆 | 量级 | 依据 |
|---|---|---|
| 4–6 路并发 | **2.44–2.57×** | docs/34（本质就是让多核的轮开销被别的推理填满） |
| **减少「轮」数**（不是提交数） | 3 核下每轮 22.3 µs × 145 轮 = 3.23 ms，占 8.46 ms 的 **38%** | 本轮 |
| 单核 + 巨型提交 | 单核 95.8% 满速，**但需要一次 588-tile 的提交** | docs/43/44 |
| 避开核 0 | 提交地板 +16 µs/次 | docs/41 |
| DDR 定频 / 加带宽 / 改驱动 | 1.59× / ≈1.0× / ≈1.0× | docs/28/32/33 |

**本轮把「粒度」这个词精确化了**：以前说「减少提交次数」，现在知道真正要减的是
**轮数**（提交数 × 每提交轮数）。三核下 145 轮 × 22.3 µs = 3.23 ms 的同步开销，
是当前配置下最大的一块可优化量。

## 6. 教训（本轮新增）

1. **★ 当两个量在数据里总是一起变化时，你分不开它们。** 提交数和轮数在 cm=3/cm=7
   下都是 77，所以「每提交地板」和「每轮开销」在本轮数据里**数学上不可分离**
   （联立会解出负的地板）。**这不是分析不够努力，是实验设计缺一个自由度。**
   正确做法是记下「需要什么数据才能分开」，而不是硬凑一个模型。
2. **★ 非单调的现象往往藏着正确的模型形式。** 「2 核比 3 核差」当时看着像噪声；
   追下去才发现耗时是按**轮**计的，而不是按提交或按工作量计的。
   **不要放过反直觉的数据点。**
3. **★ 整数倍的规律是最硬的线索。** `task_number` 是核数的整数倍、2556 个样本零例外 ——
   这一条直接把「运行时怎么分核」定死了，后面的模型才有立足点。
   **先找这种「必须成立」的规律，再建模型。**
4. **把「解释了什么」和「没解释什么」分两节写。** 本轮的模型解释了两个现象、
   留了两个窟窿。**窟窿写清楚比模型漂亮更重要** —— 上一轮我就是因为没写清楚
   才让一个 1.8× 的异常拖了一轮。
