# 战略转向：从"逆向 regcmd"转向"在 regcmd 之上做东西"

> **本文件的结论会改变项目方向，请优先阅读。**
> 依据：[01-资料搜集.md](01-资料搜集.md)（外部深度调研，142 个来源）+ 我们自己的一手实测。

## 一、必须先承认的事实：regcmd 逆向已经完成了

立项时的假设是"regcmd 是黑的，要自己逆"。**这个假设已经不成立。**

| 事实 | 证据 |
|---|---|
| **regcmd 编码已完整公开** | 至少 **4 个独立实现**都在公开文档里给出了同一套编码与 block 映射 |
| **内核驱动已上游化** | `drivers/accel/rocket` **自 Linux v6.18 进入主线**（Tomeu Vizoso，2025-07-25） |
| **用户态驱动已上游化** | Mesa **MR 29698 已合并**，随 **Mesa 25.3** 发布 Gallium `rocket` + `teflon` TFLite delegate |
| **官方解码工具齐备** | Mesa `intercept.c`（LD_PRELOAD 拦截）+ `decode.py --xml registers.xml`（唯一官方维护的解码器） |
| **微架构已定性** | **NVDLA 衍生**（主线作者原话 + Mesa MR 描述 + 内核文档，三处独立证据） |

**我们的 615 条实测样本，正好独立验证了这套公开映射**（见 [04](04-regcmd格式.md) §5.1：
每个 block_id 都对上名字，每个寄存器偏移都落在预期窗口，无一例外）。

> 换句话说：我们做的事**方向没错、结果也对**，但**这个山头已经被别人占完了**。
> 继续在 regcmd 编码上投入就是重复劳动。

## 二、哪些是死路（明确不要再做）

| 死路 | 原因 |
|---|---|
| 重做 regcmd 编码逆向 | 已被 4+ 个项目做透，我们只是又验证了一遍 |
| 重做单算子 matmul 合成 | 同上，fp16/int8/int4 都有人做了 |
| 新写一个内核驱动 | 主线已上游化，重写没有意义 |
| 自研 regcmd dump 工具 | Mesa `intercept.c` + `decode.py` 是官方维护的，别重造 |
| 期望从 TRM 拿语义 | TRM 只有地址、**且已知有错**（`PC_OPERATION_ENABLE` 位图描述就是错的） |
| 做 librknnrt ABI 兼容层 | 继承它全部限制，收益≈0 |
| 无保护的寄存器 fuzzing | **会 wedge 硬件**——这一点我们用最直接的方式验证了（见第四节） |
| 把 Panthor（GPU）/ MPP（VPU）的成果当 NPU | 零共享代码，是两条独立的路 |

## 三、真正的空白在哪里（按性价比排序）

| 优先 | 方向 | 为什么是空白 | 为什么值得做 |
|---|---|---|---|
| **1** | **量化自由度** | 硬件支持 int4/int8/int16/fp16/bf16/tf32，但工具链只给到 w8a8，且 w4a16 被直接拒绝 | **纯软件、不碰硬件、收益可量化**。可做 per-channel + importance matrix + NF4 + Hadamard 旋转；DPU 的 out-cvt 支持片上 requant，int8 卷积可直接出 int8 |
| **2** | **ONNX→regcmd 的算子覆盖** | Mesa/Teflon 只做 TFLite int8 conv 子集；官方 op 表 484 行里大量 `Not Supported` | 最务实的是先做 **ONNX 图前置重写层**（Einsum→matmul、GridSample→host 索引、F.pad→conv padding），把 `Not Supported` 变成可用 |
| **3** | **PC 链 / 算子融合 / 单提交多 task** | 所有项目都没完全解决；实测 per-submit 稳态开销 ~32ms | N 次提交压成 1 次是主要收益。硬约束：数据通路单向（activation→matmul 违规）、寄存器组状态跨 task 残留 |
| **4** | **可观测性 / 正确性判据** | **没人系统做过** | ⚠️ **这一条能省两个月**，见下 |

### 为什么"可观测性"要单独拎出来

外部资料里有一条血泪教训：

> `gahingwoo` 读硬件带宽计数器时发现，**252 个 job 全部报"完成"，但 `dt_wr=0, wt_rd=0`**
> —— 也就是说**硬件根本没算，却报告成功**。他因为缺少这个判据，浪费了两个月，
> 中间还发表过错误结论。

我们的 UAPI 里恰好有两个现成的计数器就能做这件事：
`ACTION: GET_DT_WR_AMOUNT`（14）/ `GET_DT_RD_AMOUNT`（15）/ `GET_TOTAL_RW_AMOUNT`（17）。

**在写任何优化之前，必须先能区分「真算了」和「没算却报完成」。**

## 四、⚠️ 事故记录：自制命令流把板子搞挂了

**这是本项目的真实事故，必须记录，因为它验证了一条重要教训。**

### 发生了什么

我写了最小 POC（[src/poc/rknpu_poc.c](../src/poc/rknpu_poc.c)），提交了这样一条自制命令流：

```
[0] reg=0x0000 val=0x00000000 blk=0x0041   ← OP_40 前置
[1] reg=0x0000 val=0x00000000 blk=0x0000   ← OP_NONE 空操作
[2] reg=0x0008 val=0x00000060 blk=0x0081   ← ★ OP_ENABLE 总使能
[3] reg=0x0000 val=0x00000000 blk=0x0000   ← 收尾
```

提交后：ioctl **永不返回** → 板子彻底失联（ping 不通、ARP `INCOMPLETE`、SSH 无路由）→
**需要物理断电重启**。

### 根因

**我在没有任何有效算子描述符的情况下就写了 `OP_ENABLE`。**

`OP_ENABLE`（`reg=0x0008`）是**块使能位图**，写下去会让 CNA/DPU/PPU 等模块开始工作。
而它们的描述符（张量地址、形状、步长）**全是未初始化的**——
硬件于是拿着垃圾地址去做 DMA，把内存写坏，内核崩溃。

### 教训（已加入死路清单）

1. **使能位必须最后写**，且必须在所有描述符配置完毕之后 —— 这条我照做了（放在第 3 条），
   但我**没有先配描述符**，等于把"最后写"理解成了"随便写"。
2. **第一次提交应该是"什么都不做"的流**，而不是"使能所有模块"的流。
   正确的最小实验是：只写 `OP_NONE`，验证 ioctl 能正常返回。
3. **寄存器会自清零，readback 不能验证写入**（外部资料），所以不能靠回读确认配置生效。
4. **实验前应先停掉所有依赖 NPU 的服务**（我做对了：先停了网关）。
5. **需要物理可达的恢复手段** —— 板子没有远程电源控制，这是硬约束。

## 五、修正后的下一步

### 阶段 0（恢复与预防，必须先做）

- [ ] 物理断电重启板子（需要人手）
- [ ] **确认板子恢复后，先建立"可观测性"再碰任何提交**
- [ ] 把 `rknpu_poc submit` 从"使能所有模块"改成"只发 `OP_NONE`"，
      目标只是**验证 ioctl 能返回**，不追求硬件干活
- [ ] 加保护：提交前先读一次带宽计数器，提交后再读，对比

### 阶段 1（纯软件，不碰硬件，最高性价比）

- [ ] 搭建 ONNX 图分析工具：统计一个真实模型的算子分布，
      对照官方 op 表标出哪些是 `Not Supported`
- [ ] 实现图前置重写：`Einsum → matmul`、`F.pad → conv padding` 等
- [ ] 量化实验：per-channel / Hadamard 旋转，在 CPU 上先验证数值收益

### 阶段 2（硬件，谨慎推进）

- [ ] 上主线 `accel/rocket` + Mesa，跑通 MobileNetV1（验证整条新链路）
- [ ] 用 Mesa `intercept.c` + `decode.py` 解码一条真实 regcmd，对照我们的样本确认读懂
- [ ] 只有在阶段 0 的判据齐备后，才重新尝试自制命令流

## 六、对用户原始目标的影响

用户的目标是「**提高模型部署的自由度以及优化空间**」。转向之后，这个目标**没有变**，
但实现路径更清晰了：

| 原始期望 | 转向后的落地方式 |
|---|---|
| 部署自由度 | 不再靠"自己造命令流"（成本高、风险大），而是靠**算子覆盖层**把 `Not Supported` 变成可用 |
| 优化空间 | **量化自由度**（纯软件、收益可量化）+ PC 链融合（省 ~32ms/次提交开销） |
| 不受闭源约束 | 走**主线 rocket + Mesa**，彻底摆脱 rknn-toolkit2 / librknnrt |

**我们的一手实测并非白做**：它独立验证了公开映射、给出了 block 频次分布、
记录了三个抓取踩坑的正解，并且用事故换来了"不要无保护 fuzzing"的实证。
这些都已入库。
